# Spec: 쉬운 설정과 personal access token

From: INTENT.md (dewevrei, 3a3f457). Status: implemented.
Skills applied: actions-scaleset
Extends: 0001, 0002

## Requirements

자격과 설정 (R271~R277, R314)
- R271. `[github]`에 `app-client-id`와 `app-private-key-file`만 있고 토큰 키가 없는 0002 형식의 설정 파일(`config.example.toml` 포함)은 고치지 않고 0002와 같이 읽히고 검증되며, 모든 target이 App 자격을 쓴다.
- R272. `github.token-file`이 있으면 서버의 기본 자격은 그 파일의 personal access token이다. `github.token-file`과 `github.app-client-id`나 `github.app-private-key-file`이 함께 있으면 R28과 같이 오류 대기에 들어가고, 오류는 `github: set either app-client-id and app-private-key-file, or token-file, not both`이다. 이 오류가 나면 R274의 `is required` 오류는 내지 않는다. target 하나에 `token-file`과 `app-client-id`나 `app-private-key-file`이 함께 있어도 같고, 오류는 `targets[<i>]: set either app-client-id and app-private-key-file, or token-file, not both`이다.
- R273. target의 자격은 그 target에 있는 것 중 이 순서의 첫째다: 자기 `targets.token-file`의 토큰, 자기 App(`targets.app-client-id`와 `targets.app-private-key-file`), 기본 자격(`github.token-file`이나 `[github]`의 App).
- R274. 기본 자격(App 두 키, 또는 `github.token-file`)이 없는데 자기 `token-file`도 자기 App도 없는 target이 있으면 R28과 같이 오류 대기에 들어가고, 오류는 `github: no default credential (app-client-id and app-private-key-file, or token-file) for targets without their own token-file or App: <그 target들의 targets.url>`이다. 모든 target에 자기 자격이 있으면 `[github]`를 두지 않아도 된다. App 두 키 중 하나만 있으면(`[github]`이든 target이든) 다른 키에 0001의 `is required` 오류를 낸다(0001 설정 표에서 두 App 키가 늘 필수인 것을 대체). App client ID는 비어 있지 않은 한 덩어리의 UTF-8 글자여야 하고, 공백이나 제어 문자가 있으면 `must not contain spaces or control characters`, 토큰처럼 보이면(R276의 접두어 등) 값을 인용하지 않고 `looks like a token, not a GitHub App client ID` 오류를 낸다.
- R275. R276의 검사를 통과한 토큰 파일(`github.token-file`, `targets.token-file`)은 절대 경로의 정규 파일(심볼릭 링크는 그 대상)이고, 4 KiB 이하이며, 0001 R30의 App 키 파일과 같은 모드 규칙(그룹과 다른 사용자의 권한 비트 없음)을 따르고, 끝의 줄바꿈(`\n` 또는 `\r\n`) 하나를 뺀 내용이 비어 있지 않으며 공백과 제어 문자가 없는 한 줄이어야 한다. 어기면 R28과 같이 오류 대기에 들어가고, 오류는 그 키 이름과 어긴 규칙을 보이며 파일 경로와 내용을 보이지 않는다.
- R276. 토큰 파일 키의 값이 `ghp_`, `github_pat_`, `gho_`, `ghu_`, `ghs_`, `ghr_` 중 하나로 시작하면 R275의 다른 검사(절대 경로 포함)보다 먼저, 파일을 열지 않고 그 키에 `value looks like a token, not a file path; set the path of the token file` 오류를 낸다. 그 값은 어느 출력에도 나오지 않는다.
- R314. 저장소 URL 값(`targets.url`, `init`의 `-repo`, `add-repo`·`remove-repo`·`delete-scaleset`의 URL 인자)에 `@`가 있거나, R276의 접두어 하나 뒤에 `[A-Za-z0-9_]`가 20자 이상 이어진 부분이 있으면, R231·R232의 검사와 그 값을 인용하는 다른 오류(0002 R269의 문구 포함)보다 먼저 그 키나 인자에 `value contains a credential; set the repository URL only` 오류를 내고, 그 값은 어느 출력에도 나오지 않는다(R231의 `got %q` 인용과 R269의 URL 인용을 이 경우에 대체).
- R277. 토큰 파일에서 읽은 값과 R276, R314가 거부한 값은 로그, 오류, `status`, 이 변경의 모든 명령(`init`, `add-repo`, `remove-repo`, `doctor`, `app-link`)과 기존 명령의 stdout과 stderr에 나오지 않는다(0001 R31을 personal access token과 이 변경의 명령으로 넓힌다).

토큰 target (R278~R281)
- R278. 토큰을 쓰는 target(토큰 target)의 scale set 클라이언트는 scaleset v0.5.0의 `NewClientWithPersonalAccessToken`으로 그 토큰과 저장소 URL을 주어 만들고, 그 target의 GitHub REST 호출(R241, R242)은 그 토큰을 `Authorization: Bearer`로 보낸다. 토큰 target에는 App 설치 조회와 권한 검사를 하지 않는다(R236을 대체: 설치 조회는 App 자격을 쓰는 target에만 그 target의 App으로 한다. R237, R238은 그 조회의 결과에만 걸린다). App target의 설치 조회, 서명기, 설치마다의 REST 클라이언트와 설치 토큰은 같은 App(client ID와 키)의 target들이 같이 쓴다.
- R279. 토큰 target은 시작 단계에서 R236의 자리에 `GET /repos/{owner}/{repo}/actions/runners?per_page=1`을 그 토큰으로 부른다. 이 호출은 R172의 시작 단계 호출에 든다. 일시 오류는 R24로 다시 시도한다. 401이면 그 target은 target 오류 대기에 들어가고 마지막 오류는 `personal access token for repository <owner>/<repo> was refused (401): it is invalid, expired or revoked`이다. 403(속도 제한이 아닌 것)이나 404면 target 오류 대기에 들어가고 마지막 오류는 `personal access token for repository <owner>/<repo> cannot manage its runners (<code>): a classic token needs the repo scope and admin access, a fine-grained token needs Administration: Read and write on this repository`이고, 응답에 `X-Accepted-GitHub-Permissions` 헤더가 있으면 그 값이 `[a-z_=,; ]`만으로 된 200자 이하일 때 `; GitHub says the endpoint accepts <값>`을, `X-GitHub-SSO` 헤더가 있으면 그 값(URL과 조직 ID)을 보이지 않고 `; an organization requires SAML SSO authorization of this token`을 뒤에 붙인다.
- R280. GitHub REST 호출의 R52 대기는 App target이면 설치 ID마다, 호출 종류마다 하나(R266 그대로), 토큰 target이면 같은 토큰 값마다, 호출 종류마다 하나를 두어, 같은 토큰이나 같은 설치를 쓰는 target들은 그 대기를 같이 쓰고 다른 토큰이나 설치의 target은 늦추지 않는다. R279의 호출은 그 토큰의 대기에 든 호출 종류 하나이고, R189의 대기(App JWT의 설치 조회, App마다)는 쓰지 않는다(R266을 대체).
- R281. `delete-scaleset`은 대상 target의 자격(R273)을 쓴다. 토큰 target이면 R268의 설치 조회와 권한 확인 대신 R279의 호출을 하고 그 토큰으로, 자기 App이 있는 target이면 그 App으로 설치 조회와 권한 확인을 하고 그 App으로 scale set과 runner 등록을 지운다. 그 호출이 실패하면 R269와 같이 아무것도 지우지 않고 오류를 stderr에 쓴 뒤 1로 끝난다(R268, R269를 토큰 target과 자기 App target에 대해 대체).

init (R282~R289, R316)
- R282. `init [-config <경로>] [-app-client-id <id>] [-app-private-key-file <경로>] [-token-file <경로>] [-repo <URL>[=<max-runners>]]... [-runner-image <값>] [-buildkit-image <값>]`은 `-config`(기본 `~/.config/actions-runner-scaler/config.toml`)에 설정 파일을 새로 만든다. 그 경로에 파일이 이미 있으면 아무것도 쓰지 않고 `config file <경로> already exists; edit it, or use add-repo and remove-repo`를 stderr에 쓴 뒤 1로 끝난다. 내용은 같은 폴더의 임시 파일에 모두 쓴 뒤 link(2)로 그 경로에 놓고 임시 파일을 지운다. 그래서 쓰는 동안 다른 프로세스가 같은 경로에 파일을 만들어도 그 파일을 덮어쓰지 않고(link가 실패하면 위와 같이 끝남), 그 경로에 내용 일부만 쓴 파일이 생기지 않으며, 어느 단계가 실패해도 임시 파일은 남지 않는다.
- R283. `init`이 쓴 파일은 모드 0600이고, `config.Load`가 오류 없이 읽으며, 플래그와 답으로 준 값과 나머지 키의 기본값을 갖는다. 부모 폴더가 없으면 모든 검사(R284~R288과 내용의 검증)를 통과한 뒤에만 없는 폴더를 경로 전체에 걸쳐 모드 0700으로 만든다. 폴더를 만든 뒤 파일 쓰기가 실패하면 설정 파일은 생기지 않고 1로 끝나며, 만든 폴더는 남을 수 있다.
- R284. `-repo`는 여러 번 줄 수 있고, 값 `<URL>=<n>`은 그 저장소의 `max-runners`를 n으로, `=` 없는 값은 1로 쓴다. URL이 R231의 꼴이 아니거나, R232의 조직 URL이거나, 저장소가 R233의 비교로 겹치거나, n이 1 이상의 정수가 아니면 아무것도 쓰지 않고 그 오류를 stderr에 쓴 뒤 1로 끝난다. `-token-file`과 App 플래그 중 하나를 함께 주어도 같다.
- R285. 필수 값(기본 자격, 저장소 1개 이상, `runner.image`, `buildkit.image`) 중 플래그로 주지 않았고 R286으로 채우지 못한 것만, stdin이 터미널일 때 터미널에서 묻는다. 답이 R284, R275, R276, 0001 R30의 규칙이나 R318의 이미지 값 꼴을 어기면 그 오류를 보이고 같은 질문을 다시 한다. 답 대신 입력 끝(EOF)이 오면 아무것도 쓰지 않고 1로 끝난다.
- R286. `-runner-image`가 없고 로컬 Docker에 `actions-runner-scaler-runner:local` 태그의 이미지가 있으면 그 태그를 `runner.image`로 쓴다(R322). 태그의 이미지가 없으면 채우지 않고 `image actions-runner-scaler-runner:local is not present locally, so runner.image was not filled: run image/build.sh first`를 stdout에 쓴다. `-buildkit-image`가 없으면 `image/build.sh`의 `BUILDKIT_IMAGE` 값을 `buildkit.image`로 쓴다. 이렇게 채운 값(`buildkit.image: <값>`)과, 그 BuildKit 이미지가 로컬에 없으면 `buildkit.image is not present locally: run image/build.sh to pull it`을 stdout에 쓴다. Docker에 닿지 못하면 `could not check the Docker image: <오류>`를 쓰고 `runner.image`는 채우지 못한 값으로 본다.
- R287. stdin이 터미널이 아니고 필수 값이 빠졌으면 아무것도 쓰지 않고 빠진 값마다 그 값을 주는 플래그 이름을 stderr에 쓴 뒤 1로 끝난다.
- R288. 플래그로 준 App 키 파일이나 토큰 파일이 0001 R30, R275, R276이나 `ReadAppPrivateKey`의 검사에 걸리면 아무것도 쓰지 않고 그 오류를 stderr에 쓴 뒤 1로 끝난다.
- R289. `init`은 그 설정 파일과 그 위의 없던 폴더들 밖에서 아무것도 만들거나 바꾸지 않고, GitHub를 부르지 않으며, Docker에는 이미지 조회(`GET /images/{name}/json`)와, Docker Engine 클라이언트가 API 버전을 맞추려고 첫 요청 앞에 보내는 ping(`HEAD /_ping`, 그것이 실패하거나 200이 아니면 `GET /_ping`)만 한다(확인함(근거: moby client v0.6.2 `client.go` 303~317행 버전 협상, `ping.go` 112~129행)).
- R316. `image/build.sh`는 runner 이미지를 만들 때 OCI 미리 정한 키의 라벨 `org.opencontainers.image.source=https://github.com/dewevrei/actions-runner-scaler`과 `org.opencontainers.image.title=actions-runner-scaler-runner`을 붙인다. `--record` 진단 이미지에는 붙이지 않는다. 라벨은 출처를 적는 메타데이터일 뿐이고, 스케일러, `init`, `doctor`는 라벨을 보지 않는다.

저장소 더하기와 빼기 (R290~R295, R315)
- R290. `add-repo [-config <경로>] [-max-runners <n>] [-idle <n>] [-token-file <경로> | -app-client-id <id> -app-private-key-file <경로>] <저장소 URL>`은 설정 파일 끝에 `[[targets]]` 블록 하나(`url`, `max-runners`(주지 않으면 1), 준 경우에만 `idle`, `token-file`, `app-client-id`, `app-private-key-file`)를 더하고, 그 앞의 바이트(주석, 키 순서, 빈 줄)는 바꾸지 않는다.
- R291. `remove-repo [-config <경로>] <저장소 URL>`은 owner와 repo가 R233의 비교로 같은 target의 `[[targets]]` 머리 줄부터 다음 표 머리 앞의 마지막 키 줄까지만 지우고, 나머지 바이트는 바꾸지 않는다.
- R292. 다음 경우 `add-repo`와 `remove-repo`는 파일을 바꾸지 않고 오류를 stderr에 쓴 뒤 1로 끝난다: 파일이 TOML로 읽히지 않음, URL이 R231의 꼴이 아니거나 R232의 조직 URL임, `add-repo`에서 같은 저장소가 이미 있음(R233), `add-repo`의 `-max-runners`, `-idle`, `-token-file`, `-app-client-id`, `-app-private-key-file`이 R235의 범위, `targets.idle`의 범위, R272, R274, R275, R276, 0001 R30을 어김, `remove-repo`에서 그 저장소가 없음, 파일에 같은 저장소(R233의 비교)가 이미 둘 이상 있음, `remove-repo`가 마지막 target을 지우게 됨, target이 `[[targets]]` 머리 줄로 적혀 있지 않음(인라인 배열 등), 고친 내용을 다시 읽은 target 목록이 원래 목록에 그 하나를 더하거나 뺀 것과 다름. 파일의 꼴 때문에 거부할 때(인라인 배열 등, 마지막 두 경우)는 `add-repo`면, 인자가 R314, R276, R275, R235와 `targets.idle`의 범위를 통과한 경우에만 사용자가 붙여 넣을 `[[targets]]` 블록을 stderr에 함께 쓴다. 그 블록의 값은 명령 인자에서만 오고, `token-file`은 경로만 담으며 토큰 값은 담지 않는다.
- R293. 고친 파일은 같은 폴더의 임시 파일에 원래 파일의 모드로 쓴 뒤 이름을 바꿔 원래 경로에 놓는다. 설정 파일 경로가 심볼릭 링크면 링크를 따라간 실제 파일의 폴더에서 같은 방법으로 그 실제 파일을 바꾸고 링크는 그대로 둔다. 쓰기나 이름 바꾸기가 실패하면 원래 파일은 그대로이고 임시 파일은 남지 않는다.
- R294. 두 명령이 성공하면 바꾼 저장소 URL과 `restart the scaler to apply`를 stdout에 쓰고 0으로 끝난다. `remove-repo`는 `the repository's scale set stays on GitHub; to delete it, add the repository again, stop the scaler, and run delete-scaleset`을 함께 쓴다. README는 저장소를 뺄 때 스케일러를 멈추고 `delete-scaleset`을 먼저 실행한 뒤 `remove-repo`를 실행하는 순서를 적는다.
- R295. 두 명령은 고친 파일에 그 저장소와 관계없는 검증 오류(예: 이미지 값)가 있어도 R292에 걸리지 않으면 파일을 바꾸고, 그 오류들을 `config still has problems:` 아래에 stdout으로 쓴다. 두 명령은 스케일러의 잠금(0001 R78)을 잡지 않고, GitHub와 Docker를 부르지 않으며, 설정 파일과 R315의 잠금 파일 밖에서 아무것도 만들거나 바꾸지 않는다.
- R315. `add-repo`와 `remove-repo`는 설정 파일을 읽기 전에, 심볼릭 링크를 따라간 실제 설정 파일과 같은 폴더의 `<실제 파일 이름>.lock` 파일을 `O_NOFOLLOW`로 (없으면 모드 0600으로 만들어) 열고, 연 파일이 정규 파일인지 확인한 뒤 배타 flock을 먼저 `LOCK_NB`로 시도한다. 다른 프로세스가 잡고 있어 막힐 때만 `Blocking: waiting for file lock on <잠금 파일 경로>`를 stderr에 쓰고 풀릴 때까지 기다린다. 읽기 → 고치기 → rename(R293)을 마친 뒤 또는 실패한 뒤에 놓고, 잠금 파일은 지우지 않는다. 잠금 파일 자리가 심볼릭 링크이거나 정규 파일이 아니면 설정 파일을 바꾸지 않고 오류를 stderr에 쓴 뒤 1로 끝난다.

doctor (R296~R304, R317)
- R296. `doctor [-config <경로>]`는 설계의 doctor 검사 표의 순서로 검사마다 한 줄 `<결과> <검사 이름>: <요약>`을 stdout에 쓴다. 결과는 `PASS`, `FAIL`, `UNKNOWN` 중 하나이고, `PASS`가 아닌 줄 뒤에는 `  cause: <원인>` 줄과 `  fix: <방법>` 줄이 온다. 결과와 관계없이 더 알릴 것이 있으면 그 뒤에 `  warning: <내용>` 줄이 온다(R317).
- R297. 한 검사가 `FAIL`이나 `UNKNOWN`이어도 나머지 모든 검사를 한다. 입력이 앞 검사의 실패에 걸린 검사는 `UNKNOWN`(요약 `not checked`)이고, 원인 줄 `an earlier check did not pass: <앞 검사 이름>`에 그 앞 검사의 이름을 적는다.
- R298. 마지막 줄은 `PASS <n>, FAIL <n>, UNKNOWN <n>`이고, `FAIL`이 하나라도 있으면 1, 없으면 0으로 끝난다.
- R299. `doctor`는 GitHub에 GET 요청만 보내고(그 target의 App JWT를 쓴 설치 조회, 토큰을 쓴 저장소 runner 목록과 R301의 Actions 정책 목록), 설치 토큰, 등록 토큰, JIT 설정, scale set, 메시지 세션을 만들지 않는다. Docker에는 설정을 읽은 뒤 `docker.host`(읽지 못하면 기본 주소)로 클라이언트를 만들어 ping(`HEAD /_ping`, 그것이 실패하거나 200이 아니면 `GET /_ping`, R289와 같은 Docker Engine 클라이언트 동작), `GET /info`, `GET /images/{name}/json`, 로컬에 없는 이미지 참조의 `GET /distribution/{name}/json`(R323)과 R79의 TCP 2375 확인만 한다. 파일은 읽기만 하고, 잠금(0001 R78)과 status socket을 잡거나 만들지 않는다.
- R300. App target의 GitHub 검사는 그 target의 App(자기 App, 없으면 기본 App)의 JWT로 R236의 조회를 한다. 200이고 R238의 권한이 있으면 `PASS`(요약 `App installation <id>, administration: write`), 404면 `FAIL`(R237의 문구), 권한이 없으면 `FAIL`(R238의 문구), 401이면 `FAIL`이고 원인은 `GitHub did not accept the App's JWT (401)`이다(고치는 법: `check that app-client-id and the key file belong to the same App and that the key was not deleted from the App`). R302가 다루지 않는 그 밖의 응답 코드는 `UNKNOWN`이고 원인 `GitHub answered <코드>`에 그 코드를 적는다.
- R301. 토큰 target의 GitHub 검사는 R279의 호출을 한다. 401과 403(속도 제한이 아닌 것)과 404는 `FAIL`이고 원인은 R279의 문구다. 200이고 토큰이 `github_pat_`로 시작하면 이어서 `GET /repos/{owner}/{repo}/actions/policies?per_page=1`을 부른다. 그 응답이 200이면 `PASS`(요약 `fine-grained token, Administration: write`), 403이면 `FAIL`(원인: `the token has no Administration write permission on this repository`), 그 밖이면 `UNKNOWN`(원인에 응답 코드를 적음)이다. 200이고 토큰이 `github_pat_`로 시작하지 않으면 응답의 `X-OAuth-Scopes` 헤더 값을 쉼표로 나누고 각 항목의 앞뒤 공백을 뺀 뒤, `repo`와 정확히 같은 항목이 있을 때 `PASS`(요약 `classic token, repo scope`, `public_repo`, `repo:status`는 같지 않음), 없을 때 `FAIL`, 헤더가 없을 때 `UNKNOWN`이다. R279의 호출이 위에 적지 않은 응답 코드를 받으면(R302의 경우 밖) `UNKNOWN`이고 원인에 그 코드를 적는다.
- R302. `doctor`의 GitHub 호출과 Docker 호출은 각각 10초 시한으로 한 번만 하고 다시 시도하지 않는다(Docker ping의 `HEAD` 뒤 `GET`은 클라이언트 동작으로 한 호출로 친다). GitHub 호출의 시한 초과, 전송 오류, 5xx, 속도 제한 응답(R24의 정의)과 Docker 호출의 시한 초과와 5xx는 그 검사를 `UNKNOWN`으로 하고, 속도 제한이면 원인 줄 `GitHub rate limit: run doctor again after <시각>`에 다시 해도 되는 시각(R52의 계산)을 적는다.
- R303. Docker 검사는 `docker.host`의 Docker에 ping한다. 요약은 unix 주소면 socket 경로, tcp 주소면 그 URL이다(예: `PASS Docker: /var/run/docker.sock answered`). ping이 시한 초과나 5xx면 `UNKNOWN`(R302), 그 밖의 이유로 실패하면(예: socket에 연결할 수 없음) `FAIL`(요약 `could not connect to <socket 경로나 URL>`)이고, 고치는 법은 기본 주소면 Docker Desktop을 켜고 기본 socket을 허용하라는 것, 다른 unix 주소면 그 socket 경로를 확인하라는 것, tcp 주소면 그 주소와 포트를 확인하라는 것이다. `docker.host`가 설정 검증에 걸리면 Docker 검사는 `Config`에 걸린 `UNKNOWN`이다. R79의 TCP 2375 검사는 노출되면 `FAIL`, 시한 안에 응답이 없어 노출 여부를 알 수 없으면 `UNKNOWN`, 이미지 검사는 `runner.image`와 `buildkit.image` 각각 이미지 ID가 로컬에 없거나 `Architecture`가 `arm64`가 아니면 `FAIL`(로컬에 없는 이미지 참조는 R323), 서버 한도 검사는 스케일러와 같은 한도(`scaling.server-limit`이 양수면 그 값, 아니면 `/info`로 계산한 R201의 값)를 쓰고, 그 값이 0이면(R202) 또는 모든 target의 `idle` 합이 그 값보다 크면(R167) `FAIL`이고 `PASS`면 요약에 그 값을 적는다(`<n> runners`). `scaling.server-limit`이 양수면 `/info`가 실패해도 이 검사는 `UNKNOWN`이 되지 않고, 그 키가 검증에 걸리면 `Config`에 걸린 `UNKNOWN`이다.
- R304. 설정 검사(`Config`)는 `config.Load`의 오류 중 App 키 파일과 토큰 파일의 오류를 뺀 것을 모두 원인 줄에 보이고, App 키 파일과 토큰 파일은 각각 따로 검사 줄을 두어 키 이름으로 부르며 경로를 보이지 않는다. 기본 App 키는 `App key file`(요약 `github.app-private-key-file: read`), target의 App 키는 `App key file targets[<i>].app-private-key-file`, 토큰 파일은 `Token file github.token-file`과 `Token file targets[<i>].token-file`이다. target의 자기 자격에 설정 오류(예: 두 종류를 함께 둠)가 있으면 그 target의 GitHub 검사는 다른 자격으로 검사하지 않고 `Config`에 걸린 `UNKNOWN`이다.
- R317. 토큰 target의 GitHub 검사에서 R279의 호출 응답에 `GitHub-Authentication-Token-Expiration` 헤더가 있으면, 그 줄의 요약 끝에 `, token expiry <값>`을 붙인다(값은 `[0-9A-Za-z :+-]`만으로 된 40자 이하일 때만 보이고, 아니면 `, token expiry unreadable`). 값을 먼저 `2006-01-02 15:04:05 MST` 꼴로, 안 되면 `2006-01-02 15:04:05 -0700` 꼴로 읽고, 읽을 수 있고 만료가 `doctor`를 실행한 때부터 7일 안이면(이미 지났으면 포함) 그 줄 뒤에 `  warning: the token expires at <값> (or has already expired); make a new token, replace the file and restart the scaler` 줄을 쓴다. 경고 줄은 검사 결과(`PASS` 등)와 R298의 수를 바꾸지 않는다. 두 꼴 모두로 읽을 수 없으면 경고 없이 위의 거른 값만 보인다. 헤더가 없으면 아무것도 붙이지 않는다.

App 만들기 링크 (R305~R306)
- R305. `app-link [-org <조직>] [-public]`은 stdout의 첫 줄에 GitHub App 등록 URL을 쓴다. `-org`가 없으면 `https://github.com/settings/apps/new`, 있으면 `https://github.com/organizations/<조직>/settings/apps/new`이고, 쿼리는 이 순서로 `url=https://github.com/dewevrei/actions-runner-scaler&public=<false, -public이면 true>&webhook_active=false&administration=write`다. 그 뒤 줄에 다음 할 일(이름 입력, 만들기, 개인키 만들기와 모드 0600, 저장소에 설치, `init`)을 쓴다. 이 명령은 네트워크와 파일을 쓰지 않는다.
- R306. `-org`의 값이 `[A-Za-z0-9-]+`가 아니면 아무것도 쓰지 않고 오류를 stderr에 쓴 뒤 1로 끝난다.

이미지 참조와 pull (R318~R324)
- R318. `runner.image`와 `buildkit.image`는 각각 Docker 이미지 참조 하나를 받는다: 로컬 이미지 ID(`sha256:<64자 16진수>` 또는 접두어 없는 64자 16진수), `<이름>[:<태그>]`, 또는 `<이름>[:<태그>]@<digest>`. 값은 distribution/reference v0.6.0의 `ParseAnyReference`가 오류 없이 읽어야 하고, 그 결과가 digest 참조(이름 없음)면 이미지 ID, 이름 있는 참조면 이미지 참조다. 어기면 R28과 같이 오류 대기에 들어가고, 오류는 그 키에 `must be an image ID or an image reference <name>[:<tag>][@<digest>], got %q`이다(0001 설정 표의 `runner.image` 꼴(`sha256:` 이미지 ID만)과 `buildkit.image` 꼴(`moby/buildkit:<버전>-rootless@sha256:<digest>`, digest 필수)을 대체).
- R319. 스케일러는 시작 단계(0001 R24의 `runner.image`와 `buildkit.image` 확인)에 키마다 설정 값을 그대로 이름으로 주어 `GET /images/{name}/json`을 부른다. 200이면 응답의 `Id`를 쓴다. 404이고 값이 이미지 참조면 R320으로 pull한 뒤 같은 조회를 한 번 더 하고, 200이면 그 `Id`를 쓴다. 404이고 값이 이미지 ID면 pull하지 못한다. 시작 단계에서는 이 조회와 R320의 실패가 0001 R24(일시 오류의 다시 시도)와 오류 대기(0001 R46, R47의 Docker 쪽 원인, 그 단계부터 다시 시도)로 가고, 이미지 ID가 없을 때의 오류는 `image <설정 값> is not present locally`이다. runner 하나를 만들 때마다 스케일러는 JIT 발급을 요청하기 전에 두 키를 같은 호출로 조회하고, 둘 다 있으면 그 `Id`로 BuildKit 컨테이너와 runner 컨테이너를 만든다. 이미지 참조가 로컬에 없으면 그 runner를 시작하지 않고(시작 실패로 세지 않음), 그 참조의 pull이 이미 돌고 있지 않으면 R320의 pull 하나를 배경에서 시작한다. 배경 pull은 자리 배치를 막지 않고, 끝나면(성공이든 실패든) 자리 배치를 한 번 한다(0002 R212). 배경 pull이 실패하면 0001 R24의 백오프(1초에서 시작해 최대 60초)가 지나기 전에는 같은 참조를 다시 pull하지 않고, 그동안 그 참조가 없어 시작하지 못한 runner는 R320의 오류 문구로 시작 실패로 센다. 이미지 ID가 로컬에 없거나 조회가 실패한 runner도 시작 실패로 센다. 이 실패들은 JIT 발급 전이므로 지울 등록이 없다. 그래서 같은 태그로 이미지를 다시 빌드하면 그 뒤에 만드는 runner부터 새 이미지를 쓰고, 이미 만든 컨테이너는 그대로다(0001 Design의 "이미지는 로컬 이미지 ID(`sha256:…`)로 고정하고 … pull하지 않는다"를 대체).
- R320. pull은 moby client v0.6.2의 `ImagePull`(`All` 거짓, 플랫폼 지정 없음)로 `POST /images/create`를 한 번 부른다. 이 함수는 설정 값을 `ParseNormalizedNamed`로 읽어 `fromImage`에 정규화한 이름(태그와 digest 없음, 예: `docker.io/library/<이름>`)을, `tag`에 digest가 있으면 그 digest, 없으면 태그(없으면 `latest`)를 보낸다. 레지스트리 자격은 보내지 않는다(`ImagePullOptions`에 `RegistryAuth`와 `PrivilegeFunc`를 두지 않음). 그래서 pull은 자격 없이 받을 수 있는 이미지만 받고, 비공개 레지스트리의 이미지는 pull하지 못한다. 로컬에 있는 이미지는 어느 레지스트리의 이름이든 조회(R319)로 쓴다. 응답 스트림을 끝까지 읽고, 스트림 안의 오류 메시지도 pull 실패로 본다. pull 한 번의 시한은 30분이다. pull 직전에 INFO 로그 `pulling image` 한 줄에 `key`(설정 키 이름)와 `ref`(설정 값)를 남긴다. 시작 단계에서 pull 호출의 전송 오류와 5xx는 0001 R24로 다시 시도하고, 그 밖의 실패(4xx, 스트림 안의 오류, 시한 초과)와 pull 뒤 조회의 404는 오류 대기에 들어가 0001 R47대로 다시 시도하며 오류는 `image <설정 값> is not present locally and pulling it failed: <Docker의 오류>`이다. 배경 pull(R319)의 시한도 30분이고, 실패하면 WARN 로그 `image pull failed` 한 줄에 `key`, `ref`, 오류를 남기고 R319대로 다룬다.
- R321. 키마다 R319의 조회로 얻은 이미지 ID가 시작 단계의 것이거나, 그 키에서 앞서 로그에 남긴 ID와 다르거나, 배경 pull(R319)이 성공한 바로 뒤의 조회로 얻은 것이면, 스케일러는 INFO 로그 `image` 한 줄에 `key`(`runner.image`나 `buildkit.image`), `ref`(설정 값), `id`(얻은 ID), `pulled`(그 조회 바로 앞에 R320으로 pull했으면 true)를 남긴다. 배경 pull이 성공하면 스케일러는 그 자리에서 같은 조회를 한 번 해 이 줄을 남긴다.
- R322. `init`이 R286의 조건(로컬 Docker에 `actions-runner-scaler-runner:local` 태그의 이미지가 있음)으로 `runner.image`를 채울 때는 그 이미지 ID 대신 태그 `actions-runner-scaler-runner:local`을 쓰고, 채운 값을 알리는 stdout 줄 `runner.image: actions-runner-scaler-runner:local (current ID <ID>)`에 지금 그 태그의 이미지 ID를 함께 보인다. `image/build.sh`는 끝에 `runner.image = "actions-runner-scaler-runner:local"` 줄과 `# runner image ID: <ID>` 주석 줄, `buildkit.image = "<값>"` 줄을 출력한다. `-runner-image`, `-buildkit-image`와 터미널의 답(R285)은 R318의 모든 꼴을 받는다. `init`의 Docker 호출은 R289 그대로이고 pull하지 않는다.
- R323. `doctor`의 이미지 검사(R303)는 키마다 R319와 같이 설정 값으로 `GET /images/{name}/json`을 부른다. 200이면 그 응답으로 R303의 검사(`Architecture`가 `arm64`)를 하고, 요약은 `present locally, arm64`이며 값이 이미지 참조면 `, <참조> = <이미지 ID>`를 붙인다. 404이고 값이 이미지 ID면 R303과 같이 `FAIL`이다. 404이고 값이 이미지 참조면 pull하지 않고 R320과 같이 자격 없이 `GET /distribution/{name}/json`을 한 번 부른다. 그 응답이 200이고 `Platforms`에 OS `linux`, 아키텍처 `arm64`인 항목이 있으면 두 키 모두 `PASS`(요약 `not present locally, pulled at start`)이다. 200이고 그런 항목이 없으면 `FAIL`, `Platforms`가 비었으면 `UNKNOWN`, 401이면 `FAIL`(원인: 레지스트리에 그 이미지가 없거나 읽을 권한이 없음, Docker의 오류 문구)이고, 시한 초과와 5xx는 R302와 같이 `UNKNOWN`이다. `runner.image`가 `actions-runner-scaler-runner:local`이면 `FAIL`의 고치는 법은 `run image/build.sh`다. R299의 Docker 호출 목록에 `GET /distribution/{name}/json`을 더한다.
- R324. README는 두 이미지 키의 꼴(R318), 로컬에 없는 이미지 참조는 시작 때와 runner를 만들 때 자격 없이 pull하고 비공개 레지스트리의 이미지는 미리 로컬에 받아 두어야 한다는 것(R319, R320), `image/build.sh`가 출력하는 `runner.image`가 태그라는 것, `runner.image`가 이미지 참조면 `image/build.sh`를 다시 실행한 뒤 설정을 고치거나 다시 시작하지 않아도 그 뒤의 runner가 새 이미지를 쓴다는 것, 이미지 ID면 그 ID를 새 값으로 바꾸고 스케일러(서비스)를 다시 시작한다는 것을 적는다.

문서 (R307)
- R307. README의 "GitHub setup"은 자격을 GitHub App → 저장소 하나만 고른 fine-grained 토큰 → classic 토큰의 순서로 권하고 그 이유(설계: 자격, classic 토큰의 `repo` scope는 그 사람이 닿는 모든 저장소의 코드에 쓰기를 줌)를, App은 owner마다 그 owner 소유의 비공개 App 하나를 기본으로 권하고 `-public`은 고를 수 있는 길로 적는 것을, 토큰 종류마다 필요한 scope와 권한, fine-grained 토큰이 owner 하나에만 닿는다는 것, 개인 계정 저장소에는 그 owner가 만든 토큰을 둔다는 것(Areas of concern 5), 처음 설정 순서(`app-link` → App 설치 → `image/build.sh` → `init` → `doctor` → `run`이나 `service install`)와 저장소를 뺄 때의 순서(스케일러를 멈춤 → `delete-scaleset` → `remove-repo` → 다시 시작)를 적는다.

실제 확인 (R308~R313, R325, R326)
- R308. 이 Mac의 지금 설정 파일을 고치지 않고 이 변경의 바이너리로 서비스를 다시 시작하면 60초 안에 `status`의 모든 target 줄이 `running`이 되고, 그 뒤 한 target 저장소에서 시작한 시험 job(`sleep 30` step 하나)이 성공한다(R271의 실제 확인).
- R309. 없는 경로에 `init -app-client-id … -app-private-key-file … -repo <A의 URL>`을 플래그만으로 실행하면(이미지는 R286으로 채움) 파일이 생기고, 그 파일로 실행한 `doctor`의 `FAIL`이 0이며, 그 파일로 `run`한 스케일러에서 A의 시험 job이 성공한다.
- R310. 서비스가 도는 중 `doctor`를 실행하기 전과 뒤에 `status` JSON의 target마다 `state`와 runner 수, runner 컨테이너 이름 목록, 각 target 저장소의 scale set ID, 설정 파일의 수정 시각이 같다(R299의 실제 확인).
- R311. 기본 자격이 App이고 개인 계정 저장소 P에 그 owner의 classic 토큰(`repo` scope)을 `targets.token-file`로 둔 설정으로 시작하면 App target 줄과 P 줄이 모두 `running`이 되고, 두 저장소의 시험 job이 성공한다. P에 대한 `doctor`의 GitHub 줄은 `PASS`이고, R279의 응답에 `X-OAuth-Scopes`와 `GitHub-Authentication-Token-Expiration` 헤더가 있었는지와 뒤 헤더의 값 꼴이 기록된다.
- R312. 저장소 하나만 고른 fine-grained 토큰(Repository permission "Administration: Read and write")을 `github.token-file`로 둔 설정에서 그 저장소의 시험 job이 성공하고, 그 저장소의 `doctor` GitHub 줄이 보인 결과와 R301의 `GET /repos/{owner}/{repo}/actions/policies` 응답 코드와 `GitHub-Authentication-Token-Expiration` 헤더의 값 꼴이 기록된다. 시험 뒤 그 저장소의 scale set을 `delete-scaleset`으로 지우면 0으로 끝난다(R281의 실제 확인).
- R313. `app-link`가 쓴 개인 계정 URL을 브라우저로 열면 등록 화면의 Repository permission "Administration"이 "Read and write"로, webhook이 꺼진 채로 골라져 있다. 화면의 이 두 값이 기록된다.
- R325. `runner.image = "actions-runner-scaler-runner:local"`인 설정으로 서비스가 도는 중 `image/build.sh`로 runner 이미지를 다시 빌드하면(새 이미지 ID), 서비스를 다시 시작하지 않고 설정 파일의 수정 시각이 그대로인 채, 그 뒤 한 target 저장소에서 시작한 시험 job(`sleep 30` step 하나)이 성공하고, 그 job을 받은 runner 컨테이너의 `docker inspect`의 `Image`가 새 이미지 ID이며, `runner.image`의 R321 줄이 새 이미지 ID로 남는다(R318, R319, R321의 실제 확인).
- R326. 스케일러를 멈추고 `buildkit.image`의 이미지를 로컬에서 지운 뒤(`docker image rm`) 설정을 고치지 않고 시작하면, R320으로 pull하고 `buildkit.image`의 R321 줄의 `pulled`가 true이며, 그 뒤 한 target 저장소에서 시작한 시험 job(`sleep 30` step 하나)이 성공한다. 지우기 전 같은 설정의 `doctor`의 `Image buildkit.image` 줄은 `PASS`, 지운 뒤에는 R323의 `PASS`(`not present locally, pulled at start`)이다. 그 뒤 스케일러가 도는 중 runner 컨테이너가 없을 때 그 이미지를 다시 지우고 같은 시험 job을 시작하면, `buildkit.image`의 `pulling image` 줄과 `pulled`가 true인 R321 줄이 남고 그 job이 성공한다(R319의 배경 pull, R320, R321, R323의 실제 확인).

## Design

용어: 자격은 target이 GitHub에 인증하는 수단이다. App 자격은 0002 그대로 App client ID와 개인키 파일이고, 토큰 자격은 personal access token 하나를 담은 파일이다. 기본 자격은 `[github]`에 둔 App이나 토큰 하나이고, target은 자기 `token-file`이 있으면 그 토큰을, 자기 App(`app-client-id`와 `app-private-key-file`)이 있으면 그 App을, 둘 다 없으면 기본 자격을 쓴다(R272~R274). 토큰 target은 토큰 자격을 쓰는 target, App target은 App 자격을 쓰는 target이다. 이 변경은 0002의 스케일링 결정(저장소 target, 저장소마다 scale set 하나와 `max-runners`, 서버 한도, 삭제 명령으로만 지우는 scale set)을 바꾸지 않는다. 바뀌는 것은 자격, 설정 파일을 쓰고 고치고 검사하는 명령, runner와 BuildKit 이미지를 부르는 꼴과 pull(R318~R326)이다.

**바꾸거나 넓히는 앞 변경 요구사항**
- 대체: 0001 설정 표의 App 두 키 필수(R274), 자격이 든 URL 값에 대한 R231의 `got %q` 인용과 R269의 URL 인용(R314), R236(R278, 설치 조회는 App target에만), R266(R280), R268과 R269의 토큰 target 경우(R281), 0001 설정 표의 `runner.image`와 `buildkit.image` 꼴(R318), 0001 Design의 runner 이미지 문장 "이미지는 로컬 이미지 ID(`sha256:…`)로 고정하고 … pull하지 않는다"(R319, R320).
- 넓힘: 0001 R30의 모드 규칙을 토큰 파일에(R275), 0001 R31을 personal access token과 이 변경의 명령에(R277), R172의 시작 단계 호출 목록에 R279의 호출을 더한다. R193의 다시 시도 순서에서 토큰 target은 R236의 설치 조회 대신 R279의 호출을 한다(R278, R279). 0001 R24의 두 이미지 로컬 존재 확인은 ID를 정하는 호출과 pull로(R319, R320) 넓힌다.
- 그대로: R237, R238은 App target의 설치 조회 결과에만 걸린다. R265(Actions 서비스 호출의 대기, target마다)와 R189(App JWT 설치 조회의 대기, App마다)는 바뀌지 않는다. 토큰 target은 R189의 대기를 쓰지 않는다.

**자격(R271~R281)**
- 토큰 종류와 권한: GitHub의 ARC 인증 문서는 저장소 수준 runner에 classic 토큰은 `repo` scope, fine-grained 토큰은 Repository permission "Administration: Read and write"가 필요하다고 적고, "ARC can use fine-grained personal access tokens to register self-hosted runners."라고 적는다(확인함(근거: https://docs.github.com/en/actions/tutorials/use-actions-runner-controller/authenticate-to-the-api, "Authenticating ARC with a personal access token (classic)"의 "Repository runners: `repo`", "Authenticating ARC with a fine-grained personal access token"의 "**Administration:** Read and write", 2026-11-26 읽음)). REST 문서에서 저장소 runner 목록과 등록 토큰 생성은 classic 토큰에 `repo` scope를 요구하고 "Authenticated users must have admin access to the repository to use this endpoint."라고 적는다(확인함(근거: https://docs.github.com/en/rest/actions/self-hosted-runners "List self-hosted runners for a repository", "Create a registration token for a repository", 2026-11-26 읽음)). fine-grained 토큰의 권한 표에서 저장소 runner 목록과 runner 하나의 조회는 Administration read, 등록 토큰, JIT 발급, runner 삭제는 Administration write다(확인함(근거: https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens, "Repository permissions for "Administration"", 2026-11-26 읽음)). scaleset v0.5.0은 토큰을 받으면 등록 토큰 요청(`/repos/{owner}/{repo}/actions/runners/registration-token`)에 `Bearer <토큰>`을 보내고, 그 뒤 관리 연결은 App과 같은 경로로 얻는다(확인함(근거: scaleset v0.5.0 `client.go` 230~239행 `NewClientWithPersonalAccessToken`, 883~909행 `getRunnerRegistrationToken`, 1052~1054행)). 그래서 토큰 target은 App target과 같은 라이브러리 호출을 쓰고, 다른 것은 클라이언트를 만드는 함수와 REST의 `Authorization`뿐이다. fine-grained 토큰이 이 라이브러리 경로로 scale set을 만들고 job을 받는지는 ARC 문서로 미루어 볼 뿐이라(추론) R312가 확인한다(Areas of concern 1).
- owner가 여럿일 때: fine-grained 토큰은 "Each token is limited to access resources owned by a single user or organization."이고, 그 한계 목록에 "Using fine-grained personal access token to access multiple organizations at once."가 있다(확인함(근거: https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens, "Creating a fine-grained personal access token"과 "Fine-grained personal access tokens limitations", 2026-11-26 읽음)). classic 토큰은 "can access every repository that you can access"다(같은 문서). 그래서 owner가 다른 저장소를 한 서버에서 섬기려면 owner마다 fine-grained 토큰 하나를 `targets.token-file`로 두거나, classic 토큰 하나를 쓰거나, App을 쓴다. `targets.token-file`이 이것을 위한 키다.
- App을 권장하는 이유(R307에 적는다): 라이브러리 README가 App을 "preferred", 토큰을 "Simpler but broader scoped"라 적고 "Always prefer GitHub App credentials; rotate PATs if you must use them."라 적는다(확인함(근거: scaleset v0.5.0 `README.md` 147~151행, 349행)). classic 토큰의 `repo` scope는 "Grants full access to public and private repositories"이고(확인함(근거: https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps, scope 표의 `repo`, 2026-11-26 읽음)) 사람 계정에 묶인다. App의 REST 한도는 설치마다이고, 토큰의 한도는 "your personal rate limit of 5,000 requests per hour"로 그 사람의 모든 토큰과 앱 요청이 같이 쓴다(확인함(근거: https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api, "Primary rate limit for authenticated users", "Primary rate limit for GitHub App installations", 2026-11-26 읽음)).
- 토큰 종류 구별: GitHub 토큰은 접두어로 종류를 보인다. `ghp_`는 classic, `github_pat_`는 fine-grained, `gho_`, `ghu_`, `ghs_`, `ghr_`는 OAuth와 App의 토큰이다(확인함(근거: https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/about-authentication-to-github, "GitHub's token formats", 2026-11-26 읽음)). R276은 이 접두어로 경로 자리에 붙여 넣은 토큰을 알아본다. `doctor`(R301)는 `github_pat_`가 아닌 토큰을 classic으로 본다. 접두어 없는 옛 classic 토큰도 이 경우에 든다(추론).
- 토큰 파일: 키 파일(0001 `ReadAppPrivateKey`)과 같은 열기 규칙(정규 파일, FIFO에서 막히지 않음, 경로를 오류에 넣지 않음)을 쓰고, 크기 상한은 4 KiB다. 토큰은 한 줄이라 끝의 줄바꿈 하나만 뺀다. 읽은 값은 시작할 때 비밀 목록(`logging.Secrets`)에 넣어 로그 handler가 가린다(R277). 토큰은 시작 때 한 번 읽으므로 토큰을 바꾸면 다시 시작한다(Areas of concern 6).
- URL 안의 자격(R314): 0002의 설정 검증은 틀린 `targets.url`을 `got %q`로 인용하고(확인함(근거: `internal/config/validate.go`의 R231 문구와 `msgOwnerURL`)), `delete-scaleset`은 설정에 없는 URL을 인용한다(확인함(근거: `cmd/actions-runner-scaler/deletescaleset.go` 289행)). 그래서 `https://<토큰>@github.com/<owner>/<repo>`처럼 자격을 넣은 URL은 stderr, 로그, `status`, `doctor`의 설정 줄에 토큰을 보인다. R231의 꼴은 `@`를 받지 않으므로 `@`가 든 값은 어차피 틀린 URL이고, 접두어 뒤 20자 이상의 조건은 `ghp_`처럼 시작하는 짧은 저장소 이름을 막지 않기 위해서다. 이 검사는 값을 인용하는 모든 검사보다 먼저 한다.
- 클라이언트: `internal/github`의 scale set 클라이언트 설정에 App 서명기와 설치 ID 대신 토큰을 받는 경우를 더하고, 그때 `NewClientWithPersonalAccessToken`을 부른다(R278). REST 클라이언트는 설치 토큰을 사는 경우와 고정 토큰을 보내는 경우를 둔다. daemon의 target 시작 단계는 App target이면 그 target의 App으로 R236~R238, 토큰 target이면 R279를 한다. 같은 App(client ID와 키)을 쓰는 target들은 그 App을 기본 App으로 쓰든 자기 App으로 쓰든 서명기, 설치 조회, 설치마다의 REST 클라이언트와 설치 토큰을 같이 쓰고, 설치 조회의 R52 대기도 App마다 하나다(확인함: `internal/daemon`의 `NewGitHub`, `appClients`, `authWaits`). 이 선택은 target마다 자격 하나를 가진 작은 인터페이스(시작 확인, scale set 클라이언트, REST 클라이언트를 만듦) 뒤에 두어, 시작 순서와 오류 범위(0002 Design 시작 순서, 오류 범위)는 그대로 둔다.
- R279의 호출: 토큰 target에는 설치 객체가 없어 권한을 이름으로 볼 수 없다. 그래서 읽기 호출 하나로 토큰이 그 저장소에 닿는지를 먼저 보고, 실패하면 GitHub의 응답 코드와 고칠 방법을 마지막 오류에 보인다. classic 토큰은 이 호출과 등록 토큰 생성이 같은 조건(`repo` scope와 저장소 admin 권한)이므로 통과하면 등록도 된다(추론: 위 REST 문서의 같은 두 문장). fine-grained 토큰이 Administration 읽기만 가지면 이 호출은 통과하고 scale set get-or-create(R239)에서 실패해 R172로 target 오류 대기에 들어간다(Areas of concern 2). 개인 계정 저장소와 조직 정책(classic 토큰 차단, fine-grained 승인 대기)은 Areas of concern 5다.
- 속도 제한 대기(R280): 토큰의 REST 한도는 사람마다라 같은 사람의 다른 토큰 둘도 한 한도를 같이 쓰지만, 스케일러는 토큰이 누구의 것인지 모른다. 사람을 알려면 시작마다 `GET /user`를 더 불러야 하므로 대기는 토큰 값마다 둔다. 같은 사람의 토큰 둘이 따로 기다리면 둘 다 한도 응답을 한 번씩 더 받을 수 있다(Areas of concern 4). 0002의 `installationWaits`(`internal/daemon/limits.go`)는 키를 설치 ID 대신 자격의 키(설치 ID 또는 토큰 값)로 바꾼다. 토큰 값은 메모리의 map 키로만 쓰고 출력하지 않는다.

**설정 파일**(0002 설정 표에서 바뀌는 키만 적는다)

| 키 | 기본값 | 허용 범위 / 설명 |
|---|---|---|
| `github.app-client-id`, `github.app-private-key-file` | (없음) | 둘 다 있거나 둘 다 없음(R274). 있으면 0001과 같고, client ID는 R274의 규칙을 따름. `github.token-file`과 함께 둘 수 없음(R272). 자기 자격이 없는 target의 기본 자격 |
| `github.token-file` | (없음) | 기본 자격인 토큰 파일의 절대 경로(R275, R276) |
| `targets.token-file` | (없음) | 이 target만 쓰는 토큰 파일의 절대 경로(R273, R275, R276) |
| `targets.app-client-id`, `targets.app-private-key-file` | (없음) | 이 target만 쓰는 GitHub App. 둘 다 있거나 둘 다 없음, 규칙은 `github.` 두 키와 같음. 같은 target의 `token-file`과 함께 둘 수 없음(R272, R273, R274) |
| `runner.image`, `buildkit.image` | (필수) | Docker 이미지 참조: 로컬 이미지 ID `sha256:<64자 16진수>`, `<이름>[:<태그>]`, `<이름>[:<태그>]@<digest>`(R318). 로컬에 없는 참조는 시작 때와 runner를 만들 때 pull함(R319, R320). 이미지 ID는 로컬에 있어야 함 |

기본 자격이 없으면 모든 target에 자기 `token-file`이나 자기 App이 있어야 하고, 그때는 `[github]`를 두지 않아도 된다(R274). `config.example.toml`은 App을 기본으로 두고, 토큰 키와 target의 자격 키는 주석 줄의 예로 둔다(자리표시자만). 0002의 키 `scaling.server-limit`, `docker.host`, `log.level`은 0002 설정 표에 있고, `init`이 쓰는 파일에도 기본값과 함께 적힌다.

**init(R282~R289)**
- 흐름: 플래그를 읽고(R284) → R286으로 이미지를 채우고 → 빠진 필수 값을 묻거나(R285) 플래그 이름을 알리고 끝내고(R287) → 키 파일과 토큰 파일을 검사하고(R288) → 파일 내용을 만들어 `config.Load`와 같은 규칙으로 검증한 뒤 → 같은 폴더의 임시 파일에 쓰고 `fsync`한 뒤 link(2)로 대상 경로에 놓는다(R282, R283). link는 대상이 있으면 실패하므로 덮어쓰지 않고, 대상 경로에는 다 쓴 파일만 나타난다. 없는 폴더는 경로 전체에 걸쳐 0700으로 만든다. go-gh와 runner-up도 설정 파일의 폴더를 이렇게 만든다(확인함: `cmd/actions-runner-scaler`의 `initMakeParent` 주석). 쓰기 전 검증에 걸리면 아무것도 쓰지 않는다.
- 묻는 순서와 문구: 자격 `Credential [app/token] (default app):` → App이면 `GitHub App client ID:`(그 앞에 `If you have no GitHub App yet, make one first with actions-runner-scaler app-link.`)과 `App private key file path:`, 토큰이면 `Token file path:` → `Repository URL (empty line to finish):`과 `max-runners (default 1):`을 빈 줄까지 되풀이 → `runner.image (value printed by image/build.sh):`. 비밀 값은 묻지 않고 경로만 묻는다(INTENT 제약).
- 이미지(INTENT 열린 질문 셋째): `runner.image`의 runner 이미지는 빌드 전에는 로컬에 없다. `image/build.sh`는 runner 이미지에 `actions-runner-scaler-runner:local` 태그를 붙이고 `BUILDKIT_IMAGE`를 고정값으로 둔다(확인함(근거: `image/build.sh`의 `RUNNER_TAG`, `BUILDKIT_IMAGE`)). `image/build.sh`는 runner 이미지에 OCI의 미리 정한 키 `org.opencontainers.image.source`("URL to get source code for building the image")와 `org.opencontainers.image.title`("Human-readable title of the image")을 라벨로 붙인다(R316, 확인함(근거: https://github.com/opencontainers/image-spec/blob/main/annotations.md "Pre-Defined Annotation Keys", 2026-11-26 읽음)). 라벨을 붙이기 전의 로컬 runner 이미지는 base 이미지에서 `org.opencontainers.image.source=https://github.com/actions/runner`를 물려받아 출처가 틀리게 적혀 있었다(확인함(근거: 2026-11-26 `docker image inspect actions-runner-scaler-runner:local`의 `Config.Labels`)). Dockerfile의 라벨은 base에서 물려받고 "the most-recently-applied value overrides any previously-set value"이므로(확인함(근거: https://docs.docker.com/reference/dockerfile/ LABEL, 2026-11-26 읽음)) 이 프로젝트의 값을 붙이면 그 출처도 바로잡힌다. 라벨은 메타데이터일 뿐이고 아무것도 읽지 않는다. 그래서 `init`은 그 태그의 이미지가 로컬에 있으면 `runner.image`를 그 태그로 채우고(R322, 설계: 이미지 참조와 pull), BuildKit 값은 Go 코드의 같은 상수로 채운다. 단위 테스트가 그 두 상수를 `image/build.sh`의 값과 비교해 어긋나면 실패한다. runner 이미지가 없으면 `init`은 값을 지어내지 않고 묻는다(터미널) 또는 `-runner-image`를 알린다(R287). 문구는 `image/build.sh`를 먼저 실행하라고 적는다.
- 파일 내용: `config.example.toml`과 같은 표 순서와 설명 주석을 쓰고 자리표시자 대신 값을 넣는다. 기본값인 키도 `# default` 주석과 함께 적어, 사용자가 어떤 키가 있는지 파일에서 본다. 단위 테스트는 `init`의 출력이 `config.Load`로 읽히고 준 값과 같다는 것을 본다.
- 같은 경로에 파일이 있으면 덮어쓰지 않는다(INTENT 열린 질문 여섯째). 손으로 고친 파일을 잃지 않게 하기 위해서이고, 이미 있는 파일의 저장소는 `add-repo`와 `remove-repo`로 바꾼다. 덮어쓰기 플래그는 두지 않는다(파일을 옮기거나 지우는 것은 사용자가 한다).

**add-repo와 remove-repo(R290~R295)**
- TOML 인코더로 다시 쓰면 주석과 키 순서를 잃으므로(`BurntSushi/toml`의 encoder는 주석을 갖지 않음, 추론) 두 명령은 파일을 글자 단위로 고친다. `add-repo`는 끝에 빈 줄 하나와 새 `[[targets]]` 블록을 붙이고, `remove-repo`는 그 target의 블록 줄만 지운다. 블록의 끝은 다음 표 머리 줄(`[`로 시작하는 줄) 앞의 마지막 키 줄이고, 그 뒤의 빈 줄과 주석 줄은 다음 블록의 것일 수 있어 남긴다.
- 안전 장치: 고친 내용을 다시 읽어 target 목록이 원래 목록에 그 하나만 더하거나 뺀 것인지 비교하고, 다르면 쓰지 않는다(R292). 여러 줄 문자열 안의 `[`로 시작하는 줄 같은 드문 꼴은 이 비교에서 걸린다. 인라인 배열(`targets = [...]`)이나 점 키로 적은 target은 고치지 않고 그 이유를 알린다.
- 쓰기: 임시 파일 → `fsync` → `rename`(R293). 설정 파일이 심볼릭 링크면 링크 자리에 rename하면 링크가 보통 파일로 바뀌므로, 링크를 따라간 실제 파일의 폴더에 임시 파일을 두고 그 실제 파일 자리에 rename한다. 두 명령은 읽기 전에 R315의 잠금 파일을 잡고 rename 뒤에 놓으므로, 동시에 실행한 두 명령은 차례로 돌아 어느 변경도 잃지 않는다. 잠금은 설정 파일이 아니라 따로 둔 파일에 건다. rename이 설정 파일의 inode를 바꾸므로 설정 파일에 건 잠금은 다음 명령을 막지 못하기 때문이다(추론: flock은 열린 파일에 걸림). 잠금 파일을 지우지 않는 이유도 같다(확인함(근거: runscaler 6f33444 `internal/lock/lock.go` 87~90행 주석 "unlinking a flock file can split contenders across two inodes and break mutual exclusion")). 잡는 방법은 스케일러의 단일 실행 잠금(`internal/daemon/startup.go` 52행의 `syscall.Flock`)과 같고, 기다린다는 점만 다르다. 먼저 막지 않고 시도하고 막힐 때만 한 줄을 알린 뒤 기다리는 것은 cargo와 같다(확인함(근거: rust-lang/cargo 562527a `src/util/flock.rs` 418~442행 `acquire`, "waiting for file lock on"을 "Blocking" 상태로 씀)). runner-up도 설정 옆의 파일에 기다리는 `LOCK_EX`를 건다(확인함(근거: runner-up 013cc74 `internal/lock/lock_unix.go` 58~73행 `Wait`)). flock은 잡은 프로세스가 죽으면 커널이 풀어 주므로, git의 `.lock` 파일이나 client-go처럼 `O_EXCL`로 만든 파일을 잠금으로 쓰는 방식과 달리 죽은 프로세스가 남긴 잠금이 없다(추론: flock(2)는 열린 파일 설명에 걸리고 닫히면 풀림). 잠금 파일 자리의 심볼릭 링크를 따라가지 않는 것(`O_NOFOLLOW`)은 링크가 가리키는 다른 파일을 만들거나 잠그지 않기 위해서다. 이 잠금은 스케일러의 잠금(0001 R78)과 다른 파일이라 서비스가 도는 중에도 두 명령을 쓸 수 있고, 스케일러는 설정을 시작 때 한 번 읽으므로 다시 시작해야 반영된다(INTENT 제약, R294).
- `remove-repo`와 scale set: 0002는 scale set을 `delete-scaleset`으로만 지우고 그 명령은 설정에 있는 저장소만 받는다(0002 R268). 그래서 `remove-repo`는 scale set을 지우지 않고, 남는다는 것과 지우는 방법을 알린다(R294). `remove-repo`가 `delete-scaleset`을 부르게 하면 GitHub를 바꾸게 되어 "설정 파일만 바꾼다"는 INTENT 제약에 어긋난다.

- 출력 예(자리표시자): `PASS GitHub <owner>/<repo>: App installation <id>, administration: write`, `FAIL Docker: could not connect to /var/run/docker.sock` 뒤에 `  cause: <오류>`, `  fix: start Docker Desktop and turn on Settings > Advanced > Allow the default Docker socket to be used`. 모든 줄은 영어이고, 원인에 들어가는 GitHub와 설정의 오류는 0002와 같은 영어 문구다.
- 하나가 실패해도 계속하는 이유(INTENT 열린 질문 아홉째): 첫 설정에서는 여러 곳이 한꺼번에 틀리므로 한 번 실행으로 모두 보이게 한다. 입력이 없는 검사는 지어낸 결과 대신 `UNKNOWN`과 그 앞 검사 이름을 보인다(R297). 종료 코드는 `FAIL`만 센다(R298). `UNKNOWN`은 GitHub의 일시 오류나 속도 제한(R302)처럼 설정과 관계없는 이유로도 나오므로, 그것까지 1로 하면 바른 설정도 1로 끝날 수 있기 때문이다.
- 아무것도 만들지 않는 권한 확인(INTENT 열린 질문 둘째): App은 그 target의 App JWT로 설치 객체를 읽어 `administration: write`를 이름으로 본다(R236, R238과 같은 호출, 설치 토큰을 사지 않음). classic 토큰은 저장소 runner 목록(admin 권한과 `repo` scope가 필요)의 200과 `X-OAuth-Scopes`의 `repo`로 등록 토큰 생성과 같은 조건을 본다. `X-OAuth-Scopes`는 "lists the scopes your token has authorized"이다(확인함(근거: https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps, 2026-11-26 읽음)). 이 문서의 예는 OAuth 토큰이고 classic 토큰도 이 헤더를 받는지는 미확인이라 R311이 기록한다(Areas of concern 7). fine-grained 토큰은 runner 읽기 endpoint가 모두 Administration read라 runner 목록으로는 쓰기 권한을 볼 수 없다. 같은 권한 표에서 `GET /repos/{owner}/{repo}/actions/policies`는 Administration `write`를 요구하고 다른 권한은 요구하지 않는다(확인함(근거: https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens, "Repository permissions for "Administration""의 `GET /repos/{owner}/{repo}/actions/policies` write, 2026-11-26 읽음)). 이 endpoint는 "List all Actions policies for a repository."인 읽기 호출이고 문서의 응답 코드는 200, 404, 500이며 플랜이나 미리보기 제한은 적혀 있지 않다(확인함(근거: https://docs.github.com/en/rest/actions/policies "List repository Actions policies", 2026-11-26 읽음)). 그래서 R301은 runner 목록 200 뒤에 이 호출로 쓰기 권한을 본다. 쓰기 권한이 없는 토큰의 응답이 403인지 404인지는 문서에 없어(미확인) 403만 `FAIL`로 하고 그 밖은 `UNKNOWN`으로 둔다. 이 endpoint가 모든 플랜과 개인 계정 저장소에서 응답하는지는 미확인이고 R312가 확인한다(Areas of concern 2). 등록 토큰 생성, JIT 발급, scale set 생성으로 확인하는 것은 INTENT 제약(doctor는 아무것도 만들지 않음)에 어긋나 하지 않는다.
- 서비스가 도는 중에도 안전한 이유: 잠금과 status socket을 건드리지 않고(R299), Docker 컨테이너와 네트워크를 나열하거나 지우지 않으며, GitHub에 GET만 보낸다. GitHub 호출은 스케일러와 같은 한도를 쓰지만 target마다 한 번이다.
- 거부 응답의 안내(R279, R301): GitHub는 권한이 모자란 요청의 응답에 `X-Accepted-GitHub-Permissions` 헤더로 그 endpoint에 필요한 권한을 "a comma separated list"로 알리고, 여러 조합이면 `;`로 나눈다(확인함(근거: https://docs.github.com/en/rest/using-the-rest-api/troubleshooting-the-rest-api "Resource not accessible", 2026-11-26 읽음)). SAML SSO를 강제하는 조직에 승인되지 않은 classic 토큰은 403과 함께 `X-GitHub-SSO` 헤더에 URL이나 조직 ID를 받는다(확인함(근거: https://docs.github.com/en/rest/authentication/authenticating-to-the-rest-api "Personal access tokens and SAML SSO", 2026-11-26 읽음)). runner-up도 첫 헤더를 글자 집합으로 거른 뒤 오류에 인용한다(확인함(근거: runner-up 013cc74 `internal/coordinator/github_api.go` 77~83행, 215~226행 `acceptedPermissions`)). 헤더 값은 GitHub가 준 문자열이라 거른 글자만 보이고, SSO 헤더는 값을 보이지 않고 승인이 필요하다는 것만 적는다. 이 안내로 조직 정책(Areas of concern 5)의 원인이 오류에 드러난다. 404에는 이 헤더가 없을 수 있다. 문서는 인증이 맞지 않는 비공개 자원 요청에 403 대신 404를 준다고 적는다(같은 troubleshooting 문서 "404 Not Found for an existing resource").
- 토큰 만료(R317): GitHub는 personal access token으로 부른 API 응답에 `GitHub-Authentication-Token-Expiration` 헤더로 만료 날짜를 알린다(확인함(근거: GitHub changelog 2021-07-26 "Expiration options for personal access tokens", https://github.blog/changelog/2021-07-26-expiration-options-for-personal-access-tokens/. docs.github.com에는 이 헤더를 다룬 문서가 없음, 2026-11-26 찾음)). 값의 꼴은 공식 문서에 없어 미확인이다. go-github는 `2006-01-02 15:04:05 MST`로 읽고 안 되면 `2006-01-02 15:04:05 -0700`으로 읽는다(확인함(근거: google/go-github master `github/github.go` `parseTokenExpiration`, 2026-11-26 읽음)). 둘째 꼴은 `github_pat_` 토큰의 값 `2023-04-26 23:23:18 +0200`을 사용자가 보고한 것이다(확인함(근거: https://github.com/google/go-github/issues/2649). 그 꼴이 GitHub의 정해진 꼴인지는 미확인). R317은 같은 순서로 읽고, 둘 다 안 되면 경고 없이 거른 값만 보인다. 실제 꼴은 R311, R312가 기록한다. 경고를 띄우는 기한에는 정해진 관례가 없다(추론: Composer의 `diagnose`는 만료 날짜만 보인다는 조사 결과에 기댐, 미확인). 7일은 사용자가 새 토큰을 만들 시간을 두기 위한 값이다. 경고를 결과로 바꾸지 않는 것은 아직 쓸 수 있는 토큰으로 `doctor`가 1로 끝나지 않게 하기 위해서다.

**app-link(R305, R306)**
- URL 꼴: 개인 계정은 `https://github.com/settings/apps/new`, 조직은 `https://github.com/organizations/ORGANIZATION/settings/apps/new`이고, 권한은 "use the permission name as the query parameter name"에 값 `read`나 `write`이며, `public`은 "`false` when it is only accessible to the owner of the app", `webhook_active`는 "Set to `true` to enable webhook. Webhook is disabled by default."이다. 등록하는 사람은 미리 고른 값을 바꿀 수 있다(확인함(근거: https://docs.github.com/en/apps/sharing-github-apps/registering-a-github-app-using-url-parameters, "About URL parameters for registering GitHub Apps", "GitHub App configuration parameters", "GitHub App permissions", 2026-11-26 읽음)). 권한의 이름은 설치 객체의 권한 이름과 같은 `administration`이다(확인함(근거: https://docs.github.com/en/rest/apps/apps "Get an installation for the authenticated app" 응답의 `administration` enum `read`, `write`, 2026-11-26 읽음)). ARC도 같은 꼴의 링크에 `administration=write`를 쓴다(확인함(근거: ARC eca1a62 `docs/authenticating-to-the-github-api.md` 51~63행)). 링크가 실제로 그 권한을 골라 두는지는 R313이 본다.
- 고른 값: 권한은 `administration=write` 하나다. 0002가 쓰지 않게 된 `actions=read`와 조직의 self-hosted runners 권한은 넣지 않는다(0002 Areas of concern 6). Metadata 읽기는 넣지 않는다(ARC 링크도 넣지 않음, 확인함(근거: 같은 ARC 파일)). webhook은 쓰지 않으므로 `webhook_active=false`다. 이름은 GitHub 전체에서 유일해야 하므로 미리 넣지 않고 사용자가 넣는다(추론). `url`(Homepage URL)은 이 공개 저장소다.
- `public`: 기본 `false`면 App owner만 설치할 수 있다. owner가 다른 저장소를 한 App으로 섬기려면 `-public`으로 만들거나 owner마다 토큰을 쓴다. 다음 할 일 줄에 이것을 적는다(Areas of concern 8).
- Manifest 흐름은 쓰지 않는다(INTENT 제약). URL 링크는 서버 없이 브라우저만으로 되고, 개인키는 사용자가 GitHub 화면에서 만들어 받는다. 그래서 키가 이 명령을 지나지 않는다.
- 별도 명령으로 둔 이유: App은 `init`보다 먼저 있어야 하고(client ID와 키 파일), `doctor`의 App 실패 줄과 README도 같은 링크를 가리킨다. `init`은 App을 물을 때 이 명령을 알린다.

**이미지 참조와 pull(R318~R326)**
- 이 요구사항을 둔 까닭: 이 변경 전에는 `runner.image`에 로컬 이미지 ID만, `buildkit.image`에 이름과 digest만 받고 pull하지 않았다(확인함(근거: 0001 SPEC 설정 표와 Design의 runner 이미지, `internal/config/validate.go` 39~40행 `runnerImagePattern`, `buildkitImagePattern`)). 2026-11-26 `image/build.sh`를 실행하자 태그 `actions-runner-scaler-runner:local`이 새 이미지로 옮겨졌고, 이름이 없어진 옛 이미지를 Docker Desktop이 지워, 도는 서비스의 설정에 적힌 ID가 없는 이미지를 가리켰다(확인함(근거: 그날 `docker image inspect <옛 ID>`가 "No such image"로 답함. `image/build.sh`에는 이미지를 지우는 명령(`rmi`, `prune`)이 없음)). 이 Mac의 Docker는 containerd image store를 쓴다(확인함(근거: 2026-11-26 `docker info`의 `driver-type io.containerd.snapshotter.v1`, Docker 29.6.1)).
- 다른 스케일러의 꼴과 pull: ARC의 runner pod 템플릿은 `image: ghcr.io/actions/actions-runner:latest`이고 `imagePullPolicy`를 적지 않는다(확인함(근거: ARC eca1a62 `charts/gha-runner-scale-set/values.yaml` 452~456행)). 그래서 Kubernetes의 기본값을 따른다. Kubernetes는 `imagePullPolicy`가 없으면 태그가 `:latest`가 아니거나 digest가 있을 때 `IfNotPresent`("the image is pulled only if it is not already present locally"), 태그가 `:latest`이거나 없을 때 `Always`로 정한다(확인함(근거: https://kubernetes.io/docs/concepts/containers/images/ "Image pull policy", "Default image pull policy", 2026-11-26 읽음)). runscaler는 기본값 `DefaultRunnerImage = "ghcr.io/actions/actions-runner:latest"`를 두고(확인함(근거: runscaler 6f33444 `internal/config/defaults.go` 11행)), 시작 때 runner 이미지를 pull하며(확인함(근거: 같은 커밋 `cmd/runner/main.go` 416~418행, `cmd/runner/image_preflight.go` 94~104행)), runner를 만들기 전마다 로컬에 없으면 다시 pull한다(확인함(근거: `internal/provider/docker.go` 230~259행)). runscaler는 pull의 레지스트리 자격을 Docker 설정 파일과 credential store에서 읽는다(확인함(근거: `internal/provider/docker_registry.go` 21~46행)). runpool은 Engine API의 `ImagePull`을 자격 없는 `client.ImagePullOptions{}`로 부른다(확인함(근거: runpool f1a2ab3 `internal/engine/docker/docker.go` 194~195행)). runner-up은 docker CLI를 거치므로 그 CLI의 로그인을 쓴다(추론: `docker run`은 CLI의 자격으로 pull함). runner-up은 버전 태그로 고정한 `"ghcr.io/actions/actions-runner:" + runnerVersion`을 `--pull` 없는 `docker run`에 준다(확인함(근거: runner-up 013cc74 `internal/agent/docker.go` 17행, 66~79행, `internal/agent/runner.go` 17행 `runnerVersion = "2.338.1"`)). `docker run`의 `--pull` 기본값은 `missing`("Pull the image if it was not found in the image cache, or use the cached image otherwise")이다(확인함(근거: https://docs.docker.com/reference/cli/docker/container/run/, 2026-11-26 읽음)). 이 변경은 컨테이너를 만들 때마다 로컬 이미지를 보고 있으면 쓰고 없으면 pull하는 `docker run --pull missing`과 runscaler의 꼴을 두 이미지 키 모두에 쓰고, `:latest`나 태그 없는 참조에도 같다. Kubernetes 기본값과 ARC의 `:latest` 템플릿은 `Always`라 이 경우는 다르다.
- 꼴(R318): 값은 distribution/reference의 `ParseAnyReference`로 읽는다. `ParseNormalizedNamed`의 주석은 "If the value may be an identifier use ParseAnyReference."라 적고, `ParseAnyReference`는 64자 16진수만의 값을 `sha256:` digest로, `digest.Parse`가 읽는 값을 digest로 보고, 그 밖은 `ParseNormalizedNamed`로 읽는다(확인함(근거: distribution/reference v0.6.0 `normalize.go` 52~55행, 246~255행, 이 저장소의 `go.mod`에 간접 의존으로 있음)). Docker도 접두어 없는 64자 16진수를 이미지 ID로 찾는다(확인함(근거: 2026-11-26 `docker image inspect <64자 16진수>`가 `sha256:<같은 값>`을 돌려줌)). 조회(R319)에는 설정 값을 그대로 보내고, pull(R320)에는 `ImagePull`이 정규화한 이름을 보낸다. 태그가 없는 참조는 Docker가 `:latest`로 찾는다(확인함(근거: 2026-11-26 `docker image inspect actions-runner-scaler-runner`가 "No such image: actions-runner-scaler-runner:latest"로 답함)). 이 Mac에서 `image/build.sh`로 만든 이미지의 `RepoDigests`에는 `actions-runner-scaler-runner@sha256:<이미지 ID의 16진수>`가 있고, 그 값과 `actions-runner-scaler-runner:local@sha256:<같은 값>` 모두 같은 ID로 찾아진다(확인함(근거: 2026-11-26 `docker image inspect`)).
- 찾는 호출(R319): Docker Engine API의 `GET /images/{name}/json`은 `name`에 "Image name or id"를 받고, 없으면 404 "No such image"다(확인함(근거: moby/moby api v1.56.1 `swagger.yaml`의 `/images/{name}/json`)). 이 호출은 시작 단계의 이미지 확인에 쓰는 호출이고, 없는 이미지는 오류 대기로 가 0001 R47대로 다시 확인한다(확인함(근거: 이 변경을 쓸 때의 `internal/daemon/startup.go` 266~283행, 281행 `image %s is not present locally`; `internal/docker/image.go`의 `ImageInspect`)). R319는 시작 단계의 이 호출을 첫 조회로 두고, runner를 만들 때마다 같은 호출을 다시 해 응답의 `Id`를 그 runner의 컨테이너 사양(지금은 `internal/daemon/startup.go` 436행에서 설정 값을 넣는 `RunnerImage`와 BuildKit 이미지)에 넣는다. runscaler도 runner를 만들기 전마다 로컬 이미지를 보고 없으면 pull하며, 그 이유를 "the daemon cache may be pruned while the controller remains running"이라 적는다(확인함(근거: runscaler 6f33444 `internal/provider/docker.go` 230~259행)). 이미지 ID는 레지스트리의 이름이 아니라 pull할 수 없으므로, ID 값이 로컬에 없으면 지금과 같다.
- pull(R320): `POST /images/create`는 "Pull or import an image"이고, `fromImage`에 태그도 digest도 없으면 "all tags are pulled"이다(확인함(근거: moby/moby api v1.56.1 `swagger.yaml`의 `/images/create`)). moby client v0.6.2의 `ImagePull`은 받은 값을 `ParseNormalizedNamed`로 읽어 `fromImage`에 `ref.Name()`(정규화한 이름, 태그와 digest 없음)을 넣고, `All`이 거짓이면 digest를, 없으면 `reference.TagNameOnly`로 채운 태그(없으면 `latest`)를 `tag`로 보낸다(확인함(근거: moby client v0.6.2 `image_pull.go` 38~46행, 70~79행)). 그래서 R320의 `fromImage`와 `tag`는 이 함수를 부르면 그대로 된다. 레지스트리 자격을 보내지 않는 것은 runpool과 같다. 다섯 참고 저장소(ARC, efr, runner-up, runpool, runscaler)에서 `RegistryAuth`, `credentials.NewStore`, docker CLI 설정 패키지를 쓰는 파일은 runscaler의 `internal/provider/docker_registry.go` 하나이고(확인함(근거: 2026-11-26 다섯 클론의 텍스트 검색)), 이 프로젝트의 runner 이미지는 로컬에서 만들며 BuildKit 이미지는 Docker Hub의 공개 이미지다(확인함(근거: `image/build.sh`의 `BUILDKIT_IMAGE` `moby/buildkit:…`)). 시작 단계에서 실패를 R24의 일시 오류(전송 오류, 5xx)와 그 밖으로 나누는 것은 0001 R24의 정의를 그대로 쓴 것이고, runner를 만들 때의 pull은 배경에서 돌고, 실패한 참조를 다시 pull하기 전의 간격은 0001 R24의 백오프를 그대로 쓴다(R319). 30분 시한은 runscaler의 pull 시한과 같다(확인함(근거: runscaler 6f33444 `cmd/runner/image_preflight.go` 96행, `internal/provider/docker.go` 264행 `30*time.Minute`)).
- 흐름: 시작 단계는 설정 검증(R318) → R79의 TCP 2375 확인 → `runner.image` 조회, 로컬에 없는 참조면 pull 뒤 다시 조회, R321 로그 → `buildkit.image`도 같음 → 서버 한도 → target 시작이다. 그 뒤 runner를 만들 때마다 두 키의 조회 → JIT 발급 → 네트워크, BuildKit 컨테이너, runner 컨테이너를 얻은 ID로 만듦 순서다. 조회에서 참조가 없으면 그 runner는 시작하지 않고 배경 pull을 시작하며, pull이 끝나면 자리 배치가 다시 runner를 시작한다. 자리 배치는 서버의 모든 target이 함께 쓰는 잠금 안에서 돌고 그동안 `Scale`도 기다리므로(0002 R115, `internal/scaler/placement.go`의 `Placer` 주석), 최대 30분인 pull을 그 안에서 하면 모든 target의 배치와 메시지 처리가 멈춘다. runscaler도 "Provider and GitHub API I/O never blocks the listener callback"이라 적고, 같은 이미지의 진행 중인 pull을 참조마다 하나로 묶는다(확인함(근거: runscaler 6f33444 `internal/controller/controller.go` 162행, `internal/provider/docker_image_pull.go`의 `DockerImagePullCoordinator`)). 조회를 JIT 발급 앞에 두는 것은 이미지를 기다리는 동안 등록만 된 runner를 남기지 않기 위해서다. 이미 만든 컨테이너는 만들 때의 이미지로 돈다.
- `init`(R322): 태그를 쓰면 `image/build.sh`를 다시 실행해도 설정을 고치거나 다시 시작하지 않고, 그 뒤의 runner가 새 이미지를 쓴다. 채운 줄에 지금의 ID를 함께 보인다. `image/build.sh`가 출력하는 `runner.image` 줄도 태그이고 ID는 `# runner image ID:` 주석 줄로만 보인다(R322). 설정에 ID를 적은 경우는 R324가 README에 적는다. `init`은 pull하지 않는다(R289).
- `doctor`(R323): R303의 검사는 지금도 설정 값으로 `GET /images/{name}/json`을 부른다(확인함(근거: `internal/doctor/docker.go` 103행 `ImageInspect(ctx, ref)`)). `doctor`는 아무것도 바꾸지 않으므로(INTENT 제약) pull 대신 `GET /distribution/{name}/json`("Return image digest and platform information by contacting the registry", 응답의 `Platforms`, 401 "Failed authentication or no image found")으로 레지스트리에 그 이미지가 있는지 본다(확인함(근거: moby/moby api v1.56.1 `swagger.yaml`의 `/distribution/{name}/json`, `api/types/registry/registry.go` 64~66행 `Platforms`)). 이 호출은 Docker와 레지스트리에 아무것도 만들지 않는 읽기 호출이다(추론: GET이고 설명이 정보를 돌려준다고만 적음).

**명령 표면**: 새 하위 명령은 `init`, `add-repo`, `remove-repo`, `doctor`, `app-link`이고, 모두 0002 명령처럼 `-config`(기본 `~/.config/actions-runner-scaler/config.toml`)를 받는다(`app-link` 제외). 사용법 오류는 0002의 `usageError`와 같이 1로 끝난다. 비밀은 경로로만 받고 값을 받는 플래그는 두지 않는다(INTENT 제약).

**테스트**
- 단위: 설정(R271~R277, R314, 0002 예시 파일이 그대로 읽힘, 토큰 값이 오류 문자열에 없음), 클라이언트 선택(R278), R279의 응답 코드별 결과(가짜 HTTP), 대기 키(R280, 같은 토큰 둘은 같은 대기, 다른 토큰과 설치는 다른 대기), `delete-scaleset`의 토큰 target(R281), `init`의 플래그·질문·EOF·이미 있는 파일·이미지 채움과 상수 비교(R282~R289, 가짜 터미널과 가짜 Docker), `add-repo`·`remove-repo`의 바이트 비교와 거부 경우와 붙여 넣을 블록(R290~R295, 주석과 빈 줄이 섞인 파일), 잠금(R315, 두 프로세스가 차례로 고쳐 두 변경이 모두 남음), 라벨(R316, `image/build.sh`의 `--label` 줄 확인), `doctor`의 결과 표와 의존 검사, 종료 코드, 헤더 안내와 만료 경고(R296~R304, R317, 가짜 GitHub와 Docker가 받은 메서드가 모두 GET인지 확인), `app-link`의 URL 문자열(R305, R306), 두 이미지 키의 꼴(R318, ID, 태그 있는·없는 참조, digest 붙은 참조, 접두어 없는 64자 16진수를 이미지 ID로 받음), 시작 단계와 runner 생성이 가짜 Docker의 `Id`로 컨테이너를 만들고 로컬에 없는 참조만 pull하며, 태그가 다른 이미지로 옮겨진 뒤 만든 runner가 새 `Id`를 쓰고, pull 실패의 나눔(시작 단계의 R24와 오류 대기, runner 생성의 시작 실패와 백오프)과 배경 pull이 자리 배치를 막지 않고 참조마다 하나만 돌며 끝나면 자리 배치를 한 번 함, R321 로그가 맞음(R319~R321), pull이 레지스트리 자격을 보내지 않음(R320), `init`이 태그를 채움(R322), `doctor`의 이미지 줄과 `GET /distribution/{name}/json`의 응답별 결과(R323).
- 실제: R308~R313, R325, R326. 이 Mac과 0002의 시험 저장소를 쓰고, 개인 계정 저장소 P(R311)와 fine-grained 토큰의 저장소(R312)는 사용자가 정한다. 시험 토큰은 사용자가 만들어 파일로 두고 시험 뒤 GitHub에서 지운다. 시험 scale set은 `delete-scaleset`으로 지우고 보고한다.

## Open questions from the intent

- 어떤 personal access token이 저장소 수준 scale set을 등록하고, 어떤 scope나 권한이 필요하며, fine-grained 토큰이 둘 이상의 owner에 닿는가? → 답: classic 토큰은 `repo` scope와 그 저장소의 admin 권한, fine-grained 토큰은 Repository permission "Administration: Read and write"다(확인함, 설계: 자격의 토큰 종류와 권한). fine-grained 토큰은 owner 하나에만 닿으므로 owner마다 `targets.token-file`을 둔다(확인함, 설계: 자격의 owner가 여럿일 때). fine-grained 토큰이 이 라이브러리로 job까지 받는지는 R312가 본다(Areas of concern 1).
- `doctor`가 아무것도 만들지 않고 토큰이나 App의 runner 등록 권한을 확인할 수 있는가? → 답: 된다. App은 설치 객체의 `administration: write`, classic 토큰은 runner 목록 200과 `X-OAuth-Scopes`의 `repo`, fine-grained 토큰은 runner 목록 200과 Administration write가 필요한 `GET /repos/{owner}/{repo}/actions/policies`의 200으로 본다(R300, R301, 설계: doctor). 넘김: Areas of concern 2(정책 endpoint의 응답), 7(classic의 헤더).
- 아직 이미지를 빌드하지 않았을 때 `init`은 무엇을 묻고, 로컬에서 빌드한 이미지 값을 채우는가? → 답: 채운다. `runner.image`는 태그 `actions-runner-scaler-runner:local`, `buildkit.image`는 `image/build.sh`의 고정값이다(R286, R322). runner 이미지가 없으면 터미널에서 `runner.image`를 묻고 `image/build.sh`를 먼저 실행하라고 적으며, 터미널이 아니면 `-runner-image`를 알리고 끝낸다(R285, R287).
- App 만들기 링크는 개인 계정과 조직 owner 모두에 되고, 어떤 권한을 채우는가? → 답: 둘 다 된다. 개인 계정은 `https://github.com/settings/apps/new`, 조직은 `https://github.com/organizations/<조직>/settings/apps/new`이고(확인함, 설계: app-link), 채우는 권한은 `administration=write` 하나다(R305). 개인 계정 URL의 실제 화면은 R313이 본다.
- 더하기와 빼기 명령이 손으로 고친 설정 파일의 주석과 순서를 지키는가? → 답: 지킨다. 바뀌는 블록 밖의 바이트를 그대로 두고(R290, R291), 다시 읽은 target 목록이 기대와 다르면 쓰지 않는다(R292).
- `init`의 대상 경로에 설정 파일이 이미 있으면 어떻게 하는가? → 답: 아무것도 쓰지 않고 1로 끝나며 `add-repo`와 `remove-repo`를 알린다(R282). 덮어쓰기 플래그는 없다.
- `init`은 받은 키나 토큰 파일이 있고 제한된 모드인지 확인하는가? → 답: 확인한다. 플래그로 받은 파일은 검사에 걸리면 쓰지 않고(R288), 터미널에서 받은 경로는 다시 묻는다(R285).
- 같은 토큰을 쓰는 저장소들 사이에서 REST 속도 제한 대기를 어떻게 나누는가? → 답: 같은 토큰 값마다 하나를 두어 그 토큰의 target들이 같이 쓴다(R280). 같은 사람의 다른 토큰은 따로 기다린다(Areas of concern 4).
- `doctor`가 돌릴 수 없는 검사(예: Docker가 멈춤)에 무엇을 출력하고, 그 뒤 다른 검사를 하는가? → 답: 원인이 된 검사는 `FAIL`, 그 검사에 기대는 검사(이미지, 서버 한도)는 `UNKNOWN`과 원인 검사 이름을 보이고, 나머지 검사는 모두 한다(R297, 설계: doctor 검사 표).

## Areas of concern

1. fine-grained 토큰과 scaleset 라이브러리: 라이브러리는 토큰을 등록 토큰 요청 `POST /repos/{owner}/{repo}/actions/runners/registration-token` 하나에만 쓰고(확인함(근거: scaleset v0.5.0 `client.go` 883~909행)), 그 뒤 `/actions/runner-registration`부터는 받은 등록 토큰(`RemoteAuth`)으로 인증한다(확인함(근거: 같은 파일 977~1002행)). 그 endpoint는 fine-grained 권한 표에서 Administration write다(확인함, 설계: 자격). ARC 문서와 runscaler 문서는 저장소 runner에 fine-grained 토큰의 Administration Read and write를 적고(확인함(근거: runscaler 6f33444 `docs/configuration.md` 21~24행)), efr 문서는 저장소 범위의 토큰에 Administration read and write를 적는다(확인함(근거: efr bcb9c8e `doc-site/src/content/docs/reference/configuration.md` 119~127행)). 그래서 fine-grained 토큰이 등록 경로에 닿는 근거는 문서와 코드에 있고, 실제 job까지 되는지는 R312가 본다. R312가 안 되면 README와 `doctor`가 fine-grained 토큰을 지원하지 않는다고 적고 R276과 같은 자리에서 `github_pat_` 토큰을 설정 오류로 막는 쪽으로 SPEC을 고친다. Owner: 사용자.
2. fine-grained 토큰의 쓰기 권한 확인: `doctor`는 `GET /repos/{owner}/{repo}/actions/policies`로 본다(R301, 확인함: 권한 표). 이 endpoint가 모든 플랜과 개인 계정 저장소에서 응답하는지, 쓰기 권한이 없는 토큰에 403과 404 중 무엇을 주는지는 미확인이고 R312가 응답 코드를 기록한다. 응답하지 않으면 그 줄은 `UNKNOWN`이 된다. runscaler와 runpool처럼 라이브러리 호출(`GetRunnerGroupByName` 등)로 확인하는 방법은 쓰지 않는다. 그 호출은 Actions 서비스 요청 전에 등록 토큰을 만들어(확인함(근거: scaleset v0.5.0 `client.go` 348~352행 `newActionsServiceRequestWithQuery`가 `updateTokenIfNeeded`를 부르고, 그 함수가 1102행에서 `getRunnerRegistrationToken`을 부름, 883~909행)) GitHub에 자격을 만들므로 "`doctor` creates, changes and deletes nothing on GitHub"라는 INTENT 제약에 어긋난다. 스케일러 쪽에서 Administration 읽기만 준 토큰은 R279를 통과하고 scale set get-or-create의 403으로 target 오류 대기가 되며, 그 오류는 라이브러리의 문구라 R279의 안내 문구가 붙지 않는다. Owner: 사용자.
3. classic 토큰의 `repo` scope는 그 사람이 닿는 모든 저장소의 코드에 쓰기까지 주는 넓은 권한이다(확인함, 설계: 자격). README는 App → 저장소 하나만 고른 fine-grained 토큰 → classic 토큰의 순서로 권하고 그 이유를 적어(R307) classic 토큰을 쓰는 경우를 줄이며, 쓰는 경우에는 파일 모드(R275)로만 지킨다. Owner: 사용자.
4. 토큰의 REST 한도는 사람마다인데 대기는 토큰 값마다다(R280). 같은 사람의 토큰 여러 개를 쓰면 스케일러가 한도 응답을 토큰마다 한 번씩 받을 수 있다. 영향은 시작 때의 runner 목록과 30초 대조의 이름 조회(R241, R242)이고 R52 대기가 그 뒤를 막는다. Owner: 사용자.
5. 조직 정책: 조직은 classic 토큰의 접근을 막을 수 있고(그때 403), fine-grained 토큰에 승인을 요구할 수 있으며 승인 전에는 공개 자원만 읽는다(확인함(근거: managing-your-personal-access-tokens 문서, 2026-11-26 읽음)). 두 경우 모두 R279와 R301의 `FAIL`로 드러나고, 응답에 `X-Accepted-GitHub-Permissions`나 `X-GitHub-SSO`가 있으면 그 안내가 원인에 붙는다(R279). 정책 차단 자체를 이름으로 알리는 헤더는 찾지 못했다(미확인). 개인 계정 저장소는 "a single owner who has full control of the repository"이고 권한 수준은 owner와 collaborator 둘이며 collaborator의 권한 목록에 저장소 관리는 없다(확인함(근거: https://docs.github.com/en/account-and-profile/reference/permission-levels-for-a-personal-account-repository, 2026-11-26 읽음)). runner 목록과 등록 토큰은 저장소 admin 권한을 요구하므로(설계: 자격) 그 owner의 토큰만 쓸 수 있고(추론: 두 문서), fine-grained 토큰은 "repositories where the user is an outside or repository collaborator"에 쓸 수 없다(확인함(근거: managing-your-personal-access-tokens 문서의 fine-grained 한계 목록)). 그래서 개인 계정 저장소에는 그 owner가 만든 토큰을 둔다(R307에 적는다). Owner: 각 저장소의 owner와 사용자.
6. 토큰 만료와 교체: URL 파라미터로 만든 fine-grained 토큰은 `expires_in`을 주지 않으면 30일에 만료된다(확인함(근거: https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens 의 `expires_in` 설명 "If not provided, the default is 30 days", 2026-11-26 읽음)). GitHub 화면에서 만들 때의 기본 만료는 미확인이다. `doctor`는 응답 헤더로 만료 날짜를 보이고 7일 안이면 경고한다(R317). GitHub가 만료 전에 알림 메일을 보내는 때는 미확인이다. 스케일러 자체는 만료를 미리 알리지 않는다. 만료된 토큰의 target은 다음 GitHub 호출의 401로 target 오류 대기에 들어간다(R279는 시작 단계 문구이고, 실행 중의 401은 0002 오류 범위대로 그 target의 오류다). 토큰 파일을 바꾸면 스케일러를 다시 시작해야 한다. Owner: 사용자.
7. classic 토큰의 `X-OAuth-Scopes`: 문서의 예는 OAuth 토큰이고 classic 토큰도 이 헤더를 받는지는 미확인이다. 헤더가 없으면 R301은 `UNKNOWN`이 되어 잘못 통과시키지는 않는다. R311이 기록한다. Owner: 구현(PLAN).
8. App의 `public` 값: 기본 `false`인 App은 owner만 설치할 수 있다(확인함, 설계: app-link). ARC는 개인 계정과 조직에 각각 `public=false`인 App을 만드는 링크를 준다(확인함(근거: ARC eca1a62 `docs/authenticating-to-the-github-api.md` 53행, 57행)). 그래서 README는 owner마다 그 owner 소유의 비공개 App 하나를 기본으로 권한다(R307). 다만 이 스케일러의 설정은 App 하나만 받으므로(R272) owner가 다른 저장소를 App으로 함께 섬기려면 `-public` App 하나를 쓰고, 다른 owner의 저장소는 `targets.token-file`로 섬기는 길도 있다. `-public`이면 누구나 그 App을 자기 계정에 설치할 수 있다. 설치만으로 이 스케일러의 저장소에 닿지는 않지만(설치는 설치한 owner의 저장소에만 권한을 줌, 추론), 결정은 사용자가 한다. Owner: 사용자.
9. `add-repo`와 `remove-repo`의 글자 단위 고치기는 `[[targets]]` 표 머리로 적은 파일만 다룬다. 다른 꼴의 파일은 거부되고(R292), `add-repo`는 붙여 넣을 블록을 보여 사용자가 손으로 고친다. Owner: 구현(PLAN).
10. `init`의 이미지 채움은 태그 `actions-runner-scaler-runner:local`의 이미지가 로컬에 있는지만 본다(R286). 그 태그를 다른 이미지에 옮겨 붙이면 `init`, 스케일러, `doctor`는 그 이미지를 그대로 쓰고, `doctor`의 이미지 줄은 있음과 `arm64`만 본다(R303, R323). R316의 라벨은 출처를 적는 메타데이터일 뿐 이 실수를 거르지 않는다. Owner: 사용자.
11. 동시에 실행한 `add-repo`와 `remove-repo`는 R315의 잠금으로 차례로 돈다. 편집기로 설정 파일을 고치는 동안에는 이 잠금이 걸리지 않으므로, 그동안 두 명령을 실행하면 편집기가 나중에 저장한 내용이 남는다. Owner: 사용자.
12. 로컬에서 없어진 이미지: 2026-11-26에는 `image/build.sh`가 태그를 옮긴 뒤 옛 이미지가 로컬에서 없어졌다(확인함, 설계: 이미지 참조와 pull). Docker Desktop이 이름 없는 이미지를 언제 지우는지는 미확인이다. `runner.image`가 이미지 참조면 runner를 만들 때마다 조회하므로(R319) 태그가 가리키는 이미지를 쓰고, 그 태그가 로컬에서도 레지스트리에서도 없으면 배경 pull이 실패해 그 뒤의 runner 시작은 R319대로 시작 실패로 세어진다(JIT 발급 전이라 등록은 없다). 이미지 ID면 pull할 수 없으므로 그 이미지가 없어진 뒤 만드는 runner는 같은 실패를 한다. README는 ID를 쓰는 경우 다시 빌드한 뒤 ID를 바꾸고 다시 시작하라고 적는다(R324). Owner: 사용자.
