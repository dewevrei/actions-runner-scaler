## Order of work

Each milestone must pass `gofmt -l .` (no output), `go vet ./...`, and `go test -race ./...` using only the code up to that milestone. From M2 on, `shellcheck image/*.sh` must also pass. Packages of later milestones are replaced by fakes. The formats of the container Env, `GET /v1/verdict`, the status socket and its output, and the config table follow SPEC Design "외부 계약" (External contracts). Steps that use real GitHub, Docker, or the cluster get user approval before they run; the resources they create are deleted right afterwards and reported. The term "끝난 runner" (finished runner, `done`) follows the definition in SPEC Design. R13 and R15 are dropped in SPEC, so they have no steps and no proof. 2. `internal/config` (R28, R30, R31, R68)
   - `Load`: read the file as `map[string]toml.Primitive`, read each table again as `map[string]toml.Primitive`, and `PrimitiveDecode` the keys one by one in sorted order (`decodeFile`, `decoder.table` in `config.go`). Collect all unknown keys, TOML syntax errors, and invalid sizes and durations. Do not use `MetaData.Undecoded`. The decoder walks tables in map order and stops at the first bad key, so with several errors only one of them, a different one on each run, would show (`fields` in `config.go`). Keys and tables that failed to decode are left out of validation, so the same key's error does not appear twice. Decoding goes on top of the defaults, so an omitted key keeps its default and an explicit 0 reaches validation.
   - A syntax error keeps only the line and column and drops the message (a secret pasted into a value could appear in it). A key segment is shown as is only when, after lowercasing, it matches `^[a-z0-9_-]+$` and is 40 characters or fewer (a key that differs only in uppercase is shown as is); otherwise it is shortened to its first 4 characters and its length (`displayKey`, `displaySegment` in `config.go`, R31).
   - `Validate()` collects all errors with `errors.Join`. The ranges copy the config table in SPEC "외부 계약" (under "설정 파일"). The pool name is `^[a-z0-9][a-z0-9-]{0,39}$` (first character a lowercase letter or digit, `poolNamePattern` in `validate.go`); `repo-url` rejects a `.git` suffix; CPU is at least 0.01 and less than `math.MaxInt64/1e9`, and NaN and +Inf are rejected (`problems.limits` in `validate.go`). Each `allowed-workflows` entry is `.github/workflows/<file>.yml|.yaml` and `@` is forbidden (because the gate splits on `@`).
   - The pool count error is the English message `pools: this version supports exactly 1 pool, got N` (`Config.problems` in `validate.go`, R68). Defaults: runner 1 CPU·`1g`·512, BuildKit 2 CPU·`2g`·1024, max 2, idle 0, allowed-events `["push"]`.

4. `internal/retry` (R24, R25, R41, R50, R51, R52, R95, R97, R104)
   - `retry` does not import scaleset, `github`, or `docker`. It defines `StatusCoder{HTTPStatus() int}`, `Op`, `OpError{Op, Err}`, `RateLimitError{RetryAfter, Reset, Err}`, and the sentinels `ErrRunnerGone`, `ErrJobStillRunning`, `ErrRunnerExists`, `ErrAuth`, `ErrAmbiguousScaleSet` (`internal/retry/errors.go`), and `github` and `docker` convert their own errors into these.
   - `Backoff`: from 1 second, doubling up to 60 seconds; jitter only adds up to 20% of the interval and never exceeds the cap. `Wait(ctx, err)` waits for the longer of the backoff interval and the rate-limit wait (`Backoff.Wait`).
   - Rate-limit wait (R52, R104): `min(max(RetryAfter, Reset−now, 0), MaxRateLimitWait)`; `MaxRateLimitWait` is 24 hours. If `RetryAfter` is 0 or less and there is no `Reset`, it is `DefaultRateLimitWait`, 60 seconds (the constants and `rateLimitWait` in `backoff.go`). So `Retry-After: 0` means no hint (60 seconds), and with only a past reset it waits just the backoff interval. A 429 that nobody converted is still treated as a rate limit without a hint.
   - `Classify(ctx, op, err) Class` only classifies; the call site decides the reaction according to the table under SPEC "재시도 규칙" (retry rules) (R97). Only the `op` argument determines the call site; `OpError.Op` inside the error chain is not looked at. The first matching rule decides (`Classify`):
     1. If the parent ctx is done, `Canceled`
     2. Rate limit (`RateLimitError` or 429) → `RateLimited`. Checked before the call's own deadline expiry: even if the deadline ends while reading the body after the server answered with a rate limit, the server's answer forbids an early retry (`Classify`).
     3. The call's own deadline expiry (`context.DeadlineExceeded`) → `Transient`
     4. `ErrAuth` and `ErrAmbiguousScaleSet` → `Permanent` (R41, R51). Checked before the status rules so that a 404 from the auth exchange is not read as `Gone` or `SessionLost`.
     5. `Gone`: `ErrRunnerGone`, a 404 when `op` is `RemoveRunner`, a 404 when `op` is a Docker deletion (container, network, volume) (R50)
     6. Runner sentinels: `ErrJobStillRunning` → `Transient`, `ErrRunnerExists` → `Permanent`. scaleset also wraps both in a 409 `ConflictError`, so they are checked before the 409 rule (confirmed: scaleset v0.5.0 `errors_test.go` lines 157~175, `AgentExistsException` 409, lines 171~172 `RunnerExistsError` and `ConflictError`; lines 196~214, `JobStillRunningException` 409, lines 210~211 `JobStillRunningError` and `ConflictError`).
     7. 409 from session creation, and 409 and 403 from Docker deletion → `Transient` (R24, R50)
     8. 404 when `op` is `GetMessage`, `DeleteMessage`, `AcquireJobs`, or session refresh → `SessionLost` (R25)
     9. Any other 4xx (including 403, 422, 404 from session creation, and 401 after a session refresh) → `Permanent` (R41)
     10. Everything else (transport errors, 5xx, no status) → `Transient`
   - `ratelimit.go`: `NextAllowed` holds a "next allowed time" per call kind under a mutex (R52, R104). The verdict's `GetRun` and `ListWorkflowRuns` have no kind, so they are neither recorded nor checked (R65). Docker calls have no kind either.

     | Kind | Where it is recorded and checked | When before the allowed time |
     |---|---|---|
     | JIT | runner start | skip the start (R87) |
     | `AcquireJobs` | `Scale`, session loop | `Scale` does not call it and returns `RateLimitError` so the message is not acked. The session loop waits until the latest of the backoff, the session, and this time |
     | Session (create, refresh, `GetMessage`, `DeleteMessage`) | session loop | wait, then a new session |
     | `RemoveRunner` | scale-down, start-failure cleanup (R18), deny cleanup, watch and reconcile (including R101), finalization (R21, R55, R92), R17, `delete-scaleset` | scale-down stops the remaining removals (R95). Start-failure cleanup and watch push the retry timer out to that time. Deny cleanup keeps retrying as in M4-2 |
     | `ListRepoRunners` | R17, R103, `delete-scaleset` | R17 skips without waiting. R103 does not call it until that time |
     | `GetRunnerByName`, `GetRunnerScaleSet`, get-or-create | R17, startup sequence, `delete-scaleset` | R17 logs and skips (for `GetRunnerScaleSet`, all of R17 is skipped). The startup sequence waits until that time, then tries again (R24) |

     A call made only once (finalization, R17) that falls before the allowed time is not made and is left to R17 of the next start. `delete-scaleset` is a separate process, so it waits with `Backoff.Wait` and calls again.

3. `job-started.sh` (R10, R39, R66, R82)
   - On the first line, `PATH=/usr/bin:/bin`; commands are called by absolute path. The address and name are read only from the endpoint file, and the token only from the token file, with the built-in `read`; Env is not read.
   - Query: `printf 'Authorization: Bearer %s\nX-Runner-Name: %s\n' … | /usr/bin/env -i /usr/bin/curl -q --noproxy '*' -s --connect-timeout 2 --max-time 5 -H @- -o <body file> -w '%{http_code}' "$url/v1/verdict" >"<code file>"`. `env -i` keeps name resolution and dynamic loader variables away from curl. `-S` is not used. A failure is left as one deduplicated line with status `000` and the curl exit code. The body is checked with `case`, without jq; the body (`-o`) and the status code (`-w`) are not mixed, and command substitution is not used (because it defeats `wait`).
   - On allow, delete the token file and the response files, and `exit 0` only after confirming the token file is gone. If it cannot be deleted, keep querying (the "job 시작 hook" item in SPEC "구성 요소", the decision in M4-1). On 401, pending, connection failure, or any other response, rest 2 seconds and query again; it never ends on its own.
   - On the first deny, end the Worker (`kill_worker`, the '거부 때 Worker 끝내기' (End the Worker on deny) item in SPEC Design, R11, R66): ignore the trapped signals and fatal signals, and if `START_PID` is a number of 2 or more and is not the hook itself, send the built-in `kill -KILL "$START_PID"`. On success, set `released=1`, write the kill line and `scaler-job-started: job denied; killed the worker`, then exit with 1 (the kill comes before the log). It does not query any more and does not kill `Runner.Listener` or the ancestor chain. If `START_PID` does not fit or the kill fails, write `job denied; cannot kill the worker, killing the runner`, call the kill handler below directly to end all runner processes with SIGKILL, then exit with 1.
   - It runs under `bash -e`, so every failure in querying, reading files, and waiting is caught with `|| …`.
   - curl and the 2-second `sleep` are started in the background and waited for with the built-in `wait`. The limit for one child is `CHILD_MAX=5` (seconds). On step cancellation the runner waits 7.5 seconds after SIGINT and 2.5 seconds after SIGTERM, so this is kept under 7 seconds (confirmed: v2.338.2 `ProcessInvoker.cs` lines 32~33, 443~465).
   - trap: set `trap '' PIPE`, `trap on_exit EXIT`, `trap on_signal INT TERM HUP QUIT USR1 USR2 ALRM` in this order. The kill handler (`kill_runner`) ignores the signals above and the fatal signals (VTALRM, PROF, XCPU, XFSZ, SYS, TRAP, ABRT, BUS, FPE, ILL, SEGV) as soon as it enters, and runs only once. The signal handler (`on_signal`) always calls the kill handler and exits with 1. The EXIT trap (`on_exit`) kills nothing if it ended with allow or `released=1` (only the Worker was ended on deny), and kills everything otherwise. Except when it ends with allow or has ended only the Worker on deny, it ends the following with the built-in `kill -KILL`. PID 1 and the hook itself are skipped.
     1. `START_PID` (default `$PPID`, the Worker that is the hook's parent) first of all
     2. The ancestor chain read in advance at hook start (`ancestors`) and the chain read again at kill time. The chain follows the second field (ppid) after the last `)` in `PROC_DIR/<pid>/stat`, stops when it cannot be read or the ppid is 0, 1, or itself, and goes at most 16 levels. It is read in advance because once the Worker dies and is reaped, the chain can no longer be followed upward from the Worker.
     3. Processes whose argv[0] in `PROC_DIR/[0-9]*/cmdline` ends with `Runner.Listener` or `Runner.Worker`
   - The kill happens before the stderr log (`kill_one`). stderr is a pipe held by the Worker, so it can block or be closed.
   - Method not chosen: `kill -KILL -1` (everything except PID 1 and the caller). Reason: the target cannot be replaced with a fake, so `scripts_test` running on the host would kill all user processes on the development PC.
   - The constants (`STATE_DIR`, `PROC_DIR`, `START_PID`, `CHILD_MAX`, `CONNECT_TIMEOUT`, `POLL_INTERVAL`, `RECORD`) are one line each at the top of the file, and it also runs on bash 3.2.

Each round looks only at the table and starts R101 deletions before any external call, and R103 runs in a separate goroutine, one at a time, with a 20-second timeout so it does not block reconcile. The finalization flag is checked before starting a round and before each external call.

Among the rows in the table, a row whose runner container is missing or finished (exited, dead) is treated like an exit (except `starting` and `exiting`). 1. `internal/gate/server.go` (R14, R38, R40, R43, R66)

The adapter in `daemon/adapters.go` converts `scaler.Verdict` from `scaler.Table.Authenticate` to `gate.Verdict` with an explicit switch. It does not rely on the two types having the same integer values.

On failure, it records no busy and immediately returns 401 and `{"reason":"..."}`. On success, 200 and the verdict.

The hook removes all whitespace characters from the body and reads it as that verdict only when it is exactly equal to one of these three strings (the `case` of the hook's query loop).
   - The hook's two remaining behaviors are not changed. (1) Whitespace removal: the server sends fixed bytes without whitespace, so the result is the same, and removing only whitespace cannot turn the body of another verdict into allow. (2) If deleting the token file fails after allow, the hook does not end and keeps querying. The "job 시작 hook" item (in SPEC "구성 요소") specifies "exits with 0 only after confirming it was deleted, and otherwise does not end" (R39), and since the verdict is already allow the R81 timer has stopped, so that job stays in the hook until GitHub's job time limit (Risks).
2. `internal/scaler/judge.go` (R9, R10, R11, R38, R52, R65, R81, R98, R102)

   - The Judge implementation checks `Table.Finalizing` itself inside `Start` and `Reject` and does nothing if it is on, because finalization can start between `Scale`'s check and the call (the `Judge` interface doc). The Judge counts goroutines and retry timers; `Stop()` cancels the verdict ctx and stops timers, and `Wait(ctx)` waits for them to end (M5-8).
   - Allow: `Table.Allow` (only when pending and idle or busy), and stop that runner's 180-second timer.
   - Deny (including `Reject` of R102 and the 180-second timer of M4-3, `removeDenied` and `denial`): if it wins `BeginExit` (keeps the token), immediately record the deny with `Deny` (only when the verdict is `pending`) and write the reason to the Info log. The log is "job denied; waiting for the runner to stop". After that the hook reads `deny` by querying and ends that job's `Runner.Worker` (M2-3), and the runner reports the job as failed and exits → stop grace (`denyStopGrace` 30 seconds): call the scaler's `ContainerWaiter.Wait` with a ctx derived from the Judge's ctx, and a 30-second timer on the injected clock (`clock.AfterFunc`) ends that ctx. If `Wait` returns (regardless of exit code) or gives 404 (already gone), it counts as stopped. Any other `Wait` error is logged (a repeated identical error once), and `Wait` is called again every 2 seconds (`denyRetryInterval`, injected clock) within the grace. Only stopped, 404, end of grace, and `Stop` end the wait → `RemoveContainer` (10 seconds) → once the deletion is confirmed (including not found), revoke the token → delete BuildKit and the network and `RemoveRunner` (M3-7's rules, `retire`). If it deletes because the grace ended, it writes "runner did not stop within grace" to the Info log; if it deletes because the runner stopped or was already gone (404), it writes the time taken since the deny was recorded (`elapsed`).
   - `Reject` is idempotent. If a redelivered message calls it again for the same runner, it loses `BeginExit` and does nothing. If `Deny` cannot record the deny because the verdict is not `pending` (R102 for a runner already allowed), the hook cannot see `deny` and that job's steps are already running, so it goes straight to `RemoveContainer` without grace (without calling `Wait`). The log is "verdict was not pending".
   - The Judge counts the grace wait as in-progress work. If `Stop` cancels the Judge's ctx, the wait ends right away. If only finalization starts without `Stop`, the wait ends when the container stops or the grace ends (finalization calls `Stop` right away in M5-8). Either way it is then `halted`, so it does not call `RemoveContainer` and goes to `denial.leave`.
   - If the deletion fails or takes more than 10 seconds, the verdict stays `deny` and the token is kept. The hook has already ended the Worker or keeps waiting, so no step runs. The side that won `BeginExit` (the verdict goroutine or the timer) deletes again every 2 seconds (`denyRetryInterval`) until the deletion is confirmed, regardless of the error kind, and writes the log and last error on each failure (a repeated identical error once). It does not rely on the watch or reconcile. When finalization or the error wait starts, this retry, the stop grace, the 180-second timer, and in-progress verdicts stop.
   - If the deny path stops because of finalization or `Stop` during the grace or a retry, it first revokes the token and abandons the row with `AbandonFinalize`, handing it to finalization (M5-8) (`denial.leave`). The verdict stays `deny`. If the hook already received the deny, it has already killed the Worker (on failure, all runner processes); if not yet, it gets 401 and keeps waiting as with pending (R66). Since the token is revoked, the precondition of `retire` holds even if reconcile takes that row without finalization.

If drain has started, do not create a new session (R88). Otherwise (`Transient`, `SessionLost`, `RateLimited`) create a new session.
   - New session (`newSession`): wait the backoff (or the last error's rate-limit wait if longer), then wait until the allowed time of session creation and `AcquireJobs` (R52). The wait ends on drain start or `listenCtx` cancellation, and in that case no new session is created. Session creation gets a 30-second timeout. If drain started during creation, the created session is closed right away. A creation failure is recorded and classified as `OpSessionCreate`. `Permanent` (including session creation 404) → `fatal`; otherwise wait again and create again.
   - `fatal(err)` (permanent errors of the session, scale set, and `AcquireJobs`, and an unexpected exit of the job check server) does not stop `Run`. Only the first time, it writes the Error log, the last error (`error drain: …`), the drain start mark, and closes `fatalCh`. If called again during error drain, it only writes a Debug log. During signal drain, it only writes a Warn log (R100).
6. Signal drain (`serve`, `Scaler.Drain` in `internal/scaler/drain.go`) (R20, R21, R89, R90, R91, R92, R100)
   - On the first signal after the first session (including during the session re-creation backoff), call `SetDraining(DrainSignal)`. If error drain has already been set (`Scale` sets it right before `Fatal`), treat it as a signal during error drain and immediately `finalize(true)`, then exit 0 (R21). Otherwise state `draining`, no new runners, `AcquireJobs` continues.
   - The ctx of `Scaler.Drain(ctx, DrainSignal, drain-timeout)` ends on the second signal. Regardless of the result (`DrainCompleted`, `DrainTimedOut`, `DrainInterrupted`), `finalize(true)` then exit 0 (no error wait). Permanent errors during that time are only logged (R100).
   - Behavior of `Drain` (common to both kinds):
     - `SetDraining(kind)` does not change a kind set earlier. The end condition is decided by the kind passed in. Signal: busy, `done`, and starting are all 0. Error: busy and `done` are 0. `exiting` rows are not counted.
     - A scale-down round (`removeIdleInBackground`, the same scale-down as `RemoveIdle`) starts once right away, then one runs every 5 seconds (`drainPollInterval`). Only one runs at a time. A round counts as in-progress work before it starts, so the following `WaitInFlight` waits for it. A round receives `Drain`'s ctx, so even if `Scale` holds the scale-down lock, `Drain` returns right away when the ctx ends.
     - The end is judged only when at least one round has ended and no round is running. So an idle runner that actually received a job is counted as busy before drain ends.
     - If it looks finished but `RemovalCandidates` is not empty (idle runners whose `RemoveRunner` failed with a transient error or rate limit), run one more round right away. Idle runners left by that round are not waited for and are handed to finalization.
     - The time limit is measured with the injected clock. `Drain` does not finalize. The caller finalizes next.
7. Error drain (R21, R51, R53, R54, R55)
   - When `fatalCh` is closed, run `Scaler.Drain(ctx, DrainError, drain-timeout)` with state `draining`. The ctx ends on the first signal. If `Run` is alive, keep the session and the job check server; if it has already returned, do not create a session again.
   - Idle runners are removed per R37 (scale-down rounds). On `JobStillRunningError`, wait as busy; on any other failure, delete only the runner container with `RemoveContainer` and abandon the row with `AbandonErrorDrain` (M3-6).
   - `DrainCompleted` or `DrainTimedOut` → `finalize(false)` → error wait (0 GitHub and Docker calls, R47). `DrainInterrupted` (a signal in between) → `finalize(true)` → exit 0.
8. Finalization `finalize(exiting)` (R21, R47, R55, R92, R99): runs only once. The same order is used for exiting and for entering the error wait. `exiting` means whether the process ends afterwards. Steps for objects the startup sequence did not create are skipped, and if it is before the pool objects were created, only `listenCtx` is cancelled. If the state is `running`, change it to `draining`. Take the start time as t0 and divide the budget into per-step shares. Even if an earlier step uses up its share, steps 5, 6, and 7 get their own shares. Each step moves on to the next without waiting once its share ends.
   1. `Scaler.BeginFinalize(t0 + 15 seconds)` (the table's finalization flag, the deadline timer, stopping pending cleanup timers and R101 timers), and an injected-clock timer that ends the ctx of deadline A (`deadlineA`) (`armDeadlineA`). Deadline A is used only for steps 1~4 and the cleanup calls the scaler makes during that time (`callContext`).
   2. Judge `Stop` (verdicts, 180-second timers, the deny's stop grace and deletion retries), watcher `Stop`, reconcile `Stop` (including the R103 goroutine)
   3. Cancel `listenCtx` and wait for `Run` to return until deadline A. An in-progress `DeleteMessage` ends at deadline A and no new `DeleteMessage` is called (M5-5). `Scale` returns `ErrFinalizing`, so the message is not acked.
   4. Wait for `Scaler.WaitInFlight`, the `Wait` of the watcher·Judge·reconcile, and a `Run` that has not yet returned, until deadline A + 10 seconds. If exceeded, write a Warn log and proceed. The docker undo (`undoTimeout` 10 seconds) is `WithoutCancel`, so it can run even after deadline A. It moves on only after that has ended too, so no Docker call remains after entering the error wait (R47).
   5. Cleanup of remaining rows (`removeLeftovers`, share 20 seconds): put 20 seconds on one step ctx. For every row left in the table (including `exiting`, abandoned, and busy rows, regardless of owner), call `RemoveResources` then `RemoveRunner` once, in parallel. If `RemoveResources` succeeds or is `Gone`, `MarkRemoved`. For a row whose runner ID is 0, `RemoveRunner` is not called. For each runner ID in `PendingUnregistrations()` that does not overlap with the IDs of remaining rows, `RemoveRunner` once (in parallel). The timeout of one call is the shorter of 10 seconds and the step's remaining time (`cleanupStage.call`). After the step ends, no call is started. The step does not wait past its own share. Log lines and `MarkRemoved` of calls that return late may appear after "finalize ended", but there are no new Docker·GitHub calls. This step does not use `Scaler.callContext`, because after deadline A has passed `callContext` returns `ok=false`. If it is before the `RemoveRunner` allowed time, it is not called, and failures are recorded in `NextAllowed`. Whatever remains is cleaned up by R16 and R17 of the next start.
   6. Close the session (share 8 seconds, errors only logged, R99)
   7. With one ctx of share 2 seconds, call the job check server's `Shutdown` and, if `exiting`, the status socket's `Shutdown`, in parallel. `gate.Server.Shutdown` closes the remaining connections when the ctx ends (M4-1). When going to the error wait, status is not stopped (R45).
   - Total: steps 1~3 15 seconds + step 4 10 seconds + step 5 20 seconds + step 6 8 seconds + step 7 2 seconds = at most 55 seconds. Signal drain takes at most `drain-timeout` from SIGTERM, so from SIGTERM to exit is at most drain-timeout + 55 seconds, leaving 35 seconds of slack under the wait cap of `service stop` (drain-timeout + 90 seconds, M6-2). If launchd stops it directly (bootout, logout, system shutdown), it sends SIGKILL 60 seconds after SIGTERM, so a drain longer than that is cut off (SPEC Areas of concern 25).
9. status states (R26, R45, R56, R58, R86): the daemon changes the state. The startup sequence is `starting`, after the first session `running`, during drain and during a finalization started from `running` `draining`, and the error wait is `error-wait`. In a pool line, `busy` is busy plus `done`, `idle` is starting plus idle, and `exiting` is not counted (deleted rows are not in the table). Consecutive start failures and the last start error are also read from the table. The last error is held by one `status.Recorder` (startup sequence, scaler, error drain).

1. `delete-scaleset [-config path] <pool>` (R23, R49)

     1. Lock (`daemon.LockFile`, the same file as R78). On `ErrLocked`, read or delete nothing, write the lock message to stdout, and give 1 (R49). Any other lock failure: log and 1.
     2. Read and validate the config. If it fails or that pool is not in the config, 1.
     3. GitHub client: `newGitHubPool` makes one `AppSigner` shared by REST and the scale set client (Subsystem `delete-scaleset`). `daemon.PoolGitHub` has no `DeleteScaleSet`, so it is wired separately.

     5. Member runners (`members`) are found the R17 way. For each name in `ListRepoRunners` that matches `^<pool>-[0-9a-f]{8}$` (`scaler.PoolRunnerName`, the same check as R17), call `GetRunnerByName`; if it has a registration and its `ScaleSetID` is that scale set, it is a member. Runners of other pools and same-form names in other scale sets are left out. If any list or lookup fails, membership is unknown, so delete nothing and give 1.
     6. Live containers (`liveContainers`): connect to Docker and read the list only when there are member runners. So with no members, it deletes even without Docker. A container of the runner kind whose state is not exited or dead is live (same as R17). If the Docker connection or list fails, delete nothing and give 1. If there is even one member runner with a live container, write those names and "남은 runner 컨테이너를 지운 뒤 다시 실행" to stdout and give 1. Since it holds the lock, the scaler is not running. Those containers were left by an earlier run and R16 of the next start deletes them.
     7. `RemoveRunner` for each member runner. 404 (`Gone`) counts as removed. Even if one fails, the rest are still removed. If any fails, do not call `DeleteScaleSet`; collect the failures and give 1.
     8. After `DeleteScaleSet`, check that `GetScaleSet` is nil. If the check lookup fails or the scale set remains, 1. On success, print "scale set 삭제됨: <pool> (ID n), runner 등록 N개 제거" and give 0.
   - Each call gets 30 seconds (`deleteCallTimeout`, wall-clock `context.WithTimeout`). All pages of `ListRepoRunners` are one call. `Transient` and `RateLimited` wait `Backoff.Wait` (from 1 second doubling, or the rate-limit hint if longer), then call up to 3 more times (`deleteCallRetries`). A `DeleteScaleSet` 404 received on a retry is taken to mean the first attempt went through, and it moves on to the check lookup. A 404 on the first attempt gives 1. When waiting for a rate limit, it writes "<시각>까지 대기 (속도 제한)" to stdout. Other errors are returned right away. It is a separate process, so it does not use `NextAllowed` (M1-4).
   - Expected refusals (lock held, several with the same name, live containers) are written to stdout and give 1 via `reportedError` without a log. Other failures give a `command failed` log and 1.
2. `internal/service` (`plist.go`, `service.go`, `stop.go`, `daemon_darwin.go`, `launchctl.go`) and `cmd/actions-runner-scaler/service.go` (R19, R20, R21, R44, R48, R84)
   - plist (`Plist(Job)`): label `io.github.dewevrei.actions-runner-scaler` (file `~/Library/LaunchAgents/<label>.plist`), `ProgramArguments` is the binary's absolute path and `run -config <absolute config path>`, `RunAtLoad` true, `KeepAlive`'s `SuccessfulExit` false, `ThrottleInterval` 60, `ExitTimeOut` 60 (constant `ExitTimeOut`). From macOS 26.4 launchd limits it to 60 seconds (the "운영" item of SPEC "외부 계약"), so the value launchd actually uses is written, not one computed from drain-timeout. So `Job` has no drain-timeout, and there is no int32 check that guarded against overflow and no code that reads `ExitTimeOut` from the installed plist. The drain-timeout range is checked only by config validation (greater than 0). `EnvironmentVariables` is HOME only. The scaler starts no external programs and reaches Docker through a fixed socket, so it needs neither PATH nor `DOCKER_*`. Logs are `stdout.log` and `stderr.log` in `~/Library/Logs/actions-runner-scaler/`. Non-absolute paths, labels containing `/`, and characters that cannot go in a plist are rejected.
   - Stop (`Manager.Stop(ctx, drainTimeout)`, `stop.go`): it reaches the running scaler only through the `Daemon` interface (`Find`, `Watch`, `Terminate`). The real implementation `SocketDaemon` (`daemon_darwin.go`) gets the state and pid with `status.QueryPeer`, sends SIGTERM with `kill(2)`, and waits for exit with kqueue `EVFILT_PROC`/`NOTE_EXIT` (it follows the process, not the pid number, so pid reuse does not fool it). Order: (1) `Find`. If not running, `false, nil`. (2) If the pid is 1 or less or is its own pid, error (`kill(0)` and `kill(-1)` go to process groups). (3) Set `Watch` before the signal so even an immediate exit is not missed. Then call `Find` again and continue only if it is the same pid (error if a different pid; if not running, wait 1 second for exit without a signal). So the watch is set on the process that owns the socket. (4) If the state is not `draining`, SIGTERM once. If `draining`, do not send (a second signal cuts signal drain short, and a signal during error drain ends it right away, R21). (5) Wait up to `StopLimit(drainTimeout)` = drain-timeout + 60 seconds (finalization at most 55 seconds) + 30 seconds, printing the elapsed time, state, and number of running runners every 10 seconds. If `error-wait` shows up while waiting and no signal has been sent yet, send one then (R48). (6) When the time limit passes, `*StillRunningError` (`errors.Is(err, ErrStillRunning)`; `Signaled` says whether this stop sent SIGTERM; the scaler continues the drain); when ctx ends, ctx's error. Right before each SIGTERM (at first and at error-wait), check with `ExitWatch.Exited()` (kevent with a 0-second timeout) whether that process has already ended, and do not send if it has (pid reuse). Only the pid given by `Find` is signaled, and `launchctl print` output is not read.
   - `install` (`Manager.Install(ctx, job, drainTimeout)`) order: (1) generate the plist and create the log folder (0700), (2) if loaded, first stop the scaler with `Stop` (skipped if no process listens on the socket; if the lookup fails, change nothing and error), then after it ends `bootout` and confirm with `launchctl print` that it is gone, (3) write the plist as 0644 (regardless of umask) with a temporary file in the same folder and rename, (4) `bootstrap gui/<uid>/ <plist>`. Things that can fail without launchctl are done before stopping, so those failures do not touch the running service. If `Stop` fails or exceeds its time limit, it does not bootout or write, and errors with "still loaded and its plist was not changed" (if SIGTERM was already sent, it adds a message that the scaler continues the drain and, after the drain, stays stopped until the next login, `kickstart`, or running the command again). If `Stop` succeeded but `bootout` is not confirmed, it errors with "the scaler is stopped, but <target> is still loaded with the old plist …". The cap of the wait to confirm `bootout` is `ExitTimeOut` + 30 seconds (90 seconds), checked every 1 second, and the same time limit is put on `bootout`. The scaler has already ended, so it usually finishes right away. If it is still there at the cap, error, and an error from `bootout` counts as an error only then. If writing or `bootstrap` fails after the stop, the remaining state (old plist remains and loads at the next login, not installed, written but not loaded) is written into the error message.
   - The output of `launchctl print` is not an API, so only its exit code is checked (`ExecLaunchctl.Print`). 0 is loaded, 113 is not loaded (confirmed in E-lifecycle), and other codes, cancellation, and execution failures are errors. Each print gets a 10-second time limit. `bootstrap` accepted the domain target `gui/<uid>/` with a trailing slash (E-lifecycle).
   - `uninstall` (`Manager.Uninstall(ctx, label, drainTimeout)`): if loaded, `Stop`, `bootout`, and confirm as in (2) of `install`, then delete the plist. If `Stop` exceeds its time limit, delete nothing. If not loaded and there is no plist, print that nothing is installed and exit with 0. If not loaded, the scaler is not touched.
   - Commands: `service install|stop|uninstall [-config <path>]`. Flags can go before or after the subcommand (`service install -config x`, `service -config x install`). `install` must read and validate the config, and waits for the stop using its drain-timeout. `stop` and `uninstall` use the drain-timeout from `-config`. Without `-config`, they use the installed plist's `-config` argument (`Manager.InstalledConfigPath`, `configPathOf`), and if that is missing too, `~/.config/actions-runner-scaler/config.toml`. If the config cannot be read (a scaler in error wait due to a config error), write a warning log and use the default of 10 minutes. The three commands take `stop.lock` next to the status socket with `daemon.LockFile` (flock, no wait) and run one at a time (prevents two SIGTERMs, R21). If it is held, "another service command is running" and 1 via `reportedError`, doing nothing. The lock is injected as `serviceHost.lock`. `stop` gives "the scaler is not running; nothing to stop" and 0 if not running; if it stops it, it prints that the LaunchAgent stays loaded and comes back at the next login or with `launchctl kickstart gui/<uid>/<label>`. Changing drain-timeout does not change the plist, so there is no need to reinstall. A temporary binary made by `go run` is rejected.

## Risks

- The session loop resets the backoff only after a session that succeeded in polling. There is no unit test that checks this condition directly.
- Because the poll is cut at 10 seconds (M5-5), poll requests to the Actions service and nil `Scale` calls increase about 5 times. Whether the service limits this frequency is unverified; if rate-limited, it waits per R25 and R52. A service that accepts connections but does not answer becomes an error only at the uncut poll after 5 minutes without an answer, so detection is about 5 minutes late (plus that poll's library timeout). A `JobStarted` that occurs during that poll can be up to about 50 seconds late. A dead HTTP/2 connection is closed within about 40 seconds by HTTP/2 ping as before, and the in-progress poll ends with a connection error (inferred, unverified). The 5-minute path handles a service that answers connections and pings but gives no poll result, and a session refresh that never ends. If a connection cannot be made, it is a transient error at 10 seconds. If an HTTP/2 poll waits more than 10 seconds for a free stream slot (`MaxConcurrentStreams` is full, or while waiting for a PING after the RST of a cancelled stream), it looks like an unwritten poll and becomes a transient error, and the session is re-created after backoff (inferred; rare because there is only one poll at a time). `pollTrace` relies on net/http calling `GetConn` and `WroteRequest`. When Go is upgraded, `TestGetMessageTraceSeesWrite` checks this again. For a failed poll, the library skips a retry wait it cannot finish within 10 seconds and returns the last error (`waitOutlasts`), so retries drop from 4 to 2~3 (waits of 1, 2, 4 seconds, each with jitter up to half of it, when the attempts themselves fail immediately), and that error ends `Run` as before. The listener's "Getting next message" Info log grows from about 1,700 lines a day to about 8,640 lines. When an in-progress poll is cut, a message the server has already handed to that request remains until `DeleteMessage` and should come again on the next poll (library doc). ## Decisions

- Code rules follow AGENTS.md.
- For builds, each runner gets one BuildKit container with a dedicated network. Methods not chosen: a shared BuildKit (cache and results mix between jobs), dind (privileged), the host Docker socket (full control of host Docker).
- The BuildKit security options are `seccomp=unconfined` and `--oci-worker-no-process-sandbox`. Method not chosen: `systempaths=unconfined` (lifts the masking of `/proc` and `/sys` of the Docker VM kernel). A custom seccomp profile is checked by a manual test, and if it works, SPEC is revised to switch to it.
- The BuildKit image digest is pinned as an index digest in one place at the top of `image/build.sh`, and `config.example.toml` has only a placeholder. Methods not chosen: a platform manifest digest (the reference may differ when pulled again, unverified), writing it only in the config. Whether the pinned value is an index digest is checked in M7-2.
- The runner version is pinned to v2.338.2. Reason: the evidence in SPEC for the hook invocation, environment, and cancellation paths is this version's source. If it changes, recheck the record of M7-4 and concern 11.
- The dedicated network's IPv4, IPv6, gateway mode, and ICC are all written in the create request. Methods not chosen: leaving it to daemon defaults (`default-network-opts` can change options not in the request), `--internal` (BuildKit cannot pull or push).
- This version accepts only 1 pool, but the config is a `[[pools]]` list from the start. Method not chosen: a single-table config (the config file breaks when pools are added).
- TOML is `BurntSushi/toml`; each table is received as a `Primitive`, and keys are sorted and decoded one by one (R28). Method not chosen: `MetaData.Undecoded` (the decoder stops at the first bad key, so only one error, different on each run, shows).
- Verdict state (token, verdict, busy time, verdict start, `JobCompleted` time) lives in one place, the scaler's runner table. `gate` holds only the policy, tokens, and HTTP. Method not chosen: gate holding its own state (the two states would have to be kept in sync).
- A deleted runner's row is deleted from the table. Method not chosen: keeping it in a `removed` state (it would have to be subtracted on every count, and rows pile up).
- The latest-run condition of R9 is done by looking for a newer main run of the same workflow (SPEC Design "판정" 8). Method not chosen: comparing the run's `head_sha` with main's current HEAD. Reason: the HEAD lookup (`GET /repos/{owner}/{repo}/branches/{branch}`, `…/commits/{ref}`, `…/git/ref/{ref}`) needs Contents read permission (confirmed: the Contents table of https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps , read for all three endpoints). The App's permissions would have to be widened and the App would reach the repository code. Looking up newer runs works with the Actions read permission it already has.
- For the input of the latest-run condition, `gate.LatestScan` counts each page and REST only passes pages along. Methods not chosen: REST doing the judgment too (the policy and fork filtering would leave `gate`), receiving all runs and handing them to `gate` (it would read the remaining pages even after finding a newer run).
- A deny is recorded as soon as `BeginExit` is won, and when the hook receives the deny it ends only that job's `Runner.Worker` with SIGKILL so the runner reports the job as failed and exits. The scaler waits up to 30 seconds for the runner container to stop, then deletes it. Methods not chosen: the hook simply exits with 1 on deny (if the Worker is alive, `always()` steps run), forcibly deleting the runner container first and then recording the deny (GitHub keeps the job in progress for the job lock of about 10 minutes and it uses a scale set slot; the next allowed job waited about 10 minutes), sending SIGINT to `Runner.Listener` and the hook exiting without a kill (if it overlaps with a user cancellation, the Worker can run `always()` steps), sending SIGINT to `Runner.Listener` and then killing only the Worker on the Worker's signal (a Listener that is shutting down does not report the result of the run-service job, so in testing the job completed only after about 10 minutes). The basis is the '거부 때 Worker 끝내기' (End the Worker on deny) item in SPEC Design.
- The message poll is cut at 10 seconds in the session wrapper, and a poll that ended only by that timeout is treated as an empty poll (M5-5, SPEC "스케일링 흐름" 2). 10 seconds is a choice between a `JobStarted` delay of about 10 seconds or less and about 6 polls per minute. Methods not chosen: waiting for a library fix (no maintainer answer on actions/scaleset issue #122), finding the job via REST by runner name (the source of verdict values would move from the message to REST, adding grounds to trust and code), a 5-second bound (less delay, but about 12 requests per minute), returning a cut poll as an error (`Run` would end and a session would be re-created every 10 seconds). Whether the server answers is checked with one uncut poll after 5 minutes without an answer, and a poll cut before the connection is established is singled out with `httptrace` and returned as an error. Method not chosen: treating every cut poll as an empty poll (a service that does not answer would turn into empty polls without errors, so R25's new session and status's last error would disappear and the backoff would keep being reset).
- The hook queries again at 2-second intervals. Method not chosen: a long poll that holds the request until the verdict (the server would need per-request state and a long WriteTimeout).
- The hook uses only the files written by the entrypoint and absolute paths, and passes `env -i`, `curl -q --noproxy '*'`, and the headers via stdin (`-H @-`). Runner processes are found and ended with `/proc` and the built-in `kill`, without external tools. Method not chosen: `pkill` (unverified whether it is in the image).
- Rate limits are waited for separately per call kind, and a wait does not exceed 24 hours (R52, R104). The two lookups of the verdict are an exception. Method not chosen: one shared time (a limit of one kind would also stop other calls).
- For errors, `Classify` only classifies and the call site decides the reaction. Method not chosen: common handling such as "drain on a permanent error" (violates R97, R98).
- The library's HTTP retries are not turned off; only rate limits are blocked and the wait is cut to 30 seconds. Method not chosen: turning them off with `Max 0` (loses the short retries of transport errors and 5xx, and the 401·403 retries of the admin connection request remain anyway).
- R17 only looks up the ID with `GetScaleSet` before the scale set is created. Reason: the SPEC "시작 순서" (startup sequence, in "구성 요소") places R17 before the scale set step, and R17 needs the ID.
- The CLI is a per-subcommand `FlagSet` of the standard `flag`. Method not chosen: cobra (only 5 commands).
- Docker is `moby/moby/client` v0.6.2 and `moby/moby/api` v1.56.1. Reason: the last version of the `github.com/docker/docker` module is `v28.5.2+incompatible` (2025-11-05), and the client that fits the local engine 29.x ships as `moby/moby/client` (confirmed: Go module proxy `go list -m -versions`). The source citations in `internal/docker` (`errors.go`, `spec.go`) are as of v0.6.2. If upgrading to v0.6.3 (2026-11-13), recheck those citations. Methods not chosen: the `docker/docker` module, the docker CLI (argument exposure, output parsing).
- The App JWT is signed directly with the standard library, and the same `AppSigner` is passed to `scaleset.NewClientWithJWTProvider` and shared with REST (SPEC Design "구성 요소" (components)). Reason: it uses the `*rsa.PrivateKey` already parsed by config validation as is, registers each JWT in `Secrets` until expiry so it is masked in logs (R31), and the signing code is in one place. Methods not chosen: `NewClientWithGitHubApp` (parses the PEM string again inside the library, JWTs made inside the library cannot be registered, and REST would have to sign separately), using `golang-jwt` directly (adds a dependency for one RS256 signature).
- The finalization budget is split into per-step shares (M5-8). Method not chosen: dividing a single 45 seconds as a remaining budget (if earlier steps used it all, remaining-row cleanup and session close would get 0 calls, violating R21, R55, R92).
- R101 is started by a per-runner 5-minute timer, and the 30-second reconcile is kept as a backup. Method not chosen: reconcile only (the 30-second reconcile period plus 20 seconds of deletion can exceed 5 minutes 30 seconds).
- GitHub REST directly calls only four endpoints: installation token, run lookup, latest-run lookup, runner list. Method not chosen: go-github (a large dependency).
- Container exit is detected per runner with `ContainerWait` and the 30-second reconcile. Method not chosen: the Docker event stream (needs separate handling of disconnects and resubscription, and reconcile is needed anyway).
- The status of Docker errors is recorded per call with the Engine client's request·response hooks. Method not chosen: reading only the errdefs kind (loses the status of 405, 413, 422 and attach failures).
- `maxCapacity` is always the pool's `max`. Method not chosen: lowering it during drain (server-side effect of 0 unverified).
- The token is kept in memory as plaintext and compared in constant time. Method not chosen: storing only a hash (the token never leaves the process and disappears on restart).
- A `Scale` that ends during finalization returns `ErrFinalizing` and does not ack the message. Method not chosen: returning nil (the listener would call `DeleteMessage`, causing a GitHub call right before the error wait, and the received job would not come again after a restart).
- The test pool's allowed-events is `["workflow_dispatch"]`. Method not chosen: including `push` too (E-deny (c) would need `schedule`, so the run time could not be chosen).
- Runner image: gosu, sudo, the docker group, and `config.sh` registration inside the container are not used (R32, JIT used). kustomize is not included (not in R69). The entrypoint does not do a recursive chown (R4).
- The Docker socket is the default path `/var/run/docker.sock` (`client.DefaultDockerHost`; whether it works with Docker Desktop is checked in M2-8). The test repository is `<test-org>/<test-repo>` (private).
- That steps of the same job can read the JIT config and runner credentials is kept as an accepted risk and not blocked in code (SPEC Areas of concern 18, decision: 2026-11-25, user). Reason: GitHub treats one job as one trust boundary, steps run only in main workflows that passed R9, and the runner is deleted after one job. Method not chosen: a job container (does not mount the runner root, but the runner has no Docker daemon).
