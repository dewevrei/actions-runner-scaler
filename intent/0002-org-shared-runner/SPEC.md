## Requirements

설정과 target (R105~R107)
- R105. 설정에 `[[targets]]`가 하나도 없으면 R28과 같이 오류 대기에 들어가고, target이 1개 이상 필요하다는 것과 받은 개수(0)를 마지막 오류와 로그에 남긴다. target 수의 상한은 없다(R68을 대체).
- R106. (dropped) target은 저장소이므로 저장소 URL 꼴 R231과 조직 URL의 설정 오류 R232가 대체한다.
- R107. 설정 파일에 `[[pools]]`나 `github.app-installation-id`가 있으면 R28과 같이 오류 대기에 들어가고, 그 키마다 0001 형식의 키라는 것과 대신 쓸 키를 적은 오류를 보인다(Design 설정 파일의 문구).

- R109. (dropped) R237이 대체한다.

- R113. (dropped) 저장소 수준 등록 R240이 대체한다.

동시 실행 한도 (R114~R117)
- R114. 모든 target의 runner 컨테이너 수 합(끝난 runner 포함)은 서버 한도(R201)를 넘지 않는다(R3에 더한다. R3은 target마다 그 target의 `max-runners`로 성립한다).
- R115. target의 목표 runner 수는 `min(그 target의 max-runners, 그 target의 idle + 그 target의 TotalAssignedJobs)`다. TotalAssignedJobs는 그 target이 상태 `running`이 된 뒤 받은 `Statistics`가 있는 마지막 메시지의 값이고(그 전에는 0), 메시지가 없는 poll과 `Statistics`가 없는 메시지는 그 값을 바꾸지 않는다. runner는 자리 배치의 시작 문(R187)으로만 시작한다(R1과 R2를 대체).
- R116. 스케일러는 target마다 그 target의 세션에서 poll마다 `maxCapacity`로 그 target의 `max-runners`를 보낸다. drain 중에도 같다(R90을 대체).
- R117. 그 job의 target의 runner 수가 그 target의 `max-runners`보다 적고 모든 target의 runner 수 합이 서버 한도보다 적고 시작 문(R187)에 그보다 먼저 낸 다른 job 요청이 없고 두 이미지가 로컬에 있을 때, 스케일러가 job의 첫 메시지(`JobAvailable` 또는 `JobAssigned`)를 받은 시각부터 GitHub job 기록의 `started_at`까지 60초를 넘지 않는다. R87의 경우는 뺀다(R4를 대체).

자원 제한과 Docker 용량 (R118~R122, R201~R204)
- R118. (dropped) runner 하나의 CPU 몫(`runner.cpus + buildkit.cpus`)은 두 키 각각보다 크므로 한 키가 `NCPU`보다 크면 서버 한도(R201)가 0이 되어 R202가 같은 경우를 오류 대기로 드러낸다. 키와 값은 R202의 오류로, `/info` 호출의 R24·R46 규칙은 R201로 옮겼다.
- R119. (dropped) 서버 한도(R201)가 모든 runner의 메모리 예약 합을 `MemTotal` 안에 두므로, 그 합이 `MemTotal`을 넘는 경우가 없어 경고할 일이 없다.
- R120. (dropped) 서버 한도(R201)가 모든 runner의 CPU 예약 합을 `NCPU` 안에 두므로, 그 합이 `NCPU`를 넘는 경우가 없어 경고할 일이 없다.
- R201. 스케일러는 시작할 때 서버 한도를 정하고, 실행하는 동안 다시 정하지 않는다. `scaling.server-limit`이 양수면 서버 한도는 그 값이고, 0(기본값)이면 Docker Engine API `/info` 응답 하나(`NCPU`, `MemTotal`)로 `min(floor(NCPU / (runner.cpus + buildkit.cpus)), floor(MemTotal / (runner.memory + buildkit.memory)))`를 계산한다(CPU는 정수 NanoCPUs, 메모리는 바이트로 나눈다). 계산할 때의 `/info` 호출은 시작 단계 호출로 R24와 R46을 따르고(두 목록에 더한다), 영구 오류는 R47대로 다시 시도한다. `scaling.server-limit`이 양수일 때도 `/info`를 한 번 읽지만 R203의 로그 줄에만 쓰고, 그 호출이 실패해도 경고 로그만 남기고 시작을 계속한다. Docker의 CPU나 메모리, `scaling.server-limit`을 바꾼 값은 스케일러를 다시 시작한 뒤에 쓰인다.
- R202. R201에서 계산한 서버 한도가 0이면(`runner.cpus`나 `buildkit.cpus` 하나가 `NCPU`보다 큰 경우 포함) 스케일러는 오류 대기에 들어가 R47대로 다시 확인하고, `NCPU`, `MemTotal`, runner 하나의 몫(`runner.cpus + buildkit.cpus`와 `runner.memory + buildkit.memory`), 그 몫을 이루는 네 키의 이름과 값을 마지막 오류에 보인다(문구는 Design Docker 용량 확인).
- R203. R201 뒤 스케일러는 시작 로그에 INFO `server runner limit` 한 줄을 서버 한도(`limit`), 계산한 값(`computed`, `/info`를 읽지 못했으면 0), 설정값(`configured`), `NCPU`, `MemTotal`, runner 하나의 CPU 몫과 메모리 몫과 함께 남긴다.
- R204. 모든 target의 `max-runners` 합이 서버 한도보다 크면 스케일러는 시작 로그에 INFO `max-runners of all targets exceed the server limit` 한 줄을 그 합, 서버 한도와 함께 남기고 계속 실행한다.
- R121. runner 컨테이너의 CPU, 메모리, 프로세스 수 제한은 `runner.cpus`, `runner.memory`, `runner.pids`와 같고, 메모리 스왑은 없다(R34를 대체). 하한은 Docker의 하한인 메모리 6m과 프로세스 수 1이다(설정 표).
- R122. BuildKit 컨테이너의 CPU, 메모리, 프로세스 수 제한은 `buildkit.cpus`, `buildkit.memory`, `buildkit.pids`와 같고, 메모리 스왑은 없다(R74를 대체). 하한은 R121과 같다.

판정: fork pull request 거부 (R123~R133)
- R123. 스케일러는 job 시작 hook이 보낸 이벤트 보고(이벤트 이름과 이벤트 파일 내용)만으로 판정을 내리고, 판정하려고 `JobStarted`를 기다리거나 GitHub에 요청을 보내지 않는다(R9를 대체하고 R65를 없앤다).
- R124. 끝까지 읽은 이벤트 보고의 본문이 JSON 객체 정확히 하나가 아니면(빈 본문, JSON이 아닌 본문, 배열 같은 객체 아닌 값, 객체 뒤에 공백 말고 다른 값이 더 있는 본문) 거부한다. 수는 정밀도를 잃지 않게 원래 표기대로 읽는다.
- R125. 이벤트 이름이 `^[a-z_]{1,64}$`에 맞지 않으면(빈 이름 포함) 거부한다.
- R126. 본문의 최상위 `pull_request`가 있고 null이 아니면, `pull_request.head.repo.id`, `pull_request.base.repo.id`, 최상위 `repository.id`가 모두 양의 정수(소수점과 지수가 없는 1 이상 2^63−1 이하의 수)이고 셋이 같을 때만 이 규칙을 통과한다. 그 밖에는(값이 없거나 null이거나 정수가 아니거나 서로 다르면) 거부한다. 이벤트 이름과 관계없이 적용한다.
- R127. 본문의 최상위 `workflow_run`이 있고 null이 아니면, `workflow_run.head_repository.id`, `workflow_run.repository.id`, 최상위 `repository.id`가 모두 R126의 양의 정수이고 셋이 같을 때만 이 규칙을 통과한다. 그 밖에는 거부한다. 이벤트 이름과 관계없이 적용한다.
- R128. 이벤트 이름이 `pull_request`, `pull_request_target`, `pull_request_review`, `pull_request_review_comment` 중 하나인데 최상위 `pull_request`가 없거나 null이면 거부하고, 이벤트 이름이 `workflow_run`인데 최상위 `workflow_run`이 없거나 null이면 거부한다.
- R129. R124~R128 중 어느 것으로도 거부되지 않은 보고는 허용한다. 판정은 `head.repo.fork`, 저장소의 `full_name`, `author_association`, 브랜치, ref, workflow 경로를 쓰지 않는다.
- R130. 거부할 때 스케일러는 0001의 로그 줄 `job denied; waiting for the runner to stop`에 runner 이름, 이벤트 이름, `reason`(Design 판정의 거부 사유 값)을 남기고, 본문에 `pull_request.head.repo.full_name`이나 `workflow_run.head_repository.full_name`이 문자열로 있으면 그 값을 `head_repo`로 더한다.
- R131. 토큰이 맞는 그 runner의 첫 이벤트 보고를 받으면, 스케일러는 본문을 다 읽은 때부터 1초 안에 판정을 기록하고 응답에 담는다. 예외로 drain 끝의 정리가 시작된 뒤 받은 보고는 판정하지 않고 `pending`을 돌려준다.
- R132. 판정이 기록된 runner의 뒤 이벤트 보고는 본문을 읽지 않고 기록된 판정을 돌려주며, 판정을 바꾸지 않는다.
- R133. 세션을 쓸 수 없는 동안(R25의 백오프, R54, R92)에도 스케일러는 이벤트 보고를 받으면 판정한다(R54와 R92의 "`JobStarted`를 받지 못해 R81로 지워진다"를 대체).

job 확인 서버와 hook (R134~R140)
- R134. job 확인 서버는 `POST /v1/event`의 본문을 읽기 전에 토큰을 검증하고, 실패하면 본문을 읽지 않고 바로 401을 돌려주며 판정과 그 runner의 busy 시각(R81)을 기록하지 않는다(R40을 `POST /v1/event`로 넓힌다).
- R135. `/v1/event`에 `POST`가 아닌 요청이 오면 job 확인 서버는 `Allow: POST` 헤더와 함께 405를 돌려주고, 판정과 busy 시각을 기록하지 않는다.
- R136. 토큰이 맞는 첫 이벤트 보고의 본문이 32MiB(33,554,432바이트)를 넘으면, job 확인 서버는 32MiB + 1바이트에서 읽기를 멈추고 거부(`reason` `payload-too-large`)를 기록한 뒤 413과 `{"verdict":"deny"}`를 돌려준다.
- R137. 32MiB 안에서 본문 읽기가 오류로 끝나면(연결이 닫힘, `Content-Length`보다 적게 옴, 읽기 시한), job 확인 서버는 판정하지 않고 아무것도 기록하지 않은 채 그 연결을 닫는다. 그 runner의 다음 보고는 R131의 첫 보고로 처리한다.
- R138. 토큰이 맞는 첫 `POST /v1/event`를 받은 때도 R81의 busy가 된 때의 후보다(R81의 busy 계기에 더한다).
- R139. job 시작 hook은 판정을 조회하기 전에, 자기 시작 때 환경의 `GITHUB_EVENT_NAME` 값과 `GITHUB_EVENT_PATH`가 가리키는 파일 내용을 `POST /v1/event`로 보낸다. 파일이 없거나 읽을 수 없으면 빈 본문을 보내고, `GITHUB_EVENT_NAME` 값이 `^[a-z_]{1,64}$`에 맞지 않으면 빈 이벤트 이름을 보낸다(R66의 "판정을 조회만 하고"를 대체).
- R140. hook은 `POST /v1/event`의 응답이 200이고 `verdict`가 `allow`나 `deny`면 R66대로 처리하고, 200의 `pending`, 200과 401 밖의 상태 코드(400, 405, 413, 5xx 등), 해석할 수 없는 응답이면 다시 보내지 않고 R66대로 `GET /v1/verdict`를 2초마다 조회하며, 연결 실패나 401이면 2초 쉬고 `POST /v1/event`를 다시 보낸다. 어느 경우에도 허용을 받지 않으면 0으로 끝나지 않는다.

실제 실행 확인: 판정 (R141~R147)
- R141. 조직 저장소의 main이 아닌 브랜치에서 시작한 job은 허용되어 모든 step이 돈다.
- R142. R141의 job에서 관리자 안내문의 Role을 OIDC로 받는 step은 실패한다(관리자 신뢰 정책의 결과를 실제 실행으로 확인한다).
- R143. 같은 저장소 main의 job은 스케일러가 등록한 runner에서 GitHub OIDC로 관리자 안내문의 Role을 받아 안내문의 Namespace에서 Pod 목록 조회에 성공한다(0001 R8과 같은 확인. R142의 실패가 OIDC 경로의 고장이 아니라 신뢰 정책의 거부임을 가른다).
- R144. 같은 저장소의 브랜치에서 연 pull request의 `pull_request` 이벤트로 시작된 job은 허용되어 모든 step이 돈다.
- R145. fork에서 연 pull request의 `pull_request` 이벤트로 시작된 job은 "Set up job" 뒤 step이 `if: always()` step을 포함해 하나도 돌지 않고 실패로 끝나며, 판정부터 40초 안에 runner 컨테이너가 없어진다(나중 시험, Design 테스트).
- R146. fork에서 연 pull request의 `pull_request_target` 이벤트로 시작된 job은 R145와 같이 끝난다(나중 시험, Design 테스트).
- R147. fork에서 연 pull request의 run이 끝나 일으킨 `workflow_run` 이벤트의 job은 R145와 같이 끝난다(나중 시험, Design 테스트).

- R149. (dropped) 저장소 runner 목록의 이름 조회를 쓰는 R242가 대체한다.

서비스 응답 확인과 로그 (R153~R154, R221. R221은 dropped)
- R153. 스케일러는 `GetMessage` 호출 하나 전체에 라이브러리의 poll 시한 `scaleset.MessagePollTimeout`(2분)을 두고, 그 시한으로 끝나면 그 poll을 일시 오류로 보고 그 target의 마지막 오류에 남긴 뒤 R25대로 새 세션을 만든다.
- R154. `GetMessage`가 속도 제한 오류로 끝날 때마다 스케일러는 WARN 로그 `message poll rate limited` 한 줄을 상태 코드와 다시 부를 수 있는 시각과 함께 남긴다.
- R221. (dropped) 대기 job 목록이 없어져 비교할 수가 없다. 목표는 `TotalAssignedJobs`를 그대로 쓴다(R115).

실제 실행 확인 (R156~R165. R156~R158, R165는 dropped)
- R156. (dropped) 저장소는 runner group이 아니라 설정의 `[[targets]]`로 더하므로, 설정을 고치고 다시 시작하는 R255가 대체한다.
- R157. (dropped) 저장소마다 `max-runners`를 둔 R253이 대체한다.
- R158. (dropped) R254가 대체한다.
- R159. `service stop` 뒤 `launchctl print gui/<uid>/<label>`은 0으로 끝나고(LaunchAgent가 로드된 채), `service start` 뒤 60초 안에 `status`가 `state: running`을 출력하며, 그 뒤 시작한 job이 성공한다.
- R160. job이 도는 중 실행한 `service install`은 그 job이 성공으로 끝난 뒤 0으로 끝나고, 명령이 끝난 때부터 60초 안에 LaunchAgent가 로드돼 있고 `status`가 `state: running`을 출력한다.
- R161. job이 도는 중 실행한 `service uninstall`이 0으로 끝난 뒤 `managed-by` 라벨이 붙은 컨테이너는 0개이고, `launchctl print gui/<uid>/<label>`은 113으로 끝난다.

저장소 target (R231~R235)
- R231. `targets.url`이 `https://github.com/<owner>/<repo>` 꼴이 아니면 R28과 같이 오류 대기에 들어간다. owner는 `[A-Za-z0-9-]+`, repo는 `[A-Za-z0-9._-]+`이면서 `.`과 `..`이 아니고 `.git`으로 끝나지 않으며, owner가 대소문자 구분 없이 `enterprises`인 URL(라이브러리가 enterprise 범위로 읽는 꼴), 끝 `/`, query, fragment, 셋째 경로 조각은 받지 않는다(R106을 대체).
- R232. `targets.url`이 경로 조각 하나인 `https://github.com/<owner>` 꼴(owner는 R231의 꼴)이면 R28과 같이 오류 대기에 들어가고, 그 값이 조직이나 계정의 URL이라는 것과 저장소마다 `[[targets]]` 하나에 저장소 URL을 적으라는 것을 오류에 보인다(문구는 Design 설정 파일).
- R233. owner와 repo를 각각 대소문자 구분 없이 비교해 같은 저장소를 가리키는 target이 둘 이상이면 R28과 같이 오류 대기에 들어가고, 겹친 `targets.url` 값들을 오류에 보인다(R166을 대체).
- R234. target에 `runner-group` 키가 있으면(빈 값 포함) R28과 같이 오류 대기에 들어가고, 저장소 scale set은 기본 runner group을 쓴다는 것과 그 키를 지우라는 것을 오류에 보인다(R111을 대체).
- R235. target에 `max-runners`가 없으면 그 target의 `max-runners`는 1이다.

저장소 등록 (R236~R242)
- R236. 스케일러는 시작할 때 App으로 인증하는 target마다 그 target의 App(자기 App, 없으면 기본 App. 0003 R273)의 JWT로 `GET /repos/{owner}/{repo}/installation`을 불러 설치 ID를 얻고, 그 target의 scale set 클라이언트와 REST 클라이언트는 그 설치 ID를 쓴다. 이 호출은 target의 시작 단계 호출로, 일시 오류는 R24로 다시 시도하고(R24의 시작 단계 호출 목록에 더한다) 영구 오류는 R172를 따른다(R108을 대체).
- R237. R236의 응답이 404면 그 target은 target 오류 대기(R172)에 들어가고, 그 target의 마지막 오류에 `GitHub App is not installed on repository <owner>/<repo>`를 보인다(R109를 대체).
- R238. R236 응답의 `permissions.administration`이 `write`가 아니면 그 target은 target 오류 대기(R172)에 들어가고, 빠진 권한 이름(`administration: write`)과 저장소 이름(`<owner>/<repo>`)을 그 target의 마지막 오류에 보인다(R110을 대체).
- R239. 스케일러는 target마다 그 저장소 URL을 scale set 클라이언트의 등록 URL로 쓰고, runner group ID 1에 이름이 `scaling.label`인 scale set이 없으면 만들고 있으면 다시 쓴다. 스케일러가 종료해도, 설정에서 그 target을 빼고 다시 시작해도 스케일러는 그 scale set을 지우지 않는다(R112를 대체).
- R240. 스케일러가 만든 runner는 저장소 수준에 등록되어, 실행 중에 그 target 저장소의 runner 목록(`GET /repos/{owner}/{repo}/actions/runners`)에 그 이름으로 나타나고, 설정의 다른 target 저장소의 runner 목록에는 나타나지 않는다(R113을 대체).
- R241. 스케일러는 시작할 때 target마다 그 저장소의 runner 목록(`GET /repos/{owner}/{repo}/actions/runners`, 모든 페이지)에서, 이름이 `<scaling.label>-` 뒤에 소문자 16진수 정확히 8자가 붙은 꼴이고 `GetRunnerByName`의 `RunnerScaleSetID`가 그 target의 scale set ID와 같으며 살아 있는 runner 컨테이너가 없는 등록을 제거한다. 일시 오류와 영구 오류의 처리는 0001 R17과 같다(R148을 대체).
- R242. R42의 대조는 끝난 runner는 빼고, 허용 판정이 없는 runner마다 그 runner의 target 저장소 runner 목록을 그 이름으로 조회해(`GET /repos/{owner}/{repo}/actions/runners?name=<runner 이름>`) 결과 중 이름이 정확히 같은 runner의 `busy`가 true면 그 runner를 busy로 표시한다. 조회가 실패하면 로그를 남기고 그 대조에서 그 runner를 건너뛴다(R149를 대체).

scale set 삭제 (R243~R246, R268~R269. R243~R245는 dropped)
- R243. (dropped) 설정에 없는 저장소도 받던 삭제는 설정의 target만 받는 R268이 대체한다.
- R244. (dropped) 첫 판의 조직 수준 scale set은 이미 지웠으므로 조직 URL의 삭제는 두지 않는다(Areas of concern 16).
- R245. (dropped) 조직 URL을 오류로 보는 R269가 대체한다.
- R246. 지울 이름의 scale set이 없으면 `delete-scaleset`은 아무것도 지우지 않고 scale set이 없다는 줄을 stdout에 쓴 뒤 0으로 끝난다.
- R268. `delete-scaleset [-config <경로>] <저장소 URL>`은 설정을 0001처럼 읽고 검증한 뒤, 인자의 URL과 owner와 repo가 대소문자 구분 없이 같은(R233의 비교) 설정의 `[[targets]]`를 찾아, R236의 설치 조회와 R238의 권한 확인 뒤 그 저장소의 runner group ID 1에서 이름이 `scaling.label`인 scale set과 그 runner 등록을 지우고 0으로 끝난다.

저장소마다의 최대와 서버 자리 (R247)
- R247. 자리 배치에서 runner 수(R3의 수)가 자기 `max-runners` 이상인 target은 시작 문에서 자리를 받지 않고, 같은 자리 배치에서 다른 target의 시작 요청이 서버 자리를 받는 것을 막지 않는다.

실제 실행 확인: 저장소 target (R248~R259)
- R248. 같은 조직이 소유한 서로 다른 저장소 target A와 B로 스케일러를 시작하면 `status`의 두 target 줄이 모두 `running`이 되고, 각 저장소에서 시작한 시험 job(`sleep 30` step 하나)은 그 저장소의 runner 목록에만 이름이 나타난 runner에서 돌아 성공한다(R236, R238, R239, R240의 실제 확인).
- R249. A에 `idle = 1`을 두고 시작해 A의 runner 목록에 대기 runner 이름이 나타난 뒤 스케일러 프로세스를 `kill -9`로 끝내고 다시 시작하면, 시작 로그의 오래된 등록 정리 줄이 1개 이상을 지웠다고 보이고, 그 이름이 A의 runner 목록에서 없어지며, B의 runner 목록은 바뀌지 않는다(R241의 실제 확인).
- R250. 개인 계정이 소유한 저장소 P를 A와 함께 target으로 두고 시작하면 P의 줄이 `running`이 되고, P에서 시작한 시험 job이 성공한다(Areas of concern 7).
- R251. 서버 한도가 3이고(이 Mac의 기본 자원 설정, R203의 로그로 확인) A의 `max-runners`가 1, B의 `max-runners`가 2일 때, A에서 시험 job(`sleep 120` step 하나) 3개와 B에서 같은 job 2개를 10초 안에 시작하면, 1초마다 센 A의 runner 컨테이너 수는 1을 넘지 않고 모든 runner 컨테이너 수는 3을 넘지 않으며, A의 job이 기다리는 동안 A의 runner 하나와 B의 runner 둘이 같은 때 돌고, 5개 job이 모두 성공한다(R3, R114, R116의 실제 확인. GitHub가 A의 넘는 job을 보내지 않으므로 R247의 경로는 여기서 돌지 않고 단위 테스트로만 확인한다).
- R252. 서버 한도가 3이고 A의 `max-runners`가 3, B의 `max-runners`가 2일 때(합 5가 서버 한도보다 커 R204의 INFO 줄이 나온다), A의 시험 job(`sleep 180` step 하나) 2개와 B의 같은 job 1개가 runner에서 돌기 시작한 뒤 B의 시험 job(`sleep 60` step 하나) 1개를 시작하고, `status`의 B 줄 `waiting jobs`(R222)가 1이 된 뒤 A의 같은 `sleep 60` job 1개를 시작하면, 1초마다 센 모든 runner 컨테이너 수는 3을 넘지 않고, 앞의 세 job 중 처음으로 컨테이너가 없어진 때부터 60초 안에 B의 `sleep 60` job이 runner를 받으며, A의 `sleep 60` job은 B의 그 job보다 먼저 runner를 받지 않고, 다섯 job이 모두 성공한다. 두 `sleep 60` job의 `JobAvailable`, `JobAssigned`(`JobID`와 `RunnerRequestID`), 배정 취소(`RunnerName`이 비고 `FinishTime`이 0인 `JobCompleted`)의 수와 시각이 기록된다(R187, R204의 실제 확인).
- R253. runner 하나의 몫을 줄인 시험 설정(서버 한도 6, Design 테스트)에서 A의 `max-runners`가 3, B의 `max-runners`가 2일 때, A에서 3개, B에서 2개의 시험 job(`sleep 120` step 하나와 push 없는 `docker buildx build` step 하나, Design 테스트)을 10초 안에 시작하면 runner 컨테이너 5개가 같은 때 돌고 5개 job이 모두 성공한다(R157을 대체).
- R254. R253의 5개 job이 도는 동안 A에서 시작한 여섯째 job은 기다리고, A의 runner 컨테이너 하나가 없어진 때부터 60초 안에 시작한다(R158을 대체).
- R255. 스케일러가 A와 B로 도는 중 설정에 저장소 C의 `[[targets]]`를 더하고 스케일러를 다시 시작하면(서비스로 돌면 `service restart`, 터미널에서 돌면 SIGTERM으로 멈춘 뒤 다시 실행), 다시 시작한 때부터 60초 안에 `status`의 C 줄이 `running`이 되고, C에서 `runs-on: linux-arm64-deploy`만으로 시작한 job이 성공한다(R156을 대체).
- R256. 설정의 `targets.url` 하나를 조직 URL로 두고 시작하면 스케일러는 오류 대기에 들어가 `status`의 마지막 오류에 R232의 문구를 보이고, 어느 target도 세션을 만들지 않는다(R232의 실제 확인).
- R257. App이 설치되지 않은 저장소 D와 A를 target으로 두고 시작하면 `status`의 D 줄은 `error-wait`와 R237의 오류를, A 줄은 `running`을 보이고, 그 뒤 A에서 시작한 job은 성공한다. D에 대한 R236의 응답 코드가 기록된다(R182를 대체).
- R258. (dropped) 설정에 있는 target만 지우는 R270이 대체한다.
- R270. 스케일러를 멈추고 B가 설정에 있는 채로 실행한 `delete-scaleset <B의 URL>`은 B의 scale set과 runner 등록을 지우고 0으로 끝나고, 같은 명령을 다시 실행하면 R246의 줄을 쓰고 0으로 끝난다. 그 뒤 B를 설정에서 빼고 실행한 `delete-scaleset <B의 URL>`과 `delete-scaleset <조직 URL>`은 아무것도 지우지 않고 R269의 오류와 1로 끝난다. 저장소 C를 지우지 않고 설정에서 뺀 뒤 스케일러를 다시 시작해도 C의 scale set은 남아 있어, C를 설정에 다시 넣고 실행한 `delete-scaleset <C의 URL>`이 그 scale set을 지운다(R239, R268, R269, R246의 실제 확인).
- R259. 이 변경의 실제 실행 시험(R141~R144, R159~R164, R248~R257, R270)이 모두 끝나면 그 기간(2026-11-26의 첫 판 실행 포함)의 스케일러 로그에서 R154 로그 줄의 수를 센 값이 기록된다. 따로 연속 실행 시험은 하지 않는다(R165를 대체).

나중 실제 시험 (R260~R263, 이 변경의 완료 조건이 아니다)
- R260. 호스트를 재시작하면 로그인한 때부터 5분 안에 `status`가 `state: running`을 출력하고, 그 뒤 시작한 job이 성공한다(0001 R19의 다시 확인. 팀 저장소의 배포 workflow가 이 runner로 옮겨진 뒤에 한다, Design 테스트).
- R261. B의 job이 도는 중 A를 App 설치에서 빼면(A와 B가 같은 설치를 쓰면 그 설치의 저장소 선택에서 A만 빼고, 다른 설치면 A의 설치를 지운다), 그 B의 job은 성공으로 끝나고, 뺀 때부터 70분 안에 `status`의 A 줄이 `error-wait`가 되며 그 시간이 기록되고, 그 뒤 B에서 시작한 job도 성공한다. 70분 안에 A 줄이 `error-wait`가 되지 않으면 그 사실과 그동안의 A 줄을 기록한다(Areas of concern 12)(R183을 대체).
- R262. A 줄이 `error-wait`인 동안 A를 App 설치에 다시 넣으면, 스케일러를 재시작하지 않고, 다시 넣은 뒤 처음 오는 R174의 시도 시각(`status`의 `next retry`)부터 60초 안에 A 줄이 `running`이 되고, 그 뒤 A에서 시작한 job이 성공한다(R199를 대체).
- R263. target이 A 하나이고 A의 `max-runners`가 4, 서버 한도가 3일 때(기본 자원 설정) A의 시험 job(`sleep 1800` step 하나) 3개가 runner에서 돌기 시작한 뒤, 그 셋과 다른 run으로 넷째 시험 job(`sleep 60` step 하나) 1개를 시작한다. 넷째 job은 A의 scale set에 배정된 채 기다린다. 앞의 세 job은 `sleep 1800`이 끝나거나, 스케일러 로그에 넷째 job의 다시 배정(앞과 다른 `JobID`의 `JobAssigned`)이 4번째로 나온 때 그 run을 취소해 끝낸다. 통과 조건은 넷째 job이 결국 runner를 받아 성공하는 것이다. 넷째 job의 최종 결과, 시작 시각, `JobAvailable`, `JobAssigned`(`JobID`마다), 배정 취소(`RunnerName`이 비고 `FinishTime`이 0인 `JobCompleted`)의 수와 시각, 스케일러가 `AcquireJobs`를 부른 시각이 기록된다. 넷째 job이 실패하거나 취소되면 SPEC을 runpool처럼 알리는 `maxCapacity`를 남은 자리에 맞춰 낮추는 방식으로 바꾼다(Areas of concern 12)(R230을 대체).

첫 판의 조직 수준 scale set 삭제와 delete-scaleset의 설정 읽기 (R264, R267, 모두 dropped)
- R264. (dropped) 첫 판의 조직 수준 scale set은 이 판의 실제 시험 전에 지웠다(Areas of concern 16).
- R267. (dropped) 첫 판 형식의 설정을 읽을 일이 없어져 `delete-scaleset`은 설정을 0001처럼 읽고 검증한다(R268, R269).

## Design

용어: target은 runner를 등록하는 GitHub 저장소 하나이고, 그 owner는 조직이나 개인 계정이다. 설정에 저장소 target을 하나 이상 두고(R105, R231), target마다 scale set 하나와 자기 `max-runners`를 둔다(R239, R116). 이 SPEC의 첫 판은 조직을 target으로 등록했다. 그 판의 조직 전용 요구사항은 `(dropped)`로 남기고 R231 이후의 저장소 요구사항이 대체하며, 2026-11-26에 첫 판으로 통과한 실제 시험 중 등록 수준과 관계없는 것(R141~R144, R159~R164)은 다시 하지 않는다(설계: 테스트). 0001 SPEC 요구사항의 "pool"은 이 변경에서 target 하나와 그 scale set으로 읽는다. pool마다의 설정값 중 `max`는 `targets.max-runners`(R115, R116), `idle`은 `targets.idle`, 자원 제한은 `[runner]`와 `[buildkit]`의 키(R121, R122), pool 이름은 `scaling.label`이다. 서버 한도는 모든 target의 runner 수 합의 상한으로, `scaling.server-limit`이 양수면 그 값이고 0(기본값)이면 시작 때 Docker가 보고한 CPU·메모리와 runner 하나의 자원 제한으로 계산한 runner 수다(R114, R201). target 오류 drain과 target 오류 대기는 0001의 오류 drain과 오류 대기를 target 하나에 적용한 것이고(R171~R174), 그냥 "오류 대기"는 0001처럼 스케일러 전체의 오류 대기다. busy runner는 0001 R81의 busy가 된 runner이고, 대기 runner는 0001처럼 busy가 아닌 runner다. 존재하는 runner는 0001처럼 끝난 runner를 뺀 runner다. 시작 요청은 target이 목표(R115)에 모자라는 runner 하나마다 서버의 시작 문에 내는 요청이고, 배정 job 몫이면 job 요청, `idle` 몫이면 idle 요청이다(R187). 자리 배치는 상태 `running`인 모든 target을 목표에 맞추는 서버 전체의 한 번의 계산이고, 시작 문은 그 안에서 서버 한도 아래의 빈 자리를 시작 요청에 나눠 준다(R187). 그 밖의 0001 요구사항(격리, drain, 재시도, 오류 대기, hook의 kill 규칙, 서비스)은 그대로 성립한다.

**바꾸거나 없애는 0001 요구사항**
- 대체: R1·R2의 목표 계산과 시작(R115, R187), R4(R117), R89(R220), R9(R123~R129), R17(R241), R22(R239), R23(R268, R269), R34(R121), R54와 R92의 한 문장(R133), R66의 한 구절(R139, R140), R68(R105), R74(R122), R90(R116), R103(R242).
- 좁힘: R51의 오류 drain은 오류가 난 target에만 걸린다(R171, R173). R46의 오류 대기는 target의 시작 단계 호출(설치 조회, scale set get-or-create, `SetSystemInfo`, 첫 세션 생성)에서는 그 target에만 걸리고(R172), 설정 오류, Docker 확인, job 확인 서버 listen에서는 스케일러 전체에 걸린다(R176). R47의 "설정 오류와 GitHub 쪽 영구 오류는 재시작해야 벗어난다"는 target 오류 대기에서는 R174의 다시 시도로 대체하고, 스케일러 전체의 오류 대기는 R47대로 Docker 쪽 원인이면 다시 시도하고 설정 오류면 재시작을 기다린다(R174, R175, R176). R24는 처음 시작할 때의 target 시작 단계에만 쓰고, R174의 다시 시도 안에서는 쓰지 않는다(R193). R26의 첫 줄과 종료 코드는 상태 `running`인 target도 `starting`인 target도 없을 때 R197로 바뀐다. R7(배정된 job이 없으면 runner 수가 `idle`과 같음)은 상태 `running`인 target에서만 성립하고, idle 요청이 서버 자리를 기다리는 target(R187), 다른 target의 배정 job을 위해 idle runner를 지운 target(R187의 선점), target 오류 drain과 target 오류 대기의 target(목표 0, R173, R174)에서는 성립하지 않는다. R52의 대기는 Actions 서비스 호출은 target마다, REST 호출은 설치마다 따로 둔다(R265, R266, R189). R55의 감시와 재시도 멈춤은 그 target의 runner에만 걸린다(R190). R100은 target의 영구 오류에도 적용한다(R191). R21의 "오류 drain 중 신호" 구절은 target 오류 drain에 적용하지 않는다(R179). R20, R57, R58의 "첫 세션"은 어느 target이든 처음 만든 세션이다(R178).
- 넓힘: R3은 target마다 그 target의 `max-runners`로 성립하고, 그 위에 모든 target의 합에 대한 서버 한도(R114)를 더한다. R24의 시작 단계 호출 목록에 설치 조회(R236)와 Docker `/info`(R201)를 더하고, R46의 목록에는 `/info`만 더한다(설치 조회의 영구 오류는 R172). R26과 R56의 pool 줄에 target 상태와 target의 마지막 오류를 더하고(R180), R58의 출력에 target 줄을 더한다(R198). R40의 401 규칙을 `POST /v1/event`에도 적용하고 본문을 읽기 전에 검증한다(R134). R81의 busy 계기에 토큰이 맞는 첫 `POST /v1/event`(R138)를 더하고, R81 계기의 "R103의 발견"은 R242의 발견으로 읽는다.
- 그대로: R82는 성립한다. hook은 판정 조회에 여전히 스케일러가 준 주소와 runner 이름만 쓴다. 새로 읽는 `GITHUB_EVENT_NAME`과 `GITHUB_EVENT_PATH`는 runner가 hook 환경에 넣는 값이고, hook 전에 job 코드가 돌지 않으며 workflow `env:`는 hook 환경에 들어가지 않으므로 job 코드가 hook 전에 바꿀 수 없다(설계: 판정의 "이벤트 파일을 믿는 근거").
- 없앰: R29(메모리 합 경고). 서버 한도(R201)가 runner의 메모리 예약 합을 `MemTotal` 안에 두므로 경고할 경우가 없다. R65(판정에 GitHub 조회가 없음). R52의 "판정 중의 workflow run 조회와 최신 run 조회는 예외로 R65를 따른다"는 대상 호출이 없어져 적용할 곳이 없다. R98 목록의 workflow run 조회와 최신 run 조회는 없애고, "저장소 runner 목록"은 저장소 runner 목록 전체 조회(R241)와 이름 조회(R242)로 나눈다. 두 호출의 영구 오류도 R98대로 오류 drain을 시작하지 않는다.
- 0001 Design에서 바뀌는 항목: 판정 1~8 중 토큰(판정 1), 거부 처리(판정 4), `JobWorkflowRef` 형식(판정 6), AWS(판정 7)는 그대로 두고, run 조회(판정 2), R9 조건과 `allowed-events` 설명(판정 3), 시간 순서 중 `JobStarted` 의존 부분(판정 5), 최신 run 조건(판정 8)은 없앤다. 판정 3과 판정 8이 막던 경우가 열리는 것은 Areas of concern 4다. 재시도 표의 "판정의 workflow run 조회와 최신 run 조회" 행은 없애고 "시작 단계" 행에 설치 조회와 `/info`를 더한다. "대조의 runner 목록(R103)" 행은 저장소 runner 이름 조회(R242)가 같은 규칙으로 잇는다.

**구성 요소**
- target(`internal/github`): owner와 repo를 가진 값이다. 등록 URL(`GitHubConfigURL`)은 `https://github.com/<owner>/<repo>`, 설치 조회 경로는 `/repos/{owner}/{repo}/installation`, runner 목록 경로는 `/repos/{owner}/{repo}/actions/runners`, 설치에 있어야 하는 권한은 `administration: write`이고, 모두 target의 메서드 뒤에 둔다. scaleset v0.5.0은 경로 조각이 둘이고 첫 조각이 `enterprises`(대소문자 무시)가 아닌 URL을 저장소 범위로 읽고(첫 조각이 `enterprises`면 enterprise 범위로 읽으므로 R231이 그 꼴을 받지 않는다), 등록 토큰을 `/repos/{owner}/{repo}/actions/runners/registration-token`에서 받는다(확인함: v0.5.0 `config.go` 32~73행 `parseGitHubConfigFromURL`, `client.go` 1052~1054행 `createRegistrationTokenPath`). 그래서 scale set 생성, 세션, JIT 발급, `GetRunnerByName`, `RemoveRunner`는 0001과 첫 판과 같은 라이브러리 호출을 그대로 쓴다. 0001은 같은 꼴의 등록 URL로 저장소 하나를 등록했다(확인함: 0001 SPEC 설정 표 `pools.repo-url`과 구성 요소의 GitHub 연동). 첫 판의 조직 종류는 없앤다.
- 설치 ID 조회(R236~R238): App으로 인증하는 target마다 그 target의 App(자기 App, 없으면 `[github]`의 기본 App. 0003 R273)의 JWT로 `GET /repos/{owner}/{repo}/installation`을 부른다. 이 endpoint는 JWT로만 부르고, 응답은 설치 객체(필수 `id`, 필수 `permissions`)이며, 문서의 응답 코드는 200, 301, 404다(확인함: https://docs.github.com/en/rest/apps/apps "Get a repository installation for the authenticated app" `GET /repos/{owner}/{repo}/installation`, "You must use a JWT to access this endpoint.", 응답 스키마는 "Same response schema as Get an installation for the authenticated app"이고 그 스키마에 `id` 필수 정수와 `permissions` 필수, 2026-11-26 읽음). 그래서 App이 그 저장소에 설치되지 않은 경우의 404(R237)는 문서에 있는 응답이고, 실제 응답 코드는 R257에서 기록한다. 같은 owner의 여러 저장소는 설치 하나를 같이 쓰므로 조회한 설치 ID가 같을 수 있고, 스케일러는 target마다 조회한 ID를 그대로 쓴다. 301은 스케일러의 HTTP 클라이언트가 `CheckRedirect` 없이 만들어져(확인함: `internal/daemon/adapters.go` 286행) Go의 기본 redirect 정책을 따른다(추론: net/http `Client`의 기본 정책은 10번까지 따라감). 301을 받은 저장소의 처리는 Areas of concern 5다. JWT만 쓰므로 새 App 권한이 필요 없다. 권한 검사(R238)는 첫 등록 호출의 403보다 먼저, 무엇이 빠졌는지 이름으로 알리기 위해 둔다. 설치 객체의 권한 이름은 `administration`이고 값은 `read`나 `write`다(확인함: 같은 문서 "Get an installation for the authenticated app" 응답 스키마의 `administration` enum `read`, `write`, 2026-11-26 읽음). 조회한 ID는 `ScaleSetConfig.InstallationID`와 `RESTConfig.InstallationID`에 넣는다. 서명기(`AppSigner`), 설치 조회, 설치마다의 REST 클라이언트는 App(client ID와 키)마다 하나이고, 그 App을 기본 App으로 쓰든 자기 App으로 쓰든 같은 App의 target들이 같이 쓴다(확인함: `internal/daemon`의 `NewGitHub`, `appClients`).
- App 권한(R238): 저장소 수준 등록에는 Repository permission "Administration: Read and write"가 필요하다(확인함: https://docs.github.com/en/actions/tutorials/use-actions-runner-controller/authenticate-to-the-api, "**Administration:** Read and write"의 주석 "is only required when configuring Actions Runner Controller to register at the repository scope."). REST의 GitHub App 권한 표에서 저장소 runner 목록과 runner 하나의 조회는 Administration read, 등록 토큰, JIT 발급, runner 삭제는 Administration write다(확인함: https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps "Repository permissions for Administration"의 `GET /repos/{owner}/{repo}/actions/runners` read, `GET /repos/{owner}/{repo}/actions/runners/{runner_id}` read, `POST /repos/{owner}/{repo}/actions/runners/registration-token` write, `POST /repos/{owner}/{repo}/actions/runners/generate-jitconfig` write, `DELETE /repos/{owner}/{repo}/actions/runners/{runner_id}` write, 2026-11-26 읽음). 0001은 이 권한으로 scale set 생성, 세션, JIT 발급, runner 제거를 했다(확인함: 0001 SPEC Design, 2026-11-20 App 시험). 첫 판이 쓰던 Organization permission "Self-hosted runners: Read and write"는 이 변경에서 쓰지 않는다. 판정이 GitHub를 부르지 않으므로(R123) 0001의 Actions 읽기 권한은 쓰이지 않는다. 쓰지 않게 된 권한을 뺄지는 Areas of concern 6이다.
- runner group(R239, R234): 저장소 scale set은 runner group ID 1에 둔다. 0001은 저장소 URL로 기본 runner group(id 1)에 scale set을 만들었고(확인함: 0001 SPEC Design 스케일링 흐름 1, 2026-11-20 조직 소유 저장소에서 시험), 라이브러리 예제는 group 이름이 `default`(`scaleset.DefaultRunnerGroup`)면 ID 1을 쓴다(확인함: actions/scaleset v0.5.0 `types.go` 9행, `examples/dockerscaleset/main.go` 66~68행). runner-up은 "Repository scale sets always use the default group."이라고 적는다(확인함: runner-up 013cc74 `internal/config/config.go` 136~137행). runner group은 조직과 enterprise 수준의 runner 접근을 정하는 기능이라(추론: https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/manage-access 의 조직과 enterprise 절) 저장소 target에서 고를 group이 없다. 그래서 첫 판의 `targets.runner-group`을 없애고, 남아 있으면 조용히 무시하지 않고 설정 오류로 알린다(R234). 무시하면 운영자는 group으로 접근을 좁혔다고 믿게 된다. 개인 계정 저장소에서도 ID 1이 쓰이는지는 미확인이고(actions-scaleset 스킬 references/runtime.md 1절) R250이 확인한다(Areas of concern 7). 이 변경의 스케일러는 v0.5.0의 `GetRunnerGroupByName`을 부르지 않는다.
- 같은 이름의 scale set: scale set 이름은 runner group 안에서 유일하고(확인함: https://docs.github.com/en/actions/how-tos/manage-runners/use-actions-runner-controller/deploy-runner-scale-sets "Runner scale set names are unique within the runner group they belong to.", actions/scaleset v0.5.0 `client.go` 430행 "GetRunnerScaleSet fetches a runner scale set by its name within a runner group."), 저장소 target은 모두 group ID 1에 같은 이름(`scaling.label`)의 scale set을 둔다. 등록 URL이 저장소마다 다르므로 `GetRunnerScaleSet(1, label)`은 그 저장소의 scale set만 돌려준다고 본다(추론: 0001이 저장소 하나에서 같은 호출로 그 저장소의 scale set을 찾았다). 같은 owner의 두 저장소에 같은 이름의 scale set을 따로 둘 수 있는지는 추론이고, PLAN의 첫 실제 확인과 R248이 확인한다(안 될 때의 대안은 Areas of concern 19). 첫 판의 조직 수준 scale set은 지웠으므로 같은 조직에 같은 이름의 조직 scale set은 없다(Areas of concern 16).
- 공유 자원: runner 표, 시작 문(R187), 서버 한도, Docker 클라이언트, job 확인 서버, status는 서버에 하나씩이고 모든 target이 같이 쓴다. 서명기는 App마다 하나다. target마다 따로인 것은 `max-runners`, 설치 ID, scale set 클라이언트, REST 클라이언트, scale set, 세션, listener, 시작 단계의 백오프, 상태(시작 중, 정상, target 오류 drain, target 오류 대기), 마지막 오류, 연속 시작 실패 수(R61, R86), `Statistics`가 있는 마지막 메시지의 `TotalAssignedJobs`와 시작 요청(R115, R187), R174의 다시 시도 간격과 다음 시도 시각, Actions 서비스 호출의 R52 대기(R265)다. REST 호출의 R52 대기는 설치마다 하나이고(R266), 설치 조회의 R52 대기는 App JWT 호출이라 App마다 하나다(R189). 0001 코드는 R52의 대기를 호출 종류마다 하나씩 daemon 전체에 둔다(확인함: `internal/daemon/daemon.go` 229행 `retry.NewNextAllowed`, `internal/retry/ratelimit.go` 48행 "per kind of call"). 이 변경에서는 호출이 가는 곳에 따라 둘로 나눈다. (1) GitHub REST(api.github.com)로 가는 호출은 우리 REST 클라이언트의 저장소 runner 목록과 이름 조회(R241, R242), 그리고 라이브러리 안의 등록 토큰 요청과 `/actions/runner-registration` 교환뿐이다. 설치 토큰으로 부르는 REST 호출의 속도 제한은 설치마다 따로다(확인함: github/docs 8b038c5 `data/reusables/rest-api/primary-rate-limit-github-app-installations.md`("Rate limits for the REST API" 문서가 씀), "use the installation's minimum rate limit of 5,000 requests per hour", `content/apps/using-github-apps/installing-a-github-app-on-your-enterprise.md` "Rate limits are per installation"). 그래서 우리 REST 호출의 대기는 설치 ID마다 하나를 두어(R266), 같은 설치를 쓰는 저장소 target들이 한 한도를 같이 쓰는 것을 대기에도 맞춘다. 저장소가 많아도 같은 설치면 속도 제한 응답 하나 뒤에 모두 기다리고, 다른 owner의 설치는 늦어지지 않는다. 라이브러리 안의 등록 토큰 요청은 0001처럼 라이브러리의 재시도를 따르고 우리 대기에 들어가지 않는다. (2) scale set 호출, 메시지 세션 호출, `AcquireJobs`, JIT 발급, `GetRunnerByName`, `RemoveRunner`는 REST가 아니라 Actions 서비스로 가고, `/actions/runner-registration`에서 받은 관리 연결의 토큰을 쓴다(확인함: actions/scaleset v0.5.0 `client.go` 766행 `GenerateJitRunnerConfig`, 824~826행 `GetRunnerByName`, 858~860행 `RemoveRunner`가 `newActionsServiceRequest`를 쓰고, 977~1032행 `getActionsServiceAdminConnection`이 `/actions/runner-registration`을 부름). Actions 서비스의 속도 제한이 설치마다인지, 등록(scale set)마다인지, 그 밖인지는 문서에 없다(미확인, Areas of concern 15). 그래서 그 대기는 첫 판대로 target마다, 호출 종류마다 둔다(R265). target은 scale set 하나와 관리 연결 하나를 따로 가지므로 이것이 그 호출이 실제로 나뉘는 단위다(추론). App JWT로 부르는 호출의 한도는 속도 제한 문서에 없어(content/rest, content/apps, data/reusables에서 찾음) 미확인이라 App마다 하나 둔다(Areas of concern 15). runner 표의 행은 target을 기록하고, job 확인 서버는 runner 이름으로 행을 찾아 그 행의 target에 보고를 넘긴다. 이 나눔은 참고 구현과 같다. runner-up은 조직마다 scale set과 세션을 따로 열고 세션마다 고루틴 하나로 돌린다(확인함: runner-up 013cc74 `internal/coordinator/github.go` 142~197행 `Sessions.Match`, 238~266행 `RunSet`, `internal/config/config.go` 133~135행 "Orgs get one scale set per pool each"). runscaler는 scale set마다 고루틴, 클라이언트, listener를 따로 두고 호스트 전체 한도 하나를 같이 쓴다(확인함: ysya_runscaler 6f33444 `cmd/runner/main.go` 539~541행, 574~585행).
- target 비교(R233): 같은 저장소를 두 번 적으면 같은 scale set 하나에 세션 둘이 붙게 되므로 설정 오류로 막는다. owner와 repo는 대소문자 구분 없이 비교한다. GitHub REST는 두 path parameter를 대소문자 구분 없이 다룬다(확인함: https://docs.github.com/en/rest/actions/self-hosted-runners "List self-hosted runners for a repository"의 `owner`와 `repo` 설명이 모두 대소문자를 구분하지 않는다고 적음, 2026-11-26 읽음). runpool도 같은 이유로 target URL을 소문자로 바꿔 겹침을 막는다(확인함: rhobuild_runpool f1a2ab3 `internal/config/validate.go` 198~207행, 주석 "GitHub logins and repository names are [case-insensitive]"). runner-up은 문자열이 정확히 같을 때만 막는다(확인함: runner-up 013cc74 `internal/config/config.go` 411~423행 "listed once"). 저장소 수에는 상한을 두지 않는다(R105, INTENT 제약). target 하나는 세션 하나, poll 고루틴 하나, 시작 때 설치 조회 1번과 runner 목록 조회를 더하고, 30초마다의 대조는 판정 없는 runner가 있을 때만 그 runner마다 조회 1번을 더한다(R242).
- 동시 실행 한도(R114, R115, R201): 한도는 둘이다. target의 `max-runners`는 그 target의 runner 수 상한이고 그 target 세션의 `maxCapacity`다(R115, R116, 0001 R3). 서버 한도는 모든 target의 runner 수 합의 상한이고, 따로 정하지 않으면 서버의 CPU·메모리로 정한다(R114, R201). 결정: 2026-11-26, 사용자, target마다 자기 `max-runners`를 쓰고 실제 동시 실행은 서버 스펙(CPU·메모리)에 맞춰 제한한다. INTENT 제약 "Each repository's maximum applies within the server's limit, and the server's limit follows its CPU and memory"를 이 두 한도가 맡는다. 두 한도의 나눔은 runscaler와 같다. runscaler는 scale set마다 `max-runners`를, 호스트 전체에 `concurrent`를 두고, GitLab Runner처럼 `concurrent`는 관리 프로그램 안의 runner 총수를, `max-runners`는 scale set마다의 상한을 정한다고 적는다(확인함: ysya_runscaler 6f33444 `docs/configuration.zh-TW.md` 412, 446행). runscaler의 `concurrent`는 설정값이고(확인함: 같은 파일 412행, `config.example.toml` 8행 "host-wide limit"), 서버 한도는 기본으로 runner-up의 machine 예산처럼 서버가 보고한 값에서 정하며 `scaling.server-limit`으로 runscaler처럼 덮어쓸 수 있다(R201). runner-up은 machine의 `Cores`와 `MemoryMB`를 "what the machine's places may reserve together"로 두고 "A place takes a job only while its share fits beside the shares of the machine's places whose runners are alive"라고 적으며(확인함: runner-up 013cc74 `internal/config/config.go` 168~171행), place의 `Cores`와 `MemoryMB`는 "container/VM limits and the reservation against the machine's budget"이다(확인함: 같은 파일 191~193행). 쓰고 있는 몫에 새 몫을 더해 예산을 넘으면 그 place는 job을 받지 않고(확인함: 같은 커밋 `internal/coordinator/snapshot.go` 210~232행 `tight`), machine을 더할 때 그 machine의 코어와 메모리를 읽는다(확인함: 같은 커밋 `README.md` 367행 "reads the machine's cores and memory"). 이 스케일러도 runner 컨테이너와 BuildKit 컨테이너의 CPU·메모리 제한(R121, R122)을 runner 하나의 예약으로 보고, 예약 합이 Docker가 보고한 `NCPU`와 `MemTotal`을 넘지 않게 한다. 모든 runner의 몫이 같으므로(`runner.cpus + buildkit.cpus`, `runner.memory + buildkit.memory`) 이 예산 검사는 R201의 runner 수 하나로 줄어든다. Docker의 제한은 사용의 상한이고 그만큼을 미리 잡아 두지 않으므로(확인함: https://docs.docker.com/engine/containers/resource_constraints/, `--memory` "The maximum amount of memory the container can use", `--cpus` "how much of the available CPU resources a container can use", 예약 쪽인 `--memory-reservation`도 "it doesn't guarantee that the container doesn't exceed the limit"이고 `--cpu-shares`는 "doesn't guarantee or reserve any specific CPU access", 2026-11-26 읽음), 실제 사용이 제한보다 적은 job이 많을 때는 서버가 돌릴 수 있는 수보다 적게 동시에 돈다. 그 대신 모든 runner가 동시에 제한까지 써도 합이 Docker VM의 CPU·메모리를 넘지 않는다. runner-up의 owner 몫(`RoomCores`, `RoomMemoryMB`, 확인함: 같은 파일 174~177행)은 두지 않는다(결정: 사용자, 최소 설정. Docker VM 밖 macOS의 메모리 여유는 따지지 않는다). 계산한 값이 이 Mac에 맞지 않으면 `scaling.server-limit`으로 정한다(결정: 2026-11-27, 사용자, 계산값을 기본으로 두고 설정으로 덮어씀). 그 값은 Docker가 보고한 CPU·메모리를 넘는 예약 합을 허용할 수 있고, 그 책임은 설정한 사람에게 있다. `/info`는 시작 때 한 번 읽으므로 Docker Desktop의 자원이나 `scaling.server-limit`을 바꾸면 스케일러를 다시 시작한다(R201). 나눗셈은 정수로 한다. CPU는 0001처럼 설정값에 1e9를 곱한 정수 NanoCPUs로, `NCPU`도 1e9를 곱해 나누고, 메모리는 바이트로 나눈다. 0.5 + 1 같은 소수 합에서 부동소수점 오차로 몫이 하나 작아지는 것을 막기 위해서다(추론). GitHub가 보내는 스케일 신호(`TotalAssignedJobs`)와 받는 쪽 한도(`maxCapacity`)는 모두 개수다(actions-scaleset 스킬 references/runtime.md 3절). 자리가 있는지의 판단(R187)은 자리 배치의 잠금 아래에서 한다. 빈 자리는 모든 target에 걸쳐 job 요청이 idle 요청보다 먼저, 같은 종류 안에서는 요청이 생긴 순서로 받는다(R187, 설계: 자리 배치). 축소(R37)는 target마다 하고, 목표를 넘는 수만큼 busy가 아닌 runner만 지운다(R185).
- `maxCapacity`(R116): target마다 그 target의 세션이 자기 `max-runners`를 그대로 보낸다. target들의 `max-runners` 합은 서버 한도를 넘어도 되고(R204는 INFO로만 남긴다), 그래서 GitHub가 target들에 배정한 job 수의 합은 서버 한도를 넘을 수 있으며, 실제로 도는 runner 수만 runner 표가 서버 한도로 막는다(R114). 스케일러는 받은 `JobAvailable` job을 자리와 관계없이 바로 가져가고(R169) GitHub도 `maxCapacity`만큼 스스로 그 scale set에 배정하므로, 자리가 없는 job은 그 scale set에 배정된 채 기다린다. INTENT의 "Jobs beyond what a repository's maximum or the server allows wait and start when a runner slot frees up"이 이것이다. 2026-11-26 실제 실행에서 GitHub는 모든 실행에서 job을 `maxCapacity`까지 그 scale set에 바로 배정했고(`JobAssigned`, `RunnerRequestID` 0), `JobAvailable`은 한 번도 보내지 않았으며, `maxCapacity`를 넘는 job에는 그 job을 배정할 때까지 메시지를 보내지 않았다(확인함(근거: 0002 PLAN M17 결과, 첫 판 실제 실행 2026-11-26)). 그래서 저장소의 최대를 넘는 job은 GitHub 쪽에서 기다리고, 목표는 `max-runners`를 넘지 않으므로(R115) 최대에 닿은 저장소는 다른 저장소가 쓸 수 있는 서버 자리를 잡지 않는다(INTENT Open questions의 넷째 질문). 스케일러 쪽에서도 최대에 닿은 target은 시작 문에서 건너뛰고 다른 target의 요청이 자리를 받는다(R247). 보내는 값은 runscaler, runner-up과 같은 방식이다. runscaler는 scale set마다 listener의 `MaxRunners`로 그 scale set의 `max-runners`를 보내고(확인함: ysya_runscaler 6f33444 `cmd/runner/main.go` 907~911행), scale set들의 `max-runners` 합이 호스트 한도를 넘는 것을 정상으로 보고 공유 broker가 runner 시작을 막는다(확인함: 같은 커밋 `internal/config/config.go` 574~575행 "Local max-runners values may sum above the global limit; the broker arbitrates that normal oversubscription case."). runner-up도 scale set마다 장소 수보다 큰 고정값(기본 50)을 보낸다(확인함: runner-up 013cc74 `internal/config/config.go` 86~90행 "It stays above the number of places, so the coordinator hears of every waiting job and picks the order, not GitHub.", 371~372행, `internal/coordinator/github.go` 309행). 가져가는 때는 둘이 다르다. runscaler는 받은 `JobAvailable`을 모두 바로 `AcquireJobs`로 가져가고(확인함: ysya_runscaler 6f33444 `internal/controller/messages.go` 62~66, 91행), 0001도 그랬다(0001 Design 스케일링 흐름 3). runner-up은 자리가 날 때 그 job을 위한 runner를 등록하기 바로 전에만 가져간다(확인함: runner-up 013cc74 `internal/coordinator/placement.go` 162~178행 `start`). 이 변경은 runscaler, actions-runner-controller, actions/scaleset 예제, 0001처럼 받은 즉시 가져간다(설계: 자리 배치). 라이브러리 README는 `maxCapacity`가 "allows the backend to assign jobs accurately and avoid creating backlogs your scale set cannot fulfill"이라고 적고(확인함: actions/scaleset v0.5.0 `README.md` 49행), 배정됐지만 runner가 제때 가져가지 않은 job은 GitHub가 배정을 취소하고(`JobCompleted`, `result: "canceled"`) 다시 큐에 넣으며 이것이 3번까지 일어난다고 적는다(확인함: 같은 파일 116행). 2026-11-26 실제 실행에서 약 5분 기다린 배정 job은 새 `JobID`의 `JobAssigned`로 다시 배정됐고 배정 취소 메시지(`JobCompleted`)는 오지 않았다(확인함(근거: 0002 PLAN M17 결과, 첫 판 실제 실행 2026-11-26)). 다시 배정이 몇 번까지 되고 그 뒤 job이 어떻게 되는지는 미확인이다(Areas of concern 12, R263).
- 자리 배치(R115, R169, R170, R185~R187, R210, R212, R220, R222, R247): 결정: 2026-11-27, 사용자, 가장 일반적인 방식을 따른다. 스케일러는 받은 `JobAvailable`을 받은 즉시 모두 `AcquireJobs`로 가져가고(R169), target마다 목표를 `min(max-runners, idle + TotalAssignedJobs)`로 정한다(R115). actions-runner-controller와 actions/scaleset 예제가 이렇게 한다(확인함: actions-runner-controller `cmd/ghalistener/scaler/scaler.go` 149행 `AcquireJobs`, 173행 `HandleDesiredRunnerCount(…TotalAssignedJobs)`, 339행 `min(MinRunners+count, MaxRunners)`, actions/scaleset `examples/dockerscaleset/scaler.go` 41행 `AcquireJobs`, 61행, 70행 `min(maxRunners, minRunners+count)`). runscaler도 받은 `JobAvailable`을 바로 가져간다(확인함: ysya_runscaler 6f33444 `internal/controller/messages.go` 62~66, 91행). 서버 한도는 runscaler의 broker처럼 runner 시작을 줄 세우는 서버 하나의 시작 문으로 지킨다(동작만 참고). 그래서 서버가 찬 동안 job은 그 target의 scale set에 배정된 채 GitHub에서 기다리고, 그 수는 `TotalAssignedJobs`로 목표에 들어간다.
  - 시작 문(R187): target마다 목표에 모자라는 runner 하나가 시작 요청 하나다. 존재하는 runner가 배정 job을 먼저 덮으므로(GitHub는 배정된 job을 그 scale set의 아무 대기 runner에게 준다) `min(max-runners, TotalAssignedJobs) − 존재하는 runner 수`만큼이 job 요청이고 나머지가 idle 요청이다. 요청은 모든 target에 걸친 순번을 받는다. 새 요청은 대개 그 target의 `TotalAssignedJobs`가 늘어난 메시지를 받은 때 순번을 받고, runner 표에서 행이 빠져 새로 필요해진 요청은 그 자리 배치에서 설정 순서로 받는다. 문은 빈 자리를 job 요청에 먼저 준다. INTENT의 결과가 job의 실행이고 `idle`은 시작 시간을 줄이는 설정이기 때문이다. 지금 시작할 수 없는 target은 요청과 순번을 지키고, 백오프, 속도 제한, 받는 중인 이미지처럼 곧 끝날 이유로 기다리는 target의 job 요청 몫은 다른 target의 idle 요청이 가져가지 않는다. 그 target이 다시 시작할 수 있게 되면 그 자리를 받는다. `max-runners`에 닿아 기다리는 target은 자기 runner가 빠져야 다시 시작할 수 있고 그때 서버 자리도 하나 비므로 자리를 남기지 않는다(R247).
  - 선점(R187): 대기 runner는 자기 target의 job만 받으므로, 다른 target의 대기 runner가 서버 자리를 모두 차지하면 배정 job이 영원히 runner를 받지 못할 수 있다. 그래서 job 요청이 서버가 차서 자리를 받지 못하면, 그 몫만큼 배정 job보다 많은 runner를 가진 다른 target의 busy가 아닌 runner를 가장 새것부터 지운다. busy runner는 지우지 않으므로 도는 job은 끊기지 않는다. 지운 runner가 runner 표에서 빠지면 다음 자리 배치(R170)가 그 자리를 job 요청에 준다(확인함: `internal/scaler/placement.go`의 `preempt`).
  - 자리 배치를 하는 때(R170, R212): target이 여럿이면 자리를 비운 runner와 자리를 기다리는 job의 target이 다를 수 있고, 기다리는 target의 다음 메시지를 기다리면 빈 poll이 끝날 때까지(약 50초) 늦어 R252와 R254의 60초를 넘길 수 있다. 그래서 runner 표에서 행이 빠지면 1초 안에 서버 전체의 자리 배치를 한다(R170). 메시지를 반영한 직후, 30초마다의 대조(0001 R42) 직후, 이미지 받기가 끝난 때(0003 R319)에도 한다(R212). 신호 drain과 drain 끝의 정리 중에는 0001 R20대로 새 runner를 만들지 않으므로 자리 배치도 `AcquireJobs`도 하지 않는다(R220). 자리 배치는 네트워크 호출을 포함해 잠금 하나 아래에서 하나씩만 돌고, 잠금 순서는 target `Scale`의 잠금, 자리 배치의 잠금, runner 표의 잠금이다(확인함: `internal/scaler/placement.go`의 `Placer` 주석). `AcquireJobs`는 자리 배치의 잠금 밖에서 부른다.
  - target 오류(R210, R220): target 오류 drain과 target 오류 대기의 target은 목표가 0이고(R173, R174) runner를 받지 않으므로, 그 target의 시작 요청과 `TotalAssignedJobs`를 버리고 `AcquireJobs`를 부르지 않는다. 그 target이 상태 `running`으로 돌아오면 새 세션의 메시지로 목표를 다시 정한다(R194). `AcquireJobs`의 영구 오류는 그 target의 오류 drain을 바로 시작하지만 세션은 닫지 않으므로, busy runner의 `JobStarted`와 `JobCompleted`는 계속 받는다(0001 R54, R173).
  - 받아들이는 효과: `TotalAssignedJobs`는 메시지마다의 통계라, `AcquireJobs`로 막 가져간 job이나 막 끝난 job이 한 메시지 늦게 드러날 수 있다. 그래서 runner 하나가 더 시작됐다가 다음 메시지에서 R185로 지워질 수 있다. actions-runner-controller와 같은 효과이고 되풀이되지 않으므로 막는 장치는 두지 않는다. 서버 자리를 기다리는 배정 job은 약 5분 뒤 새 `JobID`로 다시 배정됐다(확인함(근거: 0002 PLAN M17 결과, 첫 판 실제 실행 2026-11-26)). 다시 배정돼도 그 job은 `TotalAssignedJobs`에 남아 job 요청이 그대로다. 라이브러리 README는 배정 취소가 3번까지 일어난다고 적고(확인함: actions/scaleset v0.5.0 `README.md` 116행), 그 뒤의 결과는 미확인이라 나중 시험 R263이 본다(Areas of concern 12). 저장소 사이의 순서는 스케일러가 배정 수가 늘어난 메시지를 받은 순서다. GitHub 큐의 QueueTime 순서가 아니고, 저장소의 `maxCapacity`를 넘어 GitHub가 붙잡은 job은 메시지가 없어 순번이 없다(Areas of concern 18).
- `idle`의 자리(R167, R168, INTENT Open questions의 셋째 질문): target마다 `targets.idle`(0 이상 그 target의 `max-runners` 이하, 기본 0)을 첫 판 그대로 둔다. 대기 runner는 그 target의 runner 수(R3)와 모든 target의 runner 수 합(R114)에 함께 들어, 그 target의 최대와 서버 한도를 함께 쓴다. 대기 runner는 job이 오기 전에 자리 하나를 차지한다. 모든 target의 `idle` 합이 서버 한도를 넘으면 그 설정은 어느 때도 지킬 수 없으므로 오류 대기에 들어간다(R167). 계산한 서버 한도는 `/info`를 부른 뒤에야 알므로 이 검사는 R28의 설정 검증이 아니라 R202와 같은 Docker 용량 확인에서 한다. `scaling.server-limit`을 둔 때도 같은 곳에서 검사하고, 그때는 설정 오류로 본다. target 하나의 `idle`이 그 target의 `max-runners`를 넘는 것은 설정 검증(R28, 설정 표)이 막는다. runscaler도 호스트 한도가 scale set들의 최소 runner 수 합보다 작으면 설정 오류로 막는다(확인함: ysya_runscaler 6f33444 `internal/config/config.go` 576~587행 "must be >= the sum of min-runners"). 합이 서버 한도와 같으면 대기 runner만으로 모든 자리가 차서, `idle`이 0인 target의 job은 선점(R187)으로 다른 target의 대기 runner를 지운 뒤에야 runner를 받으므로 그만큼 늦게 시작한다. 그래서 시작 경고로 알린다(R168). 그 밖에, idle 요청과 어느 target의 job 요청이 같은 자리를 두고 겨루면 job 요청이 먼저이고, 서버가 차서 job 요청이 자리를 받지 못하면 다른 target이 배정 job보다 많이 가진 대기 runner를 지운다(R187). 대기 runner는 같은 target의 job이 오면 그 job을 받는다. INTENT의 결과가 job의 실행이고 `idle`은 시작 시간을 줄이는 설정이기 때문이다. runscaler는 반대로 다른 scale set의 최소 runner 수를 남는 자리보다 먼저 채운다(확인함: ysya_runscaler 6f33444 `internal/capacity/broker.go` 9~11행 "Capacity needed to satisfy another scale set's minimum is reserved before surplus is handed out"). 그 최소 수는 busy runner를 포함한 runner 수이고, 우리 `idle`은 배정 job 위에 더하는 대기 runner 수라(0001 R1) 같은 규칙을 그대로 옮기지 않는다.
- 고르지 않은 방법: (1) 서버 한도를 target들에 나눠 각 세션의 `maxCapacity`로 보내는 것. runpool은 binding마다 남은 자리의 몫을 계산해 세션의 capacity로 보낸다(확인함: rhobuild_runpool f1a2ab3 `internal/app/delivery.go` 685~696행 `announce`). 고르지 않은 이유는 둘이다. (가) 몫이 0인 target은 `maxCapacity` 0을 보내게 되는데, 0이면 배정이 보이지 않는다(0001 R90의 이유, actions/scaleset 이슈 #133). runpool은 이를 위해 수요를 알아낼 binding 하나를 따로 정한다(확인함: 같은 파일 707~711행 `discovery`). (나) 몫이 바뀔 때마다 poll의 값이 바뀌므로 GitHub가 그 값으로 어떻게 배정하는지(미확인)에 동작이 더 많이 기대게 된다. runscaler와 runner-up은 나누지 않는다(위). (2) 서버 한도를 runscaler의 `concurrent`처럼 설정값으로만 두는 것. 기본값이 Docker가 보고한 CPU·메모리를 넘는 예약 합을 허용하게 되어 서버 스펙에 맞춰 제한한다는 결정(위 동시 실행 한도)과 맞지 않으므로, 설정값은 계산값을 덮어쓰는 선택 키로만 둔다(R201). (3) runner-up처럼 서버 하나의 대기 job 목록을 두고 자리가 날 때만 `AcquireJobs`로 가져가는 것(이 SPEC의 앞선 방식). 목록의 항목, 배정 취소 표시, 통계와의 대조, 25시간 시한 같은 장치가 따로 필요하고, GitHub가 `maxCapacity`만큼 스스로 배정하므로 가져가지 않아도 대부분의 job은 이미 배정된다(설계: `maxCapacity`). actions-runner-controller, actions/scaleset 예제, runscaler는 모두 받은 즉시 가져가고 `TotalAssignedJobs`로 목표를 정한다(설계: 자리 배치).
- Docker 용량 확인(R167, R201~R204): Docker 준비와 R16 뒤, 이미지 확인 다음에 `/info`를 한 번 부르고, `scaling.server-limit`이 0이면 그 응답으로 서버 한도를 계산하고 양수면 그 값을 서버 한도로 쓴 뒤(R201) INFO `server runner limit`을 필드 `limit`, `computed`, `configured`, `ncpu`, `memTotal`, `runnerCPUs`, `runnerMemory`와 함께 남긴다(R203). `scaling.server-limit`이 양수면 `/info`의 실패는 WARN `docker info failed; using scaling.server-limit`만 남기고 계속한다. 계산한 서버 한도가 0이면(예: `runner.memory + buildkit.memory`가 `MemTotal`보다 크거나 `runner.cpus + buildkit.cpus`가 `NCPU`보다 큼) runner를 하나도 시작할 수 없으므로 오류 대기에 들어간다(R202). 이 확인의 오류는 계산한 한도면 Docker 쪽 원인이라 0001 R47대로 다시 확인하고, `scaling.server-limit`으로 정한 한도면 설정 오류다(R167, R176). 컨테이너 하나의 CPU 상한이 `NCPU`를 넘으면 Docker가 생성을 거부하므로(확인함: 0001 Areas of concern 21, moby `docker-v29.6.1` `daemon/daemon_unix.go` 482~485행) `runner.cpus`나 `buildkit.cpus` 하나가 `NCPU`보다 큰 설정은 모든 시작이 실패하는데, 그때는 runner 하나의 CPU 몫도 `NCPU`보다 커 서버 한도가 0이므로 R202가 같이 드러낸다. 그래서 따로 검사하던 R118은 dropped이고, 어느 키가 원인인지 보이도록 R202의 문구가 네 키의 값을 담는다. 문구는 `server runner limit is 0: one runner reserves <cpus> CPUs (runner.cpus <값> + buildkit.cpus <값>) and <memory> bytes (runner.memory <값> + buildkit.memory <값>), Docker reports <NCPU> CPUs and <MemTotal> bytes`다. 그다음 `idle` 합을 본다(R167, 문구 `idle of all targets (<합>) exceeds the server runner limit (<서버 한도>)`). 마지막으로 target들의 `max-runners` 합이 서버 한도보다 크면 INFO `max-runners of all targets exceed the server limit`을 필드 `sum`, `limit`과 함께 남긴다(R204). 이 경우는 runscaler가 정상으로 보는 초과 배정이라(위 `maxCapacity`) WARN으로 남기지 않는다. 예약 합이 Docker가 보고한 값을 넘는 설정은 서버 한도 아래에서 생기지 않으므로 0001 R29의 경고를 없앤다(R119, R120은 dropped). 이 Mac의 Docker VM(10 CPU, 9.70 GiB, 확인함: INTENT Open questions, 2026-11-26 스케일러 시작 로그 `server runner limit`의 `limit` 3)에서 기본값의 runner 하나의 몫은 3 CPU, 3 GiB이고 서버 한도는 min(floor(10 / 3) = 3, floor(9.70 / 3) = 3) = 3이다.

**판정(R123~R140)**
- 정책: `internal/gate`의 정책은 `Decide(eventName string, payload []byte) Decision` 하나가 된다. `Decision`은 허용 또는 거부와 거부 사유(`reason`)다. `JobStarted`의 `OwnerName`, `RepositoryName`, `WorkflowRunID`는 판정에 쓰지 않고 로그에만 남긴다. `Policy`의 허용 목록, `latest.go`, REST의 `GetRun`과 `ListWorkflowRuns`는 없앤다.
- 규칙 순서와 거부 사유: 본문 크기(R136, `payload-too-large`) → 본문이 JSON 객체 하나인지(R124, `payload-not-one-object`. `json.Decoder`의 `UseNumber`로 읽고, 첫 값 뒤에 토큰이 더 있으면 거부) → 이벤트 이름(R125, `event-name-invalid`) → 최상위 `pull_request`(R126, 값이 없거나 양의 정수가 아니면 `pull-request-repo-id-invalid`, 셋이 다르면 `pull-request-from-other-repo`) → 최상위 `workflow_run`(R127, 같은 꼴로 `workflow-run-repo-id-invalid`, `workflow-run-from-other-repo`) → 이름과 구조의 대조(R128, `pull-request-missing`, `workflow-run-missing`) → 허용(R129). 한 본문에 `pull_request`와 `workflow_run`이 둘 다 있으면 둘 다 통과해야 한다.
- 이벤트 파일로 판정하는 이유: `pull_request_target`과 `workflow_run`의 run은 기본 브랜치의 마지막 커밋과 기본 브랜치 ref로 돈다(확인함: https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows 두 절의 표 `GITHUB_SHA` "Last commit on default branch", `GITHUB_REF` "Default branch"). 그래서 workflow run REST 응답의 `head_repository`로는 그 run을 일으킨 pull request가 fork에서 왔는지 알 수 없다고 본다(추론). 이벤트 파일은 그 job을 일으킨 webhook payload 전체다(확인함: https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/run-scripts "The full webhook event payload can be found in `GITHUB_EVENT_PATH`."). fork head 정보가 이벤트에 있다는 것은 GitHub 문서가 `github.event.pull_request.head.repo.full_name`으로 fork를 가르는 예를 들고(확인함: securely-using-pull_request_target, set-up-code-coverage 문서), actions/checkout이 `pull_request_target`에서는 `pull_request.head.repo.id`를 최상위 `repository.id`와, `workflow_run`에서는 `workflow_run.head_repository.id`를 비교하는 데서 본다(확인함: actions/checkout main f548e57 `src/unsafe-pr-checkout-helper.ts` 18~55행). runner-up도 job 시작 hook에서 이 파일만 읽어 구조로 판정한다: 최상위 `pull_request`가 null이 아니면 head와 base 저장소 ID를, 최상위 `workflow_run`이 있으면 `head_repository.id`와 `repository.id`를 같은 양의 정수인지 비교하고, 그 밖은 허용하며, 읽을 수 없거나 빈 파일은 거부한다(확인함: runner-up 013cc74 `internal/agent/forkguard.go`).
- 필드의 근거: OpenAPI의 webhook 스키마에서 pull request의 opened, synchronize, closed는 `head.repo.id`와 `base.repo.id`가 필수이고, review submitted와 review comment created는 `head.repo`가 nullable이며, workflow run은 `workflow_run.head_repository.id`와 `workflow_run.repository.id`가 필수다(확인함: github/rest-api-description c9c95fe). octokit/webhooks 스키마는 지운 fork에서 `head.repo`를 null로 허용한다(확인함: octokit/webhooks 스키마). Actions 이벤트 파일에도 null이 오는지는 미확인이지만 null은 R126으로 거부되므로 안전한 쪽이다(Areas of concern 2).
- 구조로 판정하는 이유(R126, R127): 이벤트 이름만으로 PR 계열을 정하면 `pull_request`를 담는 다른 이름의 이벤트를 놓친다. 그래서 이름과 관계없이 최상위 `pull_request`와 `workflow_run`이 있으면 비교한다. 최상위 `repository.id`와도 같아야 하는 것은 head와 base가 서로 같아도 이 run의 저장소가 아닌 경우를 거부하기 위해서다. 이름 규칙(R128)은 이름이 PR 계열이나 `workflow_run`인데 R126, R127이 비교할 객체가 없는 보고를 거부한다. 그런 보고는 R126, R127을 거치지 않으므로, R128이 없으면 R129로 허용된다. 문서의 "The `pull_request` webhook event payload is empty for merged pull requests and pull requests that come from forked repositories."는 REST `GET /repos/{owner}/{repo}/actions/runs`의 `pull_requests` 배열에 대한 문장에서 왔고(확인함: github/docs#22501) 이벤트 파일에 대한 것이 아니다. 그래서 R128은 같은 저장소의 병합된 PR을 거부하지 않는다(OpenAPI상 closed 이벤트에도 `pull_request`가 필수, 아래 필드의 근거).
- 쓰지 않는 값(R129): `head.repo.fork`는 우리 저장소 자체가 다른 저장소의 fork이면 같은 저장소 PR도 true라 잘못 거부한다. `full_name`은 저장소 이름을 바꾸거나 옮기면 달라진다. `author_association`은 관계를 나타낼 뿐 쓰기 권한을 정하지 않는다(확인함: OpenAPI `author-association` enum, GraphQL `CommentAuthorAssociation`의 값 설명). 이벤트 이름만으로는 R128 밖에서 거부하지 않는다.

**status(R152, R180, R205, R222)**: status JSON은 `{"state","serverLimit","targets":[{"url","state","busy","idle","waitingJobs","maxRunners","startFailures","lastStartError","lastStartErrorAt","lastError","lastErrorAt"}],"lastError","lastErrorAt"}`이다. target의 `state`는 `starting`, `running`, `error-draining`, `error-wait` 중 하나이고 출력도 같은 낱말이다. target 줄은 `<target URL>: <state>, busy <busy>, idle <idle>, waiting jobs <waitingJobs>, max <maxRunners>, start failures <startFailures>`이고(`maxRunners`는 그 target의 `max-runners`, R205. `waitingJobs`는 마지막 자리 배치 때 그 target의 존재하는 runner가 덮지 못한 배정 job 수, R222), 시작 실패가 있으면 0001처럼 ` (<lastStartError>, <lastStartErrorAt>)`를, 상태가 `error-draining`이나 `error-wait`면 `, error: <lastError> (<lastErrorAt>)`를, `error-wait`면 그 뒤에 `, next retry <nextRetryAt>`을 붙인다(JSON의 target 객체는 처음부터 `nextRetryAt` 키를 가지며, `error-wait`가 아니면 값은 `null`이다). `total` 줄(`total: busy <n>, idle <m>, max <serverLimit>`)의 `<n>`과 `<m>`은 모든 target 줄의 `busy`, `idle` 합이고, 최대는 `serverLimit`(R201의 서버 한도)이다. `serverLimit`은 R201로 정하기 전에는 `null`이고 출력은 `max -`다. 맨 아래 `last error:` 줄은 0001처럼 스케일러 전체에서 가장 최근의 오류다. 스케일러 전체의 `state`는 0001과 같은 값을 쓴다. `state: starting`(R58)일 때도 target 줄을 출력해 어느 target이 시작 단계의 백오프에 있는지 보인다(R198). 한 target이 `error-draining`이나 `error-wait`여도 다른 target이 `running`이거나 `starting`이면 `state: running`이고 0으로 끝난다. `running`인 target도 `starting`인 target도 없으면(`error-draining`과 `error-wait`가 섞인 경우 포함) JSON의 `state`는 `running` 그대로이고, 출력의 첫 줄만 `state: running, no target`으로 바뀌며 1로 끝난다(R197). 그래서 감시하는 쪽은 종료 코드로 job을 받는 target이 하나도 없음을 안다. `starting`인 target이 있으면 곧 job을 받을 수 있으므로 0을 유지한다. `service stop`은 스케일러 전체의 state만 읽으므로 바뀌지 않는다.

**오류 범위(R171~R180, R190~R198)**: 오류는 그 오류가 닿는 범위에만 건다. 0001이 정하지 않고 남긴 범위(0001 Areas of concern 2)를 target 단위로 정한 것이다.
- target 범위: 한 target의 GitHub 호출(그 target의 설치 조회, scale set 호출, 메시지 세션 호출, `AcquireJobs`)이 영구 오류로 실패하면 그 target만 멈춘다. 이 호출들은 그 target의 설치 ID와 설치 권한에 달려 있어(설계: 구성 요소) 다른 target과 관계가 없다. 시작 단계면 그 target은 바로 target 오류 대기에 들어가고(R172), 실행 중이면 target 오류 drain에 들어간다(R171). target 오류 drain은 0001 오류 drain 규칙을 그 target에만 쓴다(R173): 그 target은 새 runner를 만들지 않고, 대기 runner는 R37로 지우고, busy runner는 끝나거나 `shutdown.drain-timeout`이 지날 때까지 기다린 뒤 남은 컨테이너를 지우고 `RemoveRunner`를 1회 시도한다. 세션을 쓸 수 있으면 그동안 세션은 유지하지만(R54) `AcquireJobs`는 부르지 않고(R220), 그 target의 시작 요청은 버린다(R210). 그 뒤 target 오류 대기에서 그 target은 세션을 닫고, R174의 간격으로 시작 단계만 다시 시도한다. 시도가 성공하면 `running`으로 돌아간다. 그 target의 runner가 빠진 자리는 R170으로 다른 target이 쓴다.
- 서버 범위: 설정, Docker, 잠금, status socket, job 확인 서버 listen은 모든 target이 같이 쓰므로 그 오류는 스케일러 전체에 건다(R176, 0001 R60, R78). 서명기는 App마다 하나이고 개인키 파일은 설정 검증이 읽고 파싱하므로(0001 Design, `internal/config`의 `ReadAppPrivateKey`) 읽지 못하는 키나 권한 비트가 틀린 키(0001 R30)는 시작 때 설정 오류로 서버 범위에 드러난다. App 자체의 인증이 거부되는 경우(App 삭제, 키 폐기)는 모든 target의 호출이 각자 영구 오류를 받아 target마다 target 오류 대기에 들어가고, 모두 들어가면 R197의 `status`가 된다. 이때도 target마다 다시 시도하므로, 원인이 GitHub 쪽에서 고쳐지면(App 권한 승인, 설치) 재시작 없이 돌아온다. 키 파일을 바꾼 경우는 설정을 다시 읽어야 하므로 재시작한다(설정은 시작 때 한 번 읽는다).
- 다시 시도(R174): 참고 구현은 target 하나의 오류에서 그 target만 스스로 다시 시도한다. runner-up은 세션이 끝나면 그 target의 scale set 확인부터 세션까지 30초 뒤 다시 하고, 찾을 수 없는(404) target은 30초에서 두 배씩 늘려 7번까지 다시 시도한 뒤 그 target만 멈춘다(확인함: runner-up 013cc74 `internal/coordinator/github.go` 202~210행, 238~266행, 272~289행 `serveSet`). ARC는 끝난 listener Pod를 지우고(확인함: ARC eca1a62 `controllers/actions.github.com/autoscalinglistener_controller.go` 529~531행, 984~991행 `listenerPodIsDead`), Pod가 없으면 새로 만든다(확인함: 같은 파일 559~583행). runscaler도 실행 중 listener 오류를 scale set마다 다시 연결한다(아래). 그래서 이 스케일러도 target 오류 대기에서 시작 단계를 다시 시도하고, 저장소 owner가 GitHub 쪽 원인(App 설치, 설치의 저장소 선택, 권한 승인)을 고치면 재시작 없이 그 target이 돌아오게 한다. runner-up은 404를 되풀이해 부를 때 "every try uses the sign-in's allowance, which every scale set and GitHub read shares: 29 sessions on one old name used it up for hours"라고 적는다(확인함: 같은 파일 232~235행). 그래서 간격을 30초에서 두 배씩 늘려 30분에서 멈춘다. 상한에서는 target 하나가 30분에 시도 한 번이고, 시도 한 번의 호출은 설치 조회 1번, 저장소 runner 목록의 페이지 수만큼, R241의 후보마다 `GetRunnerByName` 1번, scale set 조회 1번과 없을 때 생성 1번, 세션 생성 1번에 라이브러리의 토큰 교환을 더한 것이다. 시도 중 속도 제한 응답을 받으면 다음 시도는 R52가 정한 시각과 R174의 간격이 정한 시각 중 늦은 때에 한다. 시도 안에서 R24를 쓰지 않는 것(R193)은 일시 오류가 이어질 때 R24의 60초 상한 백오프가 R174의 30분 간격 안에서 끝없이 도는 것을 막기 위해서다. runner-up처럼 7번 뒤 멈추지 않는 것은 멈춘 target을 되살리려면 재시작이 필요해 다른 저장소의 job까지 신호 drain에 들게 하기 때문이다. 설정 오류는 0001 R47대로 다시 시도하지 않는다. 설정은 시작 때 한 번 읽기 때문이다(INTENT Problem). 서버 범위의 Docker 쪽 원인(Docker 준비, 노출, 이미지, 용량, listen)은 0001 R47대로 target 오류 대기와 같은 30초에서 30분까지의 간격으로 그 단계를 다시 시도한다. actions-runner-controller의 listener는 끝나서 Pod가 다시 만들어지고 runscaler는 launchd가 다시 띄우는 데 기대지만, 스케일러 안에서 다시 시도하면 그동안에도 `status`가 답한다(확인함: `internal/daemon`의 `retryStep` 주석).
- 참고 구현의 범위: runner-up은 target의 세션 오류가 다른 target의 세션을 멈추지 않는다(확인함: 위 `RunSet`, `Sessions.Match`의 세션마다 고루틴). ARC는 scale set마다 listener 프로세스 하나가 그 scale set 하나의 설정만 받는다(확인함: ARC eca1a62 `cmd/ghalistener/config/config.go` 37~40행, `cmd/ghalistener/main.go` 98~105행). runscaler는 실행 중 listener 오류를 scale set마다 5초에서 1분까지 늘리는 백오프로 다시 연결하지만(확인함: ysya_runscaler 6f33444 `cmd/runner/main.go` 733~760행), 한 scale set의 시작 단계 오류(scale set 생성 실패 등)는 모든 scale set을 멈춘다(확인함: 같은 파일 579~583행 `cancelRun()`, 642~645행). 이 스케일러는 시작 단계 오류도 target에만 거는 runner-up 쪽을 따른다. 한 저장소의 App 설치나 권한 문제로 다른 저장소의 job이 멈추지 않게 하는 것이 INTENT의 "a repository without it is reported as an error"와 첫 판의 "error handling per registration"을 지키는 것이기 때문이다.
- 신호(R178, R179): 신호 drain은 스케일러 전체에 걸리고 모든 target의 세션을 닫는다. target 오류 drain 중에 첫 신호를 받으면 그 target의 busy runner도 신호 drain으로 기다린다. 0001 R21이 오류 drain 중 신호에 기다리지 않은 것은 스케일러 전체가 이미 멈춘 경우였고, 이제는 다른 target의 job이 돌고 있으므로 그 job을 죽이지 않게 한다. 두 번째 신호는 R21대로 모든 target에서 기다리지 않는다. 신호 drain이 시작되면 target 오류 대기의 다시 시도는 멈추고, 진행 중인 시도는 호출을 취소해 세션을 만들지 않는다(R192). 신호 drain 중 target의 영구 오류는 0001 R100처럼 로그만 남기고 target 오류 drain으로 바꾸지 않는다(R191). 처음 시작 중인 target도 신호를 받으면 시작 단계를 멈춘다(R196).
- drain 끝의 정리: 신호 drain의 정리는 모든 target의 세션을 닫고 남은 runner를 지우며, 정리 시한(0001 R57의 최대 55초)은 target 수와 관계없이 하나를 같이 쓴다. target 오류 drain의 정리는 그 target의 세션과 runner에만 하고, R131의 `pending` 예외도 그 target의 runner 보고에만 적용한다. 0001 R55의 "오류 대기에 들어가기 전에 진행 중인 감시와 대조의 재시도를 멈춘다"는 그 target의 runner의 감시와 삭제 재시도만 멈추고, 30초마다의 대조(R42)는 runner 표 전체에 하나라 다른 target을 위해 계속한다(R190).

**시작 순서**: 서버 단계는 잠금(R78) → status socket(R60) → 설정 읽기와 검증 → Docker 준비(`docker.host`) → 정리(R16) → 설정 오류면 오류 대기(R28, R30, R105, R107, R231~R234) → Docker 노출 확인(R79) → 이미지 확인 → Docker 용량 확인(R201, R203, R202, R167, R204, R168의 경고 순) → job 확인 서버 listen이다. 여기까지의 실패는 스케일러 전체의 오류 대기이고, 설정 오류는 재시작을 기다리며 Docker 쪽 원인은 실패한 단계부터 다시 시도한다(R176). 그 뒤 target마다 고루틴 하나가 따로 설치 조회(R236~R238) → 정리(R241) → scale set(R239) → `SetSystemInfo` → 첫 세션 → listener를 진행한다(R177). target 단계의 일시 오류는 그 target 안에서 R24로 다시 시도하고, 영구 오류는 그 target만 target 오류 대기에 넣는다(R172). R241은 0001 R17처럼 시작을 막지 않는다. job 확인 서버를 target 단계 전에 여는 것은 어느 target이든 첫 세션 뒤 runner를 만들 수 있기 때문이다. 스케일러 상태는 어느 target이든 첫 세션을 만들면 `running`이 되고(R178), 그때 아직 시작 단계인 target의 줄은 `starting`이다. 첫 세션 전에 모든 target이 target 오류 대기에 들어가면 스케일러의 시작은 끝난 것으로 보고 R197의 `status`가 되며, target마다 R174대로 다시 시도한다(R195).

**개인 계정 저장소**: 개인 계정이 소유한 저장소도 조직 소유 저장소와 같은 저장소 target이다. 등록 URL, 설치 조회, runner 목록, 권한이 owner의 종류와 관계없이 같은 저장소 endpoint이므로 스케일러는 owner가 조직인지 개인 계정인지 가르지 않는다(확인함: 저장소 runner 목록 문서의 `owner`는 "The account owner of the repository", 2026-11-26 읽음. 설계: 구성 요소의 target과 설치 ID 조회). 그 저장소의 owner가 그 저장소에 App을 설치한다(INTENT Affected users and systems). 개인 계정 저장소의 runner group ID 1(Areas of concern 7)은 R250이 확인한다. 첫 판이 나중 일로 남긴 개인 계정 저장소 target은 이 판에서 따로 구현할 것 없이 저장소 target 하나로 들어온다.

**나중에 Linux로 옮길 때**: OS마다 다른 코드는 지금 `internal/service`와 `internal/status`에만 있다. `internal/service`는 `daemon_darwin.go`(launchd와 kqueue `EVFILT_PROC`로 종료 감시)와 `daemon_other.go`(`//go:build !darwin`)로, `internal/status`는 `peer_darwin.go`(`LOCAL_PEERPID`로 socket 상대 pid)와 `peer_other.go`(`//go:build !darwin`)로 나뉜다(확인함: 2026-11-26 `GOOS=darwin`과 `GOOS=linux`의 `go list -f '{{.ImportPath}} {{.GoFiles}}' ./...` 비교에서 두 패키지의 이 두 파일만 다름). Linux에서는 `_other.go` 자리에 `SO_PEERCRED`, pidfd나 `waitid`, systemd unit을 같은 작은 인터페이스(`status`의 `peerPID`, `service`의 `Daemon`, `ExitWatch`, 서비스 관리자) 뒤에 더한다. OS별 파일을 더하는 것은 막지 않고, R155가 Linux 빌드와 vet이 깨지지 않게 지킨다. 그 밖에 Linux에서 다를 수 있는 것은 Areas of concern 13이다. 잠금(`flock`), 상태 폴더(`~/.local/state/actions-runner-scaler`), Docker 기본 socket(`unix:///var/run/docker.sock`)은 같은 코드로 Linux에서도 빌드된다. - 판정 실제 시험의 기록: 0001의 `--record` 이미지 hook은 이벤트 파일에서 R126과 R127의 각 비교 결과(같음, 다름, 없음, null)만 기록하고 ID 값과 이름은 기록하지 않는다. 이 변경에서는 같은 저장소의 `pull_request`, `pull_request_target`, `workflow_run`을 하나씩 보고(비교 결과 `same`, 이벤트 파일 크기와 보고 시간도 기록), fork의 셋은 나중 시험인 R145~R147 때 본다.
- R253의 시험 job은 step 둘이다: `sleep 120`, 그리고 `busybox` 기반 이미지(압축 크기 10MB 이하)에 파일 하나를 더하는 Dockerfile의 push 없는 `docker buildx build`. 이 Mac의 Docker VM(10 CPU, 9.70 GiB = 약 9,932 MiB)에서 기본값의 서버 한도는 3이므로(설계: Docker 용량 확인), 시험 설정은 runner 하나의 몫을 줄인다: `runner.cpus = 0.5`, `runner.memory = "512m"`, `buildkit.cpus = 1`, `buildkit.memory = "768m"`. 몫은 1.5 CPU, 1,280 MiB이고 서버 한도는 min(floor(10 / 1.5) = 6, floor(9,932 / 1,280) = 7) = 6이다(추론: 계산. 실제 값은 R203의 로그로 본다). A의 `max-runners`는 3, B의 `max-runners`는 2다. 이 자원으로 이 빌드는 끝난다(확인함: 2026-11-26 이 Mac에서 측정. 0001의 컨테이너 옵션으로 rootless BuildKit 이미지 `moby/buildkit@sha256:7d02292556e66feea6d2d89b7ec143503b57e4f59a4efc6b7ece8547e4d3e5be`를 `--cpus 1 --memory 768m --memory-swap 768m`, runner 이미지를 `--cpus 0.5 --memory 512m --memory-swap 512m`, 둘만의 네트워크, `docker buildx create --driver remote`로 두고, `busybox:1.37`에 RUN step 하나를 더한 Dockerfile을 push 없이 빌드해 4초에 끝났고 두 컨테이너 모두 OOMKilled가 없었다. 약 2초마다 듬성듬성 잰 최대 메모리는 BuildKit 49.45 MiB, runner 컨테이너 33.08 MiB). 이 측정에서는 runner 자신의 프로세스(`Runner.Listener`, `Runner.Worker`)가 돌지 않았으므로, 첫 판의 R157 실제 실행(2026-11-26)에서 이 설정으로 5개 job이 모두 성공했다(확인함(근거: 0002 PLAN M17 결과, 첫 판 실제 실행 2026-11-26)). 메모리 부족으로 실패하면 몫의 합을 유지한 채 나누기를 바꾼다(예: `runner.memory = "768m"`, `buildkit.memory = "512m"`). 그동안 `docker stats`로 본 실제 사용량을 기록한다. R248~R252, R255~R257, R270과 나중 시험인 R261~R263은 기본 자원 설정 그대로 이 Mac에서 서버 한도 3으로 한다.
- R163의 관찰: `gh run view --json jobs`의 job 목록과 스케일러 로그의 그 job ID의 `JobStarted`, `JobCompleted` 로그를 대조한다. 판정이 `JobStarted`에 기대지 않으므로 메시지를 잃어도 job 실패로는 드러나지 않고 이 대조로만 드러난다.

## Open questions from the intent

- 이 Mac(Docker VM 10 CPU, 9.70 GiB, 기본값의 서버 한도 3)에서 저장소마다의 최대와 서버 한도를 보이려면 runner 하나의 CPU·메모리 기본값과 시험 크기를 어떻게 하는가? → 답: 기본값은 바꾸지 않는다(runner 1 CPU·`1g`, BuildKit 2 CPU·`2g`, runner 하나의 몫 3 CPU·3 GiB). 이 Mac의 서버 한도는 3이다(확인함: 2026-11-26 스케일러 시작 로그 `server runner limit`의 `limit` 3). 저장소마다의 최대와 서버 한도는 기본 자원으로 본다: 최대의 합이 서버 한도와 같은 경우 A 1, B 2(R251), 합이 서버 한도보다 큰 경우 A 3, B 2(R252, R204의 INFO 줄). INTENT의 "5 deploy jobs from different repositories" 결과는 기본 한도 3으로 볼 수 없으므로, runner 하나의 몫을 1.5 CPU, 1,280 MiB로 줄인 시험 설정(서버 한도 6)에서 A 3, B 2로 본다(R253, R254, 설계: 테스트). INTENT의 예시 서버(60 코어, 128 GB)는 기본 몫으로 서버 한도가 min(floor(60 / 3) = 20, floor(128 / 3) = 42) = 20이라, repo1 5 + repo2 10 = 15개가 같은 때 돈다(추론: R201의 계산. 128 GB를 GiB로 읽어 119 GiB로 해도 메모리 쪽은 39라 20이 그대로다).
- 첫 판(조직 수준 등록)으로 통과한 실제 시험 중 저장소 등록으로 다시 할 것은? → 답: 등록, 정리, 동시 실행, 저장소 사이의 한도와 기다림, 삭제는 다시 하거나 새로 한다(R248~R257, R259, R270). 판정(R141~R144)과 서비스 확인(R159~R162)은 등록 수준에 기대지 않으므로 PLAN이 그 코드를 바꾸지 않는 한 다시 하지 않는다. 다만 이 판이 시작 순서와 status 코드를 바꾸므로 R160은 한 번 다시 하고, R159의 다시 시작은 R255가 본다. 한 scale set 안의 자리 기다림과 재시작(첫 판의 R200, R223)은 기록으로 둔다(설계: 테스트의 "첫 판의 실제 시험 중 다시 하지 않는 것").
- 저장소가 대기(미리 시작한) runner를 둘 수 있는가, 그 runner는 저장소의 최대와 서버 한도에 어떻게 세는가? → 답: 둘 수 있다. 첫 판 그대로 target마다 `targets.idle`(0 이상 그 target의 `max-runners` 이하, 기본 0)을 두고, 대기 runner는 그 저장소의 runner 수(R3)와 모든 target의 runner 수 합(R114)에 함께 들어 그 저장소의 최대와 서버 한도를 함께 쓴다(0001 R1, R115). 모든 target의 `idle` 합이 서버 한도보다 크면 오류 대기이고(R167), 같으면 시작 경고다(R168). 자리를 두고 겨루면 기다리는 job이 `idle` 채우기보다 먼저다(R187). 설계: `idle`의 자리.
- 서버가 찼을 때 여러 저장소의 기다리는 job은 어떤 순서로 자리를 받고, 최대에 닿은 저장소가 다른 저장소가 쓸 수 있는 서버 자리를 잡을 수 있는가? → 답: 모든 target에 걸쳐 배정 job 몫의 시작 요청이 idle 몫보다 먼저, 같은 종류 안에서는 요청이 생긴 순서로 받는다(R187, R252). 최대에 닿은 저장소는 자리를 잡지 않는다. GitHub는 그 scale set에 `maxCapacity`(그 저장소의 `max-runners`)까지만 배정하고 넘는 job에는 메시지를 보내지 않으므로(확인함(근거: 0002 PLAN M17 결과, 첫 판 실제 실행 2026-11-26)) 그 job은 그 target의 `TotalAssignedJobs`에 들지 않고, 목표는 `max-runners`를 넘지 않으며, 스케일러는 최대에 닿은 target을 건너뛰고 다른 target의 요청에 자리를 준다(R115, R247, R251). 순서는 스케일러가 받은 메시지 사이의 것이라, GitHub가 붙잡은 job이 다음 배정을 받기 전에 비는 자리는 다른 저장소의 늦은 job이 받을 수 있다(넘김: Areas of concern 18).

## Areas of concern

1. 판정은 hook이 보낸 이벤트 파일을 믿는다. runner가 hook handler 직전에 서버 job 메시지의 값으로 그 파일을 쓰고, hook이 job의 첫 pre-job step이며, hook 환경에 `GITHUB_EVENT_NAME`과 `GITHUB_EVENT_PATH`가 있고 workflow `env:`는 들어가지 않는다는 것은 확인했다(확인함: actions/runner v2.338.2 d1eb12d 소스, run-scripts 문서. 설계: 판정의 "이벤트 파일을 믿는 근거"). 남은 미확인은 셋이다. (1) 우리 runner 이미지의 실제 실행에서 그 파일에 R126, R127의 값이 오는지(비교 결과만 기록해 본다. 같은 저장소의 쌍은 R141~R144의 기록 시험에서 보고, fork의 쌍은 나중 시험인 R145~R147 때 보며 그때까지 미확인이다). (2) 우리 runner 이미지의 hook 환경에 `GITHUB_EVENT_NAME`과 `GITHUB_EVENT_PATH`가 실제로 있는지(R141~R144의 기록 이미지 시험에서 두 변수의 존재를 다시 본다). (3) runner를 올린 뒤에도 `WriteWebhookPayload`가 hook handler 전에 불리고 hook이 첫 pre-job step인지. runner 버전을 올릴 때마다 위 소스 위치를 다시 본다. Owner: 사용자.
2. 이벤트 파일의 fork 경우 값: 다음은 미확인이고 나중 시험인 R145~R147의 실제 실행으로 본다(Design 테스트의 나중으로 미룬 실제 시험. 그때까지 미확인이다). (1) fork PR의 `pull_request`와 `pull_request_target` 이벤트 파일에 `pull_request.head.repo.id`와 `pull_request.base.repo.id`가 모두 오고 서로 다른지. (2) fork PR의 run이 일으킨 `workflow_run`의 `workflow_run.head_repository.id`가 fork의 ID인지. (3) `pull_request_target`(fork PR)의 run이 일으킨 `workflow_run`은 그 run이 기본 브랜치에서 돌았으므로 `head_repository`가 base 저장소여서 R127을 통과할 수 있다(추론: actions/checkout f548e57 `unsafe-pr-checkout-helper.ts`의 주석). 통과하면 fork의 입력이 `pull_request_target` run의 artifact를 거쳐 우리 runner에 닿는다. (4) 지운 fork의 `head.repo`가 null로 오는지(낮은 우선순위. null은 거부되므로 안전한 쪽이다). (5) runner는 수를 double로 들고 있다가 직렬화하므로(확인함: actions/runner v2.338.2 `NumberContextData.cs`) 2^53을 넘는 ID는 이벤트 파일에서 정밀도를 잃어 서로 다른 ID가 같게 쓰일 수 있다. 이 저장소의 ID는 10자리 수이고(확인함: 2026-11-25 `gh api repos/<owner>/<repo>`의 `id` 자릿수) 2^53은 9,007,199,254,740,992(16자리)다. 다른 저장소의 ID가 2^53에 닿는지는 미확인이다. 관찰이 R126~R128의 가정과 다르면 SPEC을 고친다. Owner: 사용자.
3. 공개 저장소에서 쓰기 권한이 없는 사람이 일으키는 job(결정: 2026-11-26, 사용자, GitHub 설정에 맡김). 스케일러는 fork PR(R126, R127) 밖에서 job을 일으킨 사람의 권한으로 거부하지 않는다. ARC와 terraform-aws-github-runner에도 그런 코드는 없다(확인함: ARC eca1a62와 terraform-aws-github-runner 클론의 grep). GitHub는 "self-hosted runners should almost never be used for public repositories on GitHub"라고 적는다(확인함: https://docs.github.com/en/actions/reference/security/secure-use). 이 위험을 줄이는 GitHub 쪽 설정은 다음과 같다. 조직 runner group의 공개 저장소 허용은 기본으로 꺼져 있지만(확인함: https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/manage-access "By default, only private repositories can access runners in a runner group"), 저장소 수준 runner에는 group이 걸리지 않는다고 보므로(추론, 설계: runner group) 이 판에서는 그 기본값이 공개 저장소를 막지 않고, 공개 저장소에 이 runner를 둘지는 설정에 그 저장소를 적는 사용자가 정한다. fork PR의 workflow run은 쓰기 권한이 있는 maintainer의 승인을 요구하게 할 수 있다(확인함: https://docs.github.com/en/actions/how-tos/manage-workflow-runs/approve-runs-from-forks "Workflow runs triggered by a contributor's pull request from a fork may require manual approval"). Actions 정책의 workflow execution protections는 actor rule(누가)과 event rule(어떤 이벤트)로 run을 막는다(확인함: https://docs.github.com/en/organizations/managing-organization-settings/actions-policies/workflow-execution-protections "Event rules control which events are permitted, such as `push`, `pull_request`, `pull_request_target`, and `workflow_dispatch`."). 그 문서는 공개 저장소의 `pull_request_target`을 막는 기본 정책이 2026-12-02부터 적용된다고 적는다(확인함: 같은 문서). 그 기능을 Free plan 조직이 쓸 수 있는지는 문서에 없다(미확인). 이 결정 아래 열린 경로는 다음과 같다. (a) fork PR에 단 `issue_comment`(`/deploy` 같은 ChatOps)로 PR head를 checkout하는 workflow: payload에는 `issue.pull_request`의 URL만 있고 head 저장소가 없어(확인함: github/rest-api-description c9c95fe의 issue comment webhook 스키마) 이벤트 파일로 가를 수 없다. (b) 두 단계 `workflow_run` 연쇄: fork PR → GitHub 호스팅 runner의 run A → A가 일으킨, 기본 브랜치에서 도는 run B → B가 일으킨 run C. C의 `workflow_run`은 B이고 B의 `head_repository`는 base 저장소라 R127을 통과하며(추론), C가 A의 artifact를 내려받으면 fork의 내용이 우리 runner에서 쓰인다. (c) 같은 저장소 PR에 외부인이 남긴 `pull_request_review`: head와 base가 같아 허용되고, 리뷰 본문은 외부인이 정한다. (d) `watch`, `fork`, `discussion_comment`: 누구나 일으킬 수 있고 기본 브랜치의 workflow가 돈다(추론: events-that-trigger-workflows의 각 활동과 공개 저장소의 기본 권한). 일으킨 사람의 쓰기 권한은 `author_association`으로 정할 수 없고(그 값은 관계를 나타냄. 확인함: OpenAPI `author-association` enum, GraphQL `CommentAuthorAssociation` 설명) 정확히 보려면 REST 협업자 권한 조회(`GET /repos/{owner}/{repo}/collaborators/{username}/permission`)가 필요하다. 이 설계는 그 조회를 하지 않는다(R123). 그래서 INTENT가 자격 노출을 받아들인 이유 중 "쓰기 권한이 있는 사람만 fork가 아닌 job을 시작한다"는 공개 저장소에서는 위 경로에서 맞지 않는다. Owner: 사용자 (결정: GitHub 설정에 맡김).
4. 0001의 최신 run 조건(0001 판정 8)과 `allowed-events` 제한(0001 판정 3, `push`, `workflow_dispatch`, `schedule`만 허용해 `pull_request_target`과 `workflow_run`을 막음)이 이 변경에서 빠진다. 그 결과 다음이 허용된다. (1) 쓰기 권한이 있는 사람의 옛 main run 재실행: 재실행은 원래 커밋 SHA와 ref로 30일까지 된다(확인함: 0001 Areas of concern 19에 인용한 re-run 문서). main ref이므로 관리자 신뢰 정책의 main 조건을 통과해 AWS Role을 받고 옛 코드를 배포할 수 있다(추론. 신뢰 정책이 옛 커밋을 가르는지는 미확인, 0001 Areas of concern 19 (6)). (2) 같은 저장소의 `pull_request_target`과 `workflow_run`: 기본 브랜치 ref로 돈다(확인함: 설계 판정의 이벤트 파일로 판정하는 이유). 기본 브랜치가 main이면 그 run이 Role을 받는지는 신뢰 정책의 subject 조건에 달렸다(미확인). 최신 run 조건을 되살리려면 같은 workflow의 다른 run을 REST로 조회해야 하는데, 그 값은 이벤트 파일에도 `JobStarted`에도 없어(추론) "판정하려고 GitHub에 요청을 보내지 않는다"(R123)와 맞지 않는다. 선택지(사실만 적음): (a) 받아들인다. (b) REST 조회를 되살리고 R123을 바꾼다. 0001처럼 Actions 읽기 권한, job마다의 조회, 조회 실패 거부(0001 R65), 속도 제한이 다시 생긴다. 이벤트 제한만은 보고된 이벤트 이름으로 REST 없이 할 수 있지만, 서버 전체에 목록 하나라 "fork pull request만 거부" 결정과 INTENT의 "어느 브랜치, pull request, 수동 실행이든 돈다"를 좁힌다. (c) GitHub 쪽 통제: workflow execution protections의 event rule로 저장소별로 `pull_request_target`, `workflow_run`을 막는다(확인함: Areas of concern 3의 문서. Free plan에서 되는지는 미확인). environment 보호 규칙(필수 검토자)은 `environment:` job이 INTENT 범위 밖이라(OIDC subject가 달라짐) 이 변경에서는 쓰지 못한다. 재실행 자체를 막는 GitHub 설정은 찾지 못했다(미확인). 다른 스케일러도 재실행이나 이벤트 종류로 막지 않는다. runner-up은 fork에서 온 job만 거부하고 "It allows every other job from the repository itself"라고 적으며, 재실행은 "Rerunning a failed job is left to GitHub and the repository"라고 적는다(확인함: runner-up 013cc74 `README.md` "Pull requests from forks" 절, `VISION.md`). ARC(eca1a62)는 이벤트 이름을 지표 라벨에만, elastic-fruit-runner(bcb9c8e)는 실행 기록에만 쓰고, runscaler(6f33444)와 runpool(f1a2ab3)에는 관련 코드가 없다(확인함: 각 클론의 grep). Owner: 사용자 (결정: (a) 받아들임. 쓰기 권한이 있는 사람의 재실행과 같은 저장소의 `pull_request_target`, `workflow_run`은 허용되고, 배포 통제는 저장소 쓰기 권한과 관리자 신뢰 정책에 맡긴다).
5. App 설치와 권한: 저장소마다 그 owner가 App을 설치하고(조직 설치가 저장소를 골라 설치했으면 그 저장소가 선택에 들어야 한다) Repository permission "Administration: Read and write"를 승인한다. 이 권한으로 scale set 생성, 세션, JIT 발급, runner 제거가 되는 것은 0001에서 조직 소유 저장소 하나로 확인했고(확인함: 0001 SPEC Design, 2026-11-20 App 시험), 개인 계정 저장소에서도 같은지는 R250에서 본다. App이 설치되지 않은 저장소에 대한 `GET /repos/{owner}/{repo}/installation`의 404는 문서에 있고(확인함: apps 문서의 응답 코드 200, 301, 404, 2026-11-26 읽음) 실제 응답 코드는 R257에서 기록한다. 조직 설치의 저장소 선택에서 빠진 저장소도 404인지는 미확인이다. 301은 저장소 이름이 바뀌거나 옮겨진 경우로 보이고(추론) 스케일러의 HTTP 클라이언트가 따라가 새 저장소의 설치를 받을 수 있지만(추론: 설계 설치 ID 조회), 등록 URL은 설정의 옛 URL 그대로라 그 등록이 되는지는 미확인이다. 저장소를 옮기면 옛 URL이 설정에 있는 채로 `delete-scaleset`으로 옛 scale set을 지운 뒤 설정의 URL을 새 이름으로 고친다(README에 적는다). 저장소 runner 목록의 `name` query가 정확히 일치하는 runner만 돌려주는지는 문서에 없다(미확인, 결과에서 이름을 다시 비교함). Owner: 사용자.
6. 쓰지 않게 된 App 권한: 이 판의 스케일러와 `delete-scaleset`은 Organization permission "Self-hosted runners: Read and write"와 Repository permission "Actions: Read"(0001의 run 조회용)를 쓰지 않는다(설계: App 권한). 두 권한을 App에서 뺄지는 사용자가 나중에 정한다. 빼면 그 App을 설치한 다른 곳에도 영향이 있다. Owner: 사용자.
7. 저장소 scale set의 runner group: 스케일러는 저장소 scale set을 runner group ID 1에 둔다(R239). 조직 소유 저장소에서 ID 1이 되는 것은 0001의 실제 실행에서 확인했다(확인함: 0001 SPEC Design 스케일링 흐름 1, 2026-11-20 시험). 개인 계정 소유 저장소에서도 ID 1이 쓰이는지는 미확인이다(actions-scaleset 스킬 references/runtime.md 1절). R250에서 확인하고, 그 저장소의 scale set 조회나 생성이 실패하면 그 target만 target 오류 대기에 들어간다(R172). 그때는 `GetRunnerGroupByName("default")`로 ID를 찾는 방식(같은 스킬 문서의 대안)으로 SPEC을 고친다. 저장소 수준 runner에는 조직 runner group의 저장소 접근과 공개 저장소 허용이 걸리지 않는다고 본다(추론, 설계: runner group). 그래서 어느 저장소가 이 runner를 쓰는지는 설정의 `[[targets]]`가 정한다. Owner: 사용자.
8. runner 이름: 이름은 `<label>-` 뒤 소문자 16진수 8자 임의값이다. 이미 있는 이름으로 JIT를 발급하면 구별할 수 있는 오류로 실패한다(확인함: actions/scaleset v0.5.0 `errors.go` 24행 `RunnerExistsError = scalesetError("runner exists")`, 237~238행이 서비스의 `AgentExistsException`을 이 오류로 바꿈). ARC는 이 오류에서 기존 runner가 같은 scale set이면 지우고 다시 시도하고, 아니면 "runner with the same name but doesn't belong to this RunnerScaleSet"으로 실패한다(확인함: ARC eca1a62 `controllers/actions.github.com/ephemeralrunner_controller.go` 859~893행). 그래서 이름은 scale set 하나를 넘어 겹친다(추론: ARC의 처리). 유일성의 범위(저장소, owner, 그보다 넓은 범위)는 문서에 없다(미확인). 겹쳐서 JIT 발급이 실패하면 R64의 시작 실패로 세고 다음 poll에 새 이름으로 다시 시도한다. 저장소에 같은 꼴 이름의 다른 runner가 있어도 R241은 scale set ID가 다르면 지우지 않는다. 실제 실행에서 겹친 이름의 JIT 발급 결과를 볼지 정한다. Owner: 사용자.
9. fork PR이 잇달아 오면 job마다 runner 자리 하나를 거부될 때까지 쓴다(판정 1초 안, R131. 거부 뒤 컨테이너가 없어질 때까지 최대 40초, R145). 공개 저장소에서는 누구나 fork PR을 열 수 있으므로, 그동안 다른 저장소의 job이 GitHub 큐에서 기다릴 수 있다(가용성). GitHub의 fork run 승인 설정(Areas of concern 3)을 켜면 승인 전에는 job이 runner에 오지 않으므로 줄어든다. Owner: 사용자.
10. 시험 저장소와 계정(결정: 2026-11-26, 사용자): R248~R257, R270의 A, B, C(R255)는 첫 판의 실제 시험에서 만든 조직의 임시 시험 저장소를 다시 쓴다. P(R250)는 사용자의 개인 계정에 새로 만드는 임시 비공개 저장소이고, 사용자가 GitHub에서 그 저장소에 App 설치를 승인한다. D(R257)는 같은 개인 계정의 둘째 임시 비공개 저장소로, App 설치의 저장소 선택에 넣지 않는다(그 응답 코드는 Areas of concern 5). P와 D는 시험 뒤 지운다. 각 저장소의 main에 시험 workflow를 쓰고 시험 뒤 지우는 것은 실제 시험의 일이다. 나중 시험인 R145~R147은 판정 시험 저장소에 접근 권한이 있는 다른 계정의 fork(비공개 저장소면 조직의 "Allow forking of private repositories" 정책도)나 공개 시험 저장소의 fork, 그리고 그 fork의 pull request가 필요하다(Design 테스트). 공개 저장소에서 R146을 하려면 2026-12-02 뒤에는 `pull_request_target`을 허용하는 event 정책이 필요하다(Areas of concern 3의 문서). 나중 시험인 R261, R262는 A를 App 설치에서 뺐다가 다시 넣으므로 그 owner의 일이다. 다시 설치하면 설치 ID가 바뀔 수 있으나 스케일러는 시작과 다시 시도 때 조회하므로(R236, R193) 설정은 바뀌지 않는다(추론: 설치 ID를 설정에 두지 않음). Owner: 사용자.
11. 서비스 무응답 감지(R153, R162): 2분 시한은 라이브러리의 poll 시한과 같고, 건강한 서버가 빈 poll을 약 50.3초 붙잡는 0001의 관찰(18번)보다 넉넉하다. 첫 판의 R162는 통과했다(확인함(근거: 0002 PLAN M17 결과, 첫 판 실제 실행 2026-11-26)). 서버가 붙잡는 시간을 2분 넘게 늘리면 poll마다 세션을 다시 만들게 된다(로그로 드러남). 실제 실행에서 "연결은 되지만 답하지 않는" 상태를 만드는 방법(호스트 방화벽 규칙으로 응답 패킷을 버림, 가로채는 프록시 등)은 이 Mac의 설정을 바꾸므로 사용자가 정한다. 연결 자체를 막으면 poll이 바로 연결 오류로 끝나 이 시한의 경로를 시험하지 못한다. Owner: 사용자.
12. 서버 자리를 기다리는 배정 job과 설치 변경에서 남은 미확인은 셋이다. (1) 다시 배정의 횟수와 그 뒤: target들의 `max-runners` 합은 서버 한도를 넘을 수 있으므로(R204) GitHub가 `maxCapacity`만큼 스스로 배정한 job이 서버 한도 때문에 runner 없이 기다릴 수 있다(확인함(근거: 0002 PLAN M17 결과, 첫 판 실제 실행 2026-11-26), GitHub가 `maxCapacity`까지 바로 배정함). 그 job은 약 5분 뒤 새 `JobID`로 다시 배정됐고 배정 취소 메시지는 없었으며, 첫 판의 스케일러에서 그 job은 자리를 지켜 runner를 받았다(확인함(근거: 같은 M17 결과, 첫 판의 R200)). 지금의 스케일러에서는 다시 배정된 job도 `TotalAssignedJobs`에 남아 그 target의 job 요청이 그대로다(설계: 자리 배치). 라이브러리 README는 배정 취소가 "up to 3 times with incremental delays"라고 적는다(확인함: actions/scaleset v0.5.0 `README.md` 116행). GitHub 문서는 "After 24 hours the GitHub Actions Service unassigns the job if no runner accepts it"(확인함: GitHub 문서 "About Actions Runner Controller")와, self-hosted job이 "can be in the queue for 24 hours before it is automatically cancelled"(확인함: GitHub Actions limits 문서)를 적는다. 셋째 다시 배정 뒤 job이 실패하는지 큐에 남는지는 문서에 없다(미확인). 실패한다면 INTENT의 "wait and start when a runner slot frees up"과 맞지 않으므로 나중 시험 R263이 기록하고, 넷째 job이 실패하거나 취소되면 SPEC을 runpool처럼 알리는 `maxCapacity`를 남은 자리에 맞춰 낮추는 방식으로 바꾼다(확인함: runpool `internal/allocator/allocator.go` 190~194행, 설계: 고르지 않은 방법 (1)). R263이 통과하면 지금 방식을 유지한다. GitHub가 scale set들의 `maxCapacity` 합이 서버 한도를 넘을 때 배정을 줄이는지도 미확인이다(서버 한도는 GitHub가 모른다). 신호 drain 중에도 세션은 `maxCapacity`로 `max-runners`를 보내므로(R116) 그동안 GitHub가 배정한 job은 runner 없이 재시작을 넘어 다시 배정될 수 있다(추론: 위 관찰). drain 중 `maxCapacity`를 0으로 낮추면 배정이 보이지 않게 되므로 이 효과를 받아들인다(0001 R90의 이유, actions/scaleset 이슈 #133). (2) 다시 배정과 통계: 목표는 `TotalAssignedJobs`가 배정되어 기다리거나 도는 job의 합이라는 뜻(actions-scaleset 스킬 references/runtime.md 4절, 라이브러리 README)에 기댄다. 배정 취소와 다시 배정 사이의 한 메시지에서 그 값이 job 하나를 빼고 세면 그동안 그 target의 job 요청이 하나 줄 수 있다(추론). 실제 값은 R263의 로그(INFO `desired runners`의 `assignedJobs`)로 본다. (3) App 설치에서 저장소를 뺀 뒤 그 target의 호출이 영구 오류를 받기까지의 시간(R261): 설치 access token은 1시간 뒤 만료된다(확인함: https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app "The installation access token will expire after 1 hour."). 설치를 일시 중지하거나 지우면 App이 그 계정의 자원에 접근하지 못한다고 문서는 적지만(확인함: github/docs 8b038c5 `content/apps/maintaining-github-apps/suspending-a-github-app-installation.md`, `content/apps/using-github-apps/reviewing-and-modifying-installed-github-apps.md`), 이미 발급된 토큰이 바로 폐기되는지, 저장소 선택에서 뺀 저장소에 그 토큰이 바로 쓰이지 않게 되는지는 적지 않는다(미확인). 그래서 늦어도 토큰 만료 뒤 첫 갱신에서 오류가 날 것으로 보고(추론) R261의 관찰을 70분으로 끊는다. 그 안에 `error-wait`가 되지 않으면 그 기록으로 R171의 감지 방법을 SPEC에서 다시 정한다. 그동안 그 target은 `running`으로 보이며 새 job의 runner 시작이 R64의 시작 실패로 세어질 수 있다(추론). R261, R262는 나중 시험이므로 그때까지 미확인이고, 이 변경에서는 가짜 클라이언트 시험으로만 확인한다. R261~R263은 나중 시험이고 이 변경의 완료 조건이 아니다(결정: 2026-11-26, 사용자). 그래서 완료 때 target들의 `max-runners` 합이 서버 한도(이 Mac에서 3)를 넘는 설정에서 배정 job이 약 5분을 넘어 자리를 기다리는 경우의 결과, 설치에서 저장소를 뺀 뒤의 감지 시간과 다시 넣은 뒤의 복귀는 미확인으로 남는다. Owner: 사용자 (결정: 나중 시험).

15. App JWT로 부르는 호출(설치 조회 R236, 라이브러리의 설치 토큰 교환)이 설치와 관계없이 App 전체의 속도 제한 하나를 같이 쓰는지는 미확인이다. 속도 제한 문서는 JWT로 부르는 요청을 다루지 않는다(확인함: github/docs 8b038c5의 content/rest, content/apps, data/reusables에서 찾음). 그래서 설치 조회의 R52 대기를 서버에 하나 둔다(R189). 설치 조회는 저장소 target마다 하므로 시작 때와 R174의 시도마다 target 수만큼 부른다. 라이브러리 안의 토큰 교환은 0001처럼 라이브러리의 재시도를 따르고 우리 대기에 들어가지 않는다(0001 Design 재시도 규칙). 설치 토큰으로 부르는 GitHub REST 호출(저장소 runner 목록과 이름 조회, 라이브러리의 등록 토큰 요청)의 한도는 설치마다 따로다(확인함: 설계 공유 자원). 그래서 우리 REST 호출의 대기는 설치마다 하나다(R266). scale set, 세션, `AcquireJobs`, JIT 발급, `GetRunnerByName`, `RemoveRunner`는 REST가 아니라 `/actions/runner-registration`의 관리 연결 토큰으로 Actions 서비스를 부른다(확인함: actions/scaleset v0.5.0 `client.go` 766, 824~826, 858~860, 977~1032행). Actions 서비스의 속도 제한이 설치마다인지, scale set마다인지, App 전체인지는 문서에 없다(미확인). 그래서 그 대기는 target마다, 호출 종류마다 둔다(R265). 같은 설치의 여러 target이 한 한도를 같이 쓴다면, 한 target의 속도 제한 응답 뒤에 다른 target도 각자 응답을 받고 각자 기다린다(추론). 실제 시험에서 속도 제한 응답이 오면 그 응답의 상태 코드, `x-ratelimit-resource`(있으면), 어느 호출(JWT 호출, REST 호출, Actions 서비스 호출)이고 어느 target과 설치의 호출이었는지를 기록한다. Owner: 사용자.
16. 첫 판의 조직 수준 scale set: 첫 판이 만든 조직 수준 scale set `linux-arm64-deploy`(scale set ID 1)는 지웠다(확인함: 2026-11-26 `delete-scaleset` 출력 "scale set 삭제됨: linux-arm64-deploy (ID 1), runner 등록 0개 제거". 그 전 조직 runner 목록은 0개). 그래서 같은 이름의 scale set이 조직 수준과 저장소 수준에 함께 있는 경우는 이 스케일러로는 생기지 않는다. 남은 위험: 누군가 같은 조직에 같은 라벨의 조직 수준 runner나 scale set을 따로 만들면, 저장소 URL의 `GetRunnerScaleSet(1, label)` 결과와 그 라벨 job의 배정이 어떻게 되는지는 미확인이다(두 scale set을 모두 돌려주면 라이브러리가 "multiple runner scale sets found with name" 오류를 내고, 확인함: actions/scaleset v0.5.0 `client.go` 455~461행, 이는 영구 오류라 같은 조직의 저장소 target이 target 오류 대기에 들어간다, R172). 이 스케일러는 조직 수준 scale set을 지우는 명령을 두지 않는다(R244 dropped). 18. 저장소 사이의 순서의 한계(R187): 순서는 스케일러가 받은 메시지 사이에서만 지켜진다. 저장소 A의 job이 A의 `maxCapacity`를 넘어 GitHub 쪽에서 기다리는 동안 A의 job 하나가 끝나면, GitHub가 기다리던 A의 job을 배정하기 전에 서버 자리가 비어 다른 저장소 B의 더 늦은 배정 job이 그 자리를 먼저 받을 수 있다. job을 잃거나 상한을 넘지는 않고, A의 job은 다음 빈 자리를 기다린다. 첫 판의 2026-11-26 관찰에서는 다음 배정(15:47:49)이 자리 비움(15:47:50)보다 먼저 왔으나(확인함(근거: 0002 PLAN M17 결과, 첫 판 실제 실행 2026-11-26)) 이 순서가 늘 같은지는 미확인이다. runner-up처럼 `maxCapacity`를 서버 한도보다 큰 고정값으로 알리면 이 경합은 없지만, 저장소마다의 최대를 GitHub 쪽에서 걸 수 없어 INTENT의 저장소별 최대와 맞지 않는다(확인함: runner-up 013cc74 `internal/config/config.go` 86~90행). runscaler도 scale set마다 자기 `max-runners`를 알리고 도착 순으로 자리를 주므로 같은 경합이 있다(추론: ysya_runscaler 6f33444 `cmd/runner/main.go` 907~911행, `internal/capacity/broker.go`). R252는 이미 배정된 두 job 사이의 순서만 본다. Owner: 사용자 (결정: 2026-11-26, 사용자, 지금 방식 유지. 알리는 `maxCapacity`는 target의 `max-runners` 그대로).

19. 같은 owner의 저장소 scale set 이름: 모든 target은 runner group ID 1에 이름이 `scaling.label`인 scale set을 둔다(R239). scale set 이름은 runner group 안에서 유일해야 하고(확인함: deploy-runner-scale-sets 문서, actions/scaleset v0.5.0 `client.go` 575행 "runner scale set names must be unique within a runner group"), 같은 owner의 두 저장소가 group ID 1에 같은 이름의 scale set을 따로 가질 수 있는지는 추론일 뿐이다(설계: 같은 이름의 scale set). 0001은 저장소 하나만 등록했다. 안 되면 둘째 저장소의 scale set 생성이 실패해 그 target이 target 오류 대기에 들어간다(R172). 대안: scale set 이름을 저장소마다 다르게(예: `<label>-<repo>`나 짧은 hash를 붙임) 하고 `Labels`는 `<label>` 하나로 둔다. `RunnerScaleSet`은 `Name`과 따로 `Labels []Label`을 가지고(확인함: v0.5.0 `types.go` 81~91행, `Label`은 64~67행의 `Type`, `Name`), 생성 때 `Labels`가 비었을 때만 이름을 라벨로 채운다(확인함: `client.go` 562~573행 `ensureLabels`). `runs-on`이 scale set 이름이 아니라 `Labels`에 맞춰지는지는 미확인이다(0001은 이름과 라벨이 같아 가를 수 없었다). 라벨을 나중에 바꾸는 `UpdateRunnerScaleSet`은 반영되지 않는다는 보고가 있으므로(actions-scaleset 스킬, 이슈 #140) 이름을 바꾸면 새로 만든다. 그래서 PLAN의 첫 실제 확인은 코드를 바꾸기 전에 한 owner 아래 두 저장소에 같은 이름의 저장소 scale set을 등록해 보는 것으로 한다(실패하면 이 대안으로 SPEC을 고친다). Owner: 사용자.
