# Spec: 조직 공용 runner 서버

From: INTENT.md (dewevrei, 4030890). Status: accepted.
Skills applied: actions-scaleset
Extends: 0001

## Requirements

설정과 target (R105~R107)
- R105. 설정에 `[[targets]]`가 하나도 없으면 R28과 같이 오류 대기에 들어가고, target이 1개 이상 필요하다는 것과 받은 개수(0)를 마지막 오류와 로그에 남긴다. target 수의 상한은 없다(R68을 대체).
- R106. `targets.url`이 `https://github.com/<조직>` 꼴(경로 조각 하나, 끝 `/`와 `.git` 없음)이 아니면 R28과 같이 오류 대기에 들어간다.
- R107. 설정 파일에 `[[pools]]`나 `github.app-installation-id`가 있으면 R28과 같이 오류 대기에 들어가고, 그 키마다 0001 형식의 키라는 것과 대신 쓸 키를 적은 오류를 보인다(Design 설정 파일의 문구).

GitHub 등록 (R108~R113)
- R108. 스케일러는 시작할 때 target마다 App JWT로 `GET /orgs/{org}/installation`을 불러 설치 ID를 얻고, 그 target의 scale set 클라이언트와 REST 클라이언트는 그 설치 ID를 쓴다. 이 호출은 target의 시작 단계 호출로, 일시 오류는 R24로 다시 시도하고(R24의 시작 단계 호출 목록에 더한다) 영구 오류는 R172를 따른다.
- R109. R108의 응답이 404면 그 target은 target 오류 대기(R172)에 들어가고, 그 target의 마지막 오류에 `GitHub App is not installed on organization <org>`를 보인다.
- R110. R108 응답의 `permissions.organization_self_hosted_runners`가 `write`가 아니면 그 target은 target 오류 대기(R172)에 들어가고, 빠진 권한 이름(`organization_self_hosted_runners: write`)과 조직 이름을 그 target의 마지막 오류에 보인다.
- R111. `targets.runner-group`이 비어 있으면 scale set을 runner group ID 1에 두고, 값이 있으면 `GetRunnerGroupByName`으로 찾은 group에 둔다. 그 이름의 group이 없으면 그 target은 target 오류 대기(R172)에 들어가고, 그 group 이름을 그 target의 마지막 오류에 보인다. 이 조회는 target의 시작 단계 호출로, 일시 오류는 R24로 다시 시도하고(R24의 목록에 더한다) 영구 오류는 R172를 따른다.
- R112. target마다 R111의 runner group에 이름이 `scaling.label`인 scale set이 없으면 만들고, 있으면 다시 쓴다. 종료해도 지우지 않는다(R22를 대체).
- R113. 스케일러가 만든 runner는 조직 수준에 등록되어, 실행 중에 조직 runner 목록(`GET /orgs/{org}/actions/runners`)에 그 이름으로 나타난다.

동시 실행 한도 (R114~R117)
- R114. 모든 target의 runner 컨테이너 수 합(끝난 runner 포함)은 서버 한도(R201)를 넘지 않는다(R3에 더한다. R3은 target마다 그 target의 `max-runners`로 성립한다).
- R115. target의 목표 runner 수는 `min(그 target의 max-runners, 그 target의 JobStarted를 받은 runner 수(R224) + 그 자리 배치에서 덮인 그 target의 entry 수 + 잠시 건너뛴 그 target의 entry 수(R213) + 그 target의 idle + 그 target의 목록에 없는 배정 job 수(R219))`이고, runner는 자리 배치(R184, R213, R214, R187)로만 시작한다(R1과 R2를 대체).
- R116. 스케일러는 target마다 그 target의 세션에서 poll마다 `maxCapacity`로 그 target의 `max-runners`를 보낸다. drain 중에도 같다(R90을 대체).
- R117. 그 job의 target의 runner 수가 그 target의 `max-runners`보다 적고 모든 target의 runner 수 합이 서버 한도보다 적고 대기 job 목록에 마지막 자리 배치에서 덮이지 않은(R213) 다른 entry가 없고 두 이미지가 로컬에 있을 때, 스케일러가 job의 첫 메시지(`JobAvailable` 또는 `JobAssigned`)를 받은 시각부터 GitHub job 기록의 `started_at`까지 60초를 넘지 않는다. R87의 경우는 뺀다(R4를 대체).

자원 제한과 Docker 용량 (R118~R122, R201~R204)
- R118. (dropped) runner 하나의 CPU 몫(`runner.cpus + buildkit.cpus`)은 두 키 각각보다 크므로 한 키가 `NCPU`보다 크면 서버 한도(R201)가 0이 되어 R202가 같은 경우를 오류 대기로 드러낸다. 키와 값은 R202의 오류로, `/info` 호출의 R24·R46 규칙은 R201로 옮겼다.
- R119. (dropped) 서버 한도(R201)가 모든 runner의 메모리 예약 합을 `MemTotal` 안에 두므로, 그 합이 `MemTotal`을 넘는 경우가 없어 경고할 일이 없다.
- R120. (dropped) 서버 한도(R201)가 모든 runner의 CPU 예약 합을 `NCPU` 안에 두므로, 그 합이 `NCPU`를 넘는 경우가 없어 경고할 일이 없다.
- R201. 스케일러는 시작할 때 Docker Engine API `/info` 응답 하나(`NCPU`, `MemTotal`)로 서버 한도를 `min(floor(NCPU / (runner.cpus + buildkit.cpus)), floor(MemTotal / (runner.memory + buildkit.memory)))`로 계산하고(CPU는 정수 NanoCPUs, 메모리는 바이트로 나눈다), 실행하는 동안 다시 계산하지 않는다. `/info` 호출은 시작 단계 호출로 R24와 R46을 따른다(두 목록에 더한다). Docker의 CPU나 메모리를 바꾼 값은 스케일러를 다시 시작한 뒤에 쓰인다.
- R202. R201의 서버 한도가 0이면(`runner.cpus`나 `buildkit.cpus` 하나가 `NCPU`보다 큰 경우 포함) 스케일러는 오류 대기에 들어가고, `NCPU`, `MemTotal`, runner 하나의 몫(`runner.cpus + buildkit.cpus`와 `runner.memory + buildkit.memory`), 그 몫을 이루는 네 키의 이름과 값을 마지막 오류에 보인다(문구는 Design Docker 용량 확인).
- R203. R201의 계산 뒤 스케일러는 시작 로그에 INFO `server runner limit` 한 줄을 서버 한도, `NCPU`, `MemTotal`, runner 하나의 CPU 몫과 메모리 몫과 함께 남긴다.
- R204. 모든 target의 `max-runners` 합이 서버 한도보다 크면 스케일러는 시작 로그에 INFO `max-runners of all targets exceed the server limit` 한 줄을 그 합, 서버 한도와 함께 남기고 계속 실행한다.
- R121. runner 컨테이너의 CPU, 메모리, 프로세스 수 제한은 `runner.cpus`, `runner.memory`, `runner.pids`와 같고, 메모리 스왑은 없다(R34를 대체).
- R122. BuildKit 컨테이너의 CPU, 메모리, 프로세스 수 제한은 `buildkit.cpus`, `buildkit.memory`, `buildkit.pids`와 같고, 메모리 스왑은 없다(R74를 대체).

판정: fork pull request 거부 (R123~R133)
- R123. 스케일러는 job 시작 hook이 보낸 이벤트 보고(이벤트 이름과 이벤트 파일 내용)만으로 판정을 내리고, 판정하려고 `JobStarted`를 기다리거나 GitHub에 요청을 보내지 않는다(R9를 대체하고 R65를 없앤다).
- R124. 끝까지 읽은 이벤트 보고의 본문이 JSON 객체 정확히 하나가 아니면(빈 본문, JSON이 아닌 본문, 배열 같은 객체 아닌 값, 객체 뒤에 공백 말고 다른 값이 더 있는 본문) 거부한다. 수는 정밀도를 잃지 않게 원래 표기대로 읽는다.
- R125. 이벤트 이름이 `^[a-z_]{1,64}$`에 맞지 않으면(빈 이름 포함) 거부한다.
- R126. 본문의 최상위 `pull_request`가 있고 null이 아니면, `pull_request.head.repo.id`, `pull_request.base.repo.id`, 최상위 `repository.id`가 모두 양의 정수(소수점과 지수가 없는 1 이상 2^63−1 이하의 수)이고 셋이 같을 때만 이 규칙을 통과한다. 그 밖에는(값이 없거나 null이거나 정수가 아니거나 서로 다르면) 거부한다. 이벤트 이름과 관계없이 적용한다.
- R127. 본문의 최상위 `workflow_run`이 있고 null이 아니면, `workflow_run.head_repository.id`, `workflow_run.repository.id`, 최상위 `repository.id`가 모두 R126의 양의 정수이고 셋이 같을 때만 이 규칙을 통과한다. 그 밖에는 거부한다. 이벤트 이름과 관계없이 적용한다.
- R128. 이벤트 이름이 `pull_request`, `pull_request_target`, `pull_request_review`, `pull_request_review_comment` 중 하나인데 최상위 `pull_request`가 없거나 null이면 거부하고, 이벤트 이름이 `workflow_run`인데 최상위 `workflow_run`이 없거나 null이면 거부한다.
- R129. R124~R128 중 어느 것으로도 거부되지 않은 보고는 허용한다. 판정은 `head.repo.fork`, 저장소의 `full_name`, `author_association`, 브랜치, ref, workflow 경로를 쓰지 않는다.
- R130. 거부할 때 스케일러는 0001의 로그 줄 `job denied; waiting for the runner to stop`에 runner 이름, 이벤트 이름, `reason`(Design 판정의 거부 사유 값)을 남기고, 본문에 `pull_request.head.repo.full_name`이나 `workflow_run.head_repository.full_name`이 문자열로 있으면 그 값을 `head_repo`로 더한다.
- R131. 토큰이 맞는 그 runner의 첫 이벤트 보고를 받으면, 스케일러는 본문을 다 읽은 때부터 1초 안에 판정을 기록하고 응답에 담는다. 예외로 drain 끝의 정리가 시작된 뒤 받은 보고는 판정하지 않고 `pending`을 돌려준다.
- R132. 판정이 기록된 runner의 뒤 이벤트 보고는 본문을 읽지 않고 기록된 판정을 돌려주며, 판정을 바꾸지 않는다.
- R133. 세션을 쓸 수 없는 동안(R25의 백오프, R54, R92)에도 스케일러는 이벤트 보고를 받으면 판정한다(R54와 R92의 "`JobStarted`를 받지 못해 R81로 지워진다"를 대체).

job 확인 서버와 hook (R134~R140)
- R134. job 확인 서버는 `POST /v1/event`의 본문을 읽기 전에 토큰을 검증하고, 실패하면 본문을 읽지 않고 바로 401을 돌려주며 판정과 그 runner의 busy 시각(R81)을 기록하지 않는다(R40을 `POST /v1/event`로 넓힌다).
- R135. `/v1/event`에 `POST`가 아닌 요청이 오면 job 확인 서버는 `Allow: POST` 헤더와 함께 405를 돌려주고, 판정과 busy 시각을 기록하지 않는다.
- R136. 토큰이 맞는 첫 이벤트 보고의 본문이 32MiB(33,554,432바이트)를 넘으면, job 확인 서버는 32MiB + 1바이트에서 읽기를 멈추고 거부(`reason` `payload-too-large`)를 기록한 뒤 413과 `{"verdict":"deny"}`를 돌려준다.
- R137. 32MiB 안에서 본문 읽기가 오류로 끝나면(연결이 닫힘, `Content-Length`보다 적게 옴, 읽기 시한), job 확인 서버는 판정하지 않고 아무것도 기록하지 않은 채 그 연결을 닫는다. 그 runner의 다음 보고는 R131의 첫 보고로 처리한다.
- R138. 토큰이 맞는 첫 `POST /v1/event`를 받은 때도 R81의 busy가 된 때의 후보다(R81의 busy 계기에 더한다).
- R139. job 시작 hook은 판정을 조회하기 전에, 자기 시작 때 환경의 `GITHUB_EVENT_NAME` 값과 `GITHUB_EVENT_PATH`가 가리키는 파일 내용을 `POST /v1/event`로 보낸다. 파일이 없거나 읽을 수 없으면 빈 본문을 보내고, `GITHUB_EVENT_NAME` 값이 `^[a-z_]{1,64}$`에 맞지 않으면 빈 이벤트 이름을 보낸다(R66의 "판정을 조회만 하고"를 대체).
- R140. hook은 `POST /v1/event`의 응답이 200이고 `verdict`가 `allow`나 `deny`면 R66대로 처리하고, 200의 `pending`, 200과 401 밖의 상태 코드(400, 405, 413, 5xx 등), 해석할 수 없는 응답이면 다시 보내지 않고 R66대로 `GET /v1/verdict`를 2초마다 조회하며, 연결 실패나 401이면 2초 쉬고 `POST /v1/event`를 다시 보낸다. 어느 경우에도 허용을 받지 않으면 0으로 끝나지 않는다.

실제 실행 확인: 판정 (R141~R147)
- R141. 조직 저장소의 main이 아닌 브랜치에서 시작한 job은 허용되어 모든 step이 돈다.
- R142. R141의 job에서 관리자 안내문의 Role을 OIDC로 받는 step은 실패한다(관리자 신뢰 정책의 결과를 실제 실행으로 확인한다).
- R143. 같은 저장소 main의 job은 조직 수준에 등록된 runner에서 GitHub OIDC로 관리자 안내문의 Role을 받아 안내문의 Namespace에서 Pod 목록 조회에 성공한다(0001 R8과 같은 확인. R142의 실패가 OIDC 경로의 고장이 아니라 신뢰 정책의 거부임을 가른다).
- R144. 같은 저장소의 브랜치에서 연 pull request의 `pull_request` 이벤트로 시작된 job은 허용되어 모든 step이 돈다.
- R145. fork에서 연 pull request의 `pull_request` 이벤트로 시작된 job은 "Set up job" 뒤 step이 `if: always()` step을 포함해 하나도 돌지 않고 실패로 끝나며, 판정부터 40초 안에 runner 컨테이너가 없어진다.
- R146. fork에서 연 pull request의 `pull_request_target` 이벤트로 시작된 job은 R145와 같이 끝난다.
- R147. fork에서 연 pull request의 run이 끝나 일으킨 `workflow_run` 이벤트의 job은 R145와 같이 끝난다.

정리와 명령 (R148~R152, R205, R222)
- R148. 스케일러는 시작할 때 target마다 조직 runner 목록(`GET /orgs/{org}/actions/runners`, 모든 페이지)에서, 이름이 `<scaling.label>-` 뒤에 소문자 16진수 정확히 8자가 붙은 꼴이고 `GetRunnerByName`의 `RunnerScaleSetID`가 그 target의 scale set ID와 같으며 살아 있는 runner 컨테이너가 없는 등록을 제거한다. 일시 오류와 영구 오류의 처리는 R17과 같다(R17을 대체).
- R149. R42의 대조는 끝난 runner는 빼고, 허용 판정이 없는 runner마다 조직 runner 목록을 그 이름으로 조회해(`GET /orgs/{org}/actions/runners?name=<runner 이름>`) 결과 중 이름이 정확히 같은 runner의 `busy`가 true면 그 runner를 busy로 표시한다. 조회가 실패하면 로그를 남기고 그 대조에서 그 runner를 건너뛴다(R103을 대체).
- R150. `delete-scaleset [-config <경로>] <target URL>` 명령은 설치 조회(R108)와 runner group 조회(R111)로 찾은 그 target의 scale set과 그 runner 등록을 지우고 0으로 끝난다(R23을 대체).
- R151. R150의 URL이 설정에 없거나, 설치 조회나 runner group 조회가 실패하면(R109, R110의 경우 포함) `delete-scaleset`은 아무것도 지우지 않고 오류를 stderr에 쓴 뒤 1로 끝난다.
- R152. `status` 명령은 `상태: 정상`과 `상태: drain 중`일 때 target 줄과 함께 `전체: 실행 중 <n>, 대기 <m>, 최대 <서버 한도>` 줄을 출력한다.
- R205. `status`의 target 줄은 `최대 <그 target의 max-runners>`를 보인다.
- R222. `status`의 target 줄은 `대기 job <n>`을, status JSON의 target 객체는 `waitingJobs`를 보이고, 두 값은 그 target의 entry 중 마지막 자리 배치에서 덮이지 않은(R213) entry 수다(배정 취소 표시가 있는 entry와 잠시 건너뛴 entry 포함).

서비스 응답 확인과 로그 (R153~R154, R221)
- R153. 마지막으로 서버가 답한 poll부터 5분이 지난 뒤의 끊지 않는 poll에는 70초 시한을 두고, 그 시한으로 끝나면 스케일러는 그 poll을 일시 오류로 보고 마지막 오류에 남긴 뒤 R25대로 새 세션을 만든다.
- R154. `GetMessage`가 속도 제한 오류로 끝날 때마다 스케일러는 WARN 로그 `message poll rate limited` 한 줄을 상태 코드와 다시 부를 수 있는 시각과 함께 남긴다.
- R221. target의 메시지의 `Statistics.TotalAvailableJobs`가 그 target의 entry 중 배정되지 않았거나 배정 취소 표시(R209)가 있는 entry 수보다 크면, 스케일러는 WARN `GitHub counts more available jobs than the scaler knows` 한 줄을 target URL, 그 값(`github`), 그 entry 수(`known`)와 함께 남기고 다른 동작은 바꾸지 않는다.

Linux 확장 준비 (R155)

대기 job 목록 (R206~R211, R225~R227)
- R206. 스케일러는 서버에 대기 job 목록 하나를 두고, 상태 `정상`인 target의 `JobAvailable`이나 `JobAssigned`를 받으면 그 메시지와 맞는 entry가 없을 때 그 job의 entry를 더한다. entry는 target, `RunnerRequestID`, workflow run ID, job 표시 이름, 배정 여부(`JobAssigned`면 배정됨), 마지막으로 받은 `JobID`, QueueTime(메시지의 `QueueTime`, 0이면 처음 본 시각), 처음 본 시각, 마지막으로 들은 시각(그 entry와 맞는 `JobAvailable`, `JobAssigned`, R209의 배정 취소를 마지막으로 반영한 시각), 배정 취소 표시를 가진다. 메시지와 entry가 맞는지는 같은 target 안에서, 둘의 `RunnerRequestID`가 모두 0이 아니면 그 값만 비교하고, 어느 한쪽이 0이면 workflow run ID와 job 표시 이름을 비교한다. `RunnerRequestID`가 0인 entry가 0이 아닌 값의 메시지와 맞으면 entry의 `RunnerRequestID`를 그 값으로 바꾼다. 한 메시지가 두 entry와 맞으면(하나는 `RunnerRequestID`로, 다른 하나는 `RunnerRequestID`가 0이라 workflow run ID와 job 표시 이름으로) `RunnerRequestID`로 맞은 entry만 그 메시지와 맞는 entry로 본다. R207~R209의 "맞는 entry"는 이렇게 맞는 entry다. 한 메시지 안에서는 `JobAvailable`, `JobAssigned`, `JobStarted`, `JobCompleted` 순으로 반영한다.
- R207. 맞는 entry가 있는 `JobAvailable`이나 `JobAssigned`를 받으면 스케일러는 새 entry를 만들지 않고, 그 entry의 QueueTime과 처음 본 시각을 그대로 두며 마지막으로 들은 시각을 바꾼다. `JobAssigned`면 그 entry를 배정된 것으로 하고 `JobID`를 그 메시지의 값으로 바꾸며 배정 취소 표시를 지운다. `JobAvailable`이 배정 취소 표시가 있는 entry에 오거나 비지 않은 `JobID`가 entry의 `JobID`와 다르면, 그 entry를 배정되지 않은 것으로 하고 `JobID`를 그 메시지의 값으로 바꾸며 배정 취소 표시를 지운다. 그 entry는 다음 자리 배치에서 R214로 다시 가져간다. 그 밖의 `JobAvailable`(같은 offer를 다시 받은 것)은 배정 여부를 바꾸지 않아, 스케일러가 `AcquireJobs`로 받은 entry(R214)는 배정된 채 남는다.
- R208. 그 target의 `JobStarted`를 받으면 맞는 entry(R206)를 지우고, R209에 해당하지 않는 `JobCompleted`(`RunnerName`이 있거나 `FinishTime`이 0이 아닌 것)를 받으면 맞는 entry를 지운다.
- R209. `RunnerName`이 비고 `FinishTime`이 0인 `JobCompleted`는 배정 취소로 보고, 맞는 entry가 배정돼 있으면 지우지 않고 마지막으로 들은 시각을 바꾸며 배정 취소 표시를 붙인다. 그 `JobCompleted`의 `JobID`가 entry의 `JobID`와 다르면 표시를 붙이지 않는다. 배정 취소 표시가 있는 entry는 R225를 따른다.
- R210. target이 target 오류 drain이나 target 오류 대기에 들어가면 스케일러는 그 target의 entry를 모두 지우고, 그 target이 상태 `정상`으로 돌아오기 전까지는 그 target의 메시지로 entry를 더하지 않는다.
- R211. 대기 job 목록은 메모리에만 있고, 스케일러가 시작하면 비어 있다.
- R225. 배정 취소 표시(R209)가 있는 entry는 자리 배치에서 cover(R224)를 쓰지 않고, `AcquireJobs`도 runner 시작도 받지 않는다(R184의 순서에서 빠진다). 그 표시는 R207로만 지워진다.
- R226. 스케일러는 target의 `Statistics`가 있는 메시지를 반영할 때마다 그 target의 `부족분 = 그 target의 entry 중 배정됐고 배정 취소 표시가 없는 entry 수 − (TotalAssignedJobs − 그 target의 JobStarted를 받은 runner 수(R224))`를 계산한다. 그 target의 `Statistics`가 있는 바로 앞 메시지와 이번 메시지에서 잇달아 부족분이 0보다 크면, 스케일러는 두 부족분 중 작은 값만큼, 앞 메시지 때 이미 배정돼 있던 그 target의 entry 중 지금 배정됐고 배정 취소 표시가 없는 entry를 마지막으로 들은 시각이 이른 것부터(같으면 R184의 순서로) 지우고, 지운 entry마다 INFO `waiting job dropped; GitHub counts fewer assigned jobs`를 target URL, `RunnerRequestID`, workflow run ID, job 표시 이름, `TotalAssignedJobs`, `JobStarted`를 받은 runner 수와 함께 남긴다.
- R227. 자리 배치는 할 때마다 먼저 QueueTime이 그때보다 25시간(GitHub가 큐의 self-hosted job을 취소하는 24시간에 1시간을 더한 값) 넘게 앞선 entry를 지우고, 지운 entry마다 INFO `waiting job expired`를 target URL, `RunnerRequestID`, QueueTime과 함께 남긴다.

자리 배치 (R169~R170, R184~R187, R212~R220, R224, R228~R229)
- R169. 자리 배치(R213)에서 R184의 순서로 본 entry 중 잠시 건너뛰지 않은 entry가, 그 entry가 쓸 수 있는 남은 cover(R213 (2), R224)가 없고 그 target의 runner 수(R3의 수)가 그 target의 `max-runners` 이상이거나 모든 target의 runner 수 합(R114의 수)이 서버 한도 이상이면, 스케일러는 그 entry에 `AcquireJobs`를 부르지 않고 runner를 시작하지 않는다(R213 (2)와 (3)의 조건의 부정). 그 job은 `JobAvailable`로만 받았으면 배정되지 않은 채, 배정됐으면 그 target의 scale set에 배정된 채 GitHub에서 기다린다.
- R170. 신호 drain 중이 아닐 때 어느 target의 runner가 runner 표에서 빠지면, 스케일러는 그때부터 1초 안에(어느 target의 `Scale`이나 자리 배치가 진행 중이면 그것이 끝난 때부터 1초 안에) 자리 배치를 한다.
- R212. 신호 drain 중이 아닐 때 스케일러는 target의 메시지를 `Scale`에서 반영한 직후와 30초마다의 대조(R42) 직후에도 자리 배치를 한다.
- R184. 자리 배치는 상태 `정상`인 모든 target의 entry 중 배정 취소 표시가 없는 entry(R225)를 QueueTime이 이른 것부터 보고, QueueTime이 같으면 처음 본 시각이 이른 것, 그것도 같으면 설정 파일의 `[[targets]]` 순서, 그다음 `RunnerRequestID`가 작은 것, 그다음 workflow run ID와 job 표시 이름의 순서로 본다.
- R224. 자리 배치는 runner 표의 잠금 아래에서, 할 때마다 target마다 cover를 한 번 센다. target의 cover는 `그 target의 busy가 아닌 runner 수 + 그 target의 busy runner 중 자기 이름의 JobStarted를 아직 받지 않은 runner 수`다. 두 수의 runner는 모두 그 target의 존재하는 runner(시작 중 포함, 0001의 끝난 runner는 뺀다)이고, runner 하나는 둘 중 한쪽에만 든다. 그래서 hook(R138)이나 대조(0001 R83, R149)로 busy가 됐지만 그 job의 `JobStarted`를 받지 않은 runner는 한 번만 세고, 자기 이름의 `JobStarted`를 받은 runner(이 SPEC에서 "`JobStarted`를 받은 runner", 그 job의 entry는 R208로 지워진다)는 세지 않는다. "`JobStarted`를 받은 runner 수"(R115, R185, R187, R219, R226)는 그 target의 존재하는 runner 중 자기 이름의 `JobStarted`를 받은 runner 수이고, 0001의 끝난 runner(`JobCompleted`를 받았고 컨테이너가 남은 runner)와 컨테이너가 없어진 runner는 세지 않는다. 그래서 `JobCompleted`를 받은 뒤 컨테이너가 남은 runner는 cover에도 `JobStarted`를 받은 runner 수에도 들지 않는다. 그 자리 배치에서 entry가 cover를 하나 쓸 때마다 그 target의 남은 cover가 하나 준다.
- R213. 자리 배치는 R184의 순서로 entry마다 다음 중 하나를 한다. (1) 그 entry의 target이 R61 백오프 중이거나, 그 entry에 필요한 그 target의 호출(`AcquireJobs`, JIT 발급)이 R52 대기(R188) 중이거나, 그 자리 배치에서 R216으로 그 target의 entry를 더 보지 않게 됐으면 그 entry를 잠시 건너뛴다. (2) 그렇지 않고 그 entry가 쓸 수 있는 그 target의 남은 cover(R224)가 있으면 cover 하나를 쓴다. 배정된 entry는 busy인 남은 cover(busy지만 `JobStarted` 전인 runner)가 있으면 그것을 먼저, 없으면 busy가 아닌 남은 cover를 쓴다. 배정되지 않은 entry는 busy가 아닌 남은 cover만 쓰고, 먼저 R214로 가져온 뒤 쓴다. busy인 남은 cover는 배정된 entry와 R187의 첫 단계(R219의 수)만 쓴다. (3) 그 entry가 쓸 수 있는 남은 cover가 없고 그 target의 runner 수(R3의 수)가 그 target의 `max-runners`보다 적고 모든 target의 runner 수 합(R114의 수)이 서버 한도보다 적으면, 배정되지 않은 entry는 먼저 R214로 가져온 뒤 그 target의 runner 하나를 시작한다. 이 runner는 그 entry의 몫이라 남은 cover에 더하지 않는다. (4) 그 밖의 entry는 건너뛰고(R169) 다음 entry를 본다. (2)나 (3)을 마친 entry가 그 자리 배치에서 덮인 entry다.
- R214. 배정되지 않은 entry가 cover를 쓰거나 runner를 받기(R213) 바로 전에, 스케일러는 그 entry의 `RunnerRequestID` 하나로 그 target 세션의 `AcquireJobs`를 부르고, 돌려받은 ID 목록에 그 ID가 있으면 그 entry를 배정된 것으로 바꾼다. 그 ID가 없으면 그 entry를 지우고 INFO `job no longer available`을 target URL, `RunnerRequestID`와 함께 남긴 뒤, cover를 쓰거나 runner를 시작하지 않고 다음 entry를 본다. 배정된 entry에는 `AcquireJobs`를 부르지 않는다(0001 Design 스케일링 흐름 3의 "`JobAvailable`마다 `AcquireJobs`"를 대체).
- R215. (dropped) 같은 target의 runner는 서로 바꿔 쓸 수 있어(GitHub는 그 scale set에 배정된 job을 그 set의 아무 runner에게 준다) runner를 entry에 표시하는 셈은 수일 뿐이므로, R224의 cover와 R213으로 대신한다.
- R216. R214의 `AcquireJobs`가 일시 오류로 끝나면 스케일러는 그 entry를 그대로 두고 로그와 그 target의 마지막 오류에 남긴 뒤, 그 자리 배치에서 그 target의 entry를 더 보지 않는다(그 entry와 그 target의 뒤 entry는 잠시 건너뛴 entry다, R213 (1)). 세션 없어짐(R25의 404)이면 그 target은 R25대로 새 세션을 만들고, 영구 오류면 R171을 따른다.
- R217. (dropped) 표시가 없어져 지울 표시도 없다. 시작에 실패하거나 job 없이 빠진 runner는 다음 자리 배치의 cover에 들지 않으므로, 그 entry는 자기 QueueTime 순서로 다시 cover나 새 runner를 받고 배정된 entry는 `AcquireJobs` 없이 받는다(R213, R214).
- R218. (dropped) runner가 같은 target의 다른 job을 받아도 cover는 target마다의 수라 넘겨줄 표시가 없다. 그 runner가 `JobStarted`를 받으면 cover에서 빠지고 그 job의 entry가 지워지므로(R208, R224) 남은 entry는 다음 자리 배치에서 다시 센다.
- R219. 스케일러는 target의 `Statistics`가 있는 메시지를 `Scale`에서 반영할 때마다 그 target의 목록에 없는 배정 job 수를 `max(0, 그 메시지의 TotalAssignedJobs − 그 target의 JobStarted를 받은 runner 수(R224) − 그 target의 entry 중 배정됐고 배정 취소 표시가 없는 entry 수)`로 계산하고, 그 target의 `Statistics`가 있는 다음 메시지까지 그 값을 쓴다. 메시지가 없는 poll(빈 poll)이나 `Statistics`가 없는 메시지는 그 값을 바꾸지 않는다.
- R187. 자리 배치는 R184의 entry를 다 본 뒤 남은 자리로, 먼저 target마다 남은 cover(R224)가 그 target의 목록에 없는 배정 job 수(R219)에 닿을 때까지, 그다음 target마다 존재하는 runner 수가 R115의 목표에 닿을 때까지 runner를 시작한다. 두 단계 모두 설정 파일의 `[[targets]]` 순서로 하고, R213 (3)의 두 한도를 지킨다. 이 규칙으로 시작한 runner는 남은 cover에 더한다. 이미 있는 대기 runner는 이 규칙으로 지우지 않는다.
- R185. target의 존재하는 runner 수가 R115의 목표보다 많으면, 스케일러는 자리 배치에서 그 차이만큼까지 R37로 busy가 아닌 runner만 지운다.
- R186. 자리 배치의 runner 시작과 `AcquireJobs`는 그 target의 R61 백오프와 그 target의 R52 대기(R188)를 따르고, 백오프나 대기 중인 target의 entry는 그 자리 배치에서 잠시 건너뛰며(R213 (1)), 그 target의 R187 시작도 건너뛴다.
- R220. 신호 drain 중에는 어느 target의 `AcquireJobs`도 부르지 않고, target 오류 drain 중인 target의 `AcquireJobs`도 부르지 않는다(R89를 대체).
- R228. R187의 첫 단계가 R219의 수와 비교하는 남은 cover에는, R219의 수를 계산한 메시지 뒤에 busy가 됐고(R138 등) 자기 이름의 `JobStarted`를 아직 받지 않았으며 entry가 쓰지 않은 runner도 든다(R224). 그래서 메시지 사이에 그런 runner가 생겨도 첫 단계는 runner를 더 시작하지 않는다. 이것은 R219의 수에서 그 runner 수를 빼고 busy가 아닌 남은 runner와 비교하는 것과 같다.
- R229. 한 자리 배치에서 R213 (1)로 잠시 건너뛴 entry(R186의 백오프나 R52 대기, R216의 일시 오류)가 하나라도 있으면, 그 자리 배치는 R187의 둘째 단계(`idle` 채우기)로 runner를 시작하지 않고, R187의 첫 단계(R219의 수)로는 runner 하나를 시작하기 전마다 `서버 한도 − 모든 target의 runner 수 합(R114의 수) − 그 자리 배치에서 잠시 건너뛴 entry 수`가 0보다 클 때만 시작한다.

속도 제한 대기 (R188~R189)
- R188. target의 설치 토큰으로 부르는 호출(scale set 호출, 메시지 세션 호출, `AcquireJobs`, JIT 발급, `RemoveRunner`, 조직 runner 목록과 이름 조회, runner group 조회)의 R52 대기는 target마다, 호출 종류마다 따로 두어, 한 target이 받은 속도 제한이 다른 target의 호출을 늦추지 않는다.
- R189. App JWT로 부르는 설치 조회(R108)의 R52 대기는 모든 target이 하나를 같이 쓴다.

오류 범위 (R171~R180, R190~R198)
- R171. 신호 drain 중이 아닐 때 한 target의 R51 호출(그 target의 메시지 세션 호출, scale set 호출, `AcquireJobs`)이 영구 오류로 실패하면 그 target만 target 오류 drain에 들어가고, 다른 target은 세션을 유지하며 자리 배치(R184, R213)로 runner를 받는다(R51의 범위를 target으로 좁힌다).
- R172. 한 target의 시작 단계 호출(R108의 설치 조회, R111의 runner group 조회, R112의 scale set get-or-create, `SetSystemInfo`, 첫 세션 생성)이 영구 오류로 실패하면(R109, R110, R111의 group 없음 포함) 그 target만 target 오류 대기에 들어가고, 다른 target의 시작과 실행은 계속된다(R46의 범위를 이 호출들에 대해 target으로 좁힌다).
- R173. target 오류 drain은 0001의 오류 drain 규칙(R53, R54, R55. R89는 R220으로 대체)을 그 target의 runner와 세션에만 적용하고, 그동안 그 target의 목표 runner 수는 0이며, 끝나면 그 target은 target 오류 대기에 들어간다.
- R174. target 오류 대기에 들어간 target은 세션을 닫고, 목표 runner 수 0인 채로 들어간 때부터 30초 뒤에 첫 다시 시도(R193)를 하며, 시도가 실패할 때마다 다음 시도까지의 간격을 두 배로 하되 30분을 넘지 않게 하고, 시도 횟수에 상한을 두지 않는다. 시도 밖에서는 그 target을 위해 GitHub를 부르지 않는다(0001 R47의 "자동으로 다시 시도하지 않고 재시작해야 벗어난다"를 target 오류 대기에서는 이것으로 대체한다. 스케일러 전체의 오류 대기는 R47 그대로다).
- R175. 모든 target이 target 오류 대기에 있어도 스케일러는 오류 대기(R47)에 들어가지 않고, 각 target은 R174대로 다시 시도한다.
- R176. 설정 오류(R28, R30, R105~R107, R166), Docker 준비 확인, Docker 노출(R79), 이미지 확인, Docker 용량 확인(R167, R201의 `/info`, R202), job 확인 서버 listen의 영구 오류는 어느 target의 시작 단계보다 먼저 스케일러를 오류 대기에 넣고, 어느 target도 세션을 만들지 않는다.
- R177. target마다의 시작 단계와 R174의 다시 시도는 다른 target과 따로 진행되어, 한 target의 R24 백오프 대기, target 오류 대기, 다시 시도가 다른 target의 첫 세션 생성과 runner 시작을 늦추지 않는다.
- R178. R20, R57, R58의 "첫 세션"은 어느 target이든 처음 만든 세션이다.
- R179. 어느 target이 target 오류 drain 중일 때 처음 받은 SIGTERM이나 SIGINT는 신호 drain(R20, R92)을 시작하고, 그 target의 busy runner도 R92대로 기다린다(R21의 "오류 drain 중에 SIGTERM이나 SIGINT를 받으면 기다리지 않음"은 target 오류 drain에 적용하지 않는다).
- R180. `status`의 target 줄은 그 target의 상태(`시작 중`, `정상`, `오류 drain 중`, `오류 대기`)를 보이고, 상태가 `오류 drain 중`이나 `오류 대기`이면 그 target의 마지막 오류와 시각을, `오류 대기`이면 R174의 다음 시도 시각도 붙인다.
- R190. target 오류 drain이 끝나 target 오류 대기에 들어가기 전에, 스케일러는 그 target의 runner에 대한 감시와 삭제 재시도만 멈추고, 30초마다의 대조(R42)는 다른 target의 runner를 위해 계속한다(R55의 "진행 중인 감시와 대조의 재시도를 멈춘다"를 target 범위로 좁힌다).
- R191. 신호 drain 중 한 target의 호출이 영구 오류로 실패하면 스케일러는 로그와 그 target의 마지막 오류만 남기고, 그 target을 target 오류 drain에 넣지 않는다(R100을 target에 적용).
- R192. 신호 drain이 시작되면 R174의 다시 시도는 멈추고, 진행 중인 시도는 그 호출을 취소하며 세션을 만들지 않는다.
- R193. R174의 다시 시도 한 번은 그 target의 시작 단계(R108의 설치 조회 → R111의 runner group 조회 → R148의 정리 → R112의 scale set get-or-create → `SetSystemInfo` → 세션 생성)를 처음부터 차례로 한다. 시도 안에서는 R24의 재시도를 쓰지 않고, 일시 오류와 영구 오류 모두 그 시도의 실패로 센다(R148의 실패는 0001 R17처럼 시도를 막지 않는다).
- R194. R193의 시도가 세션 생성까지 성공하면 그 target은 상태 `정상`으로 돌아가 그 세션의 메시지로 entry를 더하고 자리 배치로 runner를 받으며, R174의 간격은 30초로 되돌아간다.
- R195. 어느 target도 첫 세션을 만들기 전에 모든 target이 target 오류 대기에 들어가면, 스케일러의 시작은 끝난 것으로 보고 R175와 R197을 따른다.
- R196. 어느 target이든 첫 세션을 만든 뒤 SIGTERM이나 SIGINT를 받았을 때 아직 시작 단계에 있는 target은 시작 단계를 멈추고 세션을 만들지 않는다. 그 target에는 runner가 없다.
- R197. 스케일러의 상태가 `정상`이고 상태 `정상`인 target도 `시작 중`인 target도 없으면(모든 target이 `오류 drain 중`이나 `오류 대기`), `status`는 첫 줄에 `상태: 정상 target 없음`을 출력하고 target 줄, `전체` 줄, 마지막 오류를 출력한 뒤 1로 끝난다(R26을 이 경우에 대체한다).
- R198. `status`는 `상태: 시작 중`일 때도 target 줄을 출력한다(R58에 더한다).

실제 실행 확인: 여러 조직과 자리 기다림 (R181~R183, R199~R200, R223, R230)
- R181. 조직 A와 B를 target으로 두고 서버 한도가 2이며 A와 B의 `max-runners`가 각각 2일 때(이 Mac의 기본 자원 설정, Design 테스트), A의 저장소에서 시험 job(`sleep 60` step 하나) 2개가 runner에서 돌기 시작한 뒤 B의 저장소에서 같은 시험 job 1개를 시작하면, 1초마다 센 runner 컨테이너 수는 2를 넘지 않고, B의 job은 기다리는 동안 GitHub job 기록의 `status`가 `queued`이며 A의 컨테이너 하나가 없어진 때부터 60초 안에 시작하고, 세 job이 모두 성공한다(나중 시험, Design 테스트).
- R182. A에 App 설치가 없는 채로 스케일러를 시작하면, `status`의 A 줄은 `오류 대기`와 R109의 오류를, B 줄은 `정상`을 보이고, 그 뒤 B의 저장소에서 시작한 job은 성공한다(나중 시험, Design 테스트).
- R183. B의 저장소에서 job이 도는 중 A 조직에서 App 설치를 지우면, 그 B의 job은 성공으로 끝나고, 설치를 지운 때부터 70분 안에 `status`의 A 줄이 `오류 대기`가 되며 그 시간이 기록되고, 그 뒤 B의 저장소에서 시작한 job도 성공한다. 70분 안에 A 줄이 `오류 대기`가 되지 않으면 그 사실과 그동안의 A 줄을 기록한다(Areas of concern 12)(나중 시험, Design 테스트).
- R199. A 줄이 `오류 대기`인 동안 A에 App을 다시 설치하면, 스케일러를 재시작하지 않고, 다시 설치한 뒤 처음 오는 R174의 시도 시각(`status`의 다음 시도)부터 60초 안에 A 줄이 `정상`이 되고, 그 뒤 A의 저장소에서 시작한 job이 성공한다(나중 시험, Design 테스트).
- R200. target이 조직 A 하나이고 A의 `max-runners`가 3, 서버 한도가 2일 때(이 Mac의 기본 자원 설정, Design 테스트) A의 저장소에서 시험 job(`sleep 420` step 하나, 7분) 2개가 runner에서 돌기 시작한 뒤, 그 둘과 다른 run으로 A의 저장소에서 셋째 시험 job(`sleep 60` step 하나) 1개를 시작한다. 셋째 job은 대기 job 목록에서 기다린다. 통과 조건은 앞의 두 job 중 하나가 끝나 자리가 난 뒤 셋째 job이 runner를 받아 성공하는 것이다. 그 job의 최종 결과, 시작 시각, 그동안 스케일러 로그에 나온 그 job의 `JobAvailable`, `JobAssigned`, 배정 취소(R209)의 수와 시각, 스케일러가 그 job에 `AcquireJobs`를 부른 시각이 기록된다. 배정 취소가 나와도 그 job의 entry는 목록의 자리를 지키고(R209), 자리가 나면 빈 자리를 받는 것은 그 entry다(배정 취소 표시가 있는 동안은 다시 배정된 뒤에, R225). 7분은 첫 배정 취소가 약 5분 뒤에 온다는 서술을 덮도록 정한 길이다(Design 테스트).
- R223. target이 조직 A 하나이고 A의 `max-runners`가 3, 서버 한도가 2일 때 A의 저장소에서 시험 job(`sleep 120` step 하나) 2개가 runner에서 돌고, 그 둘과 다른 run인 A의 셋째 시험 job(`sleep 60` step 하나) 1개가 대기 job 목록에서 기다리는 동안 `service stop`으로 스케일러를 멈추고 그 명령이 끝난 뒤 `launchctl kickstart`로 다시 시작하면, 재시작 뒤 A의 첫 세션에서 셋째 job의 `JobAvailable`과 `JobAssigned`가 왔는지와 그 시각, R219의 목록에 없는 배정 job 수, 셋째 job이 runner를 받은 시각과 최종 결과가 기록된다. 재시작 뒤 그 job의 `JobAvailable`이나 `JobAssigned`가 오고 셋째 job이 성공하면 R211(목록을 메모리에만 둠)을 유지한다. 둘 다 오지 않았지만 R219의 수로 runner를 받아 성공해도 유지한다. 둘 다 오지 않고 R219의 수도 0이어서 셋째 job이 다음 offer까지 runner를 받지 못하거나 실패하면 목록을 저장할지 SPEC에서 다시 정한다(Areas of concern 12).
- R230. target이 조직 A 하나이고 A의 `max-runners`가 3, 서버 한도가 2일 때(R200과 같은 설정) A의 저장소에서 시험 job(`sleep 1800` step 하나) 2개가 runner에서 돌기 시작한 뒤, 그 둘과 다른 run으로 A의 저장소에서 셋째 시험 job(`sleep 60` step 하나) 1개를 시작한다. 셋째 job은 대기 job 목록에서 기다린다. 앞의 두 job은 `sleep 1800`이 끝나거나, 스케일러 로그에 셋째 job의 배정 취소(R209)가 4번째로 나온 때 그 두 job의 run을 취소해 끝낸다. 통과 조건은 셋째 job이 결국 runner를 받아 성공하는 것이다. R200과 같은 값(셋째 job의 최종 결과, 시작 시각, `JobAvailable`, `JobAssigned`, 배정 취소의 수와 시각, `AcquireJobs`를 부른 시각)이 기록된다. 셋째 job이 실패하거나 취소되면 SPEC을 runpool처럼 알리는 `maxCapacity`를 남은 자리에 맞춰 낮추는 방식으로 바꾼다(Areas of concern 12)(나중 시험, Design 테스트).

## Design

용어: target은 runner를 등록하는 GitHub 대상 하나다. 이 변경에서 target의 종류는 조직뿐이고, 설정에 조직 target을 하나 이상 둔다(R105). 0001 SPEC 요구사항의 "pool"은 이 변경에서 target 하나와 그 scale set으로 읽는다. pool마다의 설정값 중 `max`는 `targets.max-runners`(R115, R116), `idle`은 `targets.idle`, 자원 제한은 `[runner]`와 `[buildkit]`의 키(R121, R122), pool 이름은 `scaling.label`이다. 서버 한도는 모든 target의 runner 수 합의 상한으로, 설정값이 아니라 시작 때 Docker가 보고한 CPU·메모리와 runner 하나의 자원 제한으로 계산한 runner 수다(R114, R201). target 오류 drain과 target 오류 대기는 0001의 오류 drain과 오류 대기를 target 하나에 적용한 것이고(R171~R174), 그냥 "오류 대기"는 0001처럼 스케일러 전체의 오류 대기다. 대기 job 목록은 GitHub가 알린 job 중 아직 runner에서 시작하지 않은 job의 서버 하나의 목록이고, 그 항목 하나가 entry다(R206). busy runner는 0001 R81의 busy가 된 runner이고, 대기 runner는 0001처럼 busy가 아닌 runner다. `JobStarted`를 받은 runner는 자기 이름의 `JobStarted`를 받은 존재하는 runner(0001의 끝난 runner는 뺀다, R224)이고, target의 cover는 그 target의 존재하는 runner 중 `JobStarted`를 받지 않은 runner(대기 runner와, busy지만 `JobStarted` 전인 runner)의 수다(R224). 자리 배치에서 cover 하나나 새 runner를 받은 entry가 덮인 entry이고, 백오프, 속도 제한 대기, `AcquireJobs` 일시 오류로 그 배치에서 보지 않은 entry가 잠시 건너뛴 entry다(R213). 자리 배치는 entry와 `idle`에 runner를 주는 서버 전체의 한 번의 계산이다(R184, R213, R187). 그 밖의 0001 요구사항(격리, drain, 재시도, 오류 대기, hook의 kill 규칙, 서비스)은 그대로 성립한다.

**바꾸거나 없애는 0001 요구사항**
- 대체: R1·R2의 목표 계산과 시작(R115, R187), R4(R117), R89(R220), 0001 Design 스케일링 흐름 3의 "`JobAvailable`마다 `AcquireJobs`"(R169, R214), 0001 재시도 표의 "`Scale()` 안의 `AcquireJobs`" 행(R216), R9(R123~R129), R17(R148), R22(R112), R23(R150, R151), R34(R121), R54와 R92의 한 문장(R133), R66의 한 구절(R139, R140), R68(R105), R74(R122), R90(R116), R103(R149).
- 좁힘: R51의 오류 drain은 오류가 난 target에만 걸린다(R171, R173). R46의 오류 대기는 target의 시작 단계 호출(설치 조회, runner group 조회, scale set get-or-create, `SetSystemInfo`, 첫 세션 생성)에서는 그 target에만 걸리고(R172), 설정 오류, Docker 확인, job 확인 서버 listen에서는 스케일러 전체에 걸린다(R176). R47의 "자동으로 다시 시도하지 않고 재시작해야 벗어난다"는 target 오류 대기에서는 R174의 다시 시도로 대체하고, 스케일러 전체의 오류 대기에는 그대로 둔다(R174, R175). R24는 처음 시작할 때의 target 시작 단계에만 쓰고, R174의 다시 시도 안에서는 쓰지 않는다(R193). R26의 첫 줄과 종료 코드는 상태 `정상`인 target도 `시작 중`인 target도 없을 때 R197로 바뀐다. R7(배정된 job이 없으면 runner 수가 `idle`과 같음)은 상태 `정상`인 target에서만 성립하고, entry가 자리를 기다리는 target(R169), 자리 배치가 `idle` 채우기를 entry 뒤로 미룬 target(R187), 대기 runner가 entry의 cover로 쓰이는 target(R213, R224), target 오류 drain과 target 오류 대기의 target(목표 0, R173, R174)에서는 성립하지 않는다. R52의 대기는 target마다 따로 둔다(R188, R189). R55의 감시와 재시도 멈춤은 그 target의 runner에만 걸린다(R190). R100은 target의 영구 오류에도 적용한다(R191). R21의 "오류 drain 중 신호" 구절은 target 오류 drain에 적용하지 않는다(R179). R20, R57, R58의 "첫 세션"은 어느 target이든 처음 만든 세션이다(R178).
- 넓힘: R3은 target마다 그 target의 `max-runners`로 성립하고, 그 위에 모든 target의 합에 대한 서버 한도(R114)를 더한다. R24의 시작 단계 호출 목록에 설치 조회(R108), runner group 조회(R111), Docker `/info`(R201)를 더하고, R46의 목록에는 `/info`만 더한다(설치 조회와 runner group 조회의 영구 오류는 R172). R26과 R56의 pool 줄에 target 상태와 target의 마지막 오류를 더하고(R180), R58의 출력에 target 줄을 더한다(R198). R40의 401 규칙을 `POST /v1/event`에도 적용하고 본문을 읽기 전에 검증한다(R134). R81의 busy 계기에 토큰이 맞는 첫 `POST /v1/event`(R138)를 더하고, R81 계기의 "R103의 발견"은 R149의 발견으로 읽는다.
- 그대로: R82는 성립한다. hook은 판정 조회에 여전히 스케일러가 준 주소와 runner 이름만 쓴다. 새로 읽는 `GITHUB_EVENT_NAME`과 `GITHUB_EVENT_PATH`는 runner가 hook 환경에 넣는 값이고, hook 전에 job 코드가 돌지 않으며 workflow `env:`는 hook 환경에 들어가지 않으므로 job 코드가 hook 전에 바꿀 수 없다(설계: 판정의 "이벤트 파일을 믿는 근거").
- 없앰: R29(메모리 합 경고). 서버 한도(R201)가 runner의 메모리 예약 합을 `MemTotal` 안에 두므로 경고할 경우가 없다. R65(판정에 GitHub 조회가 없음). R52의 "판정 중의 workflow run 조회와 최신 run 조회는 예외로 R65를 따른다"는 대상 호출이 없어져 적용할 곳이 없다. R98 목록의 workflow run 조회와 최신 run 조회는 없애고, "저장소 runner 목록"은 조직 runner 목록(R148)과 이름 조회(R149)로 바꾼다. 두 호출의 영구 오류도 R98대로 오류 drain을 시작하지 않는다.
- 0001 Design에서 바뀌는 항목: 판정 1~8 중 토큰(판정 1), 거부 처리(판정 4), `JobWorkflowRef` 형식(판정 6), AWS(판정 7)는 그대로 두고, run 조회(판정 2), R9 조건과 `allowed-events` 설명(판정 3), 시간 순서 중 `JobStarted` 의존 부분(판정 5), 최신 run 조건(판정 8)은 없앤다. 판정 3과 판정 8이 막던 경우가 열리는 것은 Areas of concern 4다. 스케일링 흐름 2의 "끊지 않는 poll은 부모 ctx와 라이브러리 시한만으로 보낸다"는 R153의 70초 시한으로 바꾼다. 재시도 표의 "판정의 workflow run 조회와 최신 run 조회" 행은 없애고 "시작 단계" 행에 설치 조회, runner group 조회, `/info`를 더한다. "대조의 runner 목록(R103)" 행은 조직 runner 이름 조회(R149)가 같은 규칙으로 잇는다.

**구성 요소**
- target(`internal/github`): 종류(이번에는 조직만)와 이름을 가진 값이다. 종류마다 다른 것은 네 가지뿐이고 모두 target의 메서드 뒤에 둔다: 등록 URL(`GitHubConfigURL`, 조직은 `https://github.com/<org>`), 설치 조회 경로(`/orgs/{org}/installation`), runner 목록 경로(`/orgs/{org}/actions/runners`), 설치에 있어야 하는 권한(`organization_self_hosted_runners: write`). scaleset v0.5.0은 경로 조각이 하나인 URL을 조직 범위로 읽고 등록 토큰을 `/orgs/{org}/actions/runners/registration-token`에서 받는다(확인함: v0.5.0 `config.go` 55행, `client.go` 1043~1046행). 그래서 scale set 생성, 세션, JIT 발급, `GetRunnerByName`, `RemoveRunner`는 0001과 같은 라이브러리 호출을 그대로 쓴다.
- 설치 ID 조회(R108~R110): 0001은 전역 `github.app-installation-id` 하나를 썼다. 조직과 나중의 개인 계정 저장소는 설치가 서로 다르므로 target마다 App JWT로 조회한다. 이 endpoint는 JWT로만 부르고 응답은 설치 객체(필수 `id`, 필수 `permissions`)다(확인함: https://docs.github.com/en/rest/apps/apps "Get an organization installation for the authenticated app" `GET /orgs/{org}/installation`, "You must use a JWT to access this endpoint.", 응답은 "Get an installation for the authenticated app"과 같은 스키마이고 그 스키마에 "`id`: required, integer", "`permissions`: required"). 그 절의 응답 코드는 200만 적혀 있고, 404는 저장소 설치 조회 절에만 있다. App이 설치되지 않은 조직에서 404가 오는지(R109)는 미확인이다(Areas of concern 5). JWT만 쓰므로 새 App 권한이 필요 없다. 권한 검사(R110)는 첫 등록 호출의 403보다 먼저, 무엇이 빠졌는지 이름으로 알리기 위해 둔다. 조회한 ID는 `ScaleSetConfig.InstallationID`와 `RESTConfig.InstallationID`에 넣고, 서명기(`AppSigner`)는 0001처럼 전역 하나를 같이 쓴다.
- App 권한: 조직 수준 runner에는 Organization permission "Self-hosted runners: Read and write"가 필요하고, Repository permission "Administration: Read and write"는 저장소 범위 등록에만 필요하다(확인함: https://docs.github.com/en/actions/tutorials/use-actions-runner-controller/authenticate-to-the-api, "**Administration:** Read and write" 주석 "is only required when configuring Actions Runner Controller to register at the repository scope.", Organization permissions "**Self-hosted runners:** Read and write"). App이 조직의 self-hosted runner endpoint를 부르려면 `organization_self_hosted_runners` 권한이 필요하다(확인함: https://docs.github.com/en/rest/actions/self-hosted-runner-groups 도입부). 판정이 GitHub를 부르지 않으므로(R123) 0001의 Actions 읽기 권한은 이 변경의 호출에 쓰이지 않는다. 이 권한 하나로 우리 호출이 모두 되는지는 Areas of concern 5, 쓰지 않게 된 권한을 뺄지는 Areas of concern 6이다.
- runner group(R111): ARC는 group을 지정하지 않으면 ID 1을 쓰고, 지정하면 `GetRunnerGroupByName`으로 ID를 찾는다(확인함: ARC eca1a62 `autoscalingrunnerset_controller.go` 1025~1034행). 스케일러도 같게 한다. v0.5.0의 `GetRunnerGroupByName`은 그 이름의 group이 없으면 200 응답에서 "no runner group found with name" 오류를 만든다(확인함: v0.5.0 `client.go` 545행). 같은 이름의 scale set 여럿(R41)처럼 상태 코드가 없는 이 오류를 영구 오류로 분류하는 규칙을 `internal/github`의 `convertError`에 더한다. 조직의 기본 group 하나는 모든 조직에 있다(확인함: https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/manage-access "All organizations have a single default runner group."). 새 runner는 기본 group에 든다(확인함: github/docs `add-runners.md` "New runners are assigned to the default group."). REST 문서의 예시에서 기본 group은 ID 1이다(확인함: github/rest-api-description c9c95fe, `GET /orgs/{org}/actions/runner-groups` 응답 예시 `"id": 1, "name": "Default", "visibility": "all", "default": true`, `generate-jitconfig` 요청 예시 `"runner_group_id": 1`). 그러나 ID 1을 보장한다는 문장은 없고 스키마는 `default` boolean으로 기본 group을 가르므로, 모든 조직에서 ID가 1인지는 미확인이다(Areas of concern 7). 어느 저장소가 쓸지는 그 group의 저장소 접근 설정이 정하고, 공개 저장소는 group에서 따로 허용해야 한다(확인함: 같은 문서 "By default, only private repositories can access runners in a runner group, but you can override this").
- `targets.runner-group`을 바꾸면 R112는 새 group에서 같은 이름의 scale set을 찾지 못해 새로 만들고, 옛 group의 scale set은 listener 없이 남는다. scale set 이름은 group 안에서만 유일하고, 다른 group에는 같은 이름의 scale set을 둘 수 있다(확인함: https://docs.github.com/en/actions/how-tos/manage-runners/use-actions-runner-controller/deploy-runner-scale-sets "Runner scale set names are unique within the runner group they belong to.", "If you want to deploy multiple runner scale sets with the same name, they must belong to different runner groups.", actions/scaleset v0.5.0 `client.go` 430행 "GetRunnerScaleSet fetches a runner scale set by its name within a runner group."). 그래서 같은 라벨의 scale set이 둘이 되어 job이 listener 없는 쪽에 배정될 수 있으므로(추론), group을 바꾸기 전에 옛 설정으로 `delete-scaleset <target URL>`을 실행해 옛 scale set을 지운다(README에 적는다).
- 공유 자원: runner 표, 대기 job 목록(R206), 서버 한도, Docker 클라이언트, job 확인 서버, status, 서명기는 서버에 하나씩이고 모든 target이 같이 쓴다. target마다 따로인 것은 `max-runners`, 설치 ID, scale set 클라이언트, REST 클라이언트, scale set, 세션, listener, 시작 단계의 백오프, 상태(시작 중, 정상, target 오류 drain, target 오류 대기), 마지막 오류, 연속 시작 실패 수(R61, R86), 마지막 메시지로 계산한 목록에 없는 배정 job 수(R219), R174의 다시 시도 간격과 다음 시도 시각, 설치 토큰으로 부르는 호출의 R52 대기(R188)다. 설치 조회의 R52 대기는 App JWT 호출이라 서버에 하나다(R189). 0001 코드는 R52의 대기를 호출 종류마다 하나씩 daemon 전체에 둔다(확인함: `internal/daemon/daemon.go` 221행 `retry.NewNextAllowed`, `internal/retry/ratelimit.go` 43~46행 "per kind of call"). 이 변경에서는 그것을 target마다 하나씩 둔다. 설치 토큰으로 부르는 호출의 속도 제한은 설치마다 따로다(확인함: github/docs 8b038c5 `data/reusables/rest-api/primary-rate-limit-github-app-installations.md`("Rate limits for the REST API" 문서가 씀), "use the installation's minimum rate limit of 5,000 requests per hour", `content/apps/using-github-apps/installing-a-github-app-on-your-enterprise.md` "Rate limits are per installation"). 그래서 한 조직의 속도 제한 응답이 다른 조직의 호출을 늦추지 않게 한다. App JWT로 부르는 호출의 한도는 속도 제한 문서에 없어(content/rest, content/apps, data/reusables에서 찾음) 미확인이라 안전한 쪽으로 서버에 하나 둔다(Areas of concern 15). runner 표의 행은 target을 기록하고, job 확인 서버는 runner 이름으로 행을 찾아 그 행의 target에 보고를 넘긴다. 이 나눔은 참고 구현과 같다. runner-up은 조직마다 scale set과 세션을 따로 열고 세션마다 고루틴 하나로 돌린다(확인함: runner-up 013cc74 `internal/coordinator/github.go` 142~197행 `Sessions.Match`, 238~266행 `RunSet`, `internal/config/config.go` 133~135행 "Orgs get one scale set per pool each"). runscaler는 scale set마다 고루틴, 클라이언트, listener를 따로 두고 호스트 전체 한도 하나를 같이 쓴다(확인함: ysya_runscaler 6f33444 `cmd/runner/main.go` 539~541행, 574~585행).
- target 이름 비교(R166): 같은 조직을 두 번 적으면 같은 runner group의 같은 이름 scale set 하나에 세션 둘이 붙게 되므로 설정 오류로 막는다. 조직 이름은 대소문자 구분 없이 비교한다. runpool이 같은 이유로 target URL을 소문자로 바꿔 겹침을 막는다(확인함: rhobuild_runpool f1a2ab3 `internal/config/validate.go` 198~207행, 주석 "GitHub logins and repository names are [case-insensitive]"). GitHub REST API는 조직 이름을 대소문자 구분 없이 다룬다(확인함: github/rest-api-description c9c95fe `descriptions/api.github.com/api.github.com.json`, `GET /orgs/{org}/installation`, `GET /orgs/{org}/actions/runners`, `POST /orgs/{org}/actions/runners/generate-jitconfig`, `GET /orgs/{org}/actions/runner-groups`의 `org` path parameter, "The organization name. The name is not case sensitive."). 그래서 대소문자만 다른 두 이름은 같은 조직이고, 둘 다 두면 세션이 충돌한다. runner-up은 문자열이 정확히 같을 때만 막는다(확인함: runner-up 013cc74 `internal/config/config.go` 411~423행 "listed once").
- 동시 실행 한도(R114, R115, R201): 한도는 둘이다. target의 `max-runners`는 그 target의 runner 수 상한이고 그 target 세션의 `maxCapacity`다(R115, R116, 0001 R3). 서버 한도는 모든 target의 runner 수 합의 상한이고 서버의 CPU·메모리로 정한다(R114, R201). 결정: 2026-11-26, 사용자, target마다 자기 `max-runners`를 쓰고 실제 동시 실행은 서버 스펙(CPU·메모리)에 맞춰 제한한다. INTENT 제약의 "One concurrency limit covers the whole server"는 서버 한도가 맡는다. 두 한도의 나눔은 runscaler와 같다. runscaler는 scale set마다 `max-runners`를, 호스트 전체에 `concurrent`를 두고, GitLab Runner처럼 `concurrent`는 관리 프로그램 안의 runner 총수를, `max-runners`는 scale set마다의 상한을 정한다고 적는다(확인함: ysya_runscaler 6f33444 `docs/configuration.zh-TW.md` 412, 446행). 다른 점은 runscaler의 `concurrent`가 설정값이라는 것이고(확인함: 같은 파일 412행, `config.example.toml` 8행 "host-wide limit"), 서버 한도는 runner-up의 machine 예산처럼 서버가 보고한 값에서 정한다. runner-up은 machine의 `Cores`와 `MemoryMB`를 "what the machine's places may reserve together"로 두고 "A place takes a job only while its share fits beside the shares of the machine's places whose runners are alive"라고 적으며(확인함: runner-up 013cc74 `internal/config/config.go` 168~171행), place의 `Cores`와 `MemoryMB`는 "container/VM limits and the reservation against the machine's budget"이다(확인함: 같은 파일 191~193행). 쓰고 있는 몫에 새 몫을 더해 예산을 넘으면 그 place는 job을 받지 않고(확인함: 같은 커밋 `internal/coordinator/snapshot.go` 210~232행 `tight`), machine을 더할 때 그 machine의 코어와 메모리를 읽는다(확인함: 같은 커밋 `README.md` 367행 "reads the machine's cores and memory"). 이 스케일러도 runner 컨테이너와 BuildKit 컨테이너의 CPU·메모리 제한(R121, R122)을 runner 하나의 예약으로 보고, 예약 합이 Docker가 보고한 `NCPU`와 `MemTotal`을 넘지 않게 한다. 모든 runner의 몫이 같으므로(`runner.cpus + buildkit.cpus`, `runner.memory + buildkit.memory`) 이 예산 검사는 R201의 runner 수 하나로 줄어든다. Docker의 제한은 사용의 상한이고 그만큼을 미리 잡아 두지 않으므로(확인함: https://docs.docker.com/engine/containers/resource_constraints/, `--memory` "The maximum amount of memory the container can use", `--cpus` "how much of the available CPU resources a container can use", 예약 쪽인 `--memory-reservation`도 "it doesn't guarantee that the container doesn't exceed the limit"이고 `--cpu-shares`는 "doesn't guarantee or reserve any specific CPU access", 2026-11-26 읽음), 실제 사용이 제한보다 적은 job이 많을 때는 서버가 돌릴 수 있는 수보다 적게 동시에 돈다. 그 대신 모든 runner가 동시에 제한까지 써도 합이 Docker VM의 CPU·메모리를 넘지 않는다. runner-up의 owner 몫(`RoomCores`, `RoomMemoryMB`, 확인함: 같은 파일 174~177행)과 서버 한도를 손으로 덮어쓰는 설정은 두지 않는다(결정: 사용자, 최소 설정. Docker VM 밖 macOS의 메모리 여유는 따지지 않는다). `/info`는 시작 때 한 번 읽으므로 Docker Desktop의 자원을 바꾸면 스케일러를 다시 시작한다(R201). 나눗셈은 정수로 한다. CPU는 0001처럼 설정값에 1e9를 곱한 정수 NanoCPUs로, `NCPU`도 1e9를 곱해 나누고, 메모리는 바이트로 나눈다. 0.5 + 1 같은 소수 합에서 부동소수점 오차로 몫이 하나 작아지는 것을 막기 위해서다(추론). GitHub가 보내는 스케일 신호(`TotalAssignedJobs`)와 받는 쪽 한도(`maxCapacity`)는 모두 개수다(actions-scaleset 스킬 references/runtime.md 3절). 자리가 있는지의 판단(R213, R187)은 runner 표의 잠금 아래에서 한다. 빈 자리를 어느 job이 먼저 얻는지는 메시지를 먼저 받은 target이 아니라 모든 target에 걸친 QueueTime 순서가 정한다(R184, 설계: 대기 job 목록과 자리 배치). 축소(R37)는 target마다 하고, 목표를 넘는 수만큼 busy가 아닌 runner만 지운다(R185).
- `maxCapacity`(R116): target마다 그 target의 세션이 자기 `max-runners`를 그대로 보낸다. target들의 `max-runners` 합은 서버 한도를 넘어도 되고(R204는 INFO로만 남긴다), 그래서 GitHub가 target들에 배정한 job 수의 합은 서버 한도를 넘을 수 있으며, 실제로 도는 runner 수만 runner 표가 서버 한도로 막는다(R114). 스케일러는 자리가 없는 `JobAvailable` job을 가져가지 않으므로(R169) 그 job은 배정되지 않은 채 GitHub 큐에서 기다리고, GitHub가 `maxCapacity`만큼 스스로 그 scale set에 배정한 job은 배정된 채 기다린다. INTENT의 "Jobs beyond what the server can run at once wait in GitHub's queue"가 이 둘이다. 보내는 값은 runscaler, runner-up과 같은 방식이다. runscaler는 scale set마다 listener의 `MaxRunners`로 그 scale set의 `max-runners`를 보내고(확인함: ysya_runscaler 6f33444 `cmd/runner/main.go` 907~911행), scale set들의 `max-runners` 합이 호스트 한도를 넘는 것을 정상으로 보고 공유 broker가 runner 시작을 막는다(확인함: 같은 커밋 `internal/config/config.go` 574~575행 "Local max-runners values may sum above the global limit; the broker arbitrates that normal oversubscription case."). runner-up도 scale set마다 장소 수보다 큰 고정값(기본 50)을 보낸다(확인함: runner-up 013cc74 `internal/config/config.go` 86~90행 "It stays above the number of places, so the coordinator hears of every waiting job and picks the order, not GitHub.", 371~372행, `internal/coordinator/github.go` 309행). 가져가는 때는 둘이 다르다. runscaler는 받은 `JobAvailable`을 모두 바로 `AcquireJobs`로 가져가고(확인함: ysya_runscaler 6f33444 `internal/controller/messages.go` 62~66, 91행), 0001도 그랬다(0001 Design 스케일링 흐름 3). runner-up은 자리가 날 때 그 job을 위한 runner를 등록하기 바로 전에만 가져간다(확인함: runner-up 013cc74 `internal/coordinator/placement.go` 162~178행 `start`). 이 변경은 runner-up을 따른다(설계: 대기 job 목록과 자리 배치). 라이브러리 README는 `maxCapacity`가 "allows the backend to assign jobs accurately and avoid creating backlogs your scale set cannot fulfill"이라고 적고(확인함: actions/scaleset v0.5.0 `README.md` 49행), 배정됐지만 runner가 제때 가져가지 않은 job은 GitHub가 배정을 취소하고(`JobCompleted`, `result: "canceled"`) 다시 큐에 넣으며 이것이 3번까지 일어난다고 적는다(확인함: 같은 파일 116행). 그 취소가 언제 일어나는지, 3번 뒤에 job이 어떻게 되는지는 미확인이다(Areas of concern 12).
- 대기 job 목록과 자리 배치(R169, R170, R184~R187, R206~R229): 결정: 2026-11-26, 사용자, 서버 한도가 찬 동안의 job 받기는 runner-up의 방식을 따른다. 0001은 받은 `JobAvailable`을 모두 그 `Scale()` 안에서 바로 `AcquireJobs`로 가져갔다(0001 Design 스케일링 흐름 3, 재시도 표의 "`Scale()` 안의 `AcquireJobs`" 행). 이 동작에는 0001의 R 번호가 없으므로 R214가 0001 Design의 그 규칙을 대체하고, R216이 그 재시도 표 행을 대체한다. 이 변경에서 스케일러는 `JobAvailable` job을 그 job에 runner를 줄 때만, cover를 쓰거나 runner를 시작하기 바로 전에 가져가고(R213, R214), 줄 수 없는 job에는 `AcquireJobs`를 부르지 않는다(R169).
  - 참고 구현: runner-up은 `JobAvailable`과 `JobAssigned`를 모두 대기 목록에 넣고(확인함: runner-up 013cc74 `internal/coordinator/service.go` 245~261행 `Handle`), 그 이유를 "GitHub assigns most jobs to the scale set itself, as many as the capacity each poll announces, and waits for a runner from the set."라고 적는다(같은 파일 257~258행). 다시 offer되거나 배정된 job은 자리를 지키고(확인함: `queue.go` 78~105행 `waitLocked`, 첫 `SeenAt`과 `QueueTime`을 둠), job의 key는 run ID와 job 표시 이름, 그리고 0이 아닌 `RunnerRequestID`다(확인함: `queue.go` 52~59행 `keysOf`). `JobStarted`는 그 job을 목록에서 지운다(확인함: `service.go` 262~284행). `RunnerName`이 비고 `FinishTime`이 0인 `JobCompleted`는 배정 취소로 보고 자리를 지키며(확인함: `service.go` 290~299행, 주석 "When no runner reached an assigned job in five minutes, GitHub takes the assignment back, with no finish time, and assigns the job again, a moment later or in this same message. A cancelled job has a finish time.", `queue.go` 107~133행 `takeBackLocked`), 그 밖의 `JobCompleted`는 지운다(확인함: `service.go` 300~306행). 배정 취소된 job은 다시 배정될 때까지 runner를 받지 않는다(확인함: `queue.go` 172~183행 `waitingLocked`). `AcquireJobs`는 배정되지 않은 job에만 자리가 난 때 runner 등록 바로 전에 부르고, 결과에 그 ID가 없으면 "the job is no longer available"로 본다(확인함: `placement.go` 157~178행 `start`, `errGone`). 대기 job은 QueueTime이 이른 것부터 본다(확인함: `internal/plan/plan.go` 130~143행 `Rank`, `fifo`). `Statistics.TotalAvailableJobs`가 아는 job보다 많으면 WARN을 남긴다(확인함: `service.go` 314~325행). README는 "Jobs wait at GitHub without a runner until a place is free."라고 적는다(확인함: runner-up 013cc74 `README.md` 23~24행). runner를 시작한 job이 다시 offer되거나 배정되면 runner-up은 그 runner가 살아 있는 동안 다시 보낸 것으로 보고 runner를 더 시작하지 않는다(확인함: `queue.go` 88~101행 주석 "While that runner is alive this is a redelivery, or GitHub assigning again a job it took back before the runner was up; the runner takes it, and a second runner would wait for nothing."). 배치마다(확인함: `placement.go` 34행) QueueTime이 25시간 넘게 지난 대기 job을 잊는다(확인함: `queue.go` 198~209행 `expireLocked`, 206행 `now.Sub(j.QueueTime) > 25*time.Hour`). 또 GitHub가 배정한 job이 없어진 것을 알리지 않으면 그 job이 하루 동안 남아 빈 자리마다 runner를 시작하게 된다고 보고, 조용한 배정 job(10분)과 배정 취소된 job(1시간)의 workflow run을 REST로 읽어 끝난 run의 job을 잊는다(확인함: `closedruns.go` 12~35행, 59~127행 `forgetClosedRuns`, `README.md` 558~568행). runner-up은 MIT 라이선스라 PLAN에서 고지를 남기고 코드를 가져다 쓸 수 있다.
  - 이 방식이 막는 것과 막지 못하는 것: 가져가지 않는다고 해서 기다리는 모든 job이 배정을 피하지는 않는다. GitHub는 poll마다 알린 `maxCapacity`만큼의 job을 스스로 그 scale set에 배정하고(추론: runner-up `service.go` 257~258행의 서술이고 GitHub 문서가 아님), 그렇게 배정된 job도 약 5분 동안 runner가 가져가지 않으면 배정이 취소되고 다시 배정된다(추론: runner-up `service.go` 293~296행, `README.md` 560~561행 "GitHub takes an assigned job back when no runner takes it in five minutes"의 서술). 그래서 이 방식의 효과는 셋이다. (1) 서버가 돌릴 수 없는 `JobAvailable` job을 스케일러가 배정으로 바꾸지 않는다(R169). (2) 빈 자리를 받을 job을 GitHub의 메시지 순서가 아니라 스케일러가 모든 target에 걸쳐 QueueTime이 이른 것부터 고른다(R184). (3) 배정 취소를 받아도 그 job은 목록의 자리를 지킨다(R209). 배정 취소가 3번까지라는 README의 서술(actions/scaleset v0.5.0 `README.md` 116행)과 그 뒤의 결과는 여전히 미확인이고 나중 시험인 R230이 3번째 배정 취소 뒤를 기록한다. 첫 배정 취소 뒤에도 기다린 job이 자리를 지키고 runner를 받는지는 R200이 기록한다(Areas of concern 12). R230에서 기다린 job이 실패하면 대안은 runpool처럼 알리는 `maxCapacity`를 남은 자리에 맞춰 낮추는 방식이다(설계: 고르지 않은 방법 (1)).
  - INTENT 범위와의 관계: INTENT는 저장소 사이 공정성을 범위 밖에 두고 "jobs are taken in the order GitHub offers them"라고 적는다. QueueTime은 job이 GitHub 큐에 들어간 시각이므로(추론: 필드 이름과 runner-up의 `fifo`) R184의 순서는 GitHub 큐의 순서를 target 사이에도 지키는 것이고, 저장소나 조직마다의 몫은 두지 않는다. 배정된 job의 메시지는 QueueTime이 0일 수 있어(추론: runner-up `service.go` 266~267행 주석 "An assigned job carries no queue time") 그때는 처음 본 시각을 쓴다(R206).
  - entry와 cover(R206~R209, R213, R224, R225): entry는 `RunnerRequestID`, workflow run ID, job 표시 이름, 배정 여부, QueueTime, 처음 본 시각, 마지막으로 들은 시각, 마지막 `JobID`, 배정 취소 표시를 가진다(R206, 메시지 필드는 확인함: actions/scaleset v0.5.0 `types.go` 48~62행 `JobMessageBase`의 `RunnerRequestID`, `JobID`, `JobDisplayName`, `WorkflowRunID`, `QueueTime`, `FinishTime`). entry는 runner를 가리키지 않는다. GitHub는 배정된 job을 그 scale set의 아무 runner에게 주므로(추론: runner-up `queue.go` 135~141행 "GitHub gives a set's runner whichever of the set's jobs it picks") 어느 entry를 위해 시작한 runner든 같은 target의 다른 job을 받을 수 있고, entry에 runner를 매어 두는 셈은 결국 target마다의 수다. 그래서 자리 배치는 그 수를 할 때마다 runner 표에서 다시 센다(R224). cover는 아직 job을 시작하지 않은 runner, 곧 `JobStarted`를 받지 않은 runner다. hook(R138)으로 busy가 된 runner는 이미 어떤 job을 받았지만 그 job의 entry는 `JobStarted`를 받을 때까지 목록에 남으므로(R208), 그동안 그 runner를 cover로 세어 그 entry에 runner를 하나 더 주지 않고, `JobStarted`를 받은 runner로 따로 세지도 않는다(R224). `JobStarted`를 받으면 entry가 지워지고 runner는 cover에서 빠지므로 두 수가 같은 때 함께 준다. 그 runner가 받은 job이 목록에 없는 배정 job이면 그 cover는 entry 대신 R219의 수를 채운다(R187, R228). busy지만 `JobStarted` 전인 cover는 이미 GitHub가 배정한 어떤 job을 받은 runner이므로, 배정된 entry와 R219의 수만 쓰고 배정되지 않은 entry에는 주지 않는다(R213 (2)). 그 cover를 배정되지 않은 entry에 주면 그 job을 `AcquireJobs`로 가져와도 그 runner는 이미 다른 job을 돌리므로 runner 없는 배정 job이 하나 는다(추론). 그래서 그런 cover만 남고 서버가 찼으면 스케일러는 job을 가져가지 않는다(R169). 그래서 runner-up의 runner 넘겨주기(`queue.go` 142~170행 `handBackLocked`)가 필요 없다. 배정 취소된 entry는 다시 배정될 때까지 runner를 받지 않으므로 cover도 쓰지 않는다(R225, runner-up `queue.go` 172~183행과 같음). 배정 취소 뒤 `JobAvailable`이 오거나 새 `JobID`의 `JobAvailable`이 오면, 그 job은 다시 배정되지 않은 offer이므로 배정되지 않은 것으로 되돌려 다음 배치에서 다시 가져간다(R207). runner-up은 그 job을 위해 시작한 runner가 살아 있으면 다시 가져가지 않고 그 runner를 둔다(위 `queue.go` 88~101행). 이 셈에서는 살아 있는 그 runner가 cover로 세어지므로 두 번째 runner를 시작하지 않는 효과는 따로 규칙 없이 그대로이고, `AcquireJobs`만 다시 부른다. offer는 가져가야 그 scale set의 job이 되기 때문이다(actions-scaleset 스킬 references/runtime.md 4절, 5절). 같은 메시지에 다시 배정(새 `JobID`)과 앞 배정의 취소가 함께 오면 배정을 먼저 반영하므로(R206의 순서), 취소의 `JobID`가 entry의 것과 다르면 무시한다(R209, runner-up `queue.go` 107~115행과 같음). 메시지와 entry는 둘 다 `RunnerRequestID`가 0이 아니면 그 값만으로 맞춘다(R206). workflow run ID는 run을 다시 실행해도 바뀌지 않으므로(확인함: https://docs.github.com/en/actions/reference/workflows-and-actions/variables `GITHUB_RUN_ID` "This number does not change if you re-run the workflow run.", 2026-11-26 읽음) run ID와 job 표시 이름만으로는 같은 run의 다른 시도의 job을 같은 job으로 볼 수 있다(추론). runner-up은 두 key 중 하나만 맞아도 같은 job으로 본다(확인함: `queue.go` 52~59행 `keysOf`). `RunnerRequestID`가 0인 `JobAssigned`가 관찰됐으므로(actions-scaleset 스킬 references/runtime.md 4절, 이슈 #107) 한쪽이 0일 때만 run ID와 job 표시 이름을 쓴다. 대기 runner(`idle` runner, 시작 실패 뒤 남은 runner, R219로 시작한 runner)는 같은 target의 entry가 오면 그 entry의 cover가 되므로, 서버가 찬 동안에도 대기 runner가 있는 target의 job은 자리를 기다리지 않는다. cover를 쓰는 것은 자리를 새로 쓰지 않으므로 R213 (3)의 두 한도와 관계없다.
  - 자리 배치를 하는 때(R170, R212): 0001은 runner가 끝나면 그 pool의 다음 메시지(`JobCompleted`나 약 50초 뒤의 빈 poll)에서 목표를 다시 계산했다. target이 여럿이면 자리를 비운 runner와 자리를 기다리는 job의 target이 다를 수 있고, 기다리는 target의 다음 메시지는 약 50초 뒤일 수 있어 R158과 R181의 60초를 넘길 수 있다. 그래서 runner 표에서 행이 빠지면 1초 안에 서버 전체의 자리 배치를 한다(R170). 메시지를 반영한 직후와 30초마다의 대조(0001 R42) 직후에도 한다(R212). runner-up은 메시지와 10초 주기로 배치를 다시 한다(확인함: runner-up 013cc74 `internal/coordinator/serve.go` 94, 115행, `internal/config/config.go` 386~388행). 신호 drain 중에는 0001 R20대로 새 runner를 만들지 않으므로 자리 배치도 `AcquireJobs`도 하지 않는다(R220). 자리 배치는 target의 `Scale`과 같은 잠금 순서 규칙 아래에서 해, 한 target의 `Scale`과 그 target의 entry를 다루는 자리 배치가 동시에 돌지 않게 한다. runner 표의 잠금, 대기 job 목록의 잠금, target의 `Scale` 잠금을 잡는 순서와 `AcquireJobs`처럼 GitHub를 부르는 동안 잠금을 놓는 방법은 교착을 막도록 PLAN에서 정한다. 자리 배치의 시작과 `AcquireJobs`는 그 target의 R61 백오프와 R52 대기를 따른다(R186).
  - 목표(R115)와 `TotalAssignedJobs`: 고른 규칙은 `목표 = min(max-runners, JobStarted를 받은 runner + 덮인 entry + 잠시 건너뛴 entry + idle + 목록에 없는 배정 job 수)`이다. 0001의 `idle + TotalAssignedJobs`를 그대로 두지 않은 이유는 둘이다. (가) 그 값은 자리가 없어 기다리는 배정 job도 세므로, 목표가 자리 배치와 따로 움직여 `idle` 채우기(R187)가 기다리는 entry의 수만큼 runner를 시작하려 한다. (나) `AcquireJobs`로 막 가져간 job은 다음 메시지의 통계에야 들어가므로, 그 사이 그 job을 위해 시작한 runner가 목표 밖으로 보여 R37로 지워질 수 있다(추론). runner-up처럼 통계를 아예 쓰지 않는 것도 고르지 않았다(runner-up 013cc74에서 `TotalAssignedJobs`를 읽는 코드는 없다. 확인함: grep). 목록은 재시작하면 비므로(R211), 재시작 전이나 메시지를 잃은 동안 GitHub가 이미 그 scale set에 배정한 job은 목록에 없다. 통계를 쓰지 않으면 그 job은 배정 취소 뒤 다시 배정될 때(runner-up의 서술로 약 5분)까지 runner를 받지 못한다. 0001 R89의 "재시작 뒤 `TotalAssignedJobs`로 세어져 그때 runner를 받는다"도 이 경로였다. 그래서 통계는 목록이 모르는 배정 job(R219)과 목록에 남은 낡은 entry(R226)에만 쓴다. `TotalAssignedJobs`는 배정되어 기다리거나 도는 job의 합이다(actions-scaleset 스킬 references/runtime.md 4절, 라이브러리 README). 이 셈은 배정 job을 `JobStarted`로 둘로 나눈다. `JobStarted`를 받은 runner는 도는 배정 job을 세고, 배정됐고 배정 취소 표시가 없는 entry와 목록에 없는 배정 job은 아직 시작하지 않은 배정 job을 세며, 후자는 cover가 덮는다(추론). R219가 busy runner 대신 `JobStarted`를 받은 runner를 빼는 것은 hook으로 busy가 됐지만 `JobStarted` 전인 runner가 이미 cover로 세어지기 때문이다. busy로 빼면 그 runner의 job이 목록에 없는 배정 job일 때 그 job이 R219의 수에서 빠지는데 runner는 cover에 남아, 같은 runner를 두 번 센다. R219의 수는 그 target의 `Statistics`가 있는 메시지를 반영할 때만 계산하고 `Statistics`가 있는 다음 메시지까지 둔다(빈 poll과 `Statistics`가 없는 메시지는 값을 바꾸지 않는다). 메시지 사이에 runner가 끝나 `JobStarted`를 받은 runner 수가 줄 때 이 수가 늘어, 그 job의 `JobCompleted`가 오기 전에 runner 하나를 헛되이 시작하지 않게 하기 위해서다(추론). 같은 까닭으로 `JobCompleted`를 받은 뒤 컨테이너가 남은 runner는 `JobStarted`를 받은 runner 수에서 빠진다(R224). 그 job은 `JobCompleted`와 함께 온 통계에서 `TotalAssignedJobs`에 들지 않으므로(추론: `TotalAssignedJobs`의 뜻) 그 runner를 세면 R219의 수와 R226의 부족분이 하나씩 어긋나고, R115의 목표가 존재하는 runner보다 하나 커 R187이 runner를 하나 더 시작한다. 받아들이는 효과가 하나 있다. runner 행이 그 job의 `JobCompleted`보다 먼저 runner 표에서 빠지면(예: 컨테이너가 먼저 끝나 감시가 지움), 그 사이에 온 `Statistics`가 있는 메시지 하나에서 `TotalAssignedJobs`는 그 job을 아직 세는데 `JobStarted`를 받은 runner 수는 줄어 R219의 수가 1 크게 나올 수 있다. 그러면 R187이 runner 하나를 시작하고, `JobCompleted`가 든 다음 메시지에서 수가 바로잡히면 그 runner는 R185로 지워진다. 한 번의 시작이고 되풀이되지 않으므로 이를 막는 장치는 두지 않는다(추론). 반대로 메시지 사이에 대기 runner가 busy가 되어도 `JobStarted` 전까지는 cover로 남으므로 R187의 첫 단계는 runner를 더 시작하지 않고(R228), `JobStarted`는 메시지로만 오므로 그때 이 수를 다시 계산한다. 이 수만큼의 runner는 entry 없는 남은 cover로 시작하고(R187의 첫 단계), GitHub가 배정된 job을 그 scale set의 runner에게 준다(추론: 위 entry와 cover). 그래서 target의 존재하는 runner는 `JobStarted`를 받은 runner와 cover로 나뉘고, cover는 덮인 entry가 쓴 것, 잠시 건너뛴 entry가 쓸 것, 남은 cover로 나뉜다. 남은 cover가 `idle + 목록에 없는 배정 job 수`보다 많을 때만 목표를 넘으므로, 그 차이만큼의 busy가 아닌 runner만 R37로 지운다(R185). 잠시 건너뛴 entry를 목표에 넣는 것은 백오프나 속도 제한 대기가 끝나면 그 entry가 쓸 대기 runner를 그 사이에 지우지 않기 위해서다. entry가 지워져(예: runner를 받기 전에 취소된 job의 `JobCompleted`, R208) 덮을 entry가 없어진 runner도 이렇게 지워진다. 이 규칙은 가짜 메시지와 가짜 통계로 수를 세어 시험할 수 있다(설계: 테스트).
  - 낡은 entry(R225~R227): entry는 `JobStarted`나 `JobCompleted`로만 지워지므로, GitHub가 그 메시지를 보내지 않거나 메시지를 잃으면 entry가 남는다. runner-up은 run이 취소될 때 배정 취소 중인 job이나 세션과 함께 취소를 잃은 job이 하루 동안 남고, 배정된 것으로 읽히는 동안 빈 자리마다 기다릴 일 없는 runner를 시작한다고 적는다(확인함: runner-up 013cc74 `closedruns.go` 12~18행). 이 셈에서 남은 entry는 cover나 자리 하나를 계속 쓰므로 규칙 셋으로 막는다. (1) 배정 취소된 entry는 cover를 쓰지 않는다(R225). 다시 배정될 때까지 GitHub가 그 job을 아무 runner에게도 주지 않기 때문이다(runner-up `queue.go` 172~183행과 같음). (2) 통계와의 대조(R226): 배정됐고 배정 취소 표시가 없는 entry가 `TotalAssignedJobs − JobStarted를 받은 runner`보다 많으면, 그 차이만큼은 GitHub가 더는 배정된 것으로 세지 않는 entry다(추론: `TotalAssignedJobs`의 뜻). runner-up은 그런 job을 workflow run의 REST 조회로 가리지만(확인함: `closedruns.go` 59~127행 `forgetClosedRuns`), 이 스케일러는 판정에서 Actions 읽기 권한을 쓰지 않게 됐고(Areas of concern 6) job마다의 REST 조회와 그 속도 제한을 다시 들이지 않기 위해 이미 받는 통계로 한다. 한 메시지의 차이는 `AcquireJobs`로 막 가져간 job처럼(위 (나)) 늦은 통계일 수 있어, 잇단 두 메시지에서 모두 차이가 있을 때만, 앞 메시지 때 이미 배정돼 있던 entry만 지운다(추론). 어느 entry가 낡았는지는 통계로 알 수 없으므로 GitHub에게서 가장 오래 소식이 없는 entry부터 지운다(runner-up이 조용한 job을 `HeardAt`으로 고르는 것과 같은 생각, 확인함: `closedruns.go` 52~57행 `quietSince`). 잘못 지운 entry의 job은 GitHub가 다시 offer하거나 배정하면 목록에 다시 들고, 배정된 채면 그 사이 R219의 수로 runner를 받는다(추론: R219의 식). (3) 시한(R227): GitHub는 큐에서 24시간 기다린 self-hosted job을 취소하므로(확인함: INTENT Proposed outcome, https://docs.github.com/en/actions/reference/limits "Job queue time") 그보다 오래된 entry는 runner를 받을 job이 아니다. runner-up과 같이 1시간을 더한 25시간을 쓰고, runner-up처럼 자리 배치마다 본다(확인함: `queue.go` 206행, `placement.go` 34행).
  - 목록을 메모리에만 두는 이유(R211): runner-up은 대기 목록을 파일에 저장해 재시작을 넘긴다(확인함: runner-up 013cc74 `service.go` 326행이 메시지마다 `saveLocked`를 부르고, 329~333행이 `SavedState`의 `Waiting`에 대기 job을 담음). 0001은 재시작을 넘는 job 상태를 두지 않는다. 상태 폴더에는 잠금과 status socket만 있고(0001 Design 구성 요소의 status 항목), 시작 때 이전 runner 자원을 모두 지운다(0001 R16). 그래서 목록도 같은 방침을 따른다. 재시작 뒤 새 세션에서 GitHub가 기다리는 job을 `JobAvailable`이나 `JobAssigned`로 다시 보내는지는 미확인이고(Areas of concern 12), R223의 실제 시험에서 기록한다. 배정된 job은 다시 오지 않아도 R219의 수로 runner를 받는다.
  - target 오류와 목록(R210, R220): target 오류 drain과 target 오류 대기의 target은 목표가 0이고(R173, R174) runner를 받지 않으므로, 그 target의 entry를 지우고 그동안의 메시지로 entry를 더하지 않으며 `AcquireJobs`를 부르지 않는다. 그 target이 `정상`으로 돌아오면 새 세션에서 GitHub가 보내는 메시지로 목록이 다시 찬다(R194). 0001 R89(drain 중에도 `AcquireJobs`를 부름)는 이 방식에서 runner를 줄 수 없는 job을 배정으로 바꾸는 일이라 R220으로 대체한다.
  - 일시 오류와 사라진 job(R214, R216, R229): `AcquireJobs`의 결과에 그 ID가 없으면 그 job은 이미 다른 곳에 갔거나 취소된 것으로 보고 지운다(runner-up `placement.go` 173~175행과 같음). 일시 오류는 그 entry를 그대로 두고 다음 자리 배치에서 다시 시도한다. 가져간 뒤 runner 시작이 실패하면(R64) 그 runner는 runner 표에 없어 cover에 들지 않고 그 job은 그 scale set에 배정된 채이므로, 다음 자리 배치에서 자기 QueueTime 순서로 `AcquireJobs` 없이 cover나 새 runner를 받는다(R213, R214). 백오프, 속도 제한 대기, `AcquireJobs` 일시 오류로 잠시 건너뛴 entry가 있는 배치는 R187의 `idle` 채우기를 하지 않고, R187의 첫 단계(목록에 없는 배정 job)는 건너뛴 entry 수만큼의 서버 자리를 남기고서만 runner를 시작한다(R229). 그 entry가 곧 다시 볼 자리를 다른 runner가 먼저 쓰지 않게 하기 위해서다. 목록에 없는 배정 job은 GitHub가 이미 그 scale set에 배정해 기다리는 job이라, 남길 자리 밖의 자리가 있으면 미루지 않는다. 그 대가로 건너뛴 entry가 있는 동안 다른 target의 `idle` 채우기와, 남은 자리가 건너뛴 entry 수 이하일 때의 목록에 없는 배정 job의 시작이 미뤄진다. R61 백오프는 5분을 넘지 않고, 목록에 없는 배정 job은 배정 취소 뒤 다시 배정되면 entry로 들어와 R213으로 자리를 받으므로 그 지연은 한정된다(추론). 0001 R4를 대체한 R117의 60초는 그 job 말고 덮이지 않은 entry가 없을 때만 걸린다.
  - 경고(R221): runner-up처럼 `TotalAvailableJobs`가 스케일러가 아는 job보다 많으면 로그로 알린다. runner-up은 그 scale set의 모든 대기 job과 비교하지만(확인함: `service.go` 314~320행), `TotalAvailableJobs`는 배정되지 않은 job의 수이므로(추론: 필드 이름) 배정되지 않았거나 배정 취소된 entry와 비교한다. 메시지가 빠졌을 수 있음을 알리는 로그이고 동작은 바꾸지 않는다.
- `idle`의 자리(R167, R168): 대기 runner는 job이 오기 전에 자리 하나를 차지한다. 모든 target의 `idle` 합이 서버 한도를 넘으면 그 설정은 어느 때도 지킬 수 없으므로 오류 대기에 들어간다(R167). 서버 한도는 `/info`를 부른 뒤에야 알므로 이 검사는 R28의 설정 검증이 아니라 R202와 같은 Docker 용량 확인에서 한다. target 하나의 `idle`이 그 target의 `max-runners`를 넘는 것은 설정 검증(R28, 설정 표)이 막는다. runscaler도 호스트 한도가 scale set들의 최소 runner 수 합보다 작으면 설정 오류로 막는다(확인함: ysya_runscaler 6f33444 `internal/config/config.go` 576~587행 "must be >= the sum of min-runners"). 합이 서버 한도와 같으면 대기 runner만으로 모든 자리가 차서, `idle`이 0인 target의 job은 다른 target의 대기 runner가 줄지 않는 한 runner를 받지 못한다. 대기 runner는 자기 target의 job만 받으므로 그 상태가 이어질 수 있어 시작 경고로 알린다(R168). 그 밖에, `idle`을 채우는 시작과 어느 target의 대기 job이 같은 자리를 두고 겨루면 대기 job이 먼저다(R187). 자리 배치는 모든 entry와 목록에 없는 배정 job(R219)을 본 뒤 남은 자리로만 `idle`을 채우고, 이미 있는 대기 runner는 지우지 않으며, 그 대기 runner는 같은 target의 entry가 오면 그 entry의 cover가 된다(R213, R224). INTENT의 결과가 job의 실행이고 `idle`은 시작 시간을 줄이는 설정이기 때문이다. runscaler는 반대로 다른 scale set의 최소 runner 수를 남는 자리보다 먼저 채운다(확인함: ysya_runscaler 6f33444 `internal/capacity/broker.go` 9~11행 "Capacity needed to satisfy another scale set's minimum is reserved before surplus is handed out"). 그 최소 수는 busy runner를 포함한 runner 수이고, 우리 `idle`은 배정 job 위에 더하는 대기 runner 수라(0001 R1) 같은 규칙을 그대로 옮기지 않는다.
- 고르지 않은 방법: (1) 서버 한도를 target들에 나눠 각 세션의 `maxCapacity`로 보내는 것. runpool은 binding마다 남은 자리의 몫을 계산해 세션의 capacity로 보낸다(확인함: rhobuild_runpool f1a2ab3 `internal/app/delivery.go` 685~696행 `announce`). 고르지 않은 이유는 둘이다. (가) 몫이 0인 target은 `maxCapacity` 0을 보내게 되는데, 0이면 배정이 보이지 않는다(0001 R90의 이유, actions/scaleset 이슈 #133). runpool은 이를 위해 수요를 알아낼 binding 하나를 따로 정한다(확인함: 같은 파일 707~711행 `discovery`). (나) 몫이 바뀔 때마다 poll의 값이 바뀌므로 GitHub가 그 값으로 어떻게 배정하는지(미확인)에 동작이 더 많이 기대게 된다. runscaler와 runner-up은 나누지 않는다(위). (2) 서버 한도를 runscaler의 `concurrent`처럼 설정값으로 두는 것. 설정값은 Docker가 보고한 CPU·메모리를 넘는 예약 합을 허용하므로, 서버 스펙에 맞춰 제한한다는 결정(위 동시 실행 한도)과 맞지 않는다. (3) 0001과 runscaler처럼 받은 `JobAvailable`을 모두 바로 가져가는 것. 서버가 돌릴 수 없는 job까지 그 scale set의 배정으로 바꾸고, 빈 자리를 어느 job이 받을지를 GitHub가 배정된 job을 runner에게 주는 순서에 맡기게 된다(설계: 대기 job 목록과 자리 배치).
- Docker 용량 확인(R167, R201~R204): Docker 준비와 R16 뒤, 이미지 확인 다음에 `/info`를 한 번 부르고, 그 응답으로 서버 한도를 계산해(R201) INFO `server runner limit`을 필드 `limit`, `ncpu`, `memTotal`, `runnerCPUs`, `runnerMemory`와 함께 남긴다(R203). 서버 한도가 0이면(예: `runner.memory + buildkit.memory`가 `MemTotal`보다 크거나 `runner.cpus + buildkit.cpus`가 `NCPU`보다 큼) runner를 하나도 시작할 수 없으므로 오류 대기에 들어간다(R202). 컨테이너 하나의 CPU 상한이 `NCPU`를 넘으면 Docker가 생성을 거부하므로(확인함: 0001 Areas of concern 21, moby `docker-v29.6.1` `daemon/daemon_unix.go` 482~485행) `runner.cpus`나 `buildkit.cpus` 하나가 `NCPU`보다 큰 설정은 모든 시작이 실패하는데, 그때는 runner 하나의 CPU 몫도 `NCPU`보다 커 서버 한도가 0이므로 R202가 같이 드러낸다. 그래서 따로 검사하던 R118은 dropped이고, 어느 키가 원인인지 보이도록 R202의 문구가 네 키의 값을 담는다. 문구는 `server runner limit is 0: one runner reserves <cpus> CPUs (runner.cpus <값> + buildkit.cpus <값>) and <memory> bytes (runner.memory <값> + buildkit.memory <값>), Docker reports <NCPU> CPUs and <MemTotal> bytes`다. 그다음 `idle` 합을 본다(R167, 문구 `idle of all targets (<합>) exceeds the server runner limit (<서버 한도>)`). 마지막으로 target들의 `max-runners` 합이 서버 한도보다 크면 INFO `max-runners of all targets exceed the server limit`을 필드 `sum`, `limit`과 함께 남긴다(R204). 이 경우는 runscaler가 정상으로 보는 초과 배정이라(위 `maxCapacity`) WARN으로 남기지 않는다. 예약 합이 Docker가 보고한 값을 넘는 설정은 서버 한도 아래에서 생기지 않으므로 0001 R29의 경고를 없앤다(R119, R120은 dropped). 이 Mac의 Docker VM(10 CPU, 7.75 GiB, 확인함: 0001 INTENT Constraints)에서 기본값의 runner 하나의 몫은 3 CPU, 3 GiB이고 서버 한도는 min(floor(10 / 3) = 3, floor(7.75 / 3) = 2) = 2다(추론: 계산).

Actions 이벤트 파일에도 null이 오는지는 미확인이지만 null은 R126으로 거부되므로 안전한 쪽이다(Areas of concern 2).
- 구조로 판정하는 이유(R126, R127): 이벤트 이름만으로 PR 계열을 정하면 `pull_request`를 담는 다른 이름의 이벤트를 놓친다. 그래서 이름과 관계없이 최상위 `pull_request`와 `workflow_run`이 있으면 비교한다. 최상위 `repository.id`와도 같아야 하는 것은 head와 base가 서로 같아도 이 run의 저장소가 아닌 경우를 거부하기 위해서다. 이름 규칙(R128)은 이름이 PR 계열이나 `workflow_run`인데 R126, R127이 비교할 객체가 없는 보고를 거부한다. 그런 보고는 R126, R127을 거치지 않으므로, R128이 없으면 R129로 허용된다. 문서의 "The `pull_request` webhook event payload is empty for merged pull requests and pull requests that come from forked repositories."는 REST `GET /repos/{owner}/{repo}/actions/runs`의 `pull_requests` 배열에 대한 문장에서 왔고(확인함: github/docs#22501) 이벤트 파일에 대한 것이 아니다. 그래서 R128은 같은 저장소의 병합된 PR을 거부하지 않는다(OpenAPI상 closed 이벤트에도 `pull_request`가 필수, 아래 필드의 근거).

  1. `POST`가 아니면 405, `Allow: POST`(R135).
  2. 토큰 검증. 실패하면 본문을 읽지 않고 401과 `{"reason":"..."}`(R134). `host.docker.internal`로는 다른 컨테이너도 이 서버에 닿으므로, 토큰 없는 요청이 32MiB 본문을 거듭 보내도 서버가 읽지 않게 한다. 성공하면 busy 시각을 기록한다(R138).
  3. 판정이 이미 기록됐으면 본문을 읽지 않고 200과 그 판정(R132).
  4. drain 끝의 정리가 시작됐으면 본문을 읽지 않고 200과 `{"verdict":"pending"}`(R131의 예외).

- 판정과 AWS: 판정은 브랜치를 보지 않으므로 main이 아닌 job도 돈다(R141). AWS Role은 관리자 신뢰 정책이 main만 허용하므로 그런 job은 Role을 받지 못한다(R142, 0001 INTENT Problem). main job이 Role을 받는 것(R143)과 함께 보아, R142의 실패가 OIDC 경로의 고장이 아니라 신뢰 정책의 거부임을 가른다. 스케일러는 자격을 넣지 않는다(0001 R12 그대로).

**정리와 대조(R148, R149)**: 조직 runner 목록에는 이 스케일러가 만들지 않은 조직 runner도 있다. 이름 꼴과 `GetRunnerByName`의 scale set ID가 둘 다 맞아야 지우므로 다른 runner는 건드리지 않는다(0001 R17의 규칙). 목록 endpoint는 `GET /orgs/{org}/actions/runners`이고 query는 `name`("The name of a self-hosted runner."), `per_page`(최대 100), `page`이며, runner마다 필수 `name`과 `busy`가 있다(확인함: https://docs.github.com/en/rest/actions/self-hosted-runners "List self-hosted runners for an organization"). 시작 정리(R148)는 0001처럼 모든 페이지를 읽고 페이지 수 상한(`maxRunnerPages`)을 둔다. 30초마다의 대조(R149)는 조직 전체 목록을 읽지 않고 판정 없는 runner마다 `name`으로 그 runner만 조회한다. 조직에 다른 runner가 많아도 호출 수는 판정 없는 runner 하나당 30초에 한 번이다. `name`이 정확히 일치하는 것만 돌려주는지는 문서에 없으므로 결과에서 이름을 다시 비교한다. runner 이름은 `<label>-` 뒤 8자 임의값이고, 조직 안에서 유일해야 하는지는 Areas of concern 8이다.

**delete-scaleset(R150, R151)**: 명령 하나가 target 하나를 지운다. 설정 파일을 읽어 조직 이름이 대소문자 구분 없이 같은 target을 찾고(R166과 같은 비교), 설치 조회(R108)로 설치 ID와 권한을 확인한 뒤, runner group 조회(R111)로 찾은 group에서 `scaling.label` 이름의 scale set과 그 runner 등록을 지운다. 이 명령은 한 번 실행하고 끝나므로 R24의 백오프를 쓰지 않는다. 어느 조회든 실패하면 아무것도 지우지 않고 그 오류를 stderr에 쓰고 1로 끝난다. 다른 target의 scale set은 건드리지 않는다. target을 설정에서 뺄 때도 runner group을 바꿀 때처럼, 빼기 전의 설정으로 `delete-scaleset <target URL>`을 먼저 실행한다(README에 적는다). 지우지 않으면 그 조직의 scale set은 listener 없이 남고, 그 라벨의 job이 그 scale set에 배정되어 GitHub의 24시간 큐 시한까지 기다릴 수 있다(추론). 0001 R49대로 이 명령은 스케일러가 단일 실행 잠금을 잡고 있으면 아무것도 지우지 않으므로, 한 조직의 scale set을 지우려면 스케일러를 멈춰야 하고, 그때 다른 조직의 job도 신호 drain을 거친다(README에 적는다).

**서비스 응답 확인(R153)**: v0.5.0은 poll 시도 하나를 `MessagePollTimeout`(2분)으로 끊고 실패한 시도를 재시도 설정(최대 4번 더)으로 다시 보내며 시도마다 새 2분을 준다(확인함: v0.5.0 `session_client.go` 103~114행 주석, `http_client.go` 73행). 그래서 0001의 끊지 않는 poll은 연결은 되지만 답하지 않는 서비스에서 최대 약 10분 넘게 이어질 수 있어, INTENT의 약 6분을 넘는다. 건강한 서비스는 빈 poll을 약 50.3초 붙잡는다(확인함: 0001 Design 스케일링 흐름 2, 끊지 않은 poll 18번). 그래서 끊지 않는 poll에 70초 시한을 두고, 그 시한으로 끝나면 서버가 답하지 않은 것으로 본다. 감지는 5분 뒤 첫 poll(10초 간격이므로 5분~5분 10초) + 70초로 6분 20초 안이다(R162의 6분 30초). 서버가 70초 넘게 붙잡은 정상 poll은 새 세션 하나로 끝난다(R25의 백오프 1초부터). 로그는 WARN `message poll got no answer`와 경과 시간이다.

**status(R152, R180, R205, R222)**: status JSON은 `{"state","serverLimit","targets":[{"url","state","busy","idle","waitingJobs","maxRunners","startFailures","lastStartError","lastStartErrorAt","lastError","lastErrorAt"}],"lastError","lastErrorAt"}`이다. target의 `state`는 `starting`, `running`, `error-draining`, `error-wait` 중 하나이고 출력은 각각 `시작 중`, `정상`, `오류 drain 중`, `오류 대기`다. target 줄은 `<target URL>: <상태>, 실행 중 <busy>, 대기 <idle>, 대기 job <waitingJobs>, 최대 <maxRunners>, 연속 시작 실패 <startFailures>`이고(`maxRunners`는 그 target의 `max-runners`, R205. `waitingJobs`는 마지막 자리 배치에서 덮이지 않은 그 target의 entry 수, R222), 시작 실패가 있으면 0001처럼 `(<lastStartError>, <lastStartErrorAt>)`를, 상태가 `오류 drain 중`이나 `오류 대기`면 `, 오류: <lastError> (<lastErrorAt>)`를, `오류 대기`면 그 뒤에 `, 다음 시도 <nextRetryAt>`을 붙인다(JSON의 target 객체는 처음부터 `nextRetryAt` 키를 가지며, `오류 대기`가 아니면 값은 `null`이다). `전체` 줄의 `<n>`과 `<m>`은 모든 target 줄의 `busy`, `idle` 합이고, 최대는 `serverLimit`(R201의 서버 한도)이다. `serverLimit`은 R201로 계산하기 전에는 `null`이다. 맨 아래 `마지막 오류`는 0001처럼 스케일러 전체에서 가장 최근의 오류다. 스케일러 전체의 `state`는 0001과 같은 값을 쓴다. `상태: 시작 중`(R58)일 때도 target 줄을 출력해 어느 target이 시작 단계의 백오프에 있는지 보인다(R198). 한 target이 `오류 drain 중`이나 `오류 대기`여도 다른 target이 `정상`이거나 `시작 중`이면 `상태: 정상`이고 0으로 끝난다. 상태 `정상`인 target도 `시작 중`인 target도 없으면(`오류 drain 중`과 `오류 대기`가 섞인 경우 포함) JSON의 `state`는 `running` 그대로이고, 출력의 첫 줄만 `상태: 정상 target 없음`으로 바뀌며 1로 끝난다(R197). 그래서 감시하는 쪽은 종료 코드로 job을 받는 target이 하나도 없음을 안다. `시작 중`인 target이 있으면 곧 job을 받을 수 있으므로 0을 유지한다. `service stop`은 스케일러 전체의 state만 읽으므로 바뀌지 않는다.

**오류 범위(R171~R180, R190~R198)**: 오류는 그 오류가 닿는 범위에만 건다. 0001이 정하지 않고 남긴 범위(0001 Areas of concern 2)를 target 단위로 정한 것이다.
- target 범위: 한 target의 GitHub 호출(그 target의 설치 조회, runner group 조회, scale set 호출, 메시지 세션 호출, `AcquireJobs`)이 영구 오류로 실패하면 그 target만 멈춘다. 이 호출들은 그 target의 설치 ID, 설치 권한, runner group에 달려 있어(설계: 구성 요소) 다른 target과 관계가 없다. 시작 단계면 그 target은 바로 target 오류 대기에 들어가고(R172), 실행 중이면 target 오류 drain에 들어간다(R171). target 오류 drain은 0001 오류 drain 규칙을 그 target에만 쓴다(R173): 그 target은 새 runner를 만들지 않고, 대기 runner는 R37로 지우고, busy runner는 끝나거나 `shutdown.drain-timeout`이 지날 때까지 기다린 뒤 남은 컨테이너를 지우고 `RemoveRunner`를 1회 시도한다. 세션을 쓸 수 있으면 그동안 세션은 유지하지만(R54) `AcquireJobs`는 부르지 않고(R220), 그 target의 entry는 지운다(R210). 그 뒤 target 오류 대기에서 그 target은 세션을 닫고, R174의 간격으로 시작 단계만 다시 시도한다. 시도가 성공하면 `정상`으로 돌아간다. 그 target의 runner가 빠진 자리는 R170으로 다른 target이 쓴다.
- 서버 범위: 설정, Docker, 잠금, status socket, job 확인 서버 listen은 모든 target이 같이 쓰므로 그 오류는 스케일러 전체에 건다(R176, 0001 R60, R78). 서명기도 하나지만 개인키 파일은 설정 검증이 읽고 파싱하므로(0001 Design, `internal/config`의 `ReadAppPrivateKey`) 읽지 못하는 키나 권한 비트가 틀린 키(0001 R30)는 시작 때 설정 오류로 서버 범위에 드러난다. App 자체의 인증이 거부되는 경우(App 삭제, 키 폐기)는 모든 target의 호출이 각자 영구 오류를 받아 target마다 target 오류 대기에 들어가고, 모두 들어가면 R197의 `status`가 된다. 이때도 target마다 다시 시도하므로, 원인이 GitHub 쪽에서 고쳐지면(App 권한 승인, 설치) 재시작 없이 돌아온다. 키 파일을 바꾼 경우는 설정을 다시 읽어야 하므로 재시작한다(설정은 시작 때 한 번 읽는다).
- 다시 시도(R174): 참고 구현은 target 하나의 오류에서 그 target만 스스로 다시 시도한다. runner-up은 세션이 끝나면 그 target의 scale set 확인부터 세션까지 30초 뒤 다시 하고, 찾을 수 없는(404) target은 30초에서 두 배씩 늘려 7번까지 다시 시도한 뒤 그 target만 멈춘다(확인함: runner-up 013cc74 `internal/coordinator/github.go` 202~210행, 238~266행, 272~289행 `serveSet`). ARC는 끝난 listener Pod를 지우고(확인함: ARC eca1a62 `controllers/actions.github.com/autoscalinglistener_controller.go` 529~531행, 984~991행 `listenerPodIsDead`), Pod가 없으면 새로 만든다(확인함: 같은 파일 559~583행). runscaler도 실행 중 listener 오류를 scale set마다 다시 연결한다(아래). 그래서 이 스케일러도 target 오류 대기에서 시작 단계를 다시 시도하고, 조직 owner가 GitHub 쪽 원인(App 설치, 권한 승인, runner group)을 고치면 재시작 없이 그 target이 돌아오게 한다. runner-up은 404를 되풀이해 부를 때 "every try uses the sign-in's allowance, which every scale set and GitHub read shares: 29 sessions on one old name used it up for hours"라고 적는다(확인함: 같은 파일 232~235행). 그래서 간격을 30초에서 두 배씩 늘려 30분에서 멈춘다. 상한에서는 target 하나가 30분에 시도 한 번이고, 시도 한 번의 호출은 설치 조회 1번, runner group 조회 0~1번, 조직 runner 목록의 페이지 수만큼, R148의 후보마다 `GetRunnerByName` 1번, scale set 조회 1번과 없을 때 생성 1번, 세션 생성 1번에 라이브러리의 토큰 교환을 더한 것이다. 시도 중 속도 제한 응답을 받으면 다음 시도는 R52가 정한 시각과 R174의 간격이 정한 시각 중 늦은 때에 한다. 시도 안에서 R24를 쓰지 않는 것(R193)은 일시 오류가 이어질 때 R24의 60초 상한 백오프가 R174의 30분 간격 안에서 끝없이 도는 것을 막기 위해서다. runner-up처럼 7번 뒤 멈추지 않는 것은 멈춘 target을 되살리려면 재시작이 필요해 다른 조직의 job까지 신호 drain에 들게 하기 때문이다. 설정 오류와 서버 범위 오류는 0001 R47대로 다시 시도하지 않는다. 설정은 시작 때 한 번 읽고(INTENT Problem), Docker와 잠금은 운영자가 고치는 호스트 쪽 원인이기 때문이다.
- 참고 구현의 범위: runner-up은 target의 세션 오류가 다른 target의 세션을 멈추지 않는다(확인함: 위 `RunSet`, `Sessions.Match`의 세션마다 고루틴). ARC는 scale set마다 listener 프로세스 하나가 그 scale set 하나의 설정만 받는다(확인함: ARC eca1a62 `cmd/ghalistener/config/config.go` 37~40행, `cmd/ghalistener/main.go` 98~105행). runscaler는 실행 중 listener 오류를 scale set마다 5초에서 1분까지 늘리는 백오프로 다시 연결하지만(확인함: ysya_runscaler 6f33444 `cmd/runner/main.go` 733~760행), 한 scale set의 시작 단계 오류(scale set 생성 실패 등)는 모든 scale set을 멈춘다(확인함: 같은 파일 579~583행 `cancelRun()`, 642~645행). 이 스케일러는 시작 단계 오류도 target에만 거는 runner-up 쪽을 따른다. 한 조직의 설치나 group 설정 문제로 다른 조직의 job이 멈추지 않게 하는 것이 INTENT의 "each organization chooses its own repositories"와 맞기 때문이다.
- 신호(R178, R179): 신호 drain은 스케일러 전체에 걸리고 모든 target의 세션을 닫는다. target 오류 drain 중에 첫 신호를 받으면 그 target의 busy runner도 신호 drain으로 기다린다. 0001 R21이 오류 drain 중 신호에 기다리지 않은 것은 스케일러 전체가 이미 멈춘 경우였고, 이제는 다른 target의 job이 돌고 있으므로 그 job을 죽이지 않게 한다. 두 번째 신호는 R21대로 모든 target에서 기다리지 않는다. 신호 drain이 시작되면 target 오류 대기의 다시 시도는 멈추고, 진행 중인 시도는 호출을 취소해 세션을 만들지 않는다(R192). 신호 drain 중 target의 영구 오류는 0001 R100처럼 로그만 남기고 target 오류 drain으로 바꾸지 않는다(R191). 처음 시작 중인 target도 신호를 받으면 시작 단계를 멈춘다(R196).
- drain 끝의 정리: 신호 drain의 정리는 모든 target의 세션을 닫고 남은 runner를 지우며, 정리 시한(0001 R57의 최대 55초)은 target 수와 관계없이 하나를 같이 쓴다. target 오류 drain의 정리는 그 target의 세션과 runner에만 하고, R131의 `pending` 예외도 그 target의 runner 보고에만 적용한다. 0001 R55의 "오류 대기에 들어가기 전에 진행 중인 감시와 대조의 재시도를 멈춘다"는 그 target의 runner의 감시와 삭제 재시도만 멈추고, 30초마다의 대조(R42)는 runner 표 전체에 하나라 다른 target을 위해 계속한다(R190).

**시작 순서**: 서버 단계는 잠금(R78) → status socket(R60) → 설정 읽기와 검증 → Docker 준비 → 정리(R16) → 설정 오류면 오류 대기(R28, R30, R105~R107, R166) → Docker 노출 확인(R79) → 이미지 확인 → Docker 용량 확인(R201, R203, R202, R167, R204, R168의 경고 순) → job 확인 서버 listen이다. 여기까지의 영구 오류는 스케일러 전체의 오류 대기다(R176). 그 뒤 target마다 고루틴 하나가 따로 설치 조회(R108~R110) → runner group(R111) → 정리(R148) → scale set(R112) → `SetSystemInfo` → 첫 세션 → listener를 진행한다(R177). target 단계의 일시 오류는 그 target 안에서 R24로 다시 시도하고, 영구 오류는 그 target만 target 오류 대기에 넣는다(R172). R148는 0001 R17처럼 시작을 막지 않는다. job 확인 서버를 target 단계 전에 여는 것은 어느 target이든 첫 세션 뒤 runner를 만들 수 있기 때문이다. 스케일러 상태는 어느 target이든 첫 세션을 만들면 `정상`이 되고(R178), 그때 아직 시작 단계인 target의 줄은 `시작 중`이다. 첫 세션 전에 모든 target이 target 오류 대기에 들어가면 스케일러의 시작은 끝난 것으로 보고 R197의 `status`가 되며, target마다 R174대로 다시 시도한다(R195).

R145~R147의 fork는 App 설치가 필요 없는 다른 계정의 것이다). 이 넷은 App이 설치된 두 번째 조직이 필요하므로 이 변경의 실제 시험에서 하지 않고, 이 변경이 `implemented`가 되는 조건도 아니다. ## Open questions from the intent

- 서버 전체 한도는 runner 수인가 CPU·메모리 합인가, 어떤 기본값이 바뀌고 이 Mac에서 저장소 5곳 결과를 어떻게 확인하는가? → 답: CPU·메모리로 정하는 runner 수다(결정: 2026-11-26, 사용자). 서버 한도는 설정값이 아니라 시작 때 Docker가 보고한 `NCPU`, `MemTotal`과 runner 하나의 몫(`runner.cpus + buildkit.cpus`, `runner.memory + buildkit.memory`)으로 `min(floor(NCPU / CPU 몫), floor(MemTotal / 메모리 몫))`을 계산한다(R201, 설계: 동시 실행 한도). 설정의 모든 조직이 이 한도 하나를 같이 쓰고, 자리가 없는 job은 스케일러가 가져가지 않아 GitHub 큐에서 기다리며, 자리가 나면 모든 조직에 걸쳐 QueueTime이 이른 job부터 가져간다(R114, R169, R170, R184, R214). 조직마다 자기 `targets.max-runners`(기본 2)를 두고 그 값을 그 세션의 `maxCapacity`로 보내며(R115, R116), 그 합은 서버 한도를 넘어도 된다(R204). 기본값은 바뀌지 않는다(runner 1 CPU·1GB, BuildKit 2 CPU·2GB). 이 Mac(Docker VM 10 CPU, 7.75 GiB)에서 기본값의 서버 한도는 2이고, 빌드가 더 필요하면 job마다의 CPU·메모리를 올리며 그만큼 서버 한도가 줄어든다. 저장소 5곳 결과는 스케일러가 저장소마다 다르게 처리하지 않으므로(조직 단위 scale set 하나, 설계: target) 저장소 2곳에서 job 5개로, runner 하나의 몫을 1.5 CPU, 1,280 MiB로 줄인 시험 설정(서버 한도 6)과 `max-runners = 5`, 가벼운 시험 job으로 확인한다(R157, R158, 설계: 테스트). 서버 한도가 0이면 시작 때 오류 대기다(R202).
- 조직 권한 "Self-hosted runners: Read and write"는 누가 더하고 App을 조직에 설치하며, 그 권한으로 라이브러리 호출이 되는가? → 답: App 소유자인 사용자가 App 설정에 권한을 더하고, 조직 owner가 설치(또는 바뀐 권한 승인)를 한다. ARC 문서상 조직 수준 등록에는 이 권한과 Metadata 읽기면 되고 Administration은 저장소 범위에만 필요하다(확인함, 설계: App 권한). 스케일러는 시작 때 이 권한이 설치에 있는지 확인한다(R110). 우리 호출 전부가 되는지의 실제 확인은 넘김: Areas of concern 5.
- 0001 설정 형식(pool마다 저장소 URL과 workflow 허용 목록)은 어떻게 되는가? → 답: 호환하지 않고 오류 대기에서 고칠 키를 알린다(R107, 설계: 설정 파일). `[[pools]]`는 `[scaling]`, `[[targets]]`, `[runner]`·`[buildkit]` 키로 옮기고, 허용 목록은 없앤다. `[[targets]]`는 조직마다 하나씩 둘 이상 둘 수 있다(R105, R166). 바꾸거나 없애는 0001 R은 설계의 "바꾸거나 없애는 0001 요구사항"에 모두 적었다. 허용 목록이 막던 경우가 열리는 것은 넘김: Areas of concern 4.
- 0001이 넘긴 다섯 항목 → 답: INTENT의 정리대로다. 기존 workflow의 `runs-on` 변경과 main workflow의 첫 `kubectl apply -f`는 범위 밖인 workflow 이전에 속한다. reusable workflow 허용 규칙은 허용 목록이 없어져 필요 없다(R129). `environment:` job은 범위 밖이다. 빌드 메모리 측정은 하지 않고 job마다의 제한은 기본값이 있는 설정으로 남긴다(R121, R122).
- fork 거부가 fork pull request가 일으킨 `pull_request_target`과 `workflow_run` run도 덮는가? → 답: 덮는다. 최상위 `pull_request`가 있으면 head, base, run 저장소의 ID로(R126), 최상위 `workflow_run`이 있으면 `workflow_run.head_repository`, `workflow_run.repository`, run 저장소의 ID로(R127) 가르고, 실제 실행으로 확인한다(R146, R147). 같은 저장소에서 일으킨 두 이벤트의 run은 허용한다. 두 이벤트 모두 GitHub가 "Running untrusted code on the ... trigger may lead to security vulnerabilities."라고 경고한다(확인함: events-that-trigger-workflows 두 절). 남은 미확인(실제 값, `pull_request_target`이 일으킨 `workflow_run`)은 넘김: Areas of concern 2.

## Areas of concern

1. 판정은 hook이 보낸 이벤트 파일을 믿는다. runner가 hook handler 직전에 서버 job 메시지의 값으로 그 파일을 쓰고, hook이 job의 첫 pre-job step이며, hook 환경에 `GITHUB_EVENT_NAME`과 `GITHUB_EVENT_PATH`가 있고 workflow `env:`는 들어가지 않는다는 것은 확인했다(확인함: actions/runner v2.338.2 d1eb12d 소스, run-scripts 문서. 설계: 판정의 "이벤트 파일을 믿는 근거"). 남은 미확인은 셋이다. (1) 우리 runner 이미지의 실제 실행에서 그 파일에 R126, R127의 값이 오는지(R145~R147의 실제 시험에서 비교 결과만 기록해 본다). (2) 우리 runner 이미지의 hook 환경에 `GITHUB_EVENT_NAME`과 `GITHUB_EVENT_PATH`가 실제로 있는지(R145~R147의 기록 이미지 시험에서 두 변수의 존재를 다시 본다). (3) runner를 올린 뒤에도 `WriteWebhookPayload`가 hook handler 전에 불리고 hook이 첫 pre-job step인지. runner 버전을 올릴 때마다 위 소스 위치를 다시 본다. Owner: 사용자.
2. 이벤트 파일의 fork 경우 값: 다음은 미확인이고 실제 실행으로 본다. (1) fork PR의 `pull_request`와 `pull_request_target` 이벤트 파일에 `pull_request.head.repo.id`와 `pull_request.base.repo.id`가 모두 오고 서로 다른지. (2) fork PR의 run이 일으킨 `workflow_run`의 `workflow_run.head_repository.id`가 fork의 ID인지. (3) `pull_request_target`(fork PR)의 run이 일으킨 `workflow_run`은 그 run이 기본 브랜치에서 돌았으므로 `head_repository`가 base 저장소여서 R127을 통과할 수 있다(추론: actions/checkout f548e57 `unsafe-pr-checkout-helper.ts`의 주석). 통과하면 fork의 입력이 `pull_request_target` run의 artifact를 거쳐 우리 runner에 닿는다. (4) 지운 fork의 `head.repo`가 null로 오는지(낮은 우선순위. null은 거부되므로 안전한 쪽이다). (5) runner는 수를 double로 들고 있다가 직렬화하므로(확인함: actions/runner v2.338.2 `NumberContextData.cs`) 2^53을 넘는 ID는 이벤트 파일에서 정밀도를 잃어 서로 다른 ID가 같게 쓰일 수 있다. 이 저장소의 ID는 10자리 수이고(확인함: 2026-11-25 `gh api repos/<owner>/<repo>`의 `id` 자릿수) 2^53은 9,007,199,254,740,992(16자리)다. 다른 저장소의 ID가 2^53에 닿는지는 미확인이다. 관찰이 R126~R128의 가정과 다르면 SPEC을 고친다. Owner: 사용자.
3. 공개 저장소에서 쓰기 권한이 없는 사람이 일으키는 job(결정: 2026-11-26, 사용자, GitHub 설정에 맡김). 스케일러는 fork PR(R126, R127) 밖에서 job을 일으킨 사람의 권한으로 거부하지 않는다. ARC와 terraform-aws-github-runner에도 그런 코드는 없다(확인함: ARC eca1a62와 terraform-aws-github-runner 클론의 grep). GitHub는 "self-hosted runners should almost never be used for public repositories on GitHub"라고 적는다(확인함: https://docs.github.com/en/actions/reference/security/secure-use). 이 위험을 줄이는 GitHub 쪽 설정은 다음과 같다. runner group의 공개 저장소 허용은 기본으로 꺼져 있다(확인함: https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/manage-access "By default, only private repositories can access runners in a runner group"). fork PR의 workflow run은 쓰기 권한이 있는 maintainer의 승인을 요구하게 할 수 있다(확인함: https://docs.github.com/en/actions/how-tos/manage-workflow-runs/approve-runs-from-forks "Workflow runs triggered by a contributor's pull request from a fork may require manual approval"). Actions 정책의 workflow execution protections는 actor rule(누가)과 event rule(어떤 이벤트)로 run을 막는다(확인함: https://docs.github.com/en/organizations/managing-organization-settings/actions-policies/workflow-execution-protections "Event rules control which events are permitted, such as `push`, `pull_request`, `pull_request_target`, and `workflow_dispatch`."). 그 문서는 공개 저장소의 `pull_request_target`을 막는 기본 정책이 2026-12-02부터 적용된다고 적는다(확인함: 같은 문서). 그 기능을 Free plan 조직이 쓸 수 있는지는 문서에 없다(미확인). 이 결정 아래 열린 경로는 다음과 같다. (a) fork PR에 단 `issue_comment`(`/deploy` 같은 ChatOps)로 PR head를 checkout하는 workflow: payload에는 `issue.pull_request`의 URL만 있고 head 저장소가 없어(확인함: github/rest-api-description c9c95fe의 issue comment webhook 스키마) 이벤트 파일로 가를 수 없다. (b) 두 단계 `workflow_run` 연쇄: fork PR → GitHub 호스팅 runner의 run A → A가 일으킨, 기본 브랜치에서 도는 run B → B가 일으킨 run C. C의 `workflow_run`은 B이고 B의 `head_repository`는 base 저장소라 R127을 통과하며(추론), C가 A의 artifact를 내려받으면 fork의 내용이 우리 runner에서 쓰인다. (c) 같은 저장소 PR에 외부인이 남긴 `pull_request_review`: head와 base가 같아 허용되고, 리뷰 본문은 외부인이 정한다. (d) `watch`, `fork`, `discussion_comment`: 누구나 일으킬 수 있고 기본 브랜치의 workflow가 돈다(추론: events-that-trigger-workflows의 각 활동과 공개 저장소의 기본 권한). 일으킨 사람의 쓰기 권한은 `author_association`으로 정할 수 없고(그 값은 관계를 나타냄. 확인함: OpenAPI `author-association` enum, GraphQL `CommentAuthorAssociation` 설명) 정확히 보려면 REST 협업자 권한 조회(`GET /repos/{owner}/{repo}/collaborators/{username}/permission`)가 필요하다. 이 설계는 그 조회를 하지 않는다(R123). 그래서 INTENT가 자격 노출을 받아들인 이유 중 "쓰기 권한이 있는 사람만 fork가 아닌 job을 시작한다"는 공개 저장소에서는 위 경로에서 맞지 않는다. Owner: 사용자 (결정: GitHub 설정에 맡김).
4. 0001의 최신 run 조건(0001 판정 8)과 `allowed-events` 제한(0001 판정 3, `push`, `workflow_dispatch`, `schedule`만 허용해 `pull_request_target`과 `workflow_run`을 막음)이 이 변경에서 빠진다. 그 결과 다음이 허용된다. (1) 쓰기 권한이 있는 사람의 옛 main run 재실행: 재실행은 원래 커밋 SHA와 ref로 30일까지 된다(확인함: 0001 Areas of concern 19에 인용한 re-run 문서). main ref이므로 관리자 신뢰 정책의 main 조건을 통과해 AWS Role을 받고 옛 코드를 배포할 수 있다(추론. 신뢰 정책이 옛 커밋을 가르는지는 미확인, 0001 Areas of concern 19 (6)). (2) 같은 저장소의 `pull_request_target`과 `workflow_run`: 기본 브랜치 ref로 돈다(확인함: 설계 판정의 이벤트 파일로 판정하는 이유). 기본 브랜치가 main이면 그 run이 Role을 받는지는 신뢰 정책의 subject 조건에 달렸다(미확인). 최신 run 조건을 되살리려면 같은 workflow의 다른 run을 REST로 조회해야 하는데, 그 값은 이벤트 파일에도 `JobStarted`에도 없어(추론) "판정하려고 GitHub에 요청을 보내지 않는다"(R123)와 맞지 않는다. 선택지(사실만 적음): (a) 받아들인다. (b) REST 조회를 되살리고 R123을 바꾼다. 0001처럼 Actions 읽기 권한, job마다의 조회, 조회 실패 거부(0001 R65), 속도 제한이 다시 생긴다. 이벤트 제한만은 보고된 이벤트 이름으로 REST 없이 할 수 있지만, 서버 전체에 목록 하나라 "fork pull request만 거부" 결정과 INTENT의 "어느 브랜치, pull request, 수동 실행이든 돈다"를 좁힌다. (c) GitHub 쪽 통제: workflow execution protections의 event rule로 저장소별로 `pull_request_target`, `workflow_run`을 막는다(확인함: Areas of concern 3의 문서. Free plan에서 되는지는 미확인). environment 보호 규칙(필수 검토자)은 `environment:` job이 INTENT 범위 밖이라(OIDC subject가 달라짐) 이 변경에서는 쓰지 못한다. 재실행 자체를 막는 GitHub 설정은 찾지 못했다(미확인). 다른 스케일러도 재실행이나 이벤트 종류로 막지 않는다. runner-up은 fork에서 온 job만 거부하고 "It allows every other job from the repository itself"라고 적으며, 재실행은 "Rerunning a failed job is left to GitHub and the repository"라고 적는다(확인함: runner-up 013cc74 `README.md` "Pull requests from forks" 절, `VISION.md`). ARC(eca1a62)는 이벤트 이름을 지표 라벨에만, elastic-fruit-runner(bcb9c8e)는 실행 기록에만 쓰고, runscaler(6f33444)와 runpool(f1a2ab3)에는 관련 코드가 없다(확인함: 각 클론의 grep). Owner: 사용자 (결정: (a) 받아들임. 쓰기 권한이 있는 사람의 재실행과 같은 저장소의 `pull_request_target`, `workflow_run`은 허용되고, 배포 통제는 저장소 쓰기 권한과 관리자 신뢰 정책에 맡긴다).
5. App에 Organization permission "Self-hosted runners: Read and write"를 더하는 것은 App 소유자인 사용자가, 조직 설치와 바뀐 권한의 승인은 조직 owner가 한다. 이 권한으로 scale set 생성, 세션, JIT, `RemoveRunner`, 조직 runner 목록과 이름 조회(R148, R149), `delete-scaleset`이 모두 되는지는 ARC 문서와 REST 문서 도입부에서 본 것이고 실제 호출로는 미확인이다. 조직 runner 목록 문서의 endpoint 절은 fine-grained 권한을 따로 적지 않는다(확인함: self-hosted-runners 문서). `name` query가 정확히 일치하는 runner만 돌려주는지도 문서에 없다(미확인, 결과에서 이름을 다시 비교함). App이 설치되지 않은 조직에 대한 `GET /orgs/{org}/installation`의 응답 코드는 문서에 200만 있으므로(R109의 404), 미설치 조직의 응답 코드는 실제 호출로 확인한다(R182. 나중 시험이라 그때까지 미확인이다, Design 테스트). 이미 설치된 다른 곳의 권한 승인도 같이 요구될 수 있다. Owner: 사용자.
6. 쓰지 않게 된 App 권한: 이 변경의 호출은 Repository permission "Administration: Read and write"(저장소 범위 등록용)와 "Actions: Read"(0001의 run 조회용)를 쓰지 않는다(설계: App 권한). 두 권한을 App에서 뺄지, 나중의 개인 계정 저장소 target(Administration 필요)을 위해 둘지 정한다. 빼면 그 App을 설치한 다른 곳에도 영향이 있다. Owner: 사용자.
7. runner group: 공개 저장소를 쓰려면 조직 owner가 그 group에서 공개 저장소를 허용해야 한다(Areas of concern 3). 기본 group의 ID 1은 ARC의 관례이고 REST 문서의 예시에도 나온다(확인함: 설계 runner group의 group 목록과 jitconfig 예시). 그러나 문서는 ID 1을 보장한다고 적지 않고 스키마는 `default` boolean으로 기본 group을 가르므로, 모든 조직에서 ID가 1인지는 미확인이다. REST의 group 생성 기본값 `visibility: all`과 관리 문서의 "only private repositories" 기본이 서로 다른 축이라, 실제 group의 저장소 접근과 공개 허용은 시험 전에 조직 설정에서 본다. 다른 group에는 같은 이름의 scale set을 둘 수 있으므로(확인함: deploy-runner-scale-sets 문서, 설계: runner group), `targets.runner-group`을 바꾸면 옛 scale set이 남고 운영자가 바꾸기 전에 `delete-scaleset`으로 먼저 지운다. Owner: 사용자.
8. runner 이름: 이름은 `<label>-` 뒤 소문자 16진수 8자 임의값이다. 이미 있는 이름으로 JIT를 발급하면 구별할 수 있는 오류로 실패한다(확인함: actions/scaleset v0.5.0 `errors.go` 24행 `RunnerExistsError = scalesetError("runner exists")`, 237~238행이 서비스의 `AgentExistsException`을 이 오류로 바꿈). ARC는 이 오류에서 기존 runner가 같은 scale set이면 지우고 다시 시도하고, 아니면 "runner with the same name but doesn't belong to this RunnerScaleSet"으로 실패한다(확인함: ARC eca1a62 `controllers/actions.github.com/ephemeralrunner_controller.go` 859~893행). 그래서 이름은 scale set 하나를 넘어 겹친다(추론: ARC의 처리). 유일성의 범위가 조직 전체인지는 문서에 없다(미확인). 겹쳐서 JIT 발급이 실패하면 R64의 시작 실패로 세고 다음 poll에 새 이름으로 다시 시도한다. 조직에 같은 꼴 이름의 다른 runner가 있어도 R148는 scale set ID가 다르면 지우지 않는다. 실제 실행에서 겹친 이름의 JIT 발급 결과를 볼지 정한다. Owner: 사용자.
9. fork PR이 잇달아 오면 job마다 runner 자리 하나를 거부될 때까지 쓴다(판정 1초 안, R131. 거부 뒤 컨테이너가 없어질 때까지 최대 40초, R145). 공개 저장소에서는 누구나 fork PR을 열 수 있으므로, 그동안 다른 저장소의 job이 GitHub 큐에서 기다릴 수 있다(가용성). GitHub의 fork run 승인 설정(Areas of concern 3)을 켜면 승인 전에는 job이 runner에 오지 않으므로 줄어든다. Owner: 사용자.
10. 시험 저장소와 조직: R156~R158은 조직 저장소 2곳과 그 사이에 runner group에 더할 저장소 하나가, R145~R147은 다른 계정의 fork와 pull request가 필요하다. 두 번째 조직은 나중 시험(R181~R183, R199, Design 테스트)에만 필요하고, 이 변경의 실제 시험(R200, R223 포함)과 나중 시험인 R230은 조직 하나로 한다. 나중 시험 때는 그 조직에 App이 Organization permission "Self-hosted runners: Read and write"로 설치되어 있고, 그 runner group이 시험 저장소를 허용하며, 그 저장소의 main에 시험 workflow가 있어야 한다. R182, R183, R199는 그 조직의 App 설치를 지웠다가 다시 설치하므로 조직 owner의 일이고, 다시 설치하면 설치 ID가 바뀔 수 있으나 스케일러는 시작 때 조회하므로(R108) 설정은 바뀌지 않는다(추론: 설치 ID를 설정에 두지 않음). 공개 저장소에서 R146을 하려면 2026-12-02 뒤에는 `pull_request_target`을 허용하는 event 정책이 필요하다(Areas of concern 3의 문서). 기존 저장소를 쓸지, 조직에 임시 저장소를 만들고 시험 뒤 지울지, fork를 어느 계정으로 만들지, 시험 workflow를 각 main에 쓰는 것은 모두 사용자 승인 사항이다. Owner: 사용자.
11. 서비스 무응답 감지(R153, R162): 70초 시한은 건강한 서버가 빈 poll을 약 50.3초 붙잡는 관찰(18번)에 기댄다. 서버가 붙잡는 시간을 늘리면 5분마다 세션을 다시 만들게 된다(로그로 드러남). 실제 실행에서 "연결은 되지만 답하지 않는" 상태를 만드는 방법(호스트 방화벽 규칙으로 응답 패킷을 버림, 가로채는 프록시 등)은 이 Mac의 설정을 바꾸므로 사용자가 정한다. 연결 자체를 막으면 10초 poll이 바로 일시 오류가 되어(0001 스케일링 흐름 2) 6분 경로를 시험하지 못한다. Owner: 사용자.
12. 여러 조직 target에서 남은 미확인은 셋이다. (1) 자리를 기다리는 job(R169): 스케일러는 자리가 없는 `JobAvailable` job을 가져가지 않고 대기 job 목록에 둔다(R169, R206). 그러나 target마다 세션이 자기 `max-runners`를 `maxCapacity`로 보내고(R116) 그 합은 서버 한도를 넘을 수 있으므로(R204), GitHub가 poll마다 알린 수만큼의 job을 스스로 그 scale set에 배정해(추론: runner-up 013cc74 `internal/coordinator/service.go` 257~258행 "GitHub assigns most jobs to the scale set itself, as many as the capacity each poll announces". runner-up 자신의 서술이고 GitHub 문서가 아니다) 배정된 job이 서버 한도 때문에 runner를 받지 못하고 기다릴 수 있다. 가져가지 않는 것만으로는 기다리는 모든 job이 배정을 피하지 못한다. 라이브러리 README는 배정됐지만 runner가 제때 가져가지 않은 job의 배정을 GitHub가 취소하고 다시 큐에 넣으며 "This can happen up to 3 times with incremental delays"라고 적는다(확인함: actions/scaleset v0.5.0 `README.md` 116행). runner-up은 runner가 5분 안에 가져가지 않은 배정 job을 GitHub가 `FinishTime` 없이 되가져가고 곧 다시 배정한다고 적는다(추론: runner-up 013cc74 `internal/coordinator/service.go` 293~296행, `README.md` 560~561행 "GitHub takes an assigned job back when no runner takes it in five minutes". runner-up 자신의 서술이고 GitHub 문서가 아니다). 스케일러는 그 취소를 받아도 entry의 자리를 지킨다(R209). GitHub 문서는 다른 시한을 적는다: "After 24 hours the GitHub Actions Service unassigns the job if no runner accepts it"(확인함: GitHub 문서 "About Actions Runner Controller"), 그리고 self-hosted job은 "can be in the queue for 24 hours before it is automatically cancelled"(확인함: GitHub Actions limits 문서). 3번째 취소 뒤 job이 실패하는지 큐에 남는지는 문서에 없다(미확인). 실패한다면 다른 조직의 job이 자리를 오래 쓰는 동안 기다린 배정 job이 실패할 수 있고, 이는 INTENT의 "wait in GitHub's queue and start when a runner slot frees up"과 맞지 않는다. 배정 취소는 그 scale set에 배정된 job에 대한 것이므로 자리를 차지한 job이 같은 조직의 것이어도 같은 경로를 탄다(추론). 그래서 R200과 R230은 조직 하나로 한다. R200은 같은 조직의 다른 job이 자리를 약 7분 차지하는 동안 기다린 job의 `JobAvailable`, `JobAssigned`, 배정 취소의 수와 시각, 스케일러가 `AcquireJobs`를 부른 시각과 결과를 기록해, 첫 배정 취소 뒤에도 그 job이 자리를 지키고 runner를 받는지 본다. R200의 통과 조건은 기다린 job이 성공하는 것이다. 3번째 배정 취소 뒤의 결과는 나중 시험인 R230이 맡는다. R230은 자리를 최대 30분(또는 기다린 job의 4번째 배정 취소까지) 차지하는 동안 같은 값을 기록하고, 통과 조건은 기다린 job이 결국 성공하는 것이다. R230에서 실패하거나 취소되면 INTENT의 "wait in GitHub's queue"가 이 설계로 지켜지지 않는 것이므로 SPEC을 고친다. 그때 바꿀 방식은 runpool처럼 알리는 `maxCapacity`를 남은 자리에 맞춰 낮춰 GitHub가 스스로 배정하는 수를 줄이는 방식이다(확인함: runpool `internal/allocator/allocator.go` 190~194행, 설계: 고르지 않은 방법 (1)). R230이 통과하면 지금 방식을 유지한다(Owner: 사용자). R230을 미룰 수 있는 이유는 Design 테스트의 나중으로 미룬 실제 시험에 적었고, 그때까지 3번째 배정 취소 뒤의 결과는 미확인이다. GitHub가 scale set들의 `maxCapacity`를 어떻게 쓰는지(그 합이 서버 한도를 넘을 때 배정을 줄이는지)도 미확인이다. 신호 drain 중에도 세션은 `maxCapacity`로 `max-runners`를 보내지만(R116) `AcquireJobs`는 부르지 않으므로(R220), 그동안 GitHub가 스스로 그 scale set에 배정한 job은 runner를 받지 못한 채 재시작을 넘어 배정 취소되고 다시 배정될 수 있다(추론: 위 runner-up의 서술). 이것은 알고 받아들이는 효과다. drain 중 `maxCapacity`를 0으로 낮추면 배정이 보이지 않게 되기 때문이다(0001 R90의 이유, actions/scaleset 이슈 #133, actions-scaleset 스킬 references/runtime.md 3절). 배정 취소 뒤 다시 큐에 든 job이 같은 `RunnerRequestID`로 오는지도 미확인이다. 새 값으로 오면 앞 entry는 배정 취소 표시를 단 채 cover를 쓰지 않고 남다가(R225) 25시간 시한(R227)으로 지워지며, 그동안 `대기 job`(R222)과 R221의 수에 들어간다. R226의 대조는 `TotalAssignedJobs`가 배정 취소된 job을 세지 않고 `JobStarted`를 받은 job은 세는 값이라는 가정(추론)에 기댄다. 가정이 틀리면 R226이 기다리는 entry를 지우거나 낡은 entry를 남기며, 실제 시험 로그의 INFO `waiting job dropped` 줄로 드러난다. 재시작 뒤 대기 job 목록은 비므로(R211), 새 세션에서 GitHub가 기다리는 job을 `JobAvailable`이나 `JobAssigned`로 다시 보내는지도 미확인이다. 배정된 job은 다시 오지 않아도 `TotalAssignedJobs`로 runner를 받지만(R219), 배정되지 않은 job이 다시 오지 않으면 그 job은 다음 offer까지 runner를 받지 못한다. R223에서 조직 하나로 기록하고, 결과마다 따르는 일은 R223에 적었다. 다른 조직의 job이 자리를 차지할 때의 실제 동작(R181)은 나중 시험이라 그때까지 미확인이다. (2) App 설치를 지운 뒤 그 조직의 호출이 영구 오류를 받기까지의 시간(R183): 설치 access token은 1시간 뒤 만료된다(확인함: https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app "The installation access token will expire after 1 hour."). 일시 중지하면 "the app's access to the GitHub API or webhook events is blocked for that account"이고(확인함: REST 문서의 설치 일시 중지 endpoint 설명) "the GitHub App cannot access resources owned by that installation account"이며(확인함: github/docs 8b038c5 `content/apps/maintaining-github-apps/suspending-a-github-app-installation.md`), 설치를 지우면 "block it from accessing resources owned by your account"이다(확인함: 같은 커밋 `content/apps/using-github-apps/reviewing-and-modifying-installed-github-apps.md`). 그러나 어느 문서도 이미 발급된 토큰이 바로 폐기되는지 적지 않는다(미확인). 그래서 늦어도 토큰 만료 뒤 첫 갱신에서 오류가 날 것으로 보고(추론) R183의 관찰을 70분으로 끊는다. 그 안에 `오류 대기`가 되지 않으면, 세션이 쓰는 Actions 서비스 토큰이 설치 토큰과 따로 더 오래 유효하거나 GitHub가 설치 삭제 뒤에도 호출을 받는 것이므로(추론) 그 기록으로 R171의 감지 방법을 SPEC에서 다시 정한다. 그동안 그 조직은 `정상`으로 보이며 새 job의 runner 시작이 R64의 시작 실패로 세어질 수 있다(추론). R183과 R199는 나중 시험이므로(Design 테스트) 이 시간과 다시 설치 뒤의 실제 복귀는 그때까지 미확인이고, 이 변경에서는 설치 삭제와 다시 설치의 처리를 가짜 클라이언트 시험으로만 확인한다. (3) 개인 계정 저장소 target은 이 변경의 범위 밖이다. 그 기본 runner group ID와 필요한 권한 조합은 미확인이고(actions-scaleset 스킬 references/runtime.md 1절), 개인 계정 저장소를 더하는 변경에서 정한다. Owner: 사용자.

App JWT로 부르는 호출(설치 조회 R108, 라이브러리의 설치 토큰 교환)이 설치와 관계없이 App 전체의 속도 제한 하나를 같이 쓰는지는 미확인이다. 속도 제한 문서는 JWT로 부르는 요청을 다루지 않는다(확인함: github/docs 8b038c5의 content/rest, content/apps, data/reusables에서 찾음). 그래서 설치 조회의 R52 대기를 서버에 하나 둔다(R189). 라이브러리 안의 토큰 교환은 0001처럼 라이브러리의 재시도를 따르고 우리 대기에 들어가지 않는다(0001 Design 재시도 규칙). 설치 토큰으로 부르는 호출의 한도는 설치마다 따로다(확인함: 설계 공유 자원, R188). 실제 시험에서 속도 제한 응답이 오면 그 응답의 `x-ratelimit-resource`와 어느 호출(JWT 호출인지, 어느 target의 호출인지)이었는지를 기록한다.
