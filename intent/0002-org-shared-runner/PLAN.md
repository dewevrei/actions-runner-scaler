## Order of work

Every code milestone ends with all of these passing on the code up to that milestone:

```
gofmt -l .                      # no output
go vet ./...
go test -race ./...
GOOS=linux GOARCH=arm64 go build ./... && GOOS=linux GOARCH=arm64 go vet ./...
GOOS=linux GOARCH=amd64 go build ./... && GOOS=linux GOARCH=amd64 go vet ./...
shellcheck image/*.sh           # milestones that touch image/
```

Kinds: "simple" milestones are mechanical (lookups, configuration, logging, output format) and can be delegated to a smaller model. "complex" milestones carry security weight (verdict, event endpoint, hook) or concurrency weight (shared table, multi-target daemon, target drain, placement) and are not delegated.

Parallel work: the milestones of group P1 (M1 to M7) change disjoint file sets (Files that change). Each runs in its own git worktree made from the same HEAD (the commit that accepts this plan). They are merged one at a time in any order: rebase the worktree branch onto the newest `main`, run the checks above, fast-forward `main`. Because the file sets are disjoint, a rebase has no textual conflict; the checks after the rebase catch a compile-level dependency. M8 starts only after all seven P1 milestones are merged. From M8 on every milestone edits shared files (`internal/daemon/startup.go`, `daemon.go`, `adapters.go`, `fakes_test.go` and `internal/scaler/scaler.go`, `table.go`, `fakes_test.go`), so M8 to M16 run one after another on `main`, each starting from the commit of the one before; none of them runs in a worktree beside another.

Until M9 the 0001 configuration format stays in use, so every commit up to M8 builds, passes its tests and runs with a 0001 `config.toml`. From M9 on it runs with a 0002 `config.toml` (Migration).

**M2. Event verdict policy (complex: security, P1)**
1. `internal/gate/event.go`: `Decide(eventName string, payload []byte) Decision`, a pure function. `Decision` is `{Allow bool; Reason string; HeadRepo string}`. Reason constants: `payload-too-large`, `payload-not-one-object`, `event-name-invalid`, `pull-request-repo-id-invalid`, `pull-request-from-other-repo`, `workflow-run-repo-id-invalid`, `workflow-run-from-other-repo`, `pull-request-missing`, `workflow-run-missing`. The 0001 type `Decision` in `policy.go` is renamed `RunDecision` (deleted with `policy.go` in M8). (R123, R129)
2. Rule order (SPEC Design 판정, "규칙 순서와 거부 사유"); the first failing rule decides: (R124, R125, R126, R127, R128, R129)
   - Size above 32 MiB (33,554,432 bytes) → `payload-too-large` (the server stops reading earlier, M8; `Decide` checks again so it is safe alone).
   - One JSON object: a `json.Decoder` with `UseNumber` decodes the body into `map[string]json.RawMessage`; any decode error (empty body, not JSON, an array or another non-object) → `payload-not-one-object`; then `dec.Token()` must return `io.EOF`, otherwise (another value after the object) → `payload-not-one-object`. White space after the object is allowed.
   - Event name not matching `^[a-z_]{1,64}$` → `event-name-invalid`.
   - Top-level `pull_request` present and not `null`: read `pull_request.head.repo.id`, `pull_request.base.repo.id` and top-level `repository.id` by walking `map[string]json.RawMessage` levels. Each must be a JSON number token whose raw bytes match `^[1-9][0-9]*$` and that `strconv.ParseInt(…, 10, 64)` accepts; anything else (missing, `null`, string, fraction, exponent, sign, leading zero, zero, out of int64 range, an intermediate level that is not an object) → `pull-request-repo-id-invalid`; three valid values not all equal → `pull-request-from-other-repo`. IDs are never decoded into `json.Number` fields, because `encoding/json` stores a quoted string that is a valid number literal into a `json.Number` field without error (confirmed (evidence: Go 1.27.3 `encoding/json/decode.go` lines 958–963, the `reflect.String` case checks only `isValidNumber` before `SetString`; `go env GOROOT` is the go1.27.3 toolchain)).
   - Top-level `workflow_run` present and not `null`: the same with `workflow_run.head_repository.id`, `workflow_run.repository.id`, `repository.id` → `workflow-run-repo-id-invalid` or `workflow-run-from-other-repo`. When both objects are present, both must pass.
   - Event name in {`pull_request`, `pull_request_target`, `pull_request_review`, `pull_request_review_comment`} with `pull_request` missing or `null` → `pull-request-missing`; `workflow_run` with `workflow_run` missing or `null` → `workflow-run-missing`.
   - Otherwise allow. `head.repo.fork`, `full_name`, `author_association`, branch, ref and workflow path are never read for the verdict.

**M3. Hook event report (complex: security, P1)**
1. `image/job-started.sh`: at start, before the first request, save `GITHUB_EVENT_NAME` and `GITHUB_EVENT_PATH` from the hook's own environment into shell variables; nothing else from the environment is read (0001 R82 holds: the runner sets both for the hook, and workflow `env:` does not reach the hook process, confirmed (evidence: SPEC Design "이벤트 파일을 믿는 근거", actions/runner v2.338.2 `JobHookProvider.cs` line 74, `StepsRunner.cs` lines 106–112)). (R139)
2. The loop starts in phase `event`. In phase `event` the hook writes `Authorization: Bearer <token>`, `X-Runner-Name: <name>` and `X-Event-Name: <event>` on stdin into `/usr/bin/env -i /usr/bin/curl -q --noproxy '*' -s -X POST --connect-timeout 2 --max-time 5 --data-binary @<file> -H @- -o <body> -w '%{http_code}' "$url/v1/event"`. An empty event name is written as the line `X-Event-Name;`, because curl drops a header given as `Name:` with no value and sends an empty one for `Name;` (unverified: curl manual `-H, --header`; the hook test checks what the fake server receives). `<file>` is the event path when `[ -f ] && [ -r ]` hold at that moment, otherwise `/dev/null` (empty body). (R139)
3. Response handling in phase `event`: status 200 with body `{"verdict":"allow"}` or `{"verdict":"deny"}` → the 0001 allow and deny handling (token file removal, `kill_worker`); status `000` (connection failure, timeout, curl read error such as exit 26 when the file vanished after the check) or 401 → sleep 2 s and send `POST /v1/event` again; anything else (200 with `pending` or an unknown body, 400, 405, 413, 5xx, any other code) → switch to phase `verdict` and never send the POST again. Phase `verdict` is the 0001 `GET /v1/verdict` loop unchanged (0001 R66). The hook ends with 0 only after an allow. (R140)

**M5. Waiting job list: data model (complex: correctness of job accounting, P1)**

This milestone builds the list as a pure data structure in `internal/scaler/queue.go`. It has no mutex, makes no call and reads no clock: every method takes `now time.Time`, and its owner (the `Placer` of M14) holds the lock. M14 adds placement on top.

1. Entry fields (R206): (R206, R211)
   ```go
   type Entry struct { // exported so exported methods return no unexported type; fields stay unexported
       target      string    // target key
       order       int       // index of the target in config order (R184)
       requestID   int64     // RunnerRequestID; 0 until a message with a non-zero value matches
       runID       int64     // WorkflowRunID
       jobName     string    // JobDisplayName
       assigned    bool      // true after JobAssigned or a successful AcquireJobs
       jobID       string    // JobID of the last matching message
       queueTime   time.Time // message QueueTime; firstSeen when the message's is zero
       firstSeen   time.Time
       lastHeard   time.Time // last JobAvailable, JobAssigned or take-back applied (R206, R209)
       takenBack   bool      // R209
       assignedSeq uint64    // the target's Statistics sequence number current when it became assigned, plus 1 (R226)
       seq         uint64    // insertion counter, the last tie-breaker of R184
   }
   type WaitingList struct {
       entries []*Entry
       stats   map[string]*targetStats // per target key
       seq     uint64
   }
   type targetStats struct {
       statsSeq    uint64 // number of messages with Statistics applied for this target
       prevDeficit int    // deficit of the previous message with Statistics (R226); 0 before the first, which blocks a drop there
       unlisted    int    // R219 value, kept until the next message with Statistics
   }
   ```
   `NewWaitingList()` returns an empty list; the scaler process makes one at start and never persists it (R211).
2. Matching (R206), `match(target string, base scaleset.JobMessageBase) *Entry`: among entries of the same target, `byID` is the entry with `requestID != 0`, `base.RunnerRequestID != 0` and equal values; `byName` is the first entry in insertion order with `requestID == 0 || base.RunnerRequestID == 0` and equal `runID` and `jobName`. Return `byID` when it exists, else `byName`. When the returned entry has `requestID == 0` and the message has a non-zero value, set `requestID` to it. Two entries with different non-zero `requestID` and the same run and name stay two entries. (R206)
3. `Apply(target string, order int, msg *scaleset.RunnerScaleSetMessage, now time.Time) Events` applies, in this order, every `JobAvailable`, then every `JobAssigned`, then every `JobStarted`, then every `JobCompleted` of the message (R206), and returns what changed for logging (`Events` lists offered, assigned, taken back, removed entries with `runnerRequestId`, `workflowRunId`, `jobDisplayName`, `jobId`): (R206, R207, R208, R209)
   - No match for `JobAvailable` or `JobAssigned`: append an entry with `assigned` = (message is `JobAssigned`), `jobID`, `queueTime` = `QueueTime` or `now` when zero, `firstSeen = lastHeard = now`, `assignedSeq = statsSeq+1` when assigned.
   - Match for `JobAssigned`: `lastHeard = now`; `assigned = true`, `jobID = msg.JobID`, `takenBack = false`; `assignedSeq = statsSeq+1` when it was not assigned before. `queueTime` and `firstSeen` never change.
   - Match for `JobAvailable`: `lastHeard = now`; if `takenBack`, or `msg.JobID != ""` and `msg.JobID != jobID`: `assigned = false`, `jobID = msg.JobID`, `takenBack = false`. Otherwise nothing else changes, so an entry assigned by `AcquireJobs` stays assigned (R207).
   - `JobStarted` with a match: remove the entry (R208).
   - `JobCompleted` with `RunnerName == ""` and zero `FinishTime` (take-back, R209): if the match is assigned and `msg.JobID == jobID`, set `takenBack = true` and `lastHeard = now`; otherwise change nothing.
   - Any other `JobCompleted` with a match: remove the entry (R208).
4. `MarkAcquired(e *Entry)` sets `assigned = true` and `assignedSeq = statsSeq+1` for an entry `AcquireJobs` returned (M14, R214). `Remove(e)` removes one entry. `DropTarget(target)` removes every entry of the target (R210). (R210, R214)
5. `Statistics(target string, st scaleset.RunnerScaleSetStatistic, started int) StatsResult` (no clock argument: the rules it applies need no time), called for a message whose `Statistics` is not nil, after `Apply` of the same message; `started` is the target's number of runners that received their own `JobStarted` (R224, counted by the caller under the table lock). Steps, in this order: (R219, R221, R226)
   1. `statsSeq++` (now `k`). `live` = entries of the target with `assigned && !takenBack`. `deficit = live − (st.TotalAssignedJobs − started)`, computed before any drop.
   2. R226: if `prevDeficit > 0 && deficit > 0`, take `n = min(prevDeficit, deficit)` entries among the target's entries with `assigned && !takenBack && assignedSeq <= k−1` (assigned when the previous message with Statistics was applied), ordered by `lastHeard` ascending and then by the R184 order, and remove them; return them for the INFO line `waiting job dropped; GitHub counts fewer assigned jobs` with target URL, `runnerRequestId`, `workflowRunId`, `jobDisplayName`, `totalAssignedJobs`, `startedRunners`. Then `prevDeficit = deficit`, `havePrev = true`.
   3. R219: `unlisted = max(0, st.TotalAssignedJobs − started − live')`, where `live'` is the count after the drop. The value is kept until the next call; an empty poll or a message without Statistics never calls `Statistics`, so it stays unchanged.
   4. R221: `known` = entries of the target with `!assigned || takenBack`; `Warn = st.TotalAvailableJobs > known`, for the WARN line `GitHub counts more available jobs than the scaler knows` with target URL, `github`, `known`.
6. `Expire(now) []Entry` removes the entries with `now.Sub(queueTime) > 25*time.Hour` and returns them for the INFO line `waiting job expired` with target URL, `runnerRequestId`, `queueTime`. (R227)
7. `Ordered(active func(target string) bool) []*Entry` returns the entries of active targets with `!takenBack` (R225), sorted by `queueTime`, then `firstSeen`, then `order`, then `requestID`, then `runID`, then `jobName`, then `seq` (R184). `Unlisted(target)` returns the R219 value. `Count(target) int` returns all entries of the target. (R184, R225)

## Risks

- Riskiest step: M8 with M2 (verdict path). A wrong allow lets code from outside the organization run on a runner that reaches the internal network. Mitigations: `Decide` is a pure function with table tests that break one condition each; every unparsable or missing value denies; the deny path is 0001's unchanged; the endpoint never answers allow without a recorded allow.
- Riskiest step: M14 (placement). It replaces 0001's start path and holds `Placer.mu` across network calls. A lock taken out of the order `scaleMu` → `Placer.mu` → `Table.mu` deadlocks one or all targets; a counting mistake starts runners nobody needs or leaves a job without a runner. Mitigations: the lock order rule and the callback rule are in the package comment, every `Placer` method takes only `Placer.mu` and table methods, and nothing called under `Placer.mu` calls a `Placer` method other than `Kick` or takes a `scaleMu` (`Kick` is a non-blocking channel send that takes no lock, so `MarkRemoved` → `OnRemoved` → `Kick` under `Placer.mu` is allowed); a daemon-level test drives a permanent `AcquireJobs` error inside a kick-triggered placement while another target's `Scale` runs; the M5 list is tested alone first; the Proof list of M14 is the SPEC Design 테스트 list on a fake clock; `-race` tests run two targets' `Scale` and kicks concurrently.
- Riskiest step: M12 and M13 (multi-target daemon). Finalize, drain and session-loop code is restructured; a mistake breaks 0001 R21, R47, R55 or R92. The existing daemon tests keep their assertions with one target.
- M3 (hook): if the hook ends without an allow while the Worker lives, `always()` steps run (0001 Areas of concern 6). Only the request part of the loop changes; traps, `kill_worker`, `kill_runner` and the exit paths stay as in 0001. A POST loop that never leaves phase `event` only delays the job until 0001 R81 removes the runner (fail closed).
- The event file is trusted because the runner writes it right before the hook and the hook is the first pre-job step (SPEC Areas of concern 1). A runner version change can break this; the runner stays pinned at v2.338.2 and T2's record round re-checks it.
- Fork values in the event file are unverified until T2 (SPEC Areas of concern 2). The fork `pull_request_target` run's `workflow_run` chain (concern 2 (3)) is not exercised by T2; it stays an accepted path under SPEC Areas of concern 4.
- Large event bodies over the Docker Desktop VM boundary may take longer than curl's 5 s; the hook then posts again every 2 s and, if it never succeeds, 0001 R81 removes the runner after 180 s and the job fails (SPEC Areas of concern 14). T2 records sizes and times.
- jq in the record image may read IDs as double and call two IDs above 2^53 equal; this affects only the diagnostic words, not the verdict (the scaler compares raw integers).
- `GET /orgs/{org}/installation` for an organization without the App may not answer 404 (concern 5); then R109's text does not appear and the target's last error shows the other status. Default runner group ID 1 is an ARC convention, not documented (concern 7); a wrong ID shows as a scale set error in T1.
- `GetRunnerGroupByName` also returns "multiple runner group found with name" without a status; only "no runner group found" is classified permanent, so the multiple case stays transient and retries with the 1–60 s backoff (that target's start-up does not finish). GitHub group names are unique per organization (unverified).
- The 70 s deadline assumes the service holds an empty poll for about 50.3 s (concern 11). If GitHub raises that hold above 70 s, each uncut poll ends as "no answer" every 5 minutes and a new session is made; the WARN line shows it.
- GitHub assigns up to `max-runners` jobs to a scale set by itself; such a job waits assigned while the server is full and may be taken back (SPEC Areas of concern 12). T4 records the take-backs; a failed third job stops this plan for a SPEC change.
- R226 relies on the assumption that `TotalAssignedJobs` excludes taken-back jobs and includes started ones (SPEC Areas of concern 12). If it is wrong, entries are dropped or kept wrongly; the INFO `waiting job dropped` lines in T3–T5 show it.
- Fork pull requests in public repositories each hold a runner slot until denied and removed (up to about 41 s, concern 9); a burst delays other repositories' jobs.
- Rejected alternatives are in Decisions.

## Migration

- 0001's configuration is not accepted (SPEC Design 설정 파일). From M9 on, the scaler started with a 0001 `config.toml` enters the error wait and shows the two R107 messages in `status` and the log; nothing registers. The user rewrites `config.toml`: `[[pools]]` `max` → `[[targets]] max-runners`, `name` → `[scaling] label`, `idle` → `[[targets]] idle`, `runner-*` → `[runner]`, `build-*` → `[buildkit]`, `url = "https://github.com/<org>"` in `[[targets]]`, and drop `allowed-workflows`, `allowed-events` and `github.app-installation-id`.
- 0001's repository-level scale set was already deleted (confirmed (evidence: 0001 PLAN M7-9)), so no repository registration is left to clean up.
- `delete-scaleset` switches to the target URL argument in the same milestone (M9) in which the scaler starts registering at the organization level, so no commit has an organization scale set that its own `delete-scaleset` cannot remove. A binary built before M9 must not be used to delete scale sets after M9: it reads only the 0001 configuration and looks for a repository scale set.
- Before changing `targets.runner-group` or removing a target, run `delete-scaleset <target URL>` with the old configuration while the scaler is stopped (SPEC Design runner group, delete-scaleset; README in M16).
- The App keeps its 0001 permissions until the user decides on concern 6.

## Decisions

- Code rules follow AGENTS.md and the 0001 PLAN Decisions that this plan does not change.
- Dropped requirements: R118, R119, R120, R215, R217 and R218 are dropped in the SPEC and get no step; R202's text carries the keys R118 showed, and M14's cover counting replaces the marks R215, R217 and R218 described.
- The configuration switch comes with organization registration in one milestone (M9), before the multi-target work. Reason: `github.app-installation-id` disappears (R107), so the new format needs the installation lookup at once, and M11–M15 are then written against the final configuration types without temporary mappings. Method not chosen: switching the configuration last (needs a temporary organization taken from the 0001 `repo-url` and a second wiring change of every consumer).
- Seven P1 milestones with disjoint file sets, the rest one after another. Reason: from M8 on every milestone edits `internal/daemon/startup.go`, `daemon.go`, `adapters.go`, `fakes_test.go` or the core scaler files. The status package (M7) and the waiting list (M5) are built early behind an adapter (`AddPool`) and a pure data structure so they need no daemon edit. Method not chosen: parallel daemon milestones merged by hand (conflicts in the files every milestone needs).
- The verdict is made and recorded inside the `POST /v1/event` handler, synchronously, and `Record` counts as judge work. Method not chosen: hand the payload to a judge goroutine and let the hook find the verdict by polling `GET /v1/verdict` (adds at least one 2 s poll interval and a second place where the verdict can be missing).
- `Decide` lives in `gate`, recording lives in the scaler table (0001 Decision: verdict state in one place). Method not chosen: the scaler parses the payload (policy would leave `gate`, against SPEC Design 판정 "정책").
- IDs are read from raw JSON bytes after a top-level `map[string]json.RawMessage` decode. Methods not chosen: `json.Number` fields (accept a quoted number string, Go 1.27.3 `encoding/json/decode.go` lines 958–963); `map[string]any` for the whole body (allocates the full tree of a 25 MB payload).
- A body read error ends the handler with `panic(http.ErrAbortHandler)`; responses that leave the body unread set `Connection: close`. Methods not chosen: answering 400 (SPEC: the server never answers 400, and a recorded failure would turn a truncated retry into a deny); relying on Go's 256 KiB discard (reads part of an unauthenticated body).
- R131's 1 s bound is checked by a test with a deadline on the real clock, run without `-race`. Method not chosen: a benchmark (reports a number but fails nothing).
- One runner table per server; rows carry their target; both limits are checked in `Table.Add` under the table mutex. Method not chosen: a separate counter object beside per-target tables (two locks to keep in step, and SPEC Design 공유 자원 names one table).
- One `retry.NextAllowed` per target and one for App JWT calls (R188, R189). Method not chosen: target-qualified kinds inside one `NextAllowed` (changes every `Op` user for no gain).
- Placement holds one server-wide `Placer.mu`, with the lock order `scaleMu` → `Placer.mu` → `Table.mu`, and runs inline after each message and on kicks. Methods not chosen: releasing `Placer.mu` around `AcquireJobs` and starts (the entries and cover counted under the lock would be stale when the lock is taken again, and two placements could give one slot twice); a placement goroutine only (moves the start out of the `Scale` call and loses 0001's "start before the message is acknowledged").
- R226 uses the deficit as computed at each message, before its drop, as the SPEC states it. Method not chosen: the deficit after the drop (not what R226 says).
- R149 looks up each unjudged runner by name, one call per runner per 30 s round. Method not chosen: the full organization list every 30 s (call count grows with all runners of the organization, SPEC Design 정리와 대조).
- The hook sends the event file content, not its path, and switches to `GET /v1/verdict` after any answer other than 401, a connection failure or a final verdict. Methods not chosen: re-posting on 5xx or 413 (repeats large bodies; SPEC Design hook 변경), sending the path (the runner rewrites the file before each action step).
- T2's OIDC and kubectl steps use `continue-on-error` and are judged by `steps.<id>.outcome`. Method not chosen: judging by the job result (a failed OIDC step would skip the later steps, so "every step runs" could not be observed).
- Test workflows live only in the test repositories, written there with approval, and their content is fixed in M17 and M18. Method not chosen: committing them to this repository (they would carry test repository variables and are not part of the product).
